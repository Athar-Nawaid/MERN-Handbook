1. Transport Mechanisms: Polling vs SSE vs WebSockets

Traditional HTTP is unidirectional: the client requests data, and the server responds. Real-time applications require the server to push data to the client instantly.

Technology Directionality Underlying Protocol Reconnection & State Best Architectural Fit
Short Polling Client \(\to\) Server (Repeated) Standard HTTP (New TCP handshake every \(N\) seconds) Stateless. High overhead due to repeated HTTP headers. Infrequent updates where real-time latency is unnecessary (e.g. tracking package shipping status every 5 minutes).
Long Polling Client \(\to\) Server (Held) Standard HTTP (Server holds request open until data is ready) Stateless. High connection churning on frequent events. Fallback when corporate firewalls block raw WebSockets.
Server-Sent Events (SSE) Unidirectional (Server \(\to\) Client only) HTTP streaming (text/event-stream over single HTTP connection) Built-in browser auto-reconnect via EventSource; lightweight. Stock tickers, live sports scores, Twitter/news feeds, LLM token streaming (ChatGPT).
WebSockets (WS) Full-Duplex Bi-directional Independent TCP protocol (starts with HTTP 101 Upgrade, switches to WS frames) Stateful persistent socket. Minimal 2–10 byte frame overhead. Multiplayer gaming, collaborative whiteboards (Figma), financial trading terminals, interactive chat.

3. Horizontal Scaling with Redis Pub/Sub

A single Node.js process can easily maintain 50,000 idle WebSocket connections. However, in production, your application is load-balanced across multiple servers or Kubernetes pods:

+-------------------------+ +-------------------------+ | Client Alice (App) | | Client Bob (App) | +-------------------------+ +-------------------------+ | | v (Socket Connection) v (Socket Connection) +-------------------------+ +-------------------------+ | Server Instance 1 | | Server Instance 2 | +-------------------------+ +-------------------------+ | ^ | 1. Alice sends message to Bob | 3. Emits to Bob's socket v | +-------------------------------------------------------------------------------+ | REDIS PUB/SUB MESSAGE BROKER | | (2. Server 1 publishes event to channel 'chat:bob') | +-------------------------------------------------------------------------------+
Figure 13.2: Scaling Stateful WebSockets Horizontally via Redis Pub/Sub

Why Redis Pub/Sub is Required

If Alice is connected to Server 1, and Bob is connected to Server 2, Server 1 cannot write to Bob's socket directly because Bob's TCP socket descriptor exists in Server 2's memory!

By connecting all Node instances to a shared Redis Pub/Sub adapter (e.g. @socket.io/redis-adapter), when Server 1 emits a message to room room:123, Redis broadcasts the event to all server nodes, which emit it to their locally connected clients.

4. Socket Authentication and Heartbeat Presence

Authentication during Connection Handshake

// server.js - Socket.IO Authentication Middleware
const { Server } = require('socket.io');
const jwt = require('jsonwebtoken');

const io = new Server(httpServer, {
  cors: { origin: "https://myfrontend.com", credentials: true }
});

// Enforce JWT validation on connection
io.use((socket, next) => {
  const token = socket.handshake.auth.token || socket.handshake.headers['authorization']?.split(' ')[1];

  if (!token) {
    return next(new Error("Authentication error: Token missing"));
  }

  jwt.verify(token, process.env.JWT_SECRET, (err, decoded) => {
    if (err) return next(new Error("Authentication error: Invalid or expired token"));
    // Attach authenticated user identity directly to socket instance!
    socket.data.user = decoded;
    next();
  });
});

io.on('connection', (socket) => {
  const user = socket.data.user;
  console.log(`User connected: ${user.id} on socket ${socket.id}`);

  // Automatically join user to their personal private room for direct notifications
  socket.join(`user:${user.id}`);
});

Heartbeats & Presence Tracking

Network cables can be unplugged or mobile phones can enter tunnels without sending a TCP FIN packet (creating a Half-Open Socket). The server thinks the client is connected, leaking resources.

WebSockets solve this via Ping/Pong frames: the server sends a ping frame every 25 seconds; if the client does not respond with a pong frame within 20 seconds, the server forcefully closes the dead socket and marks the user offline.

Interview Questions and Answers

20 senior technical interview questions covering WebSockets, Server-Sent Events, real-time scaling, reconnection backoff, and delivery guarantees.

Q1 What are the primary differences between WebSockets and Server-Sent Events (SSE)? When would you choose SSE over WebSockets? Beginner
Spoken Interview Answer

"WebSockets provide full-duplex, bi-directional communication over a single TCP connection, allowing both client and server to transmit data independently with minimal frame overhead. Server-Sent Events (SSE) provide unidirectional streaming strictly from server to client over standard HTTP. I choose SSE when the client only needs to receive live updates—such as stock tickers, live sports scores, notification feeds, or LLM token streams (ChatGPT)—because SSE uses standard HTTP, handles corporate firewalls easily, works natively over HTTP/2, and has built-in automatic browser reconnection."

Q2 How does the HTTP 101 Switching Protocols handshake work when establishing a WebSocket connection? Intermediate
Spoken Interview Answer

"The client sends a standard HTTP GET request with headers `Upgrade: websocket`, `Connection: Upgrade`, and a random base64 string in `Sec-WebSocket-Key`. The server verifies the headers, concatenates the key with a standard RFC GUID (`258EAFA5-E914-47DA-95CA-C5AB0DC85B11`), hashes it with SHA-1, base64 encodes it, and returns HTTP `101 Switching Protocols` with `Sec-WebSocket-Accept`. Both parties immediately switch from HTTP to the binary WebSocket framing protocol over the established TCP socket."

Q3 How do you scale stateful WebSockets horizontally across multiple Node.js backend servers? Advanced
Spoken Interview Answer

"Because WebSockets maintain persistent, stateful TCP connections, two users in the same chat room might be connected to two different physical servers behind a load balancer. We scale this by connecting all Node.js server instances to a shared Redis Pub/Sub message broker (using the Socket.IO Redis adapter). When Server 1 emits a message to a room, it publishes the event to Redis, which broadcasts it to all other server nodes, allowing each node to deliver the message to its locally connected sockets."

Q4 How should authentication be handled for WebSocket connections? Can you send an Authorization header? Intermediate
Spoken Interview Answer

"Native browser `WebSocket()` JavaScript API does not allow setting custom HTTP headers like `Authorization: Bearer `. There are two secure patterns: 1. Pass the JWT token in the connection query parameter or protocol subprotocol over encrypted WSS (`wss://api.com/ws?token=...`) and validate it in the connection handler. 2. Rely on an `HttpOnly` session cookie sent automatically during the initial HTTP upgrade handshake. In Socket.IO, authentication is passed in the handshake auth payload: `socket = io({ auth: { token } })` and validated via middleware."

Q5 What is a Half-Open Socket, and how do Ping/Pong heartbeat frames resolve it? Advanced
Spoken Interview Answer

"A Half-Open Socket occurs when a network connection is broken (e.g. mobile client enters a tunnel, network cable pulled) without sending a TCP `FIN` packet. The operating system kernel and server assume the connection is still alive, keeping the socket and memory open indefinitely. Ping/Pong frames act as an application-level heartbeat: the server sends periodic `ping` frames; if the client fails to return a `pong` within a timeout, the server terminates the dead socket and updates presence to offline."

Q6 What is Socket.IO, and how does it differ from raw WebSockets? Beginner
Spoken Interview Answer

"Socket.IO is NOT just a WebSocket library; it is a real-time event-based framework. It uses Engine.IO to start connections with HTTP long-polling and transparently upgrades to WebSockets if available. It adds enterprise features on top of raw WebSockets: automatic reconnection with backoff, rooms, namespaces, acknowledgment callbacks, and packet buffering when offline."

Q7 What is the difference between Socket.IO Namespaces and Rooms? Intermediate
Spoken Interview Answer

"Namespaces allow splitting the application logic over a single shared connection with different endpoints (e.g. `/chat` vs `/admin`), supporting distinct middleware and auth pipelines. Rooms are server-only channels within a namespace that sockets can join or leave (e.g. `socket.join('room:123')`). Clients cannot see rooms directly; servers use rooms to broadcast events to a targeted subset of sockets (`io.to('room:123').emit(...)`)."

Q8 Explain the three messaging delivery guarantees: At-Most-Once, At-Least-Once, and Exactly-Once. How do you implement Exactly-Once semantics? Advanced
Spoken Interview Answer

"1. At-Most-Once: Fire-and-forget; messages may be lost but are never duplicated. 2. At-Least-Once: Messages are retried until an ACK is received; messages are never lost, but network hiccups can cause duplicates. 3. Exactly-Once: Every message is processed exactly once. In distributed real-time systems, true network Exactly-Once is physically impossible due to the Two Generals' Problem; we simulate it by pairing At-Least-Once retries with an Idempotency Key (UUID) and deduplication table at the receiver."

Q9 Scenario: A user sends a chat message while their mobile app briefly loses internet. How do you design the client and server so the message isn't lost and order is preserved? Scenario
Spoken Interview Answer

"I implement an Optimistic UI with an Offline Queue: 1. The client generates a temporary message UUID and renders the message immediately in the UI with a pending status icon. 2. The message is stored in an IndexedDB outbound queue. 3. When reconnection occurs, an offline synchronizer flushes queued messages sequentially with monotonic client timestamps. 4. The server validates, persists to DB, assigns a permanent server sequence ID, and returns an ACK matching the temporary UUID, which transitions the message status to 'sent'."

Q10 Why do WebSockets require Sticky Sessions (Session Affinity) on load balancers when using Socket.IO? Intermediate
Spoken Interview Answer

"Socket.IO begins its handshake with HTTP long-polling before upgrading to WebSockets. The client issues multiple consecutive HTTP requests to establish the session. If the load balancer routes request 1 to Server A and request 2 to Server B without sticky sessions, Server B will reject the request with `Session ID unknown` (HTTP 400), causing handshake failures. Sticky sessions ensure all HTTP requests from a client reach the same server until the WebSocket upgrade succeeds."

Q11 How do you implement User Presence Tracking (Online / Away / Offline) efficiently at scale? Advanced
Spoken Interview Answer

"Storing presence solely in database rows causes heavy disk write traffic. In production, we use Redis Hashes and TTLs: when a socket connects, we set a Redis key `presence:user_123` with a 60-second TTL. The client's socket sends periodic heartbeats refreshing the TTL. If a socket disconnects (or the server crashes and heartbeats stop), the key expires naturally in Redis. Other servers subscribe to Redis keyspace notifications (`expired` events) to broadcast offline status to friends."

Q12 What is the difference between `ws://` and `wss://`? Beginner
Spoken Interview Answer

"`ws://` is unencrypted WebSocket traffic running over plaintext TCP (port 80). `wss://` is encrypted WebSocket traffic running over TLS/SSL (port 443), identical to HTTPS. In production, you must always use `wss://` to protect message payloads from eavesdropping and prevent intermediary proxy servers and firewalls from dropping or corrupting WebSocket frames."

Q13 What is the C10K / C1000K problem, and how do Linux kernel limits (`ulimit -n`) affect WebSocket servers? Advanced
Spoken Interview Answer

"The C10K problem refers to the challenge of an OS handling 10,000+ concurrent connections simultaneously. In Linux, every active TCP socket is represented as an open File Descriptor (FD). By default, Linux limits processes to 1,024 open file descriptors (`ulimit -n`). A WebSocket server attempting to accept 1,025 connections will crash with `EMFILE: too many open files`. In production, system administrators raise `ulimit -n` to 65,536 or higher and tune kernel TCP buffer sizes."

Q14 How do you implement message delivery receipts (Sent, Delivered, Read) in a chat application? Intermediate
Spoken Interview Answer

"1. Sent: The server writes the message to the database and sends an immediate ACK callback to the sender. 2. Delivered: When the recipient's device receives the socket frame, its client automatically emits an event `{ messageId, status: 'delivered' }` back to the server, which forwards the update to the sender. 3. Read: When the recipient opens the chat screen or scrolls the message into view, the client emits `{ messageId, status: 'read' }`, and the server updates the DB and pushes the read receipt."

Q15 Scenario: During a live streaming event with 100,000 users in a single chat room, incoming messages cause high server CPU load. How do you optimize chat broadcasting? Scenario
Spoken Interview Answer

"Broadcasting 1,000 incoming messages per second individually to 100,000 sockets produces 100 million socket writes per second, overwhelming the event loop. I implement: 1. Message Throttling & Batching: Buffer incoming chat messages and broadcast them as a batched array once every 250ms. 2. Conflation/Sampling: In massive live streams (like Twitch), sample or rate-limit visible messages. 3. Move from unicast WebSockets to WebRTC data channels or SSE behind a CDN edge cache."

Q16 How do you handle JWT expiration for an active WebSocket connection that remains connected for hours? Intermediate
Spoken Interview Answer

"Since WebSockets do not send HTTP headers on every message, an initial 15-minute access token will expire while the connection is still open. There are two solutions: 1. Token Refresh over Sockets: The client listens for its local access token expiry, obtains a new token via HTTP refresh, and emits a `token_refresh` socket event with the new token. 2. Server-side Expiry Timer: The server records the token's `exp` timestamp upon connection and schedules a timer: if the client does not send a refreshed token before expiration, the server forcefully disconnects the socket."

Q17 What is Long Polling, and how does it simulate real-time communication? Beginner
Spoken Interview Answer

"In Long Polling, the client sends an HTTP request to the server. Instead of responding immediately with an empty response, the server holds the request open until new data is available (or a timeout occurs). As soon as data arrives, the server sends the HTTP response, and the client immediately issues another HTTP request to wait for the next event. It simulates real-time pushing using traditional HTTP request-response cycles."

Q18 How does WebSocket frame masking work, and why does the client mask frames while the server does not? Advanced
Spoken Interview Answer

"Under RFC 6455, all frames sent from Client to Server MUST be masked with a random 4-byte key (XORing the payload). Frames from Server to Client are unmasked. Masking prevents Cache Poisoning attacks on intermediate proxy servers: without masking, a malicious web page could craft an unmasked WebSocket frame containing an HTTP GET request, tricking an un-upgraded proxy into caching an attacker-controlled response for other users."

Q19 Scenario: How do you design a reconnection strategy on the frontend so a temporary server restart doesn't trigger a thundering herd of 50,000 simultaneous reconnections? Scenario
Spoken Interview Answer

"I implement Exponential Backoff with Jitter: the reconnection delay increases exponentially on each failed attempt (`baseDelay * 2^attempt`, capped at 30 seconds), multiplied by a random jitter factor between 0.5 and 1.5. The jitter spreads the 50,000 reconnection attempts smoothly across a 10-to-30 second window rather than all clients attempting to reconnect at the exact same second, allowing the recovering backend to accept connections without crashing."

Q20 How does WebRTC differ from WebSockets? When would you use WebRTC Data Channels? Advanced
Spoken Interview Answer

"WebSockets always route traffic through a centralized server over TCP. WebRTC establishes direct Peer-to-Peer (P2P) connections between two browsers using UDP (via STUN/TURN signaling). WebRTC Data Channels provide ultra-low latency peer-to-peer data transfer with configurable reliability (can choose unreliable/unordered mode for gaming or reliable mode for file sharing), bypassing server bandwidth completely for high-volume peer-to-peer applications."
