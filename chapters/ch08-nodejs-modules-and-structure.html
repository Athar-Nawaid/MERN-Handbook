1. npm, package.json, and package-lock.json

Every Node.js project begins with package.json. It acts as the manifest containing metadata, entry points, scripts, and dependencies.

Anatomy of a Production package.json

{
  "name": "enterprise-task-api",
  "version": "1.4.0",
  "description": "Production REST API for Task Management",
  "main": "dist/index.js",
  "type": "module",
  "scripts": {
    "dev": "nodemon --watch src --exec ts-node src/index.ts",
    "build": "tsc -p tsconfig.build.json",
    "start": "node dist/index.js",
    "test": "vitest run",
    "lint": "eslint src --ext .ts"
  },
  "dependencies": {
    "express": "^4.19.2",
    "zod": "^3.23.8",
    "pino": "^9.0.0",
    "pg": "^8.11.5"
  },
  "devDependencies": {
    "@types/express": "^4.17.21",
    "@types/node": "^20.12.7",
    "typescript": "^5.4.5",
    "vitest": "^1.5.0",
    "nodemon": "^3.1.0"
  },
  "engines": {
    "node": ">=20.0.0"
  }
}

The Critical Role of package-lock.json

When you install packages using ^1.2.0, npm installs the latest compatible minor or patch version available at that specific moment. Without a lockfile, two developers running npm install on different days (or your CI/CD pipeline deploying to production) would get different dependency versions, causing sudden production outages!

package-lock.json records the exact version of every direct and transitive dependency installed, along with cryptographic integrity SHA-512 hashes.

🚨 Mandatory CI/CD Rule: Use `npm ci`

In automated production CI/CD pipelines, never run npm install (which can modify the lockfile). Always run npm ci (Clean Install): it strictly installs dependencies based on the lockfile, throws an error if package.json and package-lock.json are out of sync, and is significantly faster!

2. Semantic Versioning (SemVer) Demystified

Node.js packages follow the Semantic Versioning specification format: MAJOR.MINOR.PATCH (e.g. 2.4.1).

SemVer Position When to Increment API Compatibility
MAJOR (X.0.0) Breaking changes, incompatible API modifications, removed functions. Incompatible. Requires code migration.
MINOR (0.X.0) New features added in a backward-compatible manner. Compatible. Existing code works without changes.
PATCH (0.0.X) Backward-compatible bug fixes and security patches. Compatible. Completely safe update.

Version Range Prefixes

  • Caret (^1.2.3): Updates to the latest compatible Minor or Patch version (e.g. up to < 2.0.0). This is npm's default.
  • Tilde (~1.2.3): Updates only to the latest compatible Patch version (e.g. up to < 1.3.0).
  • Exact (1.2.3): Installs precisely version 1.2.3 and never updates without manual edits.
  • Wildcard (* or latest): Installs the newest version available. Strictly forbidden in production environments!

4. CommonJS (CJS) vs ES Modules (ESM) Interop

When converting projects from CommonJS to ES Modules (by setting "type": "module" in package.json), common global variables like __dirname and __filename disappear.

Recreating __dirname and __filename in ESM

// Modern ES Modules (ESM)
import { fileURLToPath } from 'url';
import path from 'path';

// import.meta.url returns the file:// URL of the current module
const __filename = fileURLToPath(import.meta.url);
const __dirname = path.dirname(__filename);

console.log("Current Directory:", __dirname);
console.log("Current File:", __filename);

5. Production Layered Architecture (Controller-Service-Repository)

Putting database queries, route handling, validation, and business logic inside the same Express router file creates an unmaintainable "Spaghetti Architecture".

Senior backend engineers enforce the Three-Layer Architecture:

+-------------------------------------------------------------------------------+ | EXPRESS ROUTER / HTTP | | (Parses request, URL params, query strings, headers) | +-------------------------------------------------------------------------------+ | v +-------------------------------------------------------------------------------+ | CONTROLLER LAYER | | (Validates inputs via Zod, sets HTTP status codes, handles DTOs) | +-------------------------------------------------------------------------------+ | v +-------------------------------------------------------------------------------+ | SERVICE LAYER | | (Core business rules, calculations, orchestrates third-party APIs) | +-------------------------------------------------------------------------------+ | v +-------------------------------------------------------------------------------+ | REPOSITORY LAYER | | (Direct database queries: SQL with pg/Prisma or Mongoose) | +-------------------------------------------------------------------------------+
Figure 8.2: The Separation of Concerns in Layered Backend Engineering

Why Separation of Concerns Matters

  • Controllers are thin: They only translate HTTP into function calls. If you switch from Express to Fastify or WebSockets, your business logic remains completely untouched!
  • Services are testable: You can unit-test business logic without mocking HTTP request and response objects.
  • Repositories isolate storage: If you switch from PostgreSQL to MongoDB, you only modify the repository layer.

6. High-Performance Structured Logging (Pino vs Console)

In production environments, running console.log() is a severe anti-pattern:

  1. console.log is synchronous when writing to terminal stdout/stderr on some OS platforms, introducing event loop latency!
  2. Console strings cannot be indexed, searched, or parsed by log aggregators (Datadog, ElasticSearch/Kibana, AWS CloudWatch).
// logger.js - High-performance structured logging with Pino
const pino = require('pino');

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  // In development, format with colors; in production, emit fast raw JSON!
  transport: process.env.NODE_ENV !== 'production' ? {
    target: 'pino-pretty',
    options: { colorize: true }
  } : undefined,
  base: {
    service: 'task-api',
    pid: process.pid
  }
});

module.exports = logger;

// Usage in controllers:
// logger.info({ userId: 'u_123', action: 'CREATE_TASK' }, 'Task created successfully');
// Emits clean, fast JSON: {"level":30,"time":1713689200000,"service":"task-api","userId":"u_123","action":"CREATE_TASK","msg":"Task created successfully"}

Interview Questions and Answers

20 technical interview questions testing package management, SemVer rules, module loading mechanics, monorepos, and layered backend design.

Q1 What is the difference between `dependencies` and `devDependencies` in `package.json`? Beginner
Spoken Interview Answer

"`dependencies` are packages required for the application to run in production—such as Express, database drivers, and validation libraries. `devDependencies` are packages needed strictly for local development and build pipelines—such as TypeScript, linters, testing frameworks (Vitest/Jest), and nodemon. When deploying to production containers, we run `npm install --omit=dev` to exclude devDependencies, keeping Docker image sizes lean and attack surfaces minimal."

Q2 Why must you commit `package-lock.json` to source control? What happens if you don't? Intermediate
Spoken Interview Answer

"`package-lock.json` guarantees deterministic dependency resolution. Because `package.json` uses version ranges like `^1.2.0`, omitting the lockfile causes each team member and the production CI/CD server to install whatever latest minor/patch versions happen to be published on npm at that moment. This results in 'works on my machine' bugs and unexpected production breakage when a third-party dependency introduces an accidental bug in a patch release."

Q3 What is the difference between `npm install` and `npm ci`? Intermediate
Spoken Interview Answer

"`npm install` resolves dependencies based on `package.json` and updates `package-lock.json` if compatible newer versions exist. `npm ci` (Clean Install) is strictly for automated CI/CD environments: it deletes existing node_modules, installs exact versions strictly according to the lockfile without ever modifying it, throws an error if `package.json` and `package-lock.json` mismatch, and is significantly faster."

Q4 Explain SemVer caret (`^`) vs tilde (`~`). If a package version is `^2.4.1`, what updates are permitted? Intermediate
Spoken Interview Answer

"Tilde `~` permits updates to the latest PATCH version while locking Major and Minor (e.g. `~2.4.1` permits up to `< 2.5.0`). Caret `^` permits updates to the latest MINOR and PATCH versions while locking Major (e.g. `^2.4.1` permits up to `< 3.0.0`). The only exception with caret is pre-1.0.0 versions: because `0.X.X` denotes unstable experimental software, `^0.2.3` only updates patches (`< 0.3.0`)."

Q5 How does the Node.js module resolution algorithm traverse directories to locate a package? Advanced
Spoken Interview Answer

"When requiring a non-relative module like `require('lodash')`, Node checks if it is a built-in core module. If not, it looks for `./node_modules/lodash` in the current file's directory. If not found, it traverses upward to the parent directory `../node_modules/lodash`, repeating this climb up the entire filesystem hierarchy until it reaches the root directory. If still not found, it throws a `MODULE_NOT_FOUND` error."

Q6 Why do `__dirname` and `__filename` not exist in ES Modules? How do you replicate them? Intermediate
Spoken Interview Answer

"In CommonJS, `__dirname` and `__filename` were injected into a module wrapper function `(function(exports, require, module, __filename, __dirname) { ... })` at runtime. ES Modules have no wrapper function. To replicate them in ESM, we use `import.meta.url` with the native `url` module: `const __filename = fileURLToPath(import.meta.url); const __dirname = path.dirname(__filename);`."

Q7 What is the Layered Architecture (Controller-Service-Repository) pattern in backend engineering? Advanced
Spoken Interview Answer

"It is a separation-of-concerns pattern: 1. The Controller layer handles HTTP transport concerns (parsing request bodies, setting headers, returning status codes). 2. The Service layer contains pure business logic, calculations, and orchestrates domain operations independent of HTTP. 3. The Repository layer handles data persistence (PostgreSQL SQL queries or MongoDB calls). This decouples business logic from transport protocols and databases, making testing and refactoring straightforward."

Q8 What are `peerDependencies` in `package.json`? When are they used? Beginner
Spoken Interview Answer

"`peerDependencies` state that your package requires a specific host package to be installed by the consuming application, but your package will not install it directly. They are primarily used when building plugins or libraries—such as React component libraries specifying `peerDependencies: { 'react': '^18.0.0' }` to ensure the host app and the library share the exact same single React runtime instance."

Q9 Why is `console.log` discouraged for production backend logging? What should you use instead? Intermediate
Spoken Interview Answer

"`console.log` can be synchronous when writing to stdout/stderr in Node.js, introducing event loop latency under high traffic. Furthermore, it outputs unstructured plaintext strings that cannot be filtered or indexed by log aggregators. In production, we use high-performance structured loggers like **Pino**, which emit JSON logs asynchronously with metadata (timestamp, log level, correlation IDs, user IDs)."

Q10 What are npm/pnpm Workspaces and how do they benefit full-stack monorepos? Advanced
Spoken Interview Answer

"Workspaces allow you to manage multiple interrelated packages within a single root repository. The package manager symlinks internal packages together and hoists shared dependencies to a root `node_modules`. In a full-stack monorepo, workspaces let your React frontend and Express backend share TypeScript types, Zod schemas, and utility packages directly without needing to publish them to an external npm registry."

Q11 What is the "Dual Package Hazard" when publishing a library supporting both CJS and ESM? Intermediate
Spoken Interview Answer

"The Dual Package Hazard occurs when a consuming application inadvertently imports both the CommonJS and ES Module versions of the same library simultaneously (for example, if App imports ESM, but another dependency requires CJS). Because Node.js treats the CJS and ESM files as completely separate modules, two separate instances of the library exist in memory, breaking singletons, `instanceof` checks, and stateful tracking."

Q12 What does the `exports` field in `package.json` do, and how does it replace the `main` field? Beginner
Spoken Interview Answer

"The modern `exports` field provides fine-grained control over which internal files consumers can import, defining conditional entry points for ESM (`import`), CJS (`require`), and TypeScript (`types`). It also enforces encapsulation: any internal file not explicitly declared in `exports` cannot be imported by external consumers, preventing reliance on internal private modules."

Q13 Scenario: A security advisory reveals a critical vulnerability in a deeply nested transitive dependency. How do you resolve it without waiting for upstream package updates? Scenario
Spoken Interview Answer

"I use npm's built-in `overrides` field (or `resolutions` in pnpm/yarn) inside root `package.json`: for example, `\"overrides\": { \"vulnerable-package\": \"^2.1.4\" }`. This forces the package manager to replace that specific transitive dependency with the patched version across the entire dependency graph, and then I regenerate the lockfile using `npm install`."

Q14 How do npm scripts handle chaining with `&&` versus `&`? How do you ensure cross-platform Windows compatibility? Intermediate
Spoken Interview Answer

"`&&` executes commands sequentially, running the second command only if the first succeeds (exit code 0). `&` executes commands in parallel in the background (on Unix). To ensure cross-platform compatibility across Windows (PowerShell/cmd) and Linux, we use utilities like `concurrently` or `npm-run-all` for parallel scripts, and `cross-env` for setting environment variables in scripts."

Q15 What is Dependency Injection (DI), and how does it improve testability in Node.js services? Advanced
Spoken Interview Answer

"Dependency Injection is a technique where a class or function receives its dependencies (like database clients or email providers) as constructor arguments rather than hardcoding their instantiation internally. In Node.js, DI allows you to pass a mock in-memory database repository during unit tests without needing fragile global module mocking (like proxyquire or jest.mock), leading to fast and reliable unit tests."

Q16 What are npm pre and post lifecycle scripts? Give an example. Beginner
Spoken Interview Answer

"npm automatically matches scripts prefixed with `pre` and `post` to run before and after the target script. For example, if you define `pretest: \"npm run lint\"` and `test: \"vitest\"`, running `npm test` will automatically execute the linter before running the test suite. Similarly, `postbuild` can be used to copy static assets after compilation completes."

Q17 How does Node.js cache required modules? Can you invalidate the module cache? Advanced
Spoken Interview Answer

"Modules are cached in `require.cache` by their resolved absolute filename upon their first invocation. Subsequent `require` calls return the exact cached object without re-evaluating the code. In CommonJS, you can invalidate the cache by deleting the entry: `delete require.cache[require.resolve('./module')]`. In ES Modules, module evaluation is immutable and the module registry cannot be modified or cleared at runtime."

Q18 Scenario: How do you structure environment variable validation so a Node application fails fast on startup if secrets are missing? Scenario
Spoken Interview Answer

"I define a strict Zod schema for `process.env` in a dedicated `config.ts` file imported at the very top of `index.ts`. If required variables (like `DATABASE_URL` or `JWT_SECRET`) are missing or malformed, the schema parser throws an error with a detailed breakdown and exits the process immediately (code 1) before the HTTP server or database connections even attempt to start, preventing silent runtime failures."

Q19 What is the difference between `npm audit` and Snyk/Dependabot? Intermediate
Spoken Interview Answer

"`npm audit` checks dependencies against the npm security advisory database during local installations and CI builds. Snyk and GitHub Dependabot are continuous security platforms that monitor repositories 24/7, provide automated Pull Requests with security patches as soon as CVEs are published, and evaluate transitive dependency risk profiles."

Q20 What is a Correlation ID in backend logging, and how is it implemented? Advanced
Spoken Interview Answer

"A Correlation ID (or Request ID) is a unique UUID generated for every incoming HTTP request. Middleware assigns it to the request and logs it with every database query, third-party API call, and log statement produced during that request lifecycle. In distributed systems or microservices, searching for this single ID in a log aggregator (like Datadog or ELK) reveals the exact end-to-end trace of that specific user transaction across all backend services."
