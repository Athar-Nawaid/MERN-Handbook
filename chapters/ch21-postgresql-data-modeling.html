1. Database Normalization (1NF, 2NF, 3NF, and BCNF)

Normalization is the systematic process of organizing relational database tables to minimize data redundancy and eliminate insert, update, and delete anomalies.

Normal Form Core Requirement Common Violation & Fix
First Normal Form (1NF) Each column must contain atomic (indivisible) values. No repeating groups or comma-separated lists. Each row must be uniquely identifiable. Storing "red,blue,green" in a colors column. Fix: Create a separate item_colors relation with 1 color per row.
Second Normal Form (2NF) Must be in 1NF, and all non-key attributes must be fully functionally dependent on the entire primary key (applies to composite primary keys). In a table with composite key (order_id, product_id), storing customer_address. Fix: Move customer address to an orders or customers table.
Third Normal Form (3NF) Must be in 2NF, and no non-key attribute can depend on another non-key attribute (no transitive dependencies: \(X \to Y \to Z\)). Storing zip_code, city, and state together in employees. Since city depends on zip_code (transitive), move zip lookup to a dedicated table.
Boyce-Codd (BCNF) A stricter version of 3NF: for every functional dependency \(X \to Y\), \(X\) must be a superkey. Handles edge cases where tables have overlapping composite candidate keys.

1.1 When and Why to Denormalize

While 3NF prevents data inconsistency, heavily normalized databases require joining 6–10 tables to answer common read queries. In high-throughput read-heavy applications, strategic denormalization is justified:

  • Pre-calculated Aggregate Counters: Storing posts.likes_count or users.follower_count to avoid running expensive COUNT(*) queries on every pageview.
  • Immutable Snapshots: Copying product_price and shipping_address directly into an order_items row at checkout time so future price changes do not rewrite historical financial records.
  • Materialized Views: Pre-computing complex reporting aggregations refreshed asynchronously via background cron jobs.

2. Primary Key Strategies: BIGSERIAL vs UUIDv4 vs UUIDv7

Selecting a Primary Key format is an architectural decision that impacts index performance, distributed generation, and security.

Key Strategy Storage Size B-Tree Index Fragmentation Distributed Generation Security / Enumeration
BIGINT (IDENTITY) 8 bytes Zero Fragmentation: Monotonically increasing numbers always append to the rightmost leaf page of the B-Tree index. Requires centralized database sequence coordinator; cannot generate offline. Vulnerable to Enumeration: Attackers can guess IDs sequentially (e.g. /users/1, /users/2).
UUIDv4 (Random) 16 bytes Catastrophic Fragmentation: Random distribution causes random page splits across the entire B-Tree, degrading cache locality and write throughput. Can be safely generated anywhere (client, microservice) with zero database coordination. High Security: 122 bits of random entropy make ID guessing mathematically impossible.
UUIDv7 (Time-Ordered) 16 bytes Zero Fragmentation: Starts with a 48-bit UNIX millisecond timestamp followed by random bytes. Monotonically sorted like BIGINT! Can be generated by distributed microservices independently while retaining chronological ordering. High Security: Unpredictable random suffix prevents sequential enumeration.
sql (PostgreSQL Primary Key Definitions) 
-- Modern PostgreSQL standard for auto-incrementing integers (replaces legacy SERIAL)
CREATE TABLE products (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  price NUMERIC(10, 2) NOT NULL
);

-- UUIDv4 implementation using built-in gen_random_uuid()
CREATE TABLE accounts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  company_name VARCHAR(255) NOT NULL
);

-- UUIDv7 (PostgreSQL 17+ or via pg_uuidv7 extension)
-- Encodes millisecond timestamp in first 48 bits for sorted B-Tree performance
CREATE TABLE audit_logs (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v7(),
  action VARCHAR(100) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

3. Integrity Constraints and Referential Cascading

Relying exclusively on application code (e.g. Express or Mongoose) for data validation is an anti-pattern. Application bugs, bulk SQL imports, and concurrent race conditions will eventually corrupt data. PostgreSQL constraints provide engine-enforced invariants.

sql 
CREATE TABLE bookings (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  room_id UUID NOT NULL REFERENCES rooms(id) ON DELETE RESTRICT,
  guest_email VARCHAR(255) NOT NULL,
  price_per_night NUMERIC(10, 2) NOT NULL,
  booking_dates DATERANGE NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  -- 1. CHECK Constraint: Business validation at storage layer
  CONSTRAINT chk_positive_price CHECK (price_per_night > 0),
  CONSTRAINT chk_valid_email CHECK (guest_email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$'),

  -- 2. EXCLUDE Constraint: Prevents overlapping bookings for the SAME room!
  -- Requires btree_gist extension: CREATE EXTENSION btree_gist;
  CONSTRAINT no_overlapping_room_bookings 
    EXCLUDE USING gist (room_id WITH =, booking_dates WITH &&)
);

3.1 Referential Integrity Cascading Rules

  • ON DELETE CASCADE: Automatically deletes all child rows when the referenced parent row is deleted. Use with caution for tightly owned children (e.g. deleting an Order deletes its OrderItems).
  • ON DELETE RESTRICT / NO ACTION: Rejects deletion of the parent row if any child references exist. (Default and safest for audit trails; e.g. cannot delete a Customer who has existing Orders).
  • ON DELETE SET NULL: Retains child rows but sets foreign key column to NULL (e.g. if a User is deleted, set posts.author_id = NULL).

4. Soft Deletes: Best Practices and Hidden Traps

Soft Deletion means adding a deleted_at TIMESTAMP WITH TIME ZONE NULL column rather than physically executing DELETE FROM. While valuable for recovery and auditing, soft deletion introduces severe architectural hazards:

Soft Delete Hazard Why It Breaks PostgreSQL Architectural Solution
Unique Constraint Collisions A table with UNIQUE (email) blocks a user from re-registering with alice@test.com if an old soft-deleted row already contains that email. Use a Partial Unique Index: CREATE UNIQUE INDEX uq_active_user_email ON users (email) WHERE deleted_at IS NULL;
Query Pollution / Accidental Leaks Every single query across your entire codebase must remember to append WHERE deleted_at IS NULL. Forgetting it leaks deleted data. Create a default view (active_users) or enforce a PostgreSQL Row-Level Security (RLS) policy that filters out soft-deleted rows automatically.
Foreign Key Cascades Break Foreign keys do not recognize soft deletes; soft-deleting a parent organization leaves child users visibly active unless manual cascading updates are executed. Implement database triggers or service-layer cascading updates.
GDPR / CCPA Non-Compliance The "Right to be Forgotten" requires true data erasure. Soft-deleted rows holding PII still violate GDPR laws. Anonymize PII upon soft-delete (e.g., set email = 'deleted-' || id || '@anonymized.local') or hard-delete after a 30-day grace period.

5. Multi-Tenancy Architecture and Row-Level Security (RLS)

Multi-tenant SaaS architectures isolate data between different corporate accounts or organizations.

Multi-Tenancy Model Data Isolation Operational Complexity Cost Efficiency
Database per Tenant Absolute physical isolation. Extreme complexity: running 5,000 database instances or running migrations across 5,000 DBs. Expensive; high resource idle waste.
Schema per Tenant Logical isolation within single DB. High complexity: PostgreSQL connection pools and ORMs struggle with thousands of schemas. Moderate.
Shared Schema with Tenant ID + RLS Engine-enforced cryptographic isolation in single table. Low complexity: single database schema, unified migrations, standard connection pooling. Optimal: Maximum hardware sharing and lowest cloud cost.

5.1 Implementing Row-Level Security (RLS) in PostgreSQL

PostgreSQL Row-Level Security (RLS) transparently injects tenant-filtering predicates into every query executed by the database engine, making tenant data leakage impossible even if a junior developer writes SELECT * FROM documents without a WHERE clause!

sql (PostgreSQL Row-Level Security Setup) 
-- 1. Create multi-tenant table
CREATE TABLE documents (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL,
  title VARCHAR(255) NOT NULL,
  content TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 2. ENABLE Row-Level Security on the table
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

-- 3. Define RLS Policy tied to session variable 'app.current_tenant_id'
CREATE POLICY tenant_isolation_policy ON documents
  FOR ALL
  USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::UUID)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::UUID);

-- =====================================================================
-- APPLICATION EXECUTION PATTERN (Inside Express Database Middleware):
-- =====================================================================
-- When an Express request arrives from Tenant 'a0eebc99-...':
BEGIN;
-- Set session-scoped tenant context (local to this transaction only):
SET LOCAL app.current_tenant_id = 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11';

-- Even if developer forgets WHERE tenant_id = ..., PostgreSQL ENFORCES it!
SELECT * FROM documents; -- Only returns documents belonging to Tenant 'a0eebc99-...'!
COMMIT;

6. Zero-Downtime Database Migrations

Running uncoordinated DDL migrations (like ALTER TABLE users DROP COLUMN phone or ALTER TABLE orders ADD COLUMN status VARCHAR NOT NULL DEFAULT 'PENDING') on high-traffic production databases will lock tables for minutes or crash running application pods that expect the old schema.

6.1 The Expand-and-Contract Migration Pattern

Zero-downtime schema evolution decouples database migrations from code deployments into four distinct, backward-compatible phases:

Figure 21.1: Expand and Contract Migration Lifecycle
[ Phase 1: EXPAND (Database Migration) ]
- Add new column as NULLABLE (e.g. full_name VARCHAR).
- Both old (first_name, last_name) and new (full_name) columns exist simultaneously.

[ Phase 2: WRITE TO BOTH (Application Deployment v2) ]
- Application writes to both old and new columns.
- Reads fall back: full_name || (first_name || ' ' || last_name).

[ Phase 3: BACKFILL (Asynchronous Data Migration) ]
- Run background batch job: UPDATE users SET full_name = first_name || ' ' || last_name WHERE full_name IS NULL.
- Apply NOT NULL constraint after backfill completes.

[ Phase 4: CONTRACT (Application Deployment v3 & DB Cleanup) ]
- Deploy application v3: reads/writes exclusively from full_name.
- Execute final DB cleanup: ALTER TABLE users DROP COLUMN first_name, DROP COLUMN last_name.
⚡ Golden Rules for Safe PostgreSQL Migrations
  • Always create indexes concurrently: CREATE INDEX CONCURRENTLY builds indexes without acquiring an exclusive table write lock.
  • Always set statement timeouts: SET statement_timeout = '5s'; prevents migration locks from queueing behind long-running queries and causing connection pool exhaustion.
  • Never add NOT NULL without DEFAULT in one step: In older PostgreSQL versions, this rewrote the entire physical table. In modern PostgreSQL, add column with default, or backfill first then add constraint VALIDATE CONSTRAINT.

Problem: Write production DDL for a normalized order system including customers, orders, and order_items. Include soft deletion with partial unique indexes on customer email, ensure total prices cannot be negative, and enforce immutable historical item prices.

sql 
-- 1. Customers Table with Soft Deletion & Partial Unique Index
CREATE TABLE customers (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email VARCHAR(255) NOT NULL,
  full_name VARCHAR(100) NOT NULL,
  deleted_at TIMESTAMPTZ NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Partial unique index ensures email uniqueness ONLY among active accounts!
CREATE UNIQUE INDEX uq_active_customer_email 
  ON customers (email) 
  WHERE deleted_at IS NULL;

-- 2. Orders Table
CREATE TABLE orders (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id UUID NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
  status VARCHAR(50) NOT NULL DEFAULT 'PENDING',
  total_amount NUMERIC(12, 2) NOT NULL DEFAULT 0.00,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  
  CONSTRAINT chk_positive_total CHECK (total_amount >= 0)
);

-- 3. Order Items Table (Immutable historical price snapshot)
CREATE TABLE order_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  product_id UUID NOT NULL,
  unit_price NUMERIC(10, 2) NOT NULL, -- Historical snapshot at purchase time
  quantity INT NOT NULL,

  CONSTRAINT chk_positive_quantity CHECK (quantity > 0),
  CONSTRAINT chk_positive_price CHECK (unit_price >= 0),
  CONSTRAINT uq_order_product UNIQUE (order_id, product_id)
);

8. Chapter-Specific Interview Questions and Answers

Master these 20 high-frequency interview questions covering PostgreSQL data modeling, keys, constraints, soft deletion, and multi-tenancy.

Q01 What is the difference between 1NF, 2NF, and 3NF? Beginner
Spoken Interview Answer

"1NF requires that all column values are atomic (no comma-separated lists or arrays) and each row is unique. 2NF requires 1NF plus eliminating partial dependencies: every non-key column must depend on the entire composite primary key, not just part of it. 3NF requires 2NF plus eliminating transitive dependencies: non-key columns must depend strictly on the primary key, never on other non-key columns (e.g. moving city/state out of an address table into a zip code lookup)."

Q02 Why does random UUIDv4 cause B-Tree index fragmentation, and why is UUIDv7 superior? Intermediate
Spoken Interview Answer

"B-Tree indexes maintain sorted leaf pages. UUIDv4 is completely random, so new inserts are scattered randomly across the entire index tree. When a leaf page fills up, PostgreSQL must perform expensive 'page splits', leaving index pages half-empty, bloating disk usage, and destroying memory cache locality. UUIDv7 prefixes the identifier with a 48-bit millisecond UNIX timestamp. Because timestamps increase monotonically, new UUIDv7 rows always append cleanly to the rightmost leaf of the B-Tree, completely preventing fragmentation."

Q03 How do you solve the unique constraint conflict when implementing soft deletion? Intermediate
Spoken Interview Answer

"If a table has a regular `UNIQUE(email)` constraint, soft-deleting a row still retains `alice@test.com` in the table, blocking a future user from registering with that email. The solution is a PostgreSQL Partial Unique Index: `CREATE UNIQUE INDEX uq_active_email ON users(email) WHERE deleted_at IS NULL;`. This enforces uniqueness exclusively among active records, allowing any number of deleted records to share the same email."

Q04 What is Row-Level Security (RLS) in PostgreSQL, and how does it prevent cross-tenant data leaks? Advanced
Spoken Interview Answer

"Row-Level Security allows database administrators to attach security policies to tables. When enabled, PostgreSQL automatically rewrites incoming SQL queries at the engine planner level to inject policy conditions—such as `WHERE tenant_id = current_setting('app.current_tenant')::uuid`. Even if application code forgets to include a `WHERE tenant_id = ...` filter, the database engine enforces tenant isolation at the kernel level, completely eliminating cross-tenant data leaks."

Q05 What is the difference between ON DELETE CASCADE, ON DELETE RESTRICT, and ON DELETE SET NULL? Beginner
Spoken Interview Answer

"`ON DELETE CASCADE` automatically deletes all child rows when the parent row is deleted. `ON DELETE RESTRICT` aborts the deletion if any child rows reference the parent, preventing accidental orphan records. `ON DELETE SET NULL` keeps the child rows intact but overwrites the foreign key column with NULL."

Q06 Explain the Expand-and-Contract pattern for zero-downtime database migrations. Advanced
Spoken Interview Answer

"The Expand-and-Contract pattern decouples schema evolution into backward-compatible stages: 1. Expand: Add the new column as nullable in the database. 2. Dual-Write: Deploy application v2 that writes to both old and new columns, reading from the new column with fallback. 3. Backfill: Run an async background job migrating historical rows. 4. Contract: Deploy application v3 reading/writing exclusively to the new column, and drop the old column in a final migration."

Q07 Why must you use CREATE INDEX CONCURRENTLY in production PostgreSQL? Intermediate
Spoken Interview Answer

"A standard `CREATE INDEX` acquires an `ACCESS EXCLUSIVE` lock on the table, blocking all writes (`INSERT`, `UPDATE`, `DELETE`) until the index build finishes. On large tables, this lock can last for minutes or hours, causing production downtime. `CREATE INDEX CONCURRENTLY` performs two table scans without acquiring exclusive write locks, allowing writes to continue uninterrupted while the index is built in the background."

Q08 What are Exclusion Constraints (EXCLUDE USING gist), and when should you use them over UNIQUE constraints? Advanced
Spoken Interview Answer

"Standard `UNIQUE` constraints only test for exact equality (`=`). Exclusion constraints use GiST index operators to enforce generalized comparison invariants—most notably range overlaps (`&&`). Their classic use case is scheduling and booking systems: `EXCLUDE USING gist (room_id WITH =, booking_dates WITH &&)`. This guarantees at the database level that no two bookings for the same room can ever overlap in time, eliminating double-booking race conditions."

Q09 What is the difference between Surrogate Keys and Natural Keys? Intermediate
Spoken Interview Answer

"A Natural Key is an attribute existing in the real-world business domain that is inherently unique (e.g. Social Security Number, ISBN, or email). A Surrogate Key is an artificially generated, meaningless identifier (e.g. an auto-incrementing `BIGINT` or `UUID`). Surrogate keys are widely preferred because natural keys frequently change in the real world (e.g. users change emails), which cascades costly updates across all foreign key tables."

Q10 Why should monetary values never be stored using FLOAT or DOUBLE PRECISION? Beginner
Spoken Interview Answer

"`FLOAT` and `DOUBLE` use IEEE 754 binary floating-point representation, which cannot precisely represent fractional decimal numbers like 0.1 or 0.05. Performing arithmetic on floats accumulates rounding errors (e.g. `0.1 + 0.2 = 0.30000000000000004`), leading to financial discrepancies. Money must always be stored using exact numeric types: PostgreSQL `NUMERIC(12, 2)` or as integer cents (`BIGINT`)."

Q11 What is Boyce-Codd Normal Form (BCNF), and how does it differ from 3NF? Intermediate
Spoken Interview Answer

"BCNF is a stricter variant of 3NF. Under 3NF, a dependency `X -> Y` is permitted if `X` is a candidate key OR `Y` is a prime attribute (part of any candidate key). BCNF removes that exception: for EVERY non-trivial dependency `X -> Y`, `X` MUST be a candidate superkey. BCNF addresses tables with multiple overlapping composite candidate keys."

Q12 How do you implement an immutable audit log table in PostgreSQL without application overhead? Advanced
Spoken Interview Answer

"I implement a PostgreSQL `AFTER INSERT OR UPDATE OR DELETE` trigger on the target table. Inside the trigger function, capture `TG_OP`, the current user `SESSION_USER`, timestamp, and serialize `OLD` and `NEW` records to `JSONB` via `to_jsonb(OLD)` and `to_jsonb(NEW)`. Insert this delta into an `audit_logs` table. To make it strictly append-only, revoke `UPDATE` and `DELETE` privileges on `audit_logs` from the application database role."

Q13 Scenario: You need to add a NOT NULL column with a DEFAULT value to a table with 50 million rows in PostgreSQL 10 vs modern PostgreSQL 11+. What are the locking risks? Scenario
Spoken Interview Answer

"In PostgreSQL 10 and older, adding a column with a default value required physically rewriting all 50 million rows on disk, taking an exclusive table lock that caused prolonged downtime. Since PostgreSQL 11, adding a column with a constant default stores the default value in the system catalog metadata without rewriting rows, executing in milliseconds. However, always set `SET statement_timeout = '2s'` before running DDL to prevent lock queue pileups."

Q14 What is a Junction Table, and what constraints should it contain? Intermediate
Spoken Interview Answer

"A Junction Table (or join table) bridges a Many-to-Many relationship between two tables (e.g. `users` and `roles` via `user_roles`). It should contain foreign keys to both parent tables with `ON DELETE CASCADE`. Crucially, it must have a composite primary key or unique constraint on `(user_id, role_id)` to prevent duplicate association links."

Q15 Why does PostgreSQL's GENERATED ALWAYS AS IDENTITY replace SERIAL? Advanced
Spoken Interview Answer

"`SERIAL` is a legacy pseudo-type that created an implicit sequence and set a `DEFAULT nextval('seq')`. Because it was just a default, users could accidentally insert explicit IDs, causing sequence desynchronization errors later. `GENERATED ALWAYS AS IDENTITY` conforms to the SQL standard, manages the sequence internally, and rejects manual ID insertions unless overridden with `OVERRIDING SYSTEM VALUE`, making it much safer."

Q16 What is the difference between CHAR, VARCHAR, and TEXT in PostgreSQL? Beginner
Spoken Interview Answer

"`CHAR(n)` pads strings with trailing spaces to fixed length `n`, wasting space and causing string comparison quirks. `VARCHAR(n)` stores variable-length strings up to length `n`. `TEXT` stores arbitrary variable-length strings. Under PostgreSQL's internal storage engine (TOAST), `VARCHAR` and `TEXT` have identical performance characteristics; `VARCHAR(n)` merely adds a length validation check."

Q17 Scenario: An order checkout system needs to ensure product prices cannot change after an order is completed. How do you model this? Scenario
Spoken Interview Answer

"Never calculate order totals dynamically by joining the current `products` table! The `order_items` table must store an explicit `unit_price NUMERIC(10, 2)` column that acts as an immutable point-in-time snapshot of the price at the moment of checkout. Even if the merchant changes the product's catalog price tomorrow, the historical order item record remains fixed."

Q18 What are CHECK constraints, and can a CHECK constraint reference columns from other tables? Intermediate
Spoken Interview Answer

"A `CHECK` constraint evaluates a Boolean expression that must be satisfied for any inserted or updated row (e.g. `CHECK (age >= 18)`). By SQL standard design, a `CHECK` constraint can ONLY reference columns within the same row of that specific table; it cannot reference other rows or query other tables. Cross-table validation must be implemented via triggers or foreign keys."

Q19 What is the difference between TIMESTAMP and TIMESTAMPTZ in PostgreSQL, and why should you ALWAYS use TIMESTAMPTZ? Advanced
Spoken Interview Answer

"`TIMESTAMP` (without time zone) completely ignores time zones, storing whatever date/time was given, which causes chaos during daylight savings time and multi-region deployments. `TIMESTAMPTZ` (with time zone) converts any input timestamp to UTC and stores it as UTC internally (8 bytes). When queried, it converts UTC to the client's local session time zone. You should always use `TIMESTAMPTZ` for timestamps to avoid ambiguous historical times."

Q20 How do you safely rename a column on a high-traffic production table without breaking running services? Intermediate
Spoken Interview Answer

"Directly running `ALTER TABLE users RENAME COLUMN old_name TO new_name` breaks all running application containers still executing queries with `old_name`. Instead: 1. Add `new_name` as a new column. 2. Set up dual-writing in application code. 3. Backfill data from `old_name` to `new_name`. 4. Update application reads to use `new_name`. 5. Once all services run the new code, drop `old_name`."
