1. The Core Paradigm Comparison

The choice between PostgreSQL and MongoDB is not a question of which database is "better," but which architectural model aligns with your domain's access patterns, consistency requirements, and data relationships.

Architectural Dimension PostgreSQL (Relational SQL) MongoDB (Document NoSQL)
Primary Data Structure Flat, two-dimensional tabular relations (Tables, Rows, Columns). Hierarchical, nested BSON documents (Collections, Documents, Fields).
Schema Enforcement Strict Schema-on-Write: Data must strictly adhere to predefined DDL columns, types, and constraints before being accepted by the storage engine. Flexible Schema-on-Read: Collections do not enforce structure by default. Documents within the same collection can have distinct fields and types.
Data Relationship Handling Normalized relations linked via Foreign Keys; combined at read time using JOIN operations. Data co-location: related data is embedded into a single document whenever possible; joined using $lookup when necessary.
Query Language Declarative, standardized ANSI SQL with analytical window functions, CTEs, and recursive queries. JavaScript/BSON object-based query API and pipeline-based Aggregation Framework.
Transactions & Consistency Strict ACID guarantees across all tables and rows by default via Write-Ahead Logging (WAL) and MVCC. Atomic at single-document level; supports multi-document transactions across replica sets via two-phase commit.
Scaling Strategy Vertical Scaling: Scale up CPU/RAM on Primary; scale reads via streaming replication read replicas. Horizontal Scaling: Native automated Sharding across commodity server clusters via mongos routers.

2. ACID vs BASE: Consistency Paradigms

ACID (PostgreSQL) BASE (Traditional NoSQL / MongoDB)
Atomicity: All statements in a transaction succeed or all roll back. Basically Available: The database guarantees availability across network partitions, potentially returning degraded or secondary data.
Consistency: The database guarantees immediate consistency and invariant satisfaction (constraints, keys). Soft State: Data values may change over time due to background replication without user interaction.
Isolation: Concurrent transactions are isolated via MVCC snapshots and locks. Eventual Consistency: Replicas will become consistent eventually; reading from secondaries allows stale reads.
Durability: Commits survive crashes via fsynced Write-Ahead Logs. Configurable durability via Write Concerns (w: 1 vs w: "majority").

3. JSON Handling Showdown: PostgreSQL JSONB vs MongoDB BSON

A frequent interview debate is: "Since PostgreSQL has JSONB, why would anyone ever use MongoDB?"

While PostgreSQL's JSONB is powerful, there are fundamental architectural differences:

Capability PostgreSQL JSONB MongoDB BSON
Native Data Types Limited to JSON types (String, Number, Boolean, Array, Object, Null). Dates are stored as ISO text strings. Rich native types: Date, ObjectId, Decimal128, Int32, Int64, BinData.
Document Size Limits Up to 1 Gigabyte (compressed via PostgreSQL TOAST). Strict 16 Megabyte hard limit per document.
In-Place Field Updates Expensive: Updating a single nested field (jsonb_set) requires PostgreSQL to rewrite the ENTIRE physical row and write a new tuple version! Optimized: In-place binary updates for non-expanding fields via WiredTiger storage engine without rewriting the document.
Ecosystem & Tooling SQL queries require specialized operators (->, ->>, @>). ORM support can be awkward. Natural, seamless integration with JavaScript/TypeScript and Mongoose.

4. Schema Evolution: Strict Migrations vs Document Versioning

Managing database schema changes over a multi-year product lifecycle requires different strategies in SQL and NoSQL.

4.1 PostgreSQL: Migration Pipelines

PostgreSQL requires formal schema migration files (managed by tools like Prisma, Knex, or Flyway). Every database change requires an explicit DDL migration:

  • Pros: 100% deterministic schema state. The database catalog acts as the single source of truth. Data corruption is blocked at the gate.
  • Cons: Altering large tables requires careful coordination (the Expand-and-Contract pattern) to avoid table locks.

4.2 MongoDB: The Document Versioning Pattern

In MongoDB, migrating 100 million documents in a single batch update will exhaust server memory and lock the cluster. Instead, production MongoDB applications use the Document Versioning Pattern:

javascript (Document Versioning Pattern) 
// Schema v1 had 'name' (single string)
// Schema v2 splits into 'firstName' and 'lastName'

// Each document stores its schema version:
const userV1 = { _id: 1, name: "Alice Smith", schemaVersion: 1 };
const userV2 = { _id: 2, firstName: "Bob", lastName: "Jones", schemaVersion: 2 };

// Application Layer: Lazy Migration on Read
export function normalizeUserDocument(doc) {
  if (doc.schemaVersion === 1) {
    const [firstName, ...rest] = doc.name.split(" ");
    doc.firstName = firstName;
    doc.lastName = rest.join(" ");
    doc.schemaVersion = 2;
    delete doc.name;

    // Asynchronously update MongoDB in background so it becomes v2 permanently:
    db.collection("users").updateOne(
      { _id: doc._id },
      { $set: { firstName: doc.firstName, lastName: doc.lastName, schemaVersion: 2 }, $unset: { name: "" } }
    );
  }
  return doc;
}

5. The Senior Engineer Decision Framework

Interviewers frequently present architectural scenarios and ask: "Would you choose PostgreSQL or MongoDB for this system, and why?"

Use Case / Requirements Recommended Database Architectural Justification
Financial Ledgers, Invoicing, Banking PostgreSQL Mandatory ACID guarantees, multi-table transactions, foreign key cascades, and check constraints prevent financial data corruption and balance drift.
Complex Relational Domain (Social Network / ERP) PostgreSQL Highly connected graph/relational entities requiring multi-table joins, recursive CTEs, and declarative foreign key integrity.
E-Commerce Product Catalog with Polymorphic Attributes MongoDB (or Postgres JSONB) Products have wildly different attributes (shoes have sizes, TVs have screen resolution, food has expiration dates). A flexible document model avoids sparse tables with 100 nullable columns.
High-Velocity Append Logs, Analytics Events, IoT Metrics MongoDB High write ingest speed, native time-series collections, TTL auto-expiry indexes, and horizontal sharding across commodity nodes.
Mobile App Backend with Rapid Prototyping MongoDB Documents map directly to client-side JSON structures; mobile payloads can be stored and retrieved with zero ORM impedance mismatch.

6. Polyglot Persistence: Using Both in Production

In modern enterprise architectures, the answer is rarely "PostgreSQL only" or "MongoDB only." Systems employ Polyglot Persistence: using different databases for different microservices based on workload fit.

Figure 27.1: Polyglot Persistence Architecture in an E-Commerce Platform
[ User HTTP Requests ]
          |
          +---> [ User Auth & Order Service ] =======> [ PostgreSQL ]
          |     (Strict ACID, foreign keys, payments)
          |
          +---> [ Product Catalog Service ] =========> [ MongoDB ]
          |     (Polymorphic document specs, rapid updates)
          |
          +---> [ Event Analytics & User History ] ===> [ MongoDB ]
          |     (High-throughput writes, TTL indexes)
          |
          +---> [ Session & Shopping Cart Cache ] ====> [ Redis ]
                (Microsecond in-memory key-value)

8. Chapter-Specific Interview Questions and Answers

Master these 20 high-frequency interview questions covering the architectural trade-offs between relational PostgreSQL and document-based MongoDB.

Q01 What is the primary architectural difference between PostgreSQL and MongoDB? Beginner
Spoken Interview Answer

"PostgreSQL is a relational database adhering strictly to Schema-on-Write and ACID transactions, storing data in normalized tabular rows linked via foreign keys and queried via SQL. MongoDB is a document-oriented database using Schema-on-Read, storing data in flexible, hierarchical BSON documents where related data is co-located and embedded. PostgreSQL optimizes for consistency and relational integrity, while MongoDB optimizes for developer agility, nested data, and horizontal sharding."

Q02 What is the difference between ACID and BASE consistency models? Intermediate
Spoken Interview Answer

"ACID (Atomicity, Consistency, Isolation, Durability) guarantees immediate strong consistency: all constraints and transactions are strictly enforced at commit time. BASE (Basically Available, Soft state, Eventual consistency) trades immediate consistency for availability and partition tolerance. In BASE, replicas may temporarily serve stale data while background replication catches up, guaranteeing only that all nodes will eventually become consistent."

Q03 Since PostgreSQL has JSONB, is MongoDB obsolete? How do they compare? Advanced
Spoken Interview Answer

"No, MongoDB is not obsolete. While PostgreSQL JSONB allows storing and indexing JSON with GIN, updating a single nested field in JSONB requires PostgreSQL to rewrite the entire row on disk and write a new MVCC tuple version. MongoDB's WiredTiger engine natively supports in-place binary modifications for non-expanding fields. Furthermore, MongoDB natively handles horizontal auto-sharding and JavaScript-native developer ergonomics, whereas PostgreSQL is primarily a vertically scaled relational system."

Q04 How does schema evolution differ between PostgreSQL and MongoDB? Intermediate
Spoken Interview Answer

"In PostgreSQL, schema changes require explicit DDL migrations (e.g. `ALTER TABLE`), ensuring all rows adhere to a single unified schema at all times. In MongoDB, collections are schemaless at the database level: schema evolution is handled in application code using the Document Versioning Pattern (`schemaVersion: 2`) or lazy migrations on read, allowing old and new document structures to coexist peacefully in the same collection."

Q05 What is Polyglot Persistence, and what is an example in a modern web application? Beginner
Spoken Interview Answer

"Polyglot Persistence is the architectural practice of using multiple different database engines within the same system, matching each database to the specific workload it excels at. For example, in an e-commerce platform: PostgreSQL handles user authentication, billing, and order transactions (ACID); MongoDB stores the polymorphic product catalog and user activity logs; and Redis caches user sessions and live shopping carts."

Q06 How do multi-document transactions compare between PostgreSQL and MongoDB? Advanced
Spoken Interview Answer

"PostgreSQL was designed from day one around ACID multi-table transactions; transactions are extremely fast and lightweight, managed via Write-Ahead Logging and MVCC. MongoDB added multi-document transactions in version 4.0 across replica sets using a two-phase commit protocol. In MongoDB, multi-document transactions incur noticeable latency and overhead, and have a 60-second execution time limit. MongoDB design encourages embedding so that most writes remain atomic single-document updates."

Q07 How does horizontal scaling differ between PostgreSQL and MongoDB? Intermediate
Spoken Interview Answer

"MongoDB supports native Horizontal Sharding out-of-the-box: data is partitioned across multiple shards based on a shard key, with `mongos` routers transparently distributing queries and automated balancers migrating chunks. PostgreSQL scales writes vertically (increasing CPU/RAM on the primary); it scales reads horizontally via streaming replication read replicas, but does not have native, turnkey automatic write sharding without third-party extensions like Citus."

Q08 Scenario: You are designing a healthcare patient record system where data corruption can have legal consequences. Which database do you choose and why? Scenario
Spoken Interview Answer

"I would choose PostgreSQL. Healthcare records require strict referential integrity, strong consistency, audit compliance (HIPAA), and schema guarantees. PostgreSQL enforces foreign keys, check constraints, immutable temporal tables, and row-level security (RLS) at the engine catalog level, ensuring application-level bugs cannot write orphaned or invalid medical records."

Q09 Scenario: You are building an IoT sensor analytics platform receiving 100,000 telemetry events per second. Which database do you choose and why? Scenario
Spoken Interview Answer

"I would choose MongoDB (specifically its native Time-Series Collections or the Bucket Pattern). High write throughput, automated horizontal sharding, native TTL expiration indexes (to automatically purge data older than 90 days), and schemaless sensor payload flexibility make MongoDB well-suited for high-velocity ingest compared to relational tables with rigid constraints."

Q10 What is the Object-Relational Impedance Mismatch, and how does MongoDB solve it? Intermediate
Spoken Interview Answer

"The impedance mismatch is the conceptual friction between object-oriented code (which works with nested objects, arrays, and hierarchies) and relational databases (which store data in flat two-dimensional tables linked by keys). Developers must use ORMs to shred objects into rows on write and join them back on read. MongoDB eliminates this mismatch by storing data directly as BSON documents that mirror application JSON objects."

Q11 What are the trade-offs of embedding related data in MongoDB vs normalizing in PostgreSQL? Advanced
Spoken Interview Answer

"Embedding in MongoDB allows fetching an entire entity and its children in a single disk read with zero joins, and updates are atomic. However, it causes data duplication if child data is shared, and risks hitting the 16MB limit. Normalizing in PostgreSQL eliminates redundancy and guarantees that updating a child record updates it everywhere, but requires relational joins and foreign key index lookups on read."

Q12 What is Schema-on-Read vs Schema-on-Write? Beginner
Spoken Interview Answer

"Schema-on-Write (PostgreSQL) enforces a fixed structure before data is written; invalid rows are rejected. Schema-on-Read (MongoDB) accepts arbitrary data structures upon write; the application interpreting the data applies formatting, parsing, and defaults when the data is read."

Q13 Can you perform complex recursive hierarchy traversals in MongoDB like PostgreSQL's Recursive CTEs? Advanced
Spoken Interview Answer

"Yes, using the `$graphLookup` stage in the MongoDB Aggregation Pipeline. `$graphLookup` performs recursive searches on a collection, following a specified connecting field up to a defined `maxDepth`. However, PostgreSQL's `WITH RECURSIVE` is more expressive, supports arbitrary SQL expressions, cycle detection arrays, and complex joins during recursion."

Q14 How does backup and disaster recovery compare between PostgreSQL and MongoDB? Intermediate
Spoken Interview Answer

"PostgreSQL uses `pg_dump` for logical backups and continuous physical WAL archiving (`pgBackRest`) for point-in-time recovery (PITR) down to the exact second. MongoDB uses `mongodump` for logical backups and filesystem snapshots combined with Oplog archiving for point-in-time recovery. In sharded MongoDB clusters, coordinating consistent cluster-wide snapshots across independent shards is significantly more complex than PostgreSQL."

Q15 Why can MongoDB queries be vulnerable to NoSQL injection in Node.js? Advanced
Spoken Interview Answer

"If an Express route passes user input directly from `req.body` into a MongoDB query: `db.users.find({ username: req.body.username, password: req.body.password })`, an attacker can send JSON: `{\"username\": \"admin\", \"password\": {\"$gt\": \"\"}}`. The `$gt` operator evaluates to true for any non-empty string, authenticating the attacker as admin without knowing the password! Mitigate using `mongo-sanitize` or strict schema validation."

Q16 What is the difference between SQL JOIN and MongoDB $lookup? Beginner
Spoken Interview Answer

"A SQL `INNER JOIN` or `LEFT JOIN` combines columns from two tables into a single flat row (duplicating parent columns if there are multiple child rows). MongoDB's `$lookup` performs a Left Outer Join that attaches matching documents from a foreign collection as an **embedded array** inside the parent document, preserving the hierarchical document structure."

Q17 Scenario: A SaaS startup begins on MongoDB, but after 2 years faces severe data corruption and orphaned documents. What went wrong? Scenario
Spoken Interview Answer

"The team relied on MongoDB for a heavily relational business domain. Without database-enforced foreign keys, check constraints, and cascading rules, application bugs, manual script updates, and unhandled promise rejections created orphaned documents, duplicate records, and invalid types over time. The remedy is either enforcing strict Mongoose schema validation with pre-save hooks, or migrating relational transactional entities to PostgreSQL."

Q18 How does connection management compare between PostgreSQL (PgBouncer) and MongoDB (Native Driver)? Intermediate
Spoken Interview Answer

"PostgreSQL uses a process-per-connection architecture (~10MB RAM per connection), requiring external connection poolers like PgBouncer for high-concurrency Node.js clusters. MongoDB uses an internal thread-per-connection / thread-pool model, and the native Node.js MongoDB driver includes a sophisticated built-in client connection pool (`maxPoolSize`), eliminating the need for an external proxy in standard setups."

Q19 What is the difference between Write Concern 'majority' in MongoDB and synchronous_commit in PostgreSQL? Advanced
Spoken Interview Answer

"Both configure durability across distributed nodes. In MongoDB, `w: 'majority'` ensures the write has been stored in memory on a majority of replica set members before acknowledging the client. In PostgreSQL, `synchronous_commit = on` (default) ensures the commit is flushed to disk via WAL locally; in streaming replication, `synchronous_commit = remote_apply` ensures the WAL was flushed AND applied to standby replicas before confirming the commit."

Q20 How do you explain the trade-offs between PostgreSQL and MongoDB to a non-technical stakeholder? Intermediate
Spoken Interview Answer

"'PostgreSQL is like a strict, highly organized spreadsheet system with rigid rules: it guarantees that numbers always add up, references never break, and financial books balance perfectly. MongoDB is like a digital filing cabinet of organized folders: each folder holds all documents related to a topic in one place, allowing us to build features quickly and store varied data, but requiring our team to enforce the rules carefully.'"
