1. The Logical Query Execution Order

In standard SQL, you write queries starting with SELECT. However, the SQL database engine executes clauses in a completely different, strict logical sequence:

Figure 20.1: Logical Query Execution Order
[ Written SQL Syntax Order ]                 [ Logical Database Engine Execution Order ]
1. SELECT                                   1. FROM & JOIN (Locate & merge base tables)
2. FROM                                     2. WHERE (Filter individual base rows)
3. JOIN ... ON                              3. GROUP BY (Aggregate rows into groups)
4. WHERE                                    4. HAVING (Filter aggregated groups)
5. GROUP BY                                 5. SELECT (Evaluate expressions & column aliases)
6. HAVING                                   6. DISTINCT (Deduplicate output tuples)
7. ORDER BY                                 7. ORDER BY (Sort final result set)
8. LIMIT / OFFSET                           8. LIMIT / OFFSET (Slice pagination window)
💡 Why WHERE annual_salary > 100000 Fails with "Column Does Not Exist"

Consider this common bug: 

-- FAILS: ERROR: column "annual_salary" does not exist!
SELECT first_name, (hourly_rate * 2080) AS annual_salary
FROM employees
WHERE annual_salary > 100000;

Because WHERE (Step 2) executes before SELECT (Step 5), the column alias annual_salary has not yet been computed or registered when the filter evaluates. You must either repeat the expression in the WHERE clause or wrap the query in a CTE / subquery. Conversely, ORDER BY (Step 7) runs after SELECT, so referencing annual_salary in ORDER BY works perfectly.

2. Relational Joins in Depth

Relational joins combine columns from one or more tables based on a related attribute.

Join Type Venn Diagram Behavior Handling of Unmatched Rows Typical Real-World Use Case
INNER JOIN Intersection (\(A \cap B\)) Unmatched rows from either table are completely discarded. Fetching orders that have an associated registered user.
LEFT OUTER JOIN All of \(A\), plus matching \(B\) Preserves all rows from left table; columns from right table are populated with NULL if no match exists. Listing all users, including those who have never placed an order.
RIGHT OUTER JOIN All of \(B\), plus matching \(A\) Preserves all rows from right table; unmatched left columns filled with NULL. Rarely used; conventionally rewritten as a LEFT JOIN for readability.
FULL OUTER JOIN Union (\(A \cup B\)) Preserves all rows from both tables. Missing sides are filled with NULL. Reconciling payment records against bank statement imports.
CROSS JOIN Cartesian Product (\(A \times B\)) Every row of \(A\) is paired with every row of \(B\) (produces \(N \times M\) rows). Generating matrix grids (e.g. all shirt sizes \(\times\) all available colors).
Self Join Table joined to itself Joins a table to an aliased instance of itself via foreign key. Hierarchical models: matching employees to their manager in the same employees table.
sql (Relational Joins Demonstration) 
-- 1. INNER JOIN: Only customers who placed orders
SELECT c.name, o.id AS order_id, o.total_amount
FROM customers c
INNER JOIN orders o ON c.id = o.customer_id;

-- 2. LEFT JOIN: Find customers who have NEVER placed an order (Anti-Join Pattern)
SELECT c.name, c.email
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.id IS NULL; -- Filters to left-side rows with no right-side match!

-- 3. Self Join: Organizational hierarchy (Employee -> Manager)
SELECT 
  e.name AS employee_name,
  COALESCE(m.name, 'Top Executive / CEO') AS manager_name
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

3. Aggregations: WHERE vs HAVING

A frequent interview question tests whether candidates understand the fundamental difference between WHERE and HAVING:

  • WHERE: Filters individual rows before any grouping or aggregation takes place. Cannot use aggregate functions (e.g. WHERE SUM(amount) > 100 is a syntax error).
  • HAVING: Filters grouped buckets after GROUP BY has aggregated rows. Evaluates aggregate functions (e.g. HAVING COUNT(*) >= 5).
sql 
-- Query: Find active customers who spent more than $500 in 2024
SELECT 
  c.id, 
  c.name, 
  COUNT(o.id) AS total_orders,
  SUM(o.total_amount) AS total_spent
FROM customers c
JOIN orders o ON c.id = o.customer_id
WHERE o.created_at >= '2024-01-01' AND o.status = 'COMPLETED' -- Filters rows prior to grouping
GROUP BY c.id, c.name
HAVING SUM(o.total_amount) > 500 -- Filters aggregated groups
ORDER BY total_spent DESC;

4. Common Table Expressions (CTEs) & Recursive CTEs

A Common Table Expression (CTE) is a temporary named result set defined within the scope of a single SELECT, INSERT, UPDATE, or DELETE statement using the WITH keyword.

4.1 Standard CTEs vs Subqueries

Unlike deeply nested subqueries that read inside-out, CTEs read top-to-bottom like linear code, vastly improving maintainability. In PostgreSQL 12+, CTEs are automatically inlined by the query planner unless marked with WITH ... AS MATERIALIZED.

4.2 Recursive CTEs: Traversing Hierarchical Trees

A Recursive CTE references itself. It is essential for querying recursive structures like category trees, threaded comment replies, bill of materials, and organizational charts.

A recursive CTE consists of:

  1. Anchor Member: The base query that initiates the recursion (e.g., finding the top-level CEO).
  2. UNION ALL
  3. Recursive Member: References the CTE name to join children to their parents until no more rows are returned.
sql (Recursive CTE for Category Tree) 
-- Schema: categories (id, name, parent_id)
WITH RECURSIVE category_tree AS (
  -- 1. ANCHOR MEMBER: Find root categories (no parent)
  SELECT 
    id, 
    name, 
    parent_id, 
    1 AS depth,
    name::TEXT AS breadcrumb_path
  FROM categories
  WHERE parent_id IS NULL

  UNION ALL

  -- 2. RECURSIVE MEMBER: Find children by joining onto previous iteration
  SELECT 
    c.id, 
    c.name, 
    c.parent_id, 
    ct.depth + 1,
    ct.breadcrumb_path || ' > ' || c.name
  FROM categories c
  JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT id, name, depth, breadcrumb_path
FROM category_tree
ORDER BY breadcrumb_path;

/* Expected Output:
 id | name        | depth | breadcrumb_path
----+-------------+-------+---------------------------------------
  1 | Electronics |     1 | Electronics
  4 | Laptops     |     2 | Electronics > Laptops
  8 | Gaming      |     3 | Electronics > Laptops > Gaming
  2 | Furniture   |     1 | Furniture
  5 | Chairs      |     2 | Furniture > Chairs
*/

5. Analytical Window Functions

Standard aggregate functions (like SUM or AVG) collapse multiple rows into a single summary row.

Window Functions perform calculations across a set of table rows that are related to the current row, without collapsing the rows! Each original row retains its separate identity while displaying the computed aggregate or ranking value.

Function Behavior Tie-Breaking Example (Values: 100, 100, 80)
ROW_NUMBER() Assigns a unique sequential integer starting at 1 to every row within the partition. 1, 2, 3 (No duplicates; ties broken arbitrarily)
RANK() Assigns the same rank to identical values, but leaves gaps in the sequence. 1, 1, 3 (Rank 2 is skipped!)
DENSE_RANK() Assigns the same rank to identical values, without leaving gaps. 1, 1, 2 (No ranks skipped)
LAG(col, offset) Accesses data from a previous row in the partition without a self-join. Used for period-over-period growth comparisons.
LEAD(col, offset) Accesses data from a subsequent row in the partition. Used for forward-looking churn predictions.
sql (Window Functions in Action) 
-- Query: Find the Top 2 Highest-Earning Employees in each Department
WITH ranked_employees AS (
  SELECT 
    id,
    name,
    department_id,
    salary,
    -- Partition resets ranking for each department independently!
    DENSE_RANK() OVER (
      PARTITION BY department_id 
      ORDER BY salary DESC
    ) as salary_rank
  FROM employees
)
SELECT name, department_id, salary, salary_rank
FROM ranked_employees
WHERE salary_rank <= 2;

-- Query: Calculate Month-over-Month Revenue Growth using LAG()
SELECT 
  month,
  revenue,
  LAG(revenue, 1) OVER (ORDER BY month) AS prev_month_revenue,
  ROUND(
    ((revenue - LAG(revenue, 1) OVER (ORDER BY month)) / LAG(revenue, 1) OVER (ORDER BY month)) * 100, 
    2
  ) AS mom_growth_pct
FROM monthly_sales;

6. Three-Valued Logic and NULL Pitfalls

In SQL, NULL does not represent zero, an empty string, or false. NULL represents unknown or missing information.

Because of this, SQL operates on Three-Valued Logic (3VL): every Boolean expression evaluates to TRUE, FALSE, or UNKNOWN.

Expression Result Why It Behaves This Way
NULL = NULL UNKNOWN Two unknown values cannot be asserted as equal.
NULL <> NULL UNKNOWN Two unknown values cannot be asserted as unequal.
val IS NULL TRUE (if val is null) IS NULL is the only valid way to check for nullity.
TRUE AND UNKNOWN UNKNOWN Outcome depends on what the unknown value resolves to.
FALSE AND UNKNOWN FALSE Regardless of unknown, FALSE AND anything is always FALSE.
⚠️ The Deadly NOT IN (subquery with NULL) Trap

If a subquery returns even a single NULL value, a NOT IN condition will evaluate to UNKNOWN for every row, resulting in zero rows returned: 

-- If orders has ANY row where customer_id IS NULL:
-- "c.id NOT IN (1, 2, NULL)" expands to:
-- "(c.id != 1) AND (c.id != 2) AND (c.id != NULL)"
-- Since (c.id != NULL) is UNKNOWN, the whole expression becomes UNKNOWN!
SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM orders); -- Returns EMPTY SET!

-- FIX 1: Use NOT EXISTS (Safe against NULLs)
SELECT * FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- FIX 2: Filter out NULLs in subquery
SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL);

7. Practical Exercises & Code Walkthrough

Exercise 20.1 Calculate 7-Day Moving Averages with Window Framing

Problem: You are given a table daily_revenue(date DATE, amount NUMERIC). Write a query to compute the 7-day trailing moving average revenue for each day using window frames (including the current day and the preceding 6 days).

View Complete Solution
sql 
SELECT 
  date,
  amount,
  -- Window Frame: ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
  ROUND(
    AVG(amount) OVER (
      ORDER BY date
      ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ), 
    2
  ) AS moving_avg_7d
FROM daily_revenue
ORDER BY date;

8. Chapter-Specific Interview Questions and Answers

Master these 20 high-frequency SQL and PostgreSQL interview questions covering query lifecycles, joins, window functions, and subquery optimization.

Q01 What is the logical order of execution of an SQL query? Beginner
Spoken Interview Answer

"Although written starting with `SELECT`, the database engine executes SQL clauses in this order: 1. `FROM` and `JOIN` (identify tables and merge), 2. `WHERE` (filter individual rows), 3. `GROUP BY` (aggregate into buckets), 4. `HAVING` (filter aggregated groups), 5. `SELECT` (compute column projections and aliases), 6. `DISTINCT` (eliminate duplicates), 7. `ORDER BY` (sort results), and 8. `LIMIT` / `OFFSET` (paginate output window)."

Q02 What is the difference between WHERE and HAVING? Beginner
Spoken Interview Answer

"`WHERE` filters individual rows BEFORE any grouping occurs, and cannot contain aggregate functions like `SUM()` or `COUNT()`. `HAVING` filters grouped rows AFTER the `GROUP BY` clause has aggregated the dataset, and specifically evaluates aggregate expressions (e.g. `HAVING COUNT(*) > 5`)."

Q03 What is the difference between RANK(), DENSE_RANK(), and ROW_NUMBER()? Intermediate
Spoken Interview Answer

"When sorting values with ties (e.g. scores 100, 100, 90): `ROW_NUMBER()` assigns sequential numbers (1, 2, 3) arbitrarily breaking ties. `RANK()` assigns identical ranks to tied values but leaves gaps in the sequence (1, 1, 3). `DENSE_RANK()` assigns identical ranks to tied values without leaving gaps (1, 1, 2)."

Q04 Why does NOT IN (subquery) fail when the subquery returns a single NULL? Intermediate
Spoken Interview Answer

"Because SQL uses Three-Valued Logic. `x NOT IN (1, 2, NULL)` evaluates to `(x != 1) AND (x != 2) AND (x != NULL)`. Comparing anything with NULL using equality operators yields `UNKNOWN`. In SQL, `TRUE AND UNKNOWN` yields `UNKNOWN`. Since a `WHERE` clause only accepts rows that evaluate strictly to `TRUE`, the entire query returns zero rows. The safe alternative is to use `NOT EXISTS`, which relies on row existence rather than value comparison."

Q05 What is a Recursive CTE, and how does it execute iteratively? Advanced
Spoken Interview Answer

"A Recursive CTE uses `WITH RECURSIVE` and consists of an Anchor member, `UNION ALL`, and a Recursive member referencing the CTE itself. The engine first executes the Anchor query to seed the working table. In subsequent iterations, it executes the Recursive query joining with the working table from the previous step. It appends results to the final set and updates the working table until an iteration yields zero rows, making it ideal for graph and hierarchical tree traversal."

Q06 What is the difference between UNION and UNION ALL? Intermediate
Spoken Interview Answer

"`UNION ALL` simply concatenates two result sets together without inspecting rows. `UNION` concatenates the sets and performs an extra deduplication step (equivalent to `DISTINCT`), sorting or hashing the combined set to remove duplicates. `UNION ALL` is significantly faster and consumes less memory; you should always prefer `UNION ALL` unless duplicate elimination is explicitly required."

Q07 What is a CROSS JOIN, and when does it become dangerous? Beginner
Spoken Interview Answer

"A `CROSS JOIN` produces the Cartesian product of two tables, pairing every row from the first table with every row from the second table. If Table A has 10,000 rows and Table B has 10,000 rows, a `CROSS JOIN` produces 100,000,000 rows. It becomes dangerous when accidentally written (such as omitting a `WHERE` join condition in comma-separated `FROM TableA, TableB`), which can exhaust database memory and lock the engine."

Q08 What is an Anti-Join, and how is it implemented? Intermediate
Spoken Interview Answer

"An Anti-Join returns rows from the first table that have NO matching rows in the second table. The two most common implementations are: 1. `LEFT JOIN` combined with `WHERE right_table.id IS NULL`, and 2. `WHERE NOT EXISTS (SELECT 1 FROM right_table WHERE right_table.fk = left_table.id)`. In PostgreSQL, `NOT EXISTS` is generally preferred because the query planner can optimize it as an Anti-Semi-Join."

Q09 What is the difference between COUNT(*), COUNT(1), and COUNT(column_name)? Advanced
Spoken Interview Answer

"`COUNT(*)` and `COUNT(1)` are functionally identical in modern PostgreSQL; both count the total number of rows matching the query, including rows containing NULLs. `COUNT(column_name)`, however, only counts rows where `column_name IS NOT NULL`, completely ignoring NULL values. If a column has 10 rows and 3 are NULL, `COUNT(*)` returns 10 while `COUNT(column_name)` returns 7."

Q10 What do LEAD() and LAG() window functions do? Intermediate
Spoken Interview Answer

"`LAG(col, n)` accesses the value of `col` from `n` rows prior to the current row within the partitioned window. `LEAD(col, n)` accesses the value from `n` rows ahead. They allow computing time-series differences, such as month-over-month revenue growth or user activity gaps, in a single pass without expensive self-joins."

Q11 How does PostgreSQL handle CTE materialization since PostgreSQL 12? Advanced
Spoken Interview Answer

"Prior to PostgreSQL 12, CTEs acted as optimization fences: the CTE was always materialized (computed separately into a temporary structure), preventing the planner from pushing outer `WHERE` predicates down into the CTE. In PostgreSQL 12+, CTEs are automatically inlined like subqueries if referenced only once and lacking side-effects. You can explicitly force behavior using `WITH ... AS MATERIALIZED` or `WITH ... AS NOT MATERIALIZED`."

Q12 What is the difference between COALESCE and NULLIF? Beginner
Spoken Interview Answer

"`COALESCE(val1, val2, ...)` evaluates arguments in order and returns the first non-NULL value, commonly used for default fallbacks: `COALESCE(phone, 'N/A')`. `NULLIF(a, b)` returns `NULL` if `a === b`, otherwise returns `a`. Its classic use case is preventing division-by-zero errors: `total / NULLIF(count, 0)`."

Q13 Scenario: How would you write a query to find the second highest salary in an employees table? Scenario
Spoken Interview Answer

"The cleanest production approach uses `DENSE_RANK()`: `WITH ranked AS (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) as rnk FROM employees) SELECT salary FROM ranked WHERE rnk = 2 LIMIT 1;`. `DENSE_RANK()` correctly handles ties if multiple employees share the top salary. Alternatively, `SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees)`."

Q14 What is the difference between a Correlated Subquery and an Uncorrelated Subquery? Intermediate
Spoken Interview Answer

"An uncorrelated subquery is independent of the outer query; it executes once and passes its static result to the outer query. A correlated subquery references columns from the outer query table (e.g. `WHERE o.customer_id = c.id`). Historically, correlated subqueries executed once for every row processed by the outer query, causing performance bottlenecks, though modern query optimizers frequently rewrite them into joins."

Q15 What is the difference between ROWS and RANGE in Window Framing? Advanced
Spoken Interview Answer

"`ROWS` specifies the frame offset by a physical count of rows (e.g. `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` strictly includes 3 physical rows). `RANGE` specifies offsets by value equality of the `ORDER BY` expression. If multiple rows share the exact same `ORDER BY` value, `RANGE` treats them as duplicates and includes all peer rows within the frame, which can cause unexpected aggregate jumps."

Q16 What does the DISTINCT ON (expression) clause do in PostgreSQL? Beginner
Spoken Interview Answer

"`DISTINCT ON` is a PostgreSQL-specific extension that keeps only the first row for each group of rows sharing the specified expression values. Combined with `ORDER BY`, it provides a clean way to select the single latest or highest record per category: `SELECT DISTINCT ON (department_id) * FROM employees ORDER BY department_id, salary DESC` selects the highest-paid employee per department."

Q17 How does a Self-Join work, and what is its typical use case? Intermediate
Spoken Interview Answer

"A self-join is a regular join where a table is joined to itself under different table aliases (e.g. `FROM employees e LEFT JOIN employees m ON e.manager_id = m.id`). Its typical use case is modeling hierarchical or recursive data stored in a single table, such as employees and their managers, parent categories, or tracking flight routes with source and destination airports."

Q18 Scenario: You need to generate a sequence of all 365 calendar dates in 2024 to join with sales data and find days with zero sales. How do you generate this in PostgreSQL? Scenario
Spoken Interview Answer

"In PostgreSQL, I use the `generate_series()` function: `SELECT generate_series('2024-01-01'::DATE, '2024-12-31'::DATE, '1 day'::INTERVAL)::DATE AS calendar_date`. I then `LEFT JOIN` this date series onto the `sales` table on `calendar_date = sales.sale_date`. Days with zero sales will have `NULL` sales amounts, which can be coalesced to 0."

Q19 What is an UPSERT in PostgreSQL, and how does ON CONFLICT DO UPDATE work? Advanced
Spoken Interview Answer

"An UPSERT atomically inserts a row or updates an existing row if a unique constraint or primary key collision occurs. In PostgreSQL: `INSERT INTO users (id, email, visits) VALUES (1, 'alice@test.com', 1) ON CONFLICT (email) DO UPDATE SET visits = users.visits + 1, updated_at = NOW()`. The special pseudo-record `EXCLUDED` represents the proposed values that conflicted."

Q20 What is the difference between DROP TABLE, TRUNCATE TABLE, and DELETE FROM? Beginner
Spoken Interview Answer

"`DELETE FROM` is a DML command that deletes rows one by one, logs each deletion in WAL, executes `ON DELETE` triggers, and supports `WHERE` clauses. `TRUNCATE TABLE` is a DDL command that deallocates entire table data pages in bulk; it is much faster than `DELETE`, does not fire row triggers, and resets identity counters. `DROP TABLE` removes the table data AND the table schema definition completely from the database catalog."
