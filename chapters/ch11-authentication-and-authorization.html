1. Authentication vs Authorization: The Architectural Boundary

In engineering interviews, conflating these two terms is an immediate red flag:

Dimension Authentication (AuthN) Authorization (AuthZ)
Core Question "Who are you?" (Identity verification) "What permissions do you have?" (Access control)
Input Artifacts Passwords, MFA OTP codes, biometric passkeys, magic links, OAuth tokens. Roles (Admin, Editor), permission scopes (`tasks:write`), Access Control Lists (ACL).
HTTP Failure Code 401 Unauthorized (Credentials missing, expired, or invalid). 403 Forbidden (Identity known, but access denied for this resource).
Execution Order Always executed first in the middleware pipeline. Executed after authentication succeeds.

2. Stateful Sessions vs Stateless JWTs

How should an application remember a user between HTTP requests?

Feature Stateful Sessions (Cookies + Redis/DB) Stateless JWTs (JSON Web Tokens)
Server State Stateful: The server stores a session row in Redis/DB; the browser holds an opaque session ID cookie. Stateless: The server stores nothing; the client holds the cryptographically signed token containing user claims.
Immediate Revocation Instantaneous: Deleting the session key in Redis instantly logs out the user on their next request. Hard: A signed JWT remains valid until its exp timestamp passes, unless you maintain a centralized token blacklist.
Horizontal Scalability Requires a centralized fast shared cache (Redis) across all load-balanced application instances. Any server instance possessing the secret key can verify the token without checking a database.
Bandwidth Overhead Minimal (a short 32-byte session ID cookie). Larger (~500B–2KB) sent on every HTTP request header.
Best Use Case Monolithic web applications, traditional server-rendered apps, banking/financial systems requiring instant kill switches. Distributed microservices, mobile apps, third-party API integrations, cross-domain SSO.

3. JWT Internals: Structure and Cryptography

A JSON Web Token consists of three base64url-encoded strings separated by periods (.):

PAYLOAD (Base64Url) | | { "sub": "u_987", "role": "admin", "iat": 1713689200, "exp": 1713690100 } | +-------------------------------------------------------------------------------+ . +-------------------------------------------------------------------------------+ | 3. SIGNATURE (Cryptographic Hash) | | HMACSHA256( base64Url(Header) + "." + base64Url(Payload), secretKey ) | +-------------------------------------------------------------------------------+

🚨 Crucial Interview Rule: JWTs are NOT Encrypted!

A standard JWT is Signed, NOT Encrypted. Anyone can decode the base64 payload at jwt.io and read the contents in plaintext. Never put sensitive data (passwords, credit card numbers, or social security numbers) inside a JWT payload! The signature guarantees only that the payload has not been tampered with.

4. Access Token & Refresh Token Rotation (RTR)

How do we balance security (short lifespan) with user convenience (not forcing users to re-login every 15 minutes)? We use the dual-token architecture:

  • Access Token: Short-lived (10–15 minutes). Sent in the Authorization: Bearer <token> header. Used to authenticate API requests. Stored in memory on client.
  • Refresh Token: Long-lived (7–30 days). Stored in an HttpOnly, Secure, SameSite=Strict cookie. Used solely to request a new Access Token.
Client Backend API | | | 1. POST /api/auth/login (email, password) ----------------------------> | | <--- 2. Returns Access Token (JSON) + Refresh Token 1 (HttpOnly Cookie)-| | | | [15 Minutes Pass: Access Token Expires] | | | | 3. POST /api/auth/refresh (Cookie: Refresh Token 1) -------------------> | | | | * Backend verifies Refresh Token 1 in Database | | * Backend INVALIDATES Refresh Token 1 | | * Backend generates Refresh Token 2 & new Access Token | | | | <--- 4. Returns new Access Token + Refresh Token 2 (New Cookie) ------- |
Figure 11.2: Refresh Token Rotation Flow with One-Time Use Tokens

Automatic Token Reuse Detection

What if an attacker steals Refresh Token 1? If either the legitimate user or the attacker uses Refresh Token 1 after it has already been rotated, the server detects Token Reuse! The server immediately revokes the entire token family, terminating all active sessions for that user across all devices, thwarting the attacker.

5. Password Hashing: Bcrypt vs Argon2id

Storing plaintext passwords is gross negligence. Using fast hashing algorithms like MD5, SHA-1, or SHA-256 is equally dangerous: modern GPUs can compute over 10 billion SHA-256 hashes per second, cracking passwords via brute force in minutes.

We use Adaptive, Memory-Hard, Slow Hashing Functions:

Algorithm Design Principle Work Factors OWASP Recommendation
Argon2id Winner of the Password Hashing Competition. Highly resistant to GPU and dedicated ASIC hardware attacks by utilizing memory hardness. Configured via: Memory (m), Iterations (t), Parallelism (p). #1 Preferred Choice (Current Gold Standard).
Bcrypt Based on the Blowfish cipher. Computationally expensive; automatically incorporates a 128-bit cryptographically secure random salt. Configured via: Cost Factor / Work Factor (e.g. 12 rounds = \(2^{12} = 4096\) iterations). Widely accepted enterprise standard. Max password length limit: 72 bytes. 
// Bcrypt Password Hashing in Node.js
const bcrypt = require('bcrypt');

async function hashPassword(plainPassword) {
  // Salt rounds: 12 is optimal balance between security (~250ms) and CPU
  const saltRounds = 12;
  return bcrypt.hash(plainPassword, saltRounds);
}

async function verifyPassword(plainPassword, storedHash) {
  // bcrypt.compare prevents timing attacks automatically
  return bcrypt.compare(plainPassword, storedHash);
}

6. Role-Based Access Control (RBAC) Middleware

Authorization ensures authenticated users can only perform actions permitted by their role: 

// src/middlewares/rbac.middleware.ts
import { Request, Response, NextFunction } from "express";
import { AppError } from "../utils/AppError";

type Role = "admin" | "manager" | "member";

export function authorizeRoles(...allowedRoles: Role[]) {
  return (req: Request, res: Response, next: NextFunction) => {
    // req.user is populated by authenticateJwt middleware
    if (!req.user) {
      return next(new AppError("Authentication required", 401));
    }

    if (!allowedRoles.includes(req.user.role as Role)) {
      return next(new AppError("You do not have permission to perform this action", 403));
    }

    next();
  };
}

// Usage in Routes:
// router.delete('/users/:id', authenticateJwt, authorizeRoles('admin'), userController.deleteUser);

7. OAuth 2.0 and OpenID Connect (OIDC)

OAuth 2.0 is an Authorization framework that allows third-party applications to obtain limited access to an HTTP service on behalf of a resource owner (e.g., "Sign in with Google" or allowing Spotify to access Facebook friends).

PKCE (Proof Key for Code Exchange)

In Single-Page Applications (React) or Mobile Apps, the client cannot securely store a client_secret. OAuth 2.0 mandates PKCE (RFC 7636): the client generates a random code_verifier and sends its hashed code_challenge during the initial request, proving ownership during token exchange without a client secret.

Interview Questions and Answers

20 comprehensive interview questions testing authentication mechanics, token security, cookie flags, password hashing, and OWASP defenses.

Q1 What is the difference between Authentication and Authorization? Beginner
Spoken Interview Answer

"Authentication is verifying who a user is—confirming their identity through credentials like passwords, MFA codes, or OAuth tokens. Authorization is determining what permissions or resources that authenticated user is allowed to access—such as checking if a user has an 'admin' role. If authentication fails, the server returns 401 Unauthorized; if authorization fails, it returns 403 Forbidden."

Q2 Where should JWTs be stored on the client side: `localStorage` or `HttpOnly` cookies? Why? Intermediate
Spoken Interview Answer

"Refresh tokens should always be stored in an `HttpOnly, Secure, SameSite=Strict` cookie. `localStorage` is accessible to any JavaScript running on the page, meaning a single Cross-Site Scripting (XSS) vulnerability or malicious npm dependency can steal the user's token directly. An `HttpOnly` cookie cannot be read or stolen by JavaScript via `document.cookie`, providing robust defense against credential theft. Short-lived access tokens can be held in JavaScript memory."

Q3 What is Refresh Token Rotation (RTR), and how does Token Reuse Detection prevent hijacking? Advanced
Spoken Interview Answer

"Refresh Token Rotation ensures every refresh token can be used exactly once. When a client exchanges a refresh token for a new access token, the server invalidates that refresh token and issues a brand-new one. If an attacker and a legitimate user attempt to use the same refresh token, the server detects token reuse: it immediately revokes the entire token family, killing all active sessions for that user across all devices."

Q4 Why is salting passwords necessary? What are Rainbow Tables? Intermediate
Spoken Interview Answer

"A salt is a cryptographically random string generated uniquely for each user and concatenated with their password before hashing. A Rainbow Table is a precomputed lookup table containing millions of pre-hashed common passwords. Without salts, two users with the password 'Password123' have identical hashes, allowing attackers to look up hashes in seconds. Salting ensures identical passwords produce entirely different hashes, rendering rainbow tables useless."

Q5 What is the JWT `alg: "none"` vulnerability, and how do you protect against it? Advanced
Spoken Interview Answer

"The JWT specification permits an algorithm header of `none` for unsecured tokens. If a backend library naively trusts the `alg` specified in the incoming header, an attacker can modify their role to 'admin', set `\"alg\": \"none\"`, delete the signature, and the server would accept the token! We protect against this by explicitly specifying allowed algorithms in verification options: `jwt.verify(token, secret, { algorithms: ['HS256'] })`."

Q6 What do the `HttpOnly`, `Secure`, and `SameSite` cookie flags do? Beginner
Spoken Interview Answer

"`HttpOnly` blocks client-side JavaScript (`document.cookie`) from reading the cookie, mitigating XSS token theft. `Secure` mandates that the cookie is transmitted exclusively over encrypted HTTPS connections, preventing unencrypted plaintext sniffing. `SameSite=Strict` prevents the cookie from being sent in cross-site requests (like following third-party links or embedded forms), defending against Cross-Site Request Forgery (CSRF)."

Q7 What is Broken Object-Level Authorization (BOLA / IDOR)? Give an example. Intermediate
Spoken Interview Answer

"BOLA (formerly Insecure Direct Object References) occurs when an endpoint accesses objects directly based on user-supplied IDs (e.g. `GET /api/documents/987`) without verifying whether the authenticated user actually owns that document. An authenticated attacker simply changes `987` to `988` to view another user's private data. We prevent it by always scoping queries to the authenticated user ID: `WHERE id = $1 AND user_id = $2`."

Q8 What is the difference between Symmetric (HMAC SHA-256) and Asymmetric (RSA/ECDSA) JWT signing? Advanced
Spoken Interview Answer

"Symmetric signing (HS256) uses a single shared secret key for both signing and verification; every microservice that validates the token must possess the secret key, meaning if one service is compromised, an attacker can forge tokens. Asymmetric signing (RS256 / ES256) uses a Private/Public key pair: the Auth Server signs tokens using its private key, and all downstream microservices verify tokens using the public key without ever being able to forge them."

Q9 Scenario: How do you implement a secure "Forgot Password" reset flow? Scenario
Spoken Interview Answer

"1. Generate a cryptographically secure random token: `crypto.randomBytes(32).toString('hex')`. 2. Hash the token using SHA-256 and store the hash in the database with a 15-minute expiration and a `used: false` flag. 3. Email the UNHASHED token in a link: `https://app.com/reset?token=...`. 4. When the user submits a new password, hash the incoming token and look it up in the database. 5. If valid and unexpired, update the password, mark the token as used, and invalidate all existing active refresh tokens."

Q10 What is Account Enumeration, and how do you prevent it on login and registration endpoints? Intermediate
Spoken Interview Answer

"Account enumeration occurs when an API inadvertently reveals whether an email is registered—for example, returning 'User does not exist' vs 'Incorrect password', or varying response times due to skipping password hashing when a user is not found. We prevent it by: 1. Returning identical generic error messages: 'Invalid email or password'. 2. Ensuring constant-time execution by running a dummy password hash even if the user is not found in the database."

Q11 How does OAuth 2.0 PKCE (Proof Key for Code Exchange) prevent authorization code interception attacks? Advanced
Spoken Interview Answer

"In public clients (SPAs and mobile apps), an authorization code redirected to the browser could be intercepted by malicious browser extensions or URI schemes. With PKCE, the client generates a random secret (`code_verifier`) and sends its SHA-256 hash (`code_challenge`) during the initial authorization request. When exchanging the code for a token, the client must send the original unhashed `code_verifier`. The auth server verifies that `SHA256(verifier) === challenge`, ensuring only the entity that initiated the request can redeem the code."

Q12 What is the difference between OAuth 2.0 and OpenID Connect (OIDC)? Beginner
Spoken Interview Answer

"OAuth 2.0 is designed exclusively for Authorization: it issues an Access Token that allows an application to access APIs on the user's behalf, but tells the application nothing about who the user is. OpenID Connect is an identity layer built on top of OAuth 2.0 designed for Authentication: it introduces an `ID Token` (a signed JWT containing user profile claims like email, name, and subject ID)."

Q13 Scenario: A user reports their laptop was stolen. If your architecture uses stateless JWT access tokens with a 15-minute expiration, how do you revoke their access immediately? Scenario
Spoken Interview Answer

"1. Immediately delete or revoke all active Refresh Tokens for that user in the database, preventing new access tokens from being issued. 2. To revoke in-flight access tokens before their 15-minute expiry, publish the user's ID or token JTI (JWT ID) to a distributed in-memory Redis Blacklist with a TTL matching the token's remaining lifespan. The authentication middleware checks Redis for blacklisted tokens on protected requests."

Q14 What is a Timing Attack in authentication, and how does `crypto.timingSafeEqual()` prevent it? Intermediate
Spoken Interview Answer

"Standard string comparison (`a === b`) short-circuits and returns false on the very first mismatched character. An attacker measuring response times with microsecond precision can deduce characters one by one. `crypto.timingSafeEqual()` compares two buffers in constant time without short-circuiting, taking the exact same number of clock cycles regardless of where differences occur, completely preventing timing attacks."

Q15 How does Multi-Factor Authentication (MFA) using TOTP (Time-Based One-Time Password) work mathematically? Advanced
Spoken Interview Answer

"Under RFC 6238, during MFA setup, the server and the user's authenticator app share a secret base32 key (often via QR code). Every 30 seconds, both compute a time step counter: `T = floor(current_unix_time / 30)`. Both generate an HMAC-SHA1 hash using the secret key and the counter `T`, truncate the hash, and extract a 6-digit number. Because both calculate the same mathematical algorithm using synchronized clocks, the 6-digit code matches without sending SMS or network requests."

Q16 What are the standard claims found in a JWT payload (`sub`, `iat`, `exp`, `iss`, `aud`)? Beginner
Spoken Interview Answer

"`sub` (Subject): unique user or entity ID. `iat` (Issued At): timestamp when token was created. `exp` (Expiration Time): Unix timestamp after which token is invalid. `iss` (Issuer): entity that issued the token (e.g. auth.mycompany.com). `aud` (Audience): intended recipient service for the token."

Q17 What is the `__Host-` cookie prefix, and what security guarantees does it enforce? Intermediate
Spoken Interview Answer

"The `__Host-` prefix is a browser security standard. A cookie named with `__Host-` (e.g. `__Host-session`) is rejected by modern browsers unless: 1. It is set with the `Secure` flag over HTTPS. 2. It has `Path=/`. 3. It omits the `Domain` attribute (meaning it cannot be read, overwritten, or spoofed by subdomains like `blog.example.com`), completely closing subdomain injection attacks."

Q18 What is Session Fixation, and how do modern authentication frameworks prevent it? Advanced
Spoken Interview Answer

"Session Fixation occurs when an attacker obtains a valid unauthenticated session ID, tricks a victim into using it (via a malicious link or header), and waits for the victim to log in. If the server keeps the same session ID post-login, the attacker now possesses an authenticated session. Modern frameworks prevent this by always regenerating a brand-new session ID upon successful login (`req.session.regenerate()`)."

Q19 Scenario: Why is using bcrypt with synchronous methods (`bcrypt.hashSync`) a critical performance anti-pattern in Node.js web servers? Scenario
Spoken Interview Answer

"Bcrypt is intentionally slow and CPU-heavy. Running `bcrypt.hashSync` with 12 rounds takes ~250ms of pure synchronous CPU computation directly on the main JavaScript thread, completely blocking the Event Loop. During that quarter-second, no other HTTP requests can be accepted or processed. Asynchronous `bcrypt.hash` offloads the computation to libuv's background thread pool, leaving the main thread responsive."

Q20 What is JWKS (JSON Web Key Set), and how do microservices use it to verify RS256 JWTs? Advanced
Spoken Interview Answer

"A JWKS is a standard endpoint (e.g. `https://auth.company.com/.well-known/jwks.json`) hosted by the Authorization Server that publishes its current public keys in JSON format. When microservices receive an RS256 token, they inspect the `kid` (Key ID) header in the JWT, fetch and cache the corresponding public key from the JWKS endpoint, and verify the signature without requiring static shared secrets or redeployments when keys are rotated."
