1. How B-Tree Indexes Work Under the Hood

Without an index, finding a row in a table with 10,000,000 rows requires a Sequential Scan (Seq Scan): reading every single 8KB disk page from start to finish, requiring \(\mathcal{O}(n)\) disk reads.

A B-Tree (Balanced Tree) Index is a self-balancing tree data structure that maintains sorted data and allows searches, sequential access, insertions, and deletions in \(\mathcal{O}(\log n)\) time.

Figure 23.1: PostgreSQL B-Tree Index Architecture
                             [ ROOT PAGE ]
                             |  20 |  50  |
                            /      |       \
               +-----------+       |        +------------+
               |                   v                     |
       [ INTERNAL PAGE ]   [ INTERNAL PAGE ]     [ INTERNAL PAGE ]
       |   5  |  12  |     |  28  |  41  |       |  65  |  82  |
         /    |    \          /   |    \            /   |    \
        v     v     v        v    v     v          v    v     v
     +-----+-----+-----+  +-----+-----+-----+   +-----+-----+-----+
     | LEAF PAGE 1     |==| LEAF PAGE 2     |===| LEAF PAGE 3     | (Doubly-Linked List)
     | (k:1, TID:(0,1))|  | (k:22,TID:(2,4))|   | (k:60,TID:(5,2))|
     | (k:4, TID:(0,2))|  | (k:28,TID:(2,5))|   | (k:65,TID:(5,3))|
     +-----+-----+-----+  +-----+-----+-----+   +-----+-----+-----+
     
     TID = Item Pointer (Block Number, Offset) pointing to physical table heap page!

1.1 Anatomy of a B-Tree Search

  1. Root Page: Traversal begins at the root page (cached permanently in RAM Shared Buffers). Binary search identifies the appropriate child page pointer.
  2. Internal (Branch) Pages: Direct traversal down intermediate branches in \(\approx 3\) page hops (even for millions of rows!).
  3. Leaf Pages: Contain the actual indexed values sorted in order, paired with a Tuple Identifier (TID)—the physical (block_number, tuple_offset) in the table heap.
  4. Doubly-Linked Leaf Nodes: Leaf pages point to their left and right sibling pages, enabling ultra-fast range queries (e.g. WHERE age BETWEEN 20 AND 30) without re-traversing the tree from the root.

2. PostgreSQL Index Types: B-Tree, GIN, GiST, and BRIN

Index Type Underlying Architecture Supported Operators & Queries Ideal Real-World Use Case
B-Tree (Default) Self-balancing multi-way search tree. =, <, <=, >, >=, BETWEEN, IN, IS NULL, ORDER BY. Standard primary keys, foreign keys, email lookups, created_at timestamps.
GIN (Generalized Inverted Index) Inverted index mapping composite elements (keys/words) to lists of row pointers. @> (contains), ? (exists), @@ (full-text search), array containment. JSONB document searches, tags arrays (VARCHAR[]), full-text search. Slow writes, lightning-fast reads.
GiST (Generalized Search Tree) Lossy tree structure supporting custom hierarchical indexing. && (overlap), @> (contains), <@> (geometric distance). PostGIS geospatial geometry queries (lat/long bounding boxes), date range exclusion constraints.
BRIN (Block Range Index) Stores only the minimum and maximum values for physical blocks of pages (e.g. 128 pages). =, <, >, range queries on naturally physical sorted data. Massive append-only tables (100GB+ logs or audit tables). Uses 99% less RAM and disk than B-Tree!

3. Composite Indexes and the Leftmost Prefix Rule

A Composite Index (multi-column index) indexes multiple columns together, such as CREATE INDEX idx_orders ON orders (status, created_at);.

3.1 The Leftmost Prefix Rule

A composite index is sorted first by the first column, then by the second column, and so on:

\[ \text{Index on } (A, B, C) \implies \text{Can accelerate: } (A), (A, B), (A, B, C) \]

An index on (status, created_at) CANNOT be used for a query filtering exclusively on WHERE created_at > '2024-01-01', because the index entries are sorted primarily by status!

💡 Column Ordering Rule of Thumb

When creating multi-column indexes:

  1. Equality Columns First: Put columns evaluated with exact equality (WHERE tenant_id = 5 AND status = 'ACTIVE') on the left.
  2. Range / Sort Columns Last: Put columns evaluated with inequalities (>, <, BETWEEN) or used in ORDER BY on the right. Once the index hits a range column, it cannot use subsequent index columns for filtering!

4. Demystifying EXPLAIN (ANALYZE, BUFFERS)

Never guess what the database is doing. The EXPLAIN command displays the execution plan chosen by the PostgreSQL query planner.

  • EXPLAIN query: Shows the planner's estimated cost without executing the query.
  • EXPLAIN (ANALYZE, BUFFERS) query: Executes the query and returns actual millisecond execution times, actual row counts, and disk buffer I/O metrics.
sql (Reading EXPLAIN Output) 
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total_amount 
FROM orders 
WHERE customer_id = 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'
ORDER BY created_at DESC 
LIMIT 10;

/* OUTPUT:
Limit  (cost=0.42..28.50 rows=10 width=24) (actual time=0.035..0.048 rows=10 loops=1)
  Buffers: shared hit=5
  ->  Index Scan Backward using idx_orders_customer_created on orders  
        (cost=0.42..140.82 rows=50 width=24) (actual time=0.034..0.046 rows=10 loops=1)
        Index Cond: (customer_id = 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid)
        Buffers: shared hit=5
Planning Time: 0.112 ms
Execution Time: 0.071 ms
*/

4.1 Decoding the Plan Nodes

  • Sequential Scan (Seq Scan): Reads all table heap pages from start to finish. Normal for small tables (< 500 rows) or when fetching > 25% of table data, but catastrophic for large tables with selective filters.
  • Index Scan: Traverses B-Tree, extracts row pointers (TIDs), and reads corresponding heap pages.
  • Index Only Scan: The fastest scan! All requested columns in SELECT and WHERE are contained directly in the index (or added via INCLUDE). The database never touches the table heap on disk!
  • Bitmap Index Scan + Bitmap Heap Scan: Used when a query returns many rows. The index builds an in-memory bitmap of matching page locations, sorts them by physical disk address, and reads heap pages in sequential disk order, minimizing disk head movement.
  • Buffers: shared hit=5 means all required pages were served directly from in-memory RAM cache. shared read=10 means physical disk I/O was required.

5. Common Performance Anti-Patterns That Break Indexes

Anti-Pattern Query Why It Disables the Index Performant PostgreSQL Remedy
WHERE LOWER(email) = 'alice@acme.com' Standard B-Tree indexes store raw values (e.g. 'Alice@Acme.com'). Wrapping a column in a function forces PostgreSQL to execute a full Sequential Scan. Create an Expression / Functional Index: CREATE INDEX idx_users_lower_email ON users (LOWER(email));
WHERE name LIKE '%smith' Leading wildcards prevent B-Tree alphabetical root-to-leaf traversal. Install pg_trgm extension and build a Trigram GIN Index: CREATE INDEX idx_name_trgm ON users USING gin (name gin_trgm_ops);
WHERE created_at::DATE = '2024-01-01' Type casting a timestamp to a date prevents direct index range evaluation. Use half-open range queries: WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02'
Implicit Type Casting (e.g. phone = 1234567890 where phone is VARCHAR) PostgreSQL must cast every row's VARCHAR column to numeric before comparing, invalidating the index. Match types strictly in application queries: phone = '1234567890'.

6. The ORM N+1 Query Problem: Diagnosis and Resolution

The N+1 Query Problem is the most common database performance defect introduced by Object-Relational Mappers (ORMs like Prisma, TypeORM, Hibernate, and Mongoose).

javascript (The N+1 Antipattern in ORM Code) 
// DISASTROUS CODE:
// Query 1: Fetch 50 users (1 query)
const users = await prisma.user.findMany({ take: 50 });

for (const user of users) {
  // Query 2 to 51: Executes an independent database query FOR EVERY SINGLE USER!
  // Total queries executed: 1 + 50 = 51 queries over the network!
  const posts = await prisma.post.findMany({ where: { authorId: user.id } });
  console.log(`${user.name} has ${posts.length} posts`);
}

6.1 Three Solutions to Solve N+1

  1. Eager Loading / Joins: Tell the ORM to fetch relational children in a single SQL query: prisma.user.findMany({ include: { posts: true } }).
  2. Batching with IN (...): Fetch all parent IDs first, then issue a single child query: SELECT * FROM posts WHERE author_id IN (1, 2, 3... 50), grouping children by author ID in memory.
  3. DataLoader Pattern: In GraphQL or service architectures, DataLoader automatically batches and deduplicates individual key lookups within the same tick of the Node.js event loop into a single batch query.

7. Offset vs Keyset (Cursor) Pagination

Building pagination using OFFSET and LIMIT is intuitive, but suffers from quadratic \(\mathcal{O}(n)\) performance degradation as page numbers grow:

sql (Why OFFSET Degrades) 
-- Page 1: Fast (reads 20 rows)
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 0;

-- Page 50,000: Extremely Slow!
-- The database must scan, sort, and walk past 1,000,000 rows on disk only to THROW THEM AWAY!
SELECT * FROM orders ORDER BY id DESC LIMIT 20 OFFSET 1000000; -- Takes seconds!

7.1 Keyset (Cursor) Pagination: Constant \(\mathcal{O}(1)\) Time

Instead of telling the database how many rows to skip, Keyset Pagination remembers the values of the last record seen on the previous page and uses an index seek to jump directly to the next row:

sql (Keyset Pagination Implementation) 
-- Query for Next Page: Jumps directly via B-Tree index in < 1ms!
SELECT id, created_at, total_amount
FROM orders
WHERE (created_at, id) < ('2024-03-15 14:30:00+00', 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::uuid)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Composite Index to support this Keyset query:
CREATE INDEX idx_orders_cursor ON orders (created_at DESC, id DESC);

9. Chapter-Specific Interview Questions and Answers

Master these 20 high-frequency SQL indexing and performance interview questions covering B-Tree traversal, EXPLAIN plans, and pagination architectures.

Q01 How does a B-Tree index work internally, and what is its computational lookup complexity? Beginner
Spoken Interview Answer

"A B-Tree is a self-balancing, multi-way search tree. It consists of a root page, intermediate branch pages, and leaf pages. Leaf pages store indexed keys in sorted order along with Tuple Identifiers (TIDs) pointing to physical heap rows, and are linked via a doubly-linked list for fast range scans. Searching for a key requires binary searching through page blocks from root to leaf, executing in O(log n) time—typically requiring only 3 or 4 page reads even for millions of rows."

Q02 What is the difference between an Index Scan and an Index Only Scan in PostgreSQL? Intermediate
Spoken Interview Answer

"In an Index Scan, the engine traverses the B-Tree to find matching keys and then fetches the corresponding physical row from the table heap on disk to retrieve columns not stored in the index. In an Index Only Scan, all columns requested by the SELECT and WHERE clauses exist directly inside the index leaf page (or via the `INCLUDE` clause). As long as the visibility map confirms pages are clean, the engine answers the query entirely from the index without touching the table heap."

Q03 What is the Leftmost Prefix Rule for composite indexes? Intermediate
Spoken Interview Answer

"A composite index on `(A, B, C)` sorts data primarily by column A, then by B within identical values of A, and then by C. Because of this hierarchical sorting, the index can accelerate queries filtering on `(A)`, `(A, B)`, or `(A, B, C)`. However, it cannot accelerate a query filtering only on `(B)` or `(C)` because those keys are not sorted globally across the index, forcing PostgreSQL to perform a sequential scan."

Q04 What is a GIN index, and why is it preferred over B-Tree for JSONB and array columns? Advanced
Spoken Interview Answer

"GIN stands for Generalized Inverted Index. While a B-Tree maps one column value to one row, a GIN index takes a composite item (like a JSONB document or array) and splits it into individual components (keys, paths, elements), mapping each individual sub-element to an array of matching row pointers. For queries using containment operators (`@>` or array `&&`), GIN allows sub-millisecond lookups inside arbitrary document structures where B-Tree cannot index internal keys."

Q05 What is a BRIN index, and when should you use it over a B-Tree index? Advanced
Spoken Interview Answer

"BRIN stands for Block Range Index. Instead of indexing individual rows, it stores only the minimum and maximum values for physical blocks of heap pages (e.g. ranges of 128 pages). It is ideal for massive append-only tables (hundreds of gigabytes of logs, metrics, or time-series) where data is naturally physically sorted on disk by date or auto-incrementing ID. A BRIN index uses 99% less disk and RAM than a B-Tree index, fitting huge indexes into memory."

Q06 Why does WHERE LOWER(email) = 'test@example.com' fail to use an index on the email column? Intermediate
Spoken Interview Answer

"A standard B-Tree index on `email` stores the exact raw string values. Wrapping `email` in a runtime function `LOWER()` means the database must evaluate the function on every single row before comparing, invalidating the pre-sorted B-Tree index and forcing a full table scan. The fix is to create a functional/expression index: `CREATE INDEX idx_users_lower_email ON users (LOWER(email));`."

Q07 What is a Bitmap Index Scan in an EXPLAIN execution plan? Intermediate
Spoken Interview Answer

"A Bitmap Index Scan is chosen when a query matches many rows. Instead of immediately reading the table heap row by row (which causes random disk I/O), the Bitmap Index Scan traverses the index and builds an in-memory bitmap of physical page numbers. It then executes a Bitmap Heap Scan, reading physical data pages in strict sequential disk order, minimizing disk head thrashing and page re-reads."

Q08 What is the difference between EXPLAIN and EXPLAIN ANALYZE? Advanced
Spoken Interview Answer

"`EXPLAIN` only runs the query planner to show the estimated plan and costs based on table statistics (`pg_statistic`), without actually running the query. `EXPLAIN ANALYZE` actually executes the query on the database engine, discarding the output but measuring real execution times in milliseconds, actual row counts returned at each step, and buffer cache hits/reads. Warning: Running `EXPLAIN ANALYZE` on a `DELETE` or `UPDATE` will actually modify data!"

Q09 What is the N+1 Query Problem in ORMs, and how do you resolve it? Intermediate
Spoken Interview Answer

"The N+1 problem occurs when an application executes 1 query to fetch parent records (e.g. 50 users), and then loops over them executing N individual child queries (1 query per user to fetch their orders), resulting in 51 round-trips over the network. It is resolved by: 1. Eager loading via SQL JOINs (`include: { orders: true }`), 2. Batch fetching child rows using `WHERE user_id IN (1, 2, ... 50)`, or 3. Using the DataLoader pattern in GraphQL/Node.js."

Q10 Why does OFFSET 1000000 LIMIT 20 perform poorly, and how does Keyset pagination solve this? Advanced
Spoken Interview Answer

"With `OFFSET 1000000`, the database engine cannot jump directly to row 1,000,000; it must physically scan, sort, and discard all 1,000,000 prior rows in memory or disk before returning 20 rows, exhibiting O(n) degradation. Keyset (Cursor) pagination remembers the last seen values: `WHERE (created_at, id) < ($last_date, $last_id) ORDER BY created_at DESC, id DESC LIMIT 20`. This uses B-Tree index traversal to jump directly to the target record in O(1) constant time."

Q11 Why shouldn't you index every single column in a database table? Beginner
Spoken Interview Answer

"Indexes are not free. Every index consumes significant disk space and RAM Shared Buffers. Crucially, indexes introduce Write Amplification: every INSERT, UPDATE, or DELETE on the table requires updating all associated indexes synchronously. Over-indexing degrades write throughput, slows down bulk data imports, and prevents PostgreSQL's Heap-Only Tuples (HOT) update optimization."

Q12 What is a Covering Index, and what is the purpose of the INCLUDE clause? Intermediate
Spoken Interview Answer

"A covering index includes all columns needed by a query, enabling Index Only Scans. In PostgreSQL, the `INCLUDE` clause allows adding non-key payload columns to the index leaf pages without indexing or sorting by them: `CREATE INDEX idx ON orders (user_id) INCLUDE (total_amount)`. This keeps the B-Tree index shallow and small while avoiding table heap reads when returning `total_amount`."

Q13 Scenario: A search query uses WHERE title LIKE '%phone%'. A B-Tree index on title is ignored. How do you optimize substring search in PostgreSQL? Scenario
Spoken Interview Answer

"B-Trees only support prefix searches (`LIKE 'phone%'`) because strings are sorted from the first letter. Substring searches with leading wildcards cannot use B-Tree. The solution is to enable the `pg_trgm` extension and create a Trigram GIN index: `CREATE EXTENSION pg_trgm; CREATE INDEX idx_title_trgm ON products USING gin (title gin_trgm_ops);`. GIN splits words into 3-character trigrams, accelerating arbitrary substring searches by orders of magnitude."

Q14 What does 'Buffers: shared hit=10, read=2' mean in an EXPLAIN (BUFFERS) plan? Advanced
Spoken Interview Answer

"`shared hit` indicates the number of 8KB memory blocks retrieved directly from PostgreSQL's RAM Shared Buffers pool with zero disk latency. `read` indicates the number of blocks that were not in memory and required physical I/O from the operating system disk cache or storage drive. A high ratio of hits to reads indicates excellent query cache performance."

Q15 What is a Partial Index, and when should you use one? Intermediate
Spoken Interview Answer

"A partial index is built over a subset of a table specified by a `WHERE` clause: `CREATE INDEX idx_unpaid_invoices ON invoices (customer_id) WHERE status = 'UNPAID'`. It is useful when querying skewed data—for example, if 99% of invoices are 'PAID' and only 1% are 'UNPAID'. A partial index is 99% smaller, stays permanently in RAM, and requires zero index write overhead when paid invoices are inserted."

Q16 Why does the query planner sometimes choose a Sequential Scan over an existing Index Scan? Advanced
Spoken Interview Answer

"The cost-based planner chooses whatever plan costs the fewest disk/CPU units. It chooses a Sequential Scan if: 1. The table is very small (e.g. < 500 rows), where reading a few disk pages sequentially is faster than traversing index and heap pages. 2. The query is not selective: if a filter matches > 15–25% of rows, sequential I/O is faster than thousands of random heap page lookups. 3. Table statistics (`ANALYZE`) are stale."

Q17 How does composite index column order differ between equality filters and range filters? Intermediate
Spoken Interview Answer

"Equality columns MUST come first. Once the index evaluates an inequality or range condition (like `>` or `BETWEEN`), the B-Tree must scan across leaf pages, meaning subsequent columns in the index cannot be used for direct binary search filtering. Therefore, always order columns as: `(equality_column1, equality_column2, range_or_sort_column)`."

Q18 Scenario: A database query suddenly became 100x slower after a large data migration. The indexes are intact. What is the first command you run? Scenario
Spoken Interview Answer

"The first command is `ANALYZE table_name;`. After a large data import or migration, PostgreSQL's internal table statistics in `pg_statistic` become stale. The planner may assume the table has only 1,000 rows when it now has 10,000,000, choosing inappropriate Sequential Scans or nested loops. Running `ANALYZE` updates distribution histograms and row counts, allowing the planner to choose optimal index paths."

Q19 What is Write Amplification in the context of database indexes? Beginner
Spoken Interview Answer

"Write Amplification refers to the multiplier between the amount of data written by the user and the actual amount written to disk by the storage engine. If a table has 8 separate indexes, inserting a single 100-byte row requires writing to the table heap, writing to WAL, and updating 8 independent B-Tree index structures, multiplying disk write I/O by nearly 10x."

Q20 What are GiST indexes, and how do they support geospatial and multi-dimensional queries? Advanced
Spoken Interview Answer

"GiST stands for Generalized Search Tree. While B-Trees can only sort one-dimensional scalar values, GiST provides a template for indexing arbitrary hierarchical or spatial structures using lossy bounding boxes (R-Trees). It supports nearest-neighbor distance searches (`<->`) in PostGIS and exclusion constraints on overlapping ranges, which B-Trees cannot evaluate."
