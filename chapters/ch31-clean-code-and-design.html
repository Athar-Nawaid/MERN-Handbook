1. The SOLID Principles in Modern TypeScript

Introduced by Robert C. Martin ("Uncle Bob"), the SOLID principles are five fundamental design guidelines for object-oriented and modular programming. When properly applied in TypeScript, they prevent code rigidity, fragility, and tight coupling.

Principle Core Concept TypeScript Anti-Pattern Clean Refactoring Approach
S — Single Responsibility (SRP) A module, class, or function should have one, and only one, reason to change. An Express route handler that parses HTTP headers, validates input, executes SQL queries, sends emails, and formats responses in one 200-line function. Delegate concerns: Controller handles HTTP/status codes, Service handles business logic, Repository handles DB access, Mailer handles SMTP.
O — Open/Closed (OCP) Software entities should be open for extension, but closed for modification. A giant switch(paymentMethod) statement that must be edited and re-deployed whenever Stripe, PayPal, or Crypto is added. Use the Strategy Pattern: define a PaymentGateway interface; add new payment classes implementing the interface without touching existing code.
L — Liskov Substitution (LSP) Subtypes must be substitutable for their base types without altering program correctness. A ReadOnlyRepository extending Repository where calling save() throws an unexpected new Error("Operation not supported") runtime crash. Do not force subclasses to implement or inherit operations they cannot fulfill. Split interfaces into segregated contracts.
I — Interface Segregation (ISP) Clients should not be forced to depend on methods they do not use. A bloated IUserWorker interface containing 25 methods (email, billing, analytics, audit, payroll) passed to a component that only needs sendWelcomeEmail(). Compose fine-grained, cohesive interfaces: EmailRecipient, BillableUser, Auditable.
D — Dependency Inversion (DIP) High-level business modules should not depend on low-level modules; both should depend on abstractions (interfaces). An OrderService directly importing and calling new PostgreSQLClient(), tightly coupling domain logic to a specific database driver. Inject an IOrderRepository interface into the OrderService constructor. The database implementation is injected at runtime.

2. SOLID in Action: A Refactoring Walkthrough

Let us examine how an unmaintainable, coupled user registration function is systematically refactored using SOLID and TypeScript interfaces.

The Coupled Anti-Pattern

TypeScript: Violating SRP, OCP, and DIP 
// ❌ ANTI-PATTERN: Violates SRP, OCP, and DIP
import { Client } from 'pg';
import nodemailer from 'nodemailer';

export class UserService {
  private db: Client;

  constructor() {
    this.db = new Client({ connectionString: process.env.DATABASE_URL }); // Concrete coupling!
    this.db.connect();
  }

  async registerUser(email: string, pass: string, plan: string): Promise<void> {
    // 1. Validation mixed with business logic
    if (!email.includes('@')) throw new Error('Invalid email');

    // 2. Direct database query
    await this.db.query('INSERT INTO users(email, password) VALUES($1, $2)', [email, pass]);

    // 3. Concrete switch violating Open/Closed
    if (plan === 'stripe') {
      // charge via Stripe SDK...
    } else if (plan === 'paypal') {
      // charge via PayPal SDK...
    }

    // 4. Concrete email transport coupled directly
    const transport = nodemailer.createTransport({ host: 'smtp.mail.com' });
    await transport.sendMail({ to: email, subject: 'Welcome!', text: 'Thanks for joining' });
  }
}

The Clean, Decoupled Architecture

TypeScript: Applying SOLID with Inversion of Control 
// 1. Domain Entities & Inverted Interfaces (Abstractions)
export interface User {
  id: string;
  email: string;
  createdAt: Date;
}

export interface IUserRepository {
  save(user: { email: string; passwordHash: string }): Promise<User>;
  findByEmail(email: string): Promise<User | null>;
}

export interface IPaymentProcessor {
  processSubscription(userId: string, planId: string): Promise<void>;
}

export interface INotificationService {
  sendWelcomeNotification(email: string): Promise<void>;
}

// 2. High-Level Domain Service (Closed for modification, open for extension)
export class UserRegistrationService {
  constructor(
    private readonly userRepo: IUserRepository,
    private readonly paymentProcessor: IPaymentProcessor,
    private readonly notifier: INotificationService
  ) {}

  async register(email: string, passwordHash: string, planId: string): Promise<User> {
    const existing = await this.userRepo.findByEmail(email);
    if (existing) {
      throw new Error('User already exists');
    }

    const newUser = await this.userRepo.save({ email, passwordHash });
    await this.paymentProcessor.processSubscription(newUser.id, planId);
    await this.notifier.sendWelcomeNotification(newUser.email);

    return newUser;
  }
}

3. Lightweight Dependency Injection (DI)

Many developers believe Dependency Injection requires bulky Java-style reflection containers (like InversifyJS or NestJS). In JavaScript and TypeScript, Constructor Injection with a simple Composition Root provides 100% of DI benefits with zero framework overhead.

                         +-----------------------------+

      +-----------------+      +-----------------+      +-----------------+

TypeScript: Pure TypeScript Composition Root (Zero Framework) 
// src/container.ts (The Composition Root)
import { Pool } from 'pg';
import { PostgresUserRepository } from './repositories/PostgresUserRepository';
import { StripePaymentProcessor } from './services/StripePaymentProcessor';
import { SesNotificationService } from './services/SesNotificationService';
import { UserRegistrationService } from './services/UserRegistrationService';
import { UserController } from './controllers/UserController';

export function buildContainer() {
  const pool = new Pool({ connectionString: process.env.DATABASE_URL });

  // Instantiate low-level adapters
  const userRepo = new PostgresUserRepository(pool);
  const paymentProcessor = new StripePaymentProcessor(process.env.STRIPE_SECRET_KEY!);
  const notifier = new SesNotificationService();

  // Inject into high-level business service
  const registrationService = new UserRegistrationService(userRepo, paymentProcessor, notifier);

  // Inject into HTTP Controller
  const userController = new UserController(registrationService);

  return { userController, pool };
}
💡 Why Pure Constructor Injection Wins in Unit Tests

When unit testing UserRegistrationService, you never need complex mocking libraries like jest.mock(). You simply pass in-memory test stubs directly into the constructor: new UserRegistrationService(new InMemoryUserRepo(), new MockPayment(), new MockNotifier()). Tests execute in sub-milliseconds with zero disk or network I/O.

The Layered Architecture (Controller-Service-Repository) is the standard structural paradigm for enterprise Node.js and Express applications.

5. Pragmatic Design: DRY, KISS, and YAGNI

While design patterns are powerful, dogmatic adherence to them leads to catastrophic over-engineering. Senior engineers balance software principles with practical business delivery.

Principle Core Premise Over-Engineering Hazard (Anti-Pattern) Senior Engineering Pragmatism
DRY (Don't Repeat Yourself) Every piece of domain knowledge must have a single, unambiguous representation in a system. Merging two completely distinct features (e.g., User Address and Billing Address) into a generic "GenericLocationEntity" because they happen to share three field names. "Duplication is far cheaper than the wrong abstraction" (Sandi Metz). Allow code to be duplicated 2–3 times before extracting a common abstraction (Rule of Three).
KISS (Keep It Simple, Stupid) Systems work best if they are kept simple rather than made complicated. Adding an event-driven Kafka message bus and CQRS event sourcing to an application that handles 50 requests per day. Build the simplest working solution that satisfies non-functional requirements. Prefer straightforward synchronous SQL transactions until scale demands distributed systems.
YAGNI (You Aren't Gonna Need It) Never implement functionality until it is actually necessary. Writing an abstract multi-database driver supporting Cassandra, CouchDB, and SQLite "just in case the startup changes databases next year." Design clean interfaces so that replacing an implementation later is easy, but only write code required for today's user stories.

6. Code Smells & Refactoring Patterns

A Code Smell is a surface symptom in source code that indicates a deeper architectural design weakness.

Code Smell Symptom & Danger Target Refactoring Technique
God Object / Large Class A single file or class exceeding 1,000 lines that controls almost all application behavior. Extract Class / Module: Group related methods and state into smaller, cohesive service classes following SRP.
Long Parameter List A function signature taking 7+ positional arguments (createUser(fn, ln, email, age, phone, role, zip...)). Easy to pass arguments in wrong order! Introduce Parameter Object: Group arguments into a single typed TypeScript object or interface (createUser(input: CreateUserInput)).
Primitive Obsession Using raw primitives (strings, numbers) for rich domain concepts like currency, postal codes, or email addresses. Value Object Pattern: Encapsulate the primitive inside a dedicated Value Object with validation rules (e.g., class Money { amount, currency }).
Feature Envy A method in Class A continuously queries Class B's internal getters to perform calculations rather than letting Class B compute its own result. Move Method: Relocate the calculation method inside Class B where the data naturally resides.
Shotgun Surgery Making a single small business change requires modifying 15 different files across the codebase. Co-locate and Consolidate: Realign boundaries so that single domain changes affect only one cohesive module.

7. Practical Exercises

Exercise 1: Refactoring a God Handler into Controller-Service-Repository

Scenario: You inherit an Express endpoint app.post('/api/orders') that executes pg.Pool queries, calculates tax, calls Stripe, and writes to disk in a single block. Refactor it into a OrderService that accepts an IOrderRepository interface.

View Complete Solution
TypeScript Solution 
export interface Order {
  id: string;
  userId: string;
  total: number;
  status: 'pending' | 'paid';
}

export interface IOrderRepository {
  create(order: Omit<Order, 'id'>): Promise<Order>;
}

export class OrderService {
  constructor(private readonly orderRepo: IOrderRepository) {}

  async createOrder(userId: string, items: Array<{ price: number; quantity: number }>): Promise<Order> {
    if (items.length === 0) {
      throw new Error('Cannot create an empty order');
    }

    const subtotal = items.reduce((acc, item) => acc + item.price * item.quantity, 0);
    const tax = subtotal * 0.08; // 8% sales tax calculation
    const total = subtotal + tax;

    return this.orderRepo.create({
      userId,
      total,
      status: 'pending'
    });
  }
}

Exercise 2: Implementing the Open/Closed Principle with the Strategy Pattern

Scenario: Refactor a discount calculation engine from an ugly if/else chain into a strategy-based pattern that allows adding new discount types (e.g., SeasonalDiscount, VIPDiscount) without altering the core calculator.

View Complete Solution
TypeScript Solution 
export interface IDiscountStrategy {
  calculate(rawTotal: number): number;
}

export class VipDiscountStrategy implements IDiscountStrategy {
  calculate(rawTotal: number): number {
    return rawTotal * 0.8; // 20% discount for VIPs
  }
}

export class SeasonalDiscountStrategy implements IDiscountStrategy {
  calculate(rawTotal: number): number {
    return Math.max(0, rawTotal - 15); // $15 flat seasonal coupon
  }
}

export class StandardDiscountStrategy implements IDiscountStrategy {
  calculate(rawTotal: number): number {
    return rawTotal; // No discount
  }
}

export class CheckoutCalculator {
  constructor(private strategy: IDiscountStrategy) {}

  setStrategy(strategy: IDiscountStrategy): void {
    this.strategy = strategy;
  }

  getFinalTotal(subtotal: number): number {
    return this.strategy.calculate(subtotal);
  }
}

8. Chapter-Specific Interview Questions & Answers

20 high-frequency interview questions covering SOLID principles, Dependency Injection, the Repository Pattern, code smells, and clean architecture.

Q01 What is the Single Responsibility Principle (SRP) and how do you identify its violation? Beginner
Spoken Interview Answer

"The Single Responsibility Principle states that a class or module should have only one reason to change, meaning it should focus on a single actor or business concern. A common violation in full-stack code is an Express route handler that parses HTTP headers, validates input fields, executes SQL queries, formats PDF receipts, and sends emails all within the same function."

Q02 What is Dependency Inversion Principle (DIP) and how does it differ from Dependency Injection (DI)? Beginner
Spoken Interview Answer

"Dependency Inversion is the high-level design principle stating that high-level business modules should depend on abstractions (interfaces) rather than low-level concrete implementations. Dependency Injection is the actual design pattern or technique used to implement DIP, where dependencies are passed into a class (e.g., via constructor arguments) rather than instantiated internally."

Q03 What is the Controller-Service-Repository pattern and why is it beneficial? Beginner
Spoken Interview Answer

"It separates concerns into three distinct layers: Controllers handle HTTP transport (request parsing, status codes, response serialization); Services encapsulate core business logic and workflows without HTTP coupling; and Repositories handle database persistence and querying. This makes business logic 100% testable without database or web server mocks and allows the same service to be called from CLI or message queues."

Q04 What is the DRY principle and what is the danger of premature DRYing? Beginner
Spoken Interview Answer

"DRY (Don't Repeat Yourself) aims to prevent duplication of domain knowledge. The danger of premature DRYing is creating the 'Wrong Abstraction': merging two unrelated pieces of code that happen to look identical today into a complex generic function. When those features diverge in business requirements tomorrow, developers are forced to add messy flags and conditionals. Duplication is cheaper than the wrong abstraction."

Q05 What is the YAGNI principle and how do you practice it in product development? Beginner
Spoken Interview Answer

"YAGNI stands for 'You Aren't Gonna Need It'. It advises against building features, abstractions, or infrastructure for speculative future needs. In practice, you write clean, modular code that solves today's concrete user requirements while keeping interfaces decoupled enough that extending or refactoring the system later remains straightforward."

Q06 What is the Open/Closed Principle (OCP) and how do you implement it in TypeScript? Intermediate
Spoken Interview Answer

"Open/Closed states that code should be open for extension but closed for modification. In TypeScript, we implement OCP using interfaces and polymorphism (like the Strategy Pattern). Instead of modifying a centralized `switch` statement every time a new payment processor or notification channel is added, we define an interface and create a new class implementing that interface, requiring zero modifications to existing code."

Q07 What is the Liskov Substitution Principle (LSP) and how is it commonly violated? Intermediate
Spoken Interview Answer

"LSP dictates that derived classes must be usable through their base interface without breaking client expectations. A common violation occurs when a subclass overrides a base class method with a no-op or throws an unsupported exception—like a `ReadOnlyDatabaseRepository` throwing an error inside `save()`. If a client expecting a repository crashes, LSP has been violated."

Q08 What is the Interface Segregation Principle (ISP) and why is it relevant in TypeScript? Intermediate
Spoken Interview Answer

"ISP states that clients should not be forced to depend on methods they do not use. In TypeScript, creating large 'God Interfaces' with dozens of properties and methods forces mock implementations in unit tests to stub unnecessary functions. By segregating interfaces into smaller, role-focused contracts (`Readable`, `Writable`, `Auditable`), components remain decoupled."

Q09 What is a Composition Root in Dependency Injection? Intermediate
Spoken Interview Answer

"The Composition Root is the single location near the application's entry point (e.g., `server.ts` or `container.ts`) where the entire dependency graph is wired together. Concrete repositories, database connection pools, and external adapters are instantiated here and injected into services and controllers. The rest of the application remains completely unaware of how dependencies are instantiated."

Q10 What is the Primitive Obsession code smell and how do Value Objects fix it? Intermediate
Spoken Interview Answer

"Primitive Obsession is the habit of using basic primitives (like strings and numbers) to represent domain concepts with specific rules (like Email, Currency, or Phone Number). Value Objects fix this by encapsulating the primitive inside a dedicated class or type with self-contained validation and equality logic, ensuring invalid values cannot exist in domain entities."

Q11 What is Feature Envy and how do you refactor it? Intermediate
Spoken Interview Answer

"Feature Envy occurs when a method in one class extensively accesses the getters and internal data of another class to calculate a result. The remedy is the 'Move Method' refactoring: move the logic into the class that actually owns the data, upholding object encapsulation and the 'Tell, Don't Ask' principle."

Q12 Why should you avoid passing Express req and res objects into domain service functions? Intermediate
Spoken Interview Answer

"Passing `req` and `res` into service functions leaks HTTP transport concerns into core business logic. It makes unit testing painful because you must mock complex HTTP objects, and it prevents reusing that service inside background job consumers (BullMQ), WebSocket handlers, or CLI scripts where no HTTP request exists."

Q13 What is the difference between an Anemic Domain Model and a Rich Domain Model? Intermediate
Spoken Interview Answer

"An Anemic Domain Model consists of entities that are purely bags of getters and setters with zero logic, forcing all business rules into procedural service classes. A Rich Domain Model co-locates business behavior, validation rules, and invariants directly inside the domain entity itself (e.g., `order.applyDiscount()`), preventing invalid states."

Q14 What is Shotgun Surgery and what architectural flaw does it indicate? Intermediate
Spoken Interview Answer

"Shotgun Surgery happens when making a single small conceptual change requires editing many different files across the codebase. It indicates poor cohesion and tight coupling: responsibilities that belong together have been fragmented across multiple modules, increasing regression risk."

Q15 What is Hexagonal Architecture (Ports and Adapters) and how does it relate to DIP? Advanced
Spoken Interview Answer

"Hexagonal Architecture isolates pure business logic in the center, interacting with the outside world through 'Ports' (interfaces). 'Adapters' implement those ports for specific infrastructure—such as an Express Controller (driving adapter) or a PostgreSQL repository (driven adapter). It is a complete embodiment of DIP: the core domain never depends on databases or UI frameworks."

Q16 How do you manage database transactions cleanly when using the Repository Pattern? Advanced
Spoken Interview Answer

"Transactions span multiple repository operations. A clean pattern is the Unit of Work pattern or passing a transactional client context: `userRepo.withTransaction(client).save()`. Alternatively, implement a transaction runner in the service layer: `transactionManager.run(async (tx) => { await repoA.save(tx); await repoB.save(tx); })`."

Q17 Why can excessive use of Design Patterns become an anti-pattern? Advanced
Spoken Interview Answer

"Design patterns solve specific, known problems. Applying them prematurely or dogmatically creates indirection, cognitive load, and boilerplates—such as AbstractFactoryBuilderDecorators for simple CRUD operations. Pragmatic engineering applies patterns only when the underlying complexity or variation actually justifies the abstraction."

Q18 What is the Law of Demeter (Principle of Least Knowledge)? Advanced
Spoken Interview Answer

"The Law of Demeter states that a module should only talk to its immediate collaborators and not navigate the internal object structure of its dependencies (avoiding 'train wrecks' like `order.getUser().getAddress().getZipCode()`). Violating it tightly couples code to the entire structural hierarchy, meaning changes to `Address` break `OrderProcessing`."

Q19 How do you structure functional programming patterns to achieve clean architecture without classes? Advanced
Spoken Interview Answer

"In functional TypeScript, DI is achieved via Higher-Order Functions and Currying: a factory function takes repository closures as arguments and returns the domain function: `const makeRegisterUser = (repo: UserRepo) => async (email, pass) => { ... }`. Pure business logic is modeled as pure functions, and I/O effects are deferred to the boundaries."

Q20 How do you balance clean architecture against delivery speed in early-stage startups? Intermediate
Spoken Interview Answer

"In early startups, product-market fit is the priority. I practice 'Pragmatic Modular Design': keep business logic separated from HTTP controllers and write clean SQL queries, but avoid over-engineering with 5 layers of microservices, event sourcing, or heavy DI frameworks. Modular monoliths with clean boundaries can be shipped rapidly today and refactored seamlessly tomorrow."
