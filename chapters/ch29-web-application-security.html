1. The OWASP Top 10 for Full-Stack Engineers

The Open Web Application Security Project (OWASP) curates the definitive industry consensus on the most critical security risks facing modern web applications.

OWASP Risk Full-Stack Real-World Attack Scenario Primary Defense Mechanism
A01: Broken Access Control (BOLA/IDOR) A logged-in user changes the URL or body from /invoices/101 to /invoices/102 and reads another customer’s private invoice. Always scope data access queries by authenticated user ID (WHERE id = $1 AND account_id = $2) and enforce server-side RBAC/ABAC.
A02: Cryptographic Failures Storing passwords in plaintext or MD5/SHA-1; transmitting tokens over unencrypted HTTP; storing sensitive tokens in localStorage. Use Argon2id or Bcrypt (cost factor \(\ge 12\)); enforce HTTPS with HSTS; store auth tokens in HttpOnly; Secure; SameSite=Strict cookies.
A03: Injection (SQL, NoSQL, Command) Submitting ' OR 1=1 -- into login forms, or passing {"$ne": null} to bypass MongoDB authentication. Parameterized prepared statements in SQL, strict Zod schema validation, and sanitizing NoSQL queries (express-mongo-sanitize).
A04: Insecure Design Password reset workflows without rate limiting allowing credential brute-forcing; lack of multi-factor authentication (MFA) on admin accounts. Threat modeling during architecture; strict rate limiting (Redis token buckets) on sensitive endpoints; anti-enumeration responses.
A05: Security Misconfiguration Leaving default credentials; enabling directory listing; exposing verbose stack traces in production 500 error responses; missing security headers. Automated infrastructure-as-code hardening; use Helmet.js; disable X-Powered-By; sanitize error envelopes in production.
A06: Vulnerable & Outdated Components Using npm packages containing known Remote Code Execution (RCE) or prototype pollution vulnerabilities. Automated vulnerability scanning in CI/CD (npm audit, Snyk, Dependabot); pinning lockfiles with npm ci.
A07: Identification & Auth Failures Credential stuffing, session fixation, permitting weak passwords ("123456"), or issuing JWTs without signature verification. Enforce strong password rules (zxcvbn); MFA; cryptographic signature verification with RS256/EdDSA; Refresh Token Rotation (RTR).
A08: Software & Data Integrity Failures Loading untrusted third-party CDN scripts without Subresource Integrity (SRI); insecure deserialization of untrusted serialized objects. Use SRI hash checks (integrity="sha384-..."); avoid eval() or unsafe deserialization libraries; verify webhook HMAC signatures.
A09: Security Logging & Monitoring Failures Failing to log failed login spikes or privilege escalations; logging plaintext credit cards or passwords in application logs. Structured JSON logging (Pino); correlation IDs; real-time alert thresholds on 401/403 surges; strict PII masking/redaction filters.
A10: Server-Side Request Forgery (SSRF) An endpoint accepts a user-provided image URL and downloads AWS metadata from http://169.254.169.254/latest/meta-data/. Resolve DNS, validate IP addresses against private/loopback/cloud metadata subnets before dispatching outbound requests.

2. Injection Attacks: SQL vs. NoSQL vs. Command Injection

SQL Injection (SQLi)

SQL Injection occurs when untrusted user input is directly concatenated or interpolated into a raw SQL query string, allowing the attacker to break out of the data context into the command execution context.

JavaScript: Vulnerable vs Secure SQL Queries 
// ❌ VULNERABLE: Direct string interpolation
const query = `SELECT * FROM users WHERE email = '${req.body.email}' AND password = '${req.body.password}'`;
// Attacker enters email: "admin@site.com' --"
// Resulting query: SELECT * FROM users WHERE email = 'admin@site.com' --' AND password = '...'
// The rest of the query is commented out! The attacker logs in without a password!

// ✅ SECURE: Parameterized Prepared Statements
const safeQuery = 'SELECT id, email, password_hash FROM users WHERE email = $1';
const { rows } = await pool.query(safeQuery, [req.body.email]);
// The database engine compiles the SQL query plan FIRST, treating $1 strictly as literal data.

NoSQL Operator Injection

MongoDB applications using Mongoose or native drivers are immune to traditional SQL injection, but are highly vulnerable to NoSQL Operator Injection. When an Express application accepts parsed JSON objects directly from req.body, an attacker can submit MongoDB query operators (such as $gt, $ne, or $regex) instead of primitive strings.

JavaScript: MongoDB NoSQL Injection Exploit and Defense 
// Vulnerable Express Endpoint
app.post('/api/login', async (req, res) => {
  // Attacker sends JSON payload:
  // { "username": "admin", "password": { "$ne": null } }
  
  // ❌ VULNERABLE: req.body.password is parsed as an Object: { $ne: null }
  const user = await User.findOne({
    username: req.body.username,
    password: req.body.password // Query becomes: password is NOT null!
  });

  if (user) {
    // Attacker bypasses authentication completely!
    res.json({ token: generateJwt(user) });
  }
});

// ✅ DEFENSE LAYER 1: Strict Runtime Type Validation with Zod
import { z } from 'zod';

const LoginSchema = z.object({
  username: z.string().min(3).max(50),
  password: z.string().min(8) // Must be a string! Objects are rejected with 422!
});

// ✅ DEFENSE LAYER 2: Sanitize keys starting with '$' or containing '.'
import mongoSanitize from 'express-mongo-sanitize';
app.use(mongoSanitize()); // Strips all $ operators from req.body, req.query, req.params

Command Injection

Command injection occurs when user input is passed directly to system shells (e.g., using Node’s child_process.exec).

JavaScript: Command Injection Vulnerability & Fix 
import { exec, execFile } from 'child_process';

// ❌ VULNERABLE: Spawns a shell (/bin/sh or cmd.exe)
// Attacker enters domain: "google.com; rm -rf /"
exec(`ping -c 4 ${req.body.domain}`, (err, stdout) => { ... });

// ✅ SECURE: execFile bypasses shell interpretation entirely!
// Arguments are passed as an array directly to the OS binary
execFile('ping', ['-c', '4', req.body.domain], (err, stdout) => { ... });

3. Broken Object Level Authorization (BOLA / IDOR)

Broken Object Level Authorization (BOLA), formerly classified as Insecure Direct Object Reference (IDOR), is ranked by OWASP as the #1 most critical vulnerability in modern APIs.

It occurs when an endpoint exposes an internal database identifier (e.g., /api/documents/5920) and fails to verify whether the authenticated user has explicit rights to access that specific document instance.

ASCII Diagram: BOLA / IDOR Attack Vector 
Attacker (User 99)                   API Endpoint                    PostgreSQL DB
      |                                   |                                |
      |-- GET /invoices/101 ------------>|                                |
      |   Authorization: Bearer User99    |                                |
      |                                   |-- SELECT * FROM invoices       |
      |                                   |   WHERE id = 101; ----------->|
      |                                   |<-- Returns Invoice (User 42)---|
      |                                   | (No owner verification!)       |
      |<-- 200 OK [Victim's Invoice!] ----|                                |
      | (Attacker accesses private data belonging to User 42)              |

The Architectural Defense: Scoped Database Queries

TypeScript: Enforcing Tenant & Ownership Scoping 
import { Request, Response } from 'express';
import { pool } from '../db';

export async function getInvoice(req: Request, res: Response): Promise<void> {
  const invoiceId = req.params.id;
  const currentUserId = req.user.id; // Extracted from verified JWT session

  // ✅ ALWAYS scope queries by BOTH the target entity ID AND the authenticated owner ID
  const query = `
    SELECT id, amount, status, created_at
    FROM invoices
    WHERE id = $1 AND user_id = $2;
  `;

  const { rows } = await pool.query(query, [invoiceId, currentUserId]);

  if (rows.length === 0) {
    // Return 404 instead of 403 to prevent resource enumeration attacks!
    res.status(404).json({
      type: 'https://api.myapp.com/errors/not-found',
      title: 'Resource Not Found',
      status: 404,
      detail: 'No invoice found with the specified identifier.'
    });
    return;
  }

  res.json({ data: rows[0] });
}
💡 Security Best Practice: 404 vs 403 on IDOR Probing

When an authenticated user attempts to access an object they do not own, returning 403 Forbidden confirms to the attacker that the object exists (enabling resource enumeration). Returning 404 Not Found denies the attacker any intelligence regarding whether the ID is valid or invalid.

4. Server-Side Request Forgery (SSRF)

Server-Side Request Forgery (SSRF) occurs when a web backend is persuaded by an attacker to fetch a remote resource (e.g., an image avatar URL, a PDF export link, or an incoming webhook health check) without restricting the destination address.

Attackers exploit SSRF to scan internal network infrastructure (bypassing public firewalls) or query cloud provider instance metadata endpoints to steal IAM credentials:

  • AWS Metadata: http://169.254.169.254/latest/meta-data/iam/security-credentials/
  • GCP Metadata: http://metadata.google.internal/computeMetadata/v1/
  • Internal Services: http://localhost:6379 (Redis), http://10.0.0.5:9200 (Elasticsearch).

Defense: Validating Resolved IP Addresses (Anti-DNS Rebinding)

TypeScript: Production Safe HTTP Fetcher Defending Against SSRF 
import dns from 'dns/promises';
import http from 'http';
import https from 'https';
import ipaddr from 'ipaddr.js';
import { URL } from 'url';

export async function isSafeUrl(targetUrl: string): Promise<boolean> {
  try {
    const parsed = new URL(targetUrl);

    // 1. Only permit standard HTTP/HTTPS protocols
    if (parsed.protocol !== 'http:' && parsed.protocol !== 'https:') {
      return false;
    }

    // 2. Resolve DNS hostname to raw IP addresses
    const lookup = await dns.lookup(parsed.hostname, { all: true });
    if (lookup.length === 0) return false;

    for (const record of lookup) {
      const addr = ipaddr.parse(record.address);
      const range = addr.range();

      // 3. Reject loopback (127.0.0.1), private (RFC 1918), linkLocal (169.254.x.x AWS), broadcast
      const blockedRanges = [
        'loopback',
        'private',
        'linkLocal',
        'carrierGradeNat',
        'uniqueLocal',
        'unspecified'
      ];

      if (blockedRanges.includes(range)) {
        return false;
      }
    }

    return true;
  } catch {
    return false;
  }
}

5. Cross-Site Scripting (XSS) & Modern Content Security Policy (CSP)

Cross-Site Scripting (XSS) occurs when malicious JavaScript code is injected into a trusted web application and executed within the victim’s browser context.

XSS Variety Execution Flow Primary Mitigation
Stored XSS (Persistent) Malicious script payload is permanently stored in the database (e.g., user bio or comment) and executed whenever other users view the page. Contextual HTML entity encoding; DOMPurify sanitization of user HTML; strict database validation.
Reflected XSS (Non-Persistent) Payload is reflected immediately off the web server in an error message or search query parameter (e.g., ?q=<script>...</script>). Auto-escaping template engines (React JSX auto-escapes string bindings); HTTP response encoding.
DOM-based XSS Attack payload is executed entirely in client-side JavaScript by unsafe DOM manipulation (e.g., reading location.hash into element.innerHTML). Avoid dangerouslySetInnerHTML, innerHTML, document.write, or eval(). Use textContent.

Why React Protects Against XSS (And Where It Fails)

By default, React JSX automatically escapes all string variables rendered inside curly braces {userInput}. React converts characters like <, >, &, and " into safe HTML entities, rendering them harmlessly as text.

TypeScript: React XSS Traps and DOMPurify Remediation 
import DOMPurify from 'dompurify';

// ❌ VULNERABLE: Bypasses React's built-in escaping!
function DangerousComment({ rawHtml }: { rawHtml: string }) {
  return <div dangerouslySetInnerHTML={{ __html: rawHtml }} />;
}

// ❌ VULNERABLE: javascript: protocol pseudo-URLs in anchor tags!
function MaliciousLink({ userUrl }: { userUrl: string }) {
  // If userUrl = "javascript:alert(document.cookie)"
  return <a href={userUrl}>Click my profile!</a>;
}

// ✅ SECURE: DOMPurify Sanitization
function SafeComment({ rawHtml }: { rawHtml: string }) {
  const sanitized = DOMPurify.sanitize(rawHtml, {
    ALLOWED_TAGS: ['b', 'i', 'em', 'strong', 'a'],
    ALLOWED_ATTR: ['href']
  });
  return <div dangerouslySetInnerHTML={{ __html: sanitized }} />;
}

6. Hardening Express with Security Headers (Helmet.js)

HTTP response headers instruct browsers how to enforce sandboxing, SSL transport, and cross-origin resource sharing. The industry standard package for securing Express headers is Helmet.js.

TypeScript: Production Express Helmet Configuration 
import express from 'express';
import helmet from 'helmet';

const app = express();

// Configure comprehensive security headers
app.use(
  helmet({
    // 1. Content Security Policy (CSP): Restricts origins of scripts/styles/images
    contentSecurityPolicy: {
      directives: {
        defaultSrc: ["'self'"],
        scriptSrc: ["'self'"],
        styleSrc: ["'self'", "'unsafe-inline'"],
        imgSrc: ["'self'", 'data:', 'https://images.myapp.com'],
        connectSrc: ["'self'", 'https://api.myapp.com'],
        objectSrc: ["'none'"],
        upgradeInsecureRequests: []
      }
    },
    // 2. Strict-Transport-Security (HSTS): Forces HTTPS for 1 year including subdomains
    hsts: {
      maxAge: 31536000,
      includeSubDomains: true,
      preload: true
    },
    // 3. Prevent MIME-type sniffing (CVE-2018-1002200)
    noSniff: true,
    // 4. Clickjacking defense: prevents embedding inside iframes
    frameguard: {
      action: 'deny'
    },
    // 5. Hide X-Powered-By: Express header
    hidePoweredBy: true
  })
);

7. Secrets Management & Environment Hygiene

Accidental exposure of database passwords, API tokens, and JWT private keys in public git repositories or client-side bundles is an catastrophic vulnerability.

Anti-Pattern Why It Is Fatal Production Industry Standard
Committing .env files to Git Git history is immutable; credentials remain in public git commits indefinitely even if deleted in a later commit. Add .env* to .gitignore; inject environment variables at runtime via AWS Secrets Manager, HashiCorp Vault, or Doppler.
Prefixing private secrets with REACT_APP_ or VITE_ Bundlers (Vite, Webpack) embed any variable prefixed with VITE_ or NEXT_PUBLIC_ into client JavaScript bundles! Only expose truly public keys (like Stripe Publishable Key). Backend secrets (Stripe Secret Key, DB URLs) must NEVER enter frontend code.
Baking secrets into Docker image layers Anyone with access to the Docker image can run docker history or inspect image layers to extract secrets. Use multi-stage Docker builds with BuildKit secrets (RUN --mount=type=secret...).

View Complete Solution
TypeScript Solution 
import dns from 'dns/promises';
import ipaddr from 'ipaddr.js';

export async function validateRemoteUrl(rawUrl: string): Promise<string> {
  const parsed = new URL(rawUrl);

  if (!['http:', 'https:'].includes(parsed.protocol)) {
    throw new Error('Only HTTP and HTTPS protocols are permitted.');
  }

  const addresses = await dns.lookup(parsed.hostname, { all: true });
  if (addresses.length === 0) {
    throw new Error('Unable to resolve hostname.');
  }

  for (const { address } of addresses) {
    const parsedIp = ipaddr.parse(address);
    const range = parsedIp.range();

    if (['private', 'loopback', 'linkLocal', 'uniqueLocal'].includes(range)) {
      throw new Error(`Forbidden target IP range: ${range} (${address})`);
    }
  }

  return rawUrl;
}

Exercise 2: NoSQL Query Sanitizer Middleware

Scenario: Create a lightweight Express middleware function from scratch (without external dependencies) that recursively scans req.body and strips any object keys that begin with $.

View Complete Solution
TypeScript Solution 
import { Request, Response, NextFunction } from 'express';

function sanitizeObject(obj: any): any {
  if (Array.isArray(obj)) {
    return obj.map(sanitizeObject);
  }
  if (obj !== null && typeof obj === 'object') {
    const clean: Record<string, any> = {};
    for (const [key, value] of Object.entries(obj)) {
      // Strip any key starting with '$' or containing '.'
      if (!key.startsWith('$') && !key.includes('.')) {
        clean[key] = sanitizeObject(value);
      }
    }
    return clean;
  }
  return obj;
}

export function customNoSqlSanitizer(req: Request, res: Response, next: NextFunction): void {
  if (req.body) req.body = sanitizeObject(req.body);
  if (req.query) req.query = sanitizeObject(req.query);
  if (req.params) req.params = sanitizeObject(req.params);
  next();
}

9. Chapter-Specific Interview Questions & Answers

20 high-frequency interview questions covering OWASP Top 10 vulnerabilities, BOLA/IDOR prevention, NoSQL operator injection, SSRF defense, and security headers.

Q01 What is SQL Injection and how do parameterized queries completely prevent it? Beginner
Spoken Interview Answer

"SQL Injection occurs when untrusted user input is directly concatenated into a SQL statement, allowing user input to be parsed as executable commands. Parameterized queries completely prevent this because the database pre-compiles the SQL syntax and query execution plan before binding the parameters. User input is treated strictly as literal data, making it impossible to alter the query logic."

Q02 What is NoSQL Injection and how does it manifest in MongoDB applications? Beginner
Spoken Interview Answer

"NoSQL injection occurs when query operators (like `$ne`, `$gt`, or `$regex`) are passed in place of primitive values via JSON request bodies. For instance, passing `{\"username\": \"admin\", \"password\": {\"$ne\": null}}` into a Mongoose `findOne()` query bypasses password verification entirely because the condition 'password is not null' evaluates to true."

Q03 What is Broken Object Level Authorization (BOLA / IDOR)? Beginner
Spoken Interview Answer

"BOLA (formerly IDOR) is ranked as the #1 API security vulnerability by OWASP. It happens when an endpoint accepts a resource identifier (such as `/orders/123`) from the client and retrieves that object without verifying if the authenticated user has legitimate ownership or authorization rights to access that specific record."

Q04 What is Stored XSS vs Reflected XSS? Beginner
Spoken Interview Answer

"Stored XSS occurs when a malicious script is permanently persisted in the server database (e.g., in a blog comment or user profile) and executed whenever other users view that record. Reflected XSS is non-persistent: the payload is delivered via a crafted URL or form parameter and reflected immediately by the server in an error message or search page."

Q05 How does React protect against Cross-Site Scripting (XSS) by default? Beginner
Spoken Interview Answer

"React JSX automatically escapes all string expressions rendered inside curly braces `{userInput}` before inserting them into the DOM. Characters like `<` and `>` are converted to HTML entities, rendering them harmlessly as text rather than executable script tags. React only becomes vulnerable if developers bypass this using `dangerouslySetInnerHTML` or dynamic `javascript:` pseudo-protocols in links."

Q06 How do you effectively prevent BOLA / IDOR at the database query level? Intermediate
Spoken Interview Answer

"Never trust client-supplied identifiers alone. Always scope database queries by both the requested resource ID and the authenticated user's ID extracted from the verified session or JWT: `SELECT * FROM orders WHERE id = $1 AND user_id = $2`. In multi-tenant systems, scope by `tenant_id` or utilize PostgreSQL Row-Level Security (RLS)."

Q07 What is Server-Side Request Forgery (SSRF) and how do attackers exploit it in cloud environments? Intermediate
Spoken Interview Answer

"SSRF occurs when an attacker tricks a backend server into making HTTP requests to internal or unauthorized destinations. In cloud environments like AWS, attackers submit the link-local metadata IP `http://169.254.169.254/latest/meta-data/` into webhook or avatar upload endpoints to harvest temporary EC2 IAM credentials."

Q08 How do you defend against SSRF and DNS Rebinding attacks? Intermediate
Spoken Interview Answer

"We validate URLs by strictly allowing only HTTP/HTTPS protocols, resolving the hostname to its underlying IP address, and checking that the IP does not belong to private (RFC 1918), loopback (127.0.0.1), or link-local (169.254.x.x) ranges. To defend against DNS Rebinding, we pin the verified IP address and issue the HTTP request directly to that IP rather than re-resolving the hostname."

Q09 What is Content Security Policy (CSP) and how does it mitigate XSS? Intermediate
Spoken Interview Answer

"CSP is an HTTP response header that restricts which domain origins can execute scripts, load stylesheets, or connect websockets in the browser. Even if an attacker injects an inline ``. The browser verifies the downloaded file's hash before execution; if the CDN was tampered with, the script is rejected."

Q17 What is Prototype Pollution in JavaScript and how does it lead to Remote Code Execution (RCE)? Advanced
Spoken Interview Answer

"Prototype pollution happens when an application recursively merges untrusted JSON objects containing `__proto__` or `constructor.prototype` keys into existing objects. This pollutes `Object.prototype`, adding properties to every object in the V8 runtime. If a backend library later checks for optional config properties (like `shell: true`), the injected property can trigger RCE."

Q18 How do you prevent Timing Attacks during password verification and HMAC signature comparison? Advanced
Spoken Interview Answer

"Standard string equality (`===`) exits early on the first mismatched character, allowing attackers to measure microscopic response time differences to deduce valid signatures or hashes character-by-character. To eliminate this side-channel attack, we use `crypto.timingSafeEqual()`, which compares buffers in constant time regardless of where differences occur."

Q19 What are the security implications of CORS misconfigurations (Access-Control-Allow-Origin: *)? Advanced
Spoken Interview Answer

"Setting `Access-Control-Allow-Origin: *` allows any public website to make AJAX requests and read API responses. While acceptable for public read-only assets, if coupled with credentials (`Access-Control-Allow-Credentials: true`), browsers reject wildcard origins. However, poorly implemented backends that dynamically reflect the request's `Origin` header allow arbitrary malicious sites to make authenticated requests and steal private data."

Q20 How do you securely manage production secrets in containerized Node.js applications? Intermediate
Spoken Interview Answer

"Never bake secrets into `.env` files or Docker image layers. Instead, utilize secret managers (like AWS Secrets Manager, Vault, or Doppler) and inject credentials as runtime environment variables into Kubernetes pods or ECS containers. In CI/CD, use automated secret scanners (like GitGuardian or Trivy) to block commits containing API keys."
