1. Scenario 1: Design a Scalable URL Shortener (TinyURL / Bitly)

Requirements & Capacity Estimation

  • Functional Requirements: 1) Given a long URL, return a unique short URL (e.g., https://tiny.cc/a8f2Q); 2) Redirect requests visiting the short URL to the original long URL with sub-10ms latency; 3) Expire links after a configurable TTL.
  • Scale & Math:
    • 500 Million new URLs created per month \(\rightarrow \approx 200\text{ write QPS}\).
    • Read-to-Write ratio is 100:1 \(\rightarrow 20,000\text{ read QPS}\) (Peak: \(40,000\text{ QPS}\)).
    • 10-year storage: \(500\text{M} \times 12 \times 10 = 60\text{ Billion records} \times 500\text{ bytes} \approx 30\text{ Terabytes}\).

Short Code Generation: Base62 vs. Token Range

A 7-character string using alphanumeric characters (a–z, A–Z, 0–9 = 62 characters) yields: \[ 62^7 \approx 3.52 \text{ Trillion unique combinations} \] This comfortably exceeds our 60 Billion 10-year requirement.

💡 301 Moved Permanently vs. 302/307 Temporary Redirect

Returning 301 Moved Permanently causes browsers to cache the redirect locally, eliminating future server hits. However, if your business requires collecting click analytics (referrers, location, click counts), you must return 302 Found or 307 Temporary Redirect so every click reaches your server.

2. Scenario 2: Design a Real-Time Chat Engine (Slack / WhatsApp)

Core Challenges

  1. Persistent Connections: HTTP request-response is unsuitable for real-time messaging due to connection overhead; requires WebSockets.
  2. Cross-Server Message Routing: User A is connected to WebSocket Server 1, while User B is connected to WebSocket Server 2. How does Server 1 deliver User A’s message to User B?
  3. Online Presence Tracking: How do thousands of users know which friends are currently online without polling?

Presence Service Design

Clients send a lightweight heartbeat ping every 30 seconds over their active WebSocket. The gateway runs: SET presence:userId "online" EX 60. If the user's mobile app loses network coverage, the key naturally expires after 60 seconds without explicit teardown logic. When a user opens a chat room, the frontend queries the presence status of room participants via a single Redis MGET.

3. Scenario 3: Design a Distributed Rate Limiter

Algorithm How It Works Pros & Cons
Token Bucket (Amazon, Stripe) Tokens added to a bucket at a fixed fill rate \(\text{req}/\text{sec}\). Each request removes 1 token. If bucket is empty, request rejected. Pros: Memory efficient; permits bursts of traffic up to bucket capacity.
Cons: Two parameters to tune (bucket size, refill rate).
Leaky Bucket (Shopify) Requests enter a FIFO queue and are processed at a constant output rate. If queue overflows, new requests drop. Pros: Smooths out bursty traffic into steady outflow.
Cons: Bursty traffic experiences latency delays while queued.
Fixed Window Counter Counts requests within fixed time windows (e.g., 00:00–00:01). Resets counter at window boundary. Pros: Very simple.
Cons: Boundary Burst Flaw: If limit is 100/min, sending 100 requests at 00:59 and 100 at 01:01 permits 200 requests in 2 seconds!
Sliding Window Counter (Cloudflare) Blends the count from the previous window with current window progress: \(\text{Count} = \text{Current} + \text{Previous} \times (1 - \text{overlap})\). Pros: Solves boundary burst problem with minimal memory overhead (only 2 counters per client).

Distributed Synchronization with Redis Lua Script

To prevent race conditions across multiple Node.js instances executing rate limit checks, the Token Bucket algorithm is evaluated atomically inside Redis using Lua:

Lua: Atomic Token Bucket Evaluation in Redis 
-- KEYS[1]: ratelimit:<user_id>
-- ARGV[1]: max_capacity (e.g. 100)
-- ARGV[2]: refill_rate_per_sec (e.g. 10)
-- ARGV[3]: current_timestamp_sec
-- ARGV[4]: requested_tokens (e.g. 1)

local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill_rate = tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local requested = tonumber(ARGV[4])

local data = redis.call("HMGET", key, "tokens", "last_updated")
local tokens = tonumber(data[1])
local last_updated = tonumber(data[2])

if not tokens then
  tokens = capacity
  last_updated = now
else
  -- Calculate tokens generated since last access
  local elapsed = math.max(0, now - last_updated)
  tokens = math.min(capacity, tokens + (elapsed * refill_rate))
  last_updated = now
end

if tokens >= requested then
  tokens = tokens - requested
  redis.call("HMSET", key, "tokens", tokens, "last_updated", last_updated)
  redis.call("EXPIRE", key, 3600)
  return 1 -- Allowed
else
  return 0 -- Rejected (Rate Limit Exceeded)
end

5. Practical Exercises

Exercise 1: Base62 Encoder & Decoder in TypeScript

Scenario: Implement a Base62 encoder and decoder in TypeScript to convert a 64-bit integer into a short URL string and vice-versa.

View Complete Solution
TypeScript Solution 
const BASE62_CHARS = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';

export function encodeBase62(num: bigint): string {
  if (num === 0n) return '0';
  let result = '';
  let n = num;
  const base = 62n;

  while (n > 0n) {
    const remainder = Number(n % base);
    result = BASE62_CHARS[remainder] + result;
    n = n / base;
  }
  return result;
}

export function decodeBase62(str: string): bigint {
  let result = 0n;
  const base = 62n;

  for (let i = 0; i < str.length; i++) {
    const char = str[i];
    const index = BigInt(BASE62_CHARS.indexOf(char));
    if (index === -1n) throw new Error(`Invalid Base62 character: ${char}`);
    result = result * base + index;
  }
  return result;
}

// Example: encodeBase62(1000000001n) -> "15FTG1"

Exercise 2: Distributed Chat Room Connection Router in Node.js

Scenario: Write a routing handler that takes an incoming message for a specific room and broadcasts it to all connected local WebSocket clients, while publishing it to Redis Pub/Sub for other cluster nodes.

View Complete Solution
TypeScript Solution 
import Redis from 'ioredis';
import { WebSocket } from 'ws';

const pub = new Redis();
const sub = new Redis();

// Map of roomId -> Set of local WebSocket client connections
const localRooms = new Map<string, Set<WebSocket>>();

// Listen for messages published across cluster
sub.subscribe('chat:broadcast');
sub.on('message', (channel, messageStr) => {
  const { roomId, message, originServerId } = JSON.parse(messageStr);
  const clients = localRooms.get(roomId);
  if (clients) {
    for (const ws of clients) {
      if (ws.readyState === WebSocket.OPEN) {
        ws.send(JSON.stringify(message));
      }
    }
  }
});

export function handleIncomingClientMessage(
  roomId: string,
  message: any,
  currentServerId: string
): void {
  // Publish to Redis so all other cluster gateways deliver to their local connections
  pub.publish(
    'chat:broadcast',
    JSON.stringify({ roomId, message, originServerId: currentServerId })
  );
}

6. Chapter-Specific Interview Questions & Answers

20 high-frequency interview questions covering practical system design walkthroughs: URL shorteners, real-time chat, rate limiters, and notification engines.

Q01 Why is Base62 encoding preferred over MD5 or SHA-256 for URL shorteners? Beginner
Spoken Interview Answer

"MD5 and SHA-256 generate 128-bit or 256-bit hashes that require truncation, which immediately introduces hash collisions that require database lookup resolution. Base62 encodes unique auto-incrementing 64-bit integers directly into alphanumeric characters (`[0-9a-zA-Z]`), mathematically guaranteeing zero collisions with maximum character density."

Q02 What HTTP status code should a URL shortener return: 301 or 302? Beginner
Spoken Interview Answer

"If the goal is minimizing server load, use 301 Moved Permanently, which browsers aggressively cache locally. However, if the business requires click analytics (tracking location, referrers, device types, or total visits), you must return 302 Found or 307 Temporary Redirect so every click is directed to your server for analytics ingestion."

Q03 Why are WebSockets used for real-time chat rather than HTTP polling? Beginner
Spoken Interview Answer

"HTTP polling repeatedly opens and closes TCP connections and sends repetitive HTTP headers (~1 KB overhead per poll), creating massive CPU and bandwidth drag. WebSockets perform a single HTTP 101 Upgrade handshake to establish a bi-directional, persistent TCP connection, transmitting subsequent messages in tiny 2-byte framing packets with sub-millisecond delivery."

Q04 What is the Token Bucket rate limiting algorithm? Beginner
Spoken Interview Answer

"The Token Bucket algorithm models a bucket of fixed capacity that continuously refills with tokens at a constant rate. Each incoming request consumes one token. If tokens are available, the request proceeds; if empty, it is rejected with 429 Too Many Requests. It is widely favored because it easily accommodates temporary traffic bursts up to the bucket capacity."

Q05 What is the difference between Transactional and Marketing notifications? Beginner
Spoken Interview Answer

"Transactional notifications (OTPs, password resets, payment receipts) are urgent, non-optional, and must be delivered within seconds via dedicated high-priority queues. Marketing notifications (promotions, weekly digests) can tolerate delays, must respect user opt-out preferences, and are processed through lower-priority, bulk-throttled queues."

Q06 How does a Token Range Service generate unique IDs across multiple application servers? Intermediate
Spoken Interview Answer

"A central coordinator like ZooKeeper allocates discrete numeric ranges to each server—e.g., Server A gets 1M–2M, Server B gets 2M–3M. Each server generates sequential IDs locally from its allocated memory range with zero network latency. When a server exhausts its range, it requests a new block from ZooKeeper, guaranteeing globally unique IDs without database bottlenecks."

Q07 How do you track user online/offline presence in a real-time chat application at scale? Intermediate
Spoken Interview Answer

"Clients send a heartbeat ping every 30 seconds over their WebSocket connection. The backend sets a Redis key: `SET presence:userId 'online' EX 60`. If the user disconnects or loses signal, the key naturally expires after 60 seconds without complex teardown logic. Checking presence is an O(1) Redis lookup, and friend lists query status via `MGET`."

Q08 What is the Boundary Burst flaw in Fixed Window rate limiters? Intermediate
Spoken Interview Answer

"In a Fixed Window counter allowing 100 requests per minute, an attacker can send 100 requests at second 59 and another 100 requests at second 01 of the next minute. Both windows pass successfully, but the server receives 200 requests in a 2-second span—twice the configured rate limit. Sliding window algorithms eliminate this vulnerability."

Q09 How do you prevent duplicate notifications from being delivered to users? Intermediate
Spoken Interview Answer

"We enforce Idempotency Keys across the pipeline. When a notification event is ingested, we generate a deterministic key (e.g., `notif:order-shipped:order-123`) and attempt to acquire a Redis reservation (`SET key 1 NX EX 86400`). If the key already exists, the notification is discarded as a duplicate before reaching third-party SMS or email gateways."

Q10 How do you scale message storage for a chat application with billions of messages? Intermediate
Spoken Interview Answer

"We use wide-column NoSQL databases like Apache Cassandra or ScyllaDB. The partition key is `conversation_id`, co-locating all messages for a chat room on the same physical cluster nodes, while the clustering key is a time-ordered `message_id` (or Snowflake ID) sorted descending, allowing fast retrieval of the latest 50 messages with zero cross-node joins."

Q11 Why should rate limiters be executed inside Redis via Lua scripts? Intermediate
Spoken Interview Answer

"Evaluating a rate limiter requires reading the current token count, calculating elapsed time, refilling tokens, and decrementing the balance. If executed as separate commands from Node.js, concurrent requests cause race conditions where multiple requests read the same balance. Redis executes Lua scripts atomically on its single thread, eliminating concurrency bugs."

Q12 How does an API Gateway integrate with a Distributed Rate Limiter? Intermediate
Spoken Interview Answer

"The API Gateway acts as the reverse proxy ingress point. Before routing requests to backend microservices, gateway middleware extracts client identifiers (API key or IP) and queries the distributed rate limiter. If within quota, it forwards the request with rate-limiting headers; if exceeded, it short-circuits immediately with status `429 Too Many Requests`."

Q13 How do you deliver chat messages to offline users? Intermediate
Spoken Interview Answer

"When the gateway detects that the recipient has no active WebSocket connection, the message is persisted to database storage, and a background task is pushed to an asynchronous queue. The worker formats a mobile push notification payload and dispatches it to Apple APNs or Google FCM, ensuring the user receives a lock screen alert."

Q14 What is the 80/20 caching rule applied to URL shorteners? Intermediate
Spoken Interview Answer

"The Pareto Principle dictates that 20% of short URLs generate 80% of total read traffic. In capacity planning, we provision Redis to cache exactly that hot 20% of URLs in RAM. For 20,000 daily read QPS, caching the top 20% guarantees that 80%+ of redirect queries return in 2–3ms directly from memory, shielding the primary database."

Q15 How do you handle a celebrity user with 100,000 participants in a chat room? Advanced
Spoken Interview Answer

"Broadcasting a message to 100,000 WebSocket connections on a single server causes event loop lag and network saturation. We treat massive channels as live broadcasts: messages are published to Apache Kafka partitioned across a tree of regional edge gateway clusters. Edge servers fan out messages locally, and presence status is disabled or throttled to batch updates."

Q16 How do you ensure strict chronological message ordering across distributed chat clients? Advanced
Spoken Interview Answer

"We cannot rely on physical client timestamps due to clock drift and timezone differences. Instead, we use a centralized Snowflake ID generator or database sequence number per conversation. Messages within a conversation are ordered by this monotonic integer sequence ID, ensuring consistent ordering across all participant devices."

Q17 How do you handle third-party notification gateway outages (SendGrid / Twilio downtime)? Advanced
Spoken Interview Answer

"We wrap external gateway clients in a Circuit Breaker pattern. If SendGrid returns 5xx errors or timeouts exceeding an error threshold, the circuit trips to OPEN. The worker automatically routes traffic to a fallback provider (e.g., AWS SES), retrying failed jobs using exponential backoff with jitter before moving exhausted attempts to a Dead-Letter Queue."

Q18 How do you prevent URL shortener abuse (phishing, malware redirection)? Advanced
Spoken Interview Answer

"Upon long URL submission, the ingestion pipeline checks the target domain against Google Safe Browsing APIs and Spamhaus blocklists. We enforce user authentication for high-volume creation, rate limit creation by IP, and run asynchronous crawlers that periodically verify target destinations haven't been altered to point to malicious redirects."

Q19 How does Sliding Window Counter calculate request allowance mathematically? Advanced
Spoken Interview Answer

"It approximates the rolling window using two static counters: the previous window count and the current window count. The formula is: `Estimated_Requests = Current_Count + Previous_Count * (1 - Current_Window_Progress)`. If current time is 30% into the minute, it factors in 70% of the previous minute's requests, eliminating boundary bursts with only two Redis integer keys."

Q20 What is your framework for handling trade-offs in system design interviews? Intermediate
Spoken Interview Answer

"I never present a technology as universally superior. Every architectural choice has an engineering cost: choosing microservices adds operational overhead; choosing NoSQL sacrifices ACID transactions; choosing Redis adds memory costs. I explicitly state both the benefit and drawback of each decision, tying it directly to the problem's functional and non-functional requirements."
