1. Component Architecture & Design Patterns

As frontend codebases grow beyond dozens of engineers, disorganized component structures create brittle "prop drilling hell", coupled business logic, and code duplication. Modern React leverages proven design patterns to maintain separation of concerns.

1.1 Container vs Presentational Components

Originally popularized by Dan Abramov, this pattern separates how things work from how things look:

  • Presentational Components: Pure UI components. They receive data and callbacks via props, have zero awareness of Redux, APIs, or global state, and are easily testable in Storybook.
  • Container Components: State orchestrators. They call API hooks, query Redux/Context, handle side-effects, and pass plain props down to presentational components.
📌 Modern Evolution: Custom Hooks as Containers

With the advent of React Hooks, the container pattern has largely transitioned from wrapper JSX components to Custom Hooks. Instead of creating a UserProfileContainer.jsx that wraps UserProfileView.jsx, developers extract data fetching and logic into useUserProfile(userId) and invoke it directly inside the component or a lean page coordinator.

1.2 The Compound Component Pattern

The Compound Component Pattern allows multiple components to work together seamlessly with shared implicit state, mirroring native HTML elements like <select> and <option>. It provides maximum flexibility to consumers without exposing internal state management.

javascript (Compound Component Implementation) 
// src/components/Accordion.jsx
import React, { createContext, useContext, useState } from "react";

// 1. Create Internal Context for implicit state sharing
const AccordionContext = createContext(null);

function useAccordion() {
  const context = useContext(AccordionContext);
  if (!context) {
    throw new Error("Accordion sub-components must be rendered inside an  provider.");
  }
  return context;
}

// 2. Main Container Component
export function Accordion({ children, defaultOpenIndex = null }) {
  const [openIndex, setOpenIndex] = useState(defaultOpenIndex);

  const toggleIndex = (index) => {
    setOpenIndex((prev) => (prev === index ? null : index));
  };

  return (
    <AccordionContext.Provider value={{ openIndex, toggleIndex }}>
      <div className="accordion-root">{children}</div>
    </AccordionContext.Provider>
  );
}

// 3. Item Wrapper Component
Accordion.Item = function AccordionItem({ index, children }) {
  return <div className="accordion-item" data-index={index}>{children}</div>;
};

// 4. Header / Trigger Component
Accordion.Header = function AccordionHeader({ index, children }) {
  const { openIndex, toggleIndex } = useAccordion();
  const isOpen = openIndex === index;

  return (
    <button
      type="button"
      className={`accordion-trigger ${isOpen ? "active" : ""}`}
      onClick={() => toggleIndex(index)}
      aria-expanded={isOpen}
    >
      {children}
      <span className="chevron">{isOpen ? "▲" : "▼"}</span>
    </button>
  );
};

// 5. Collapsible Panel Body Component
Accordion.Panel = function AccordionPanel({ index, children }) {
  const { openIndex } = useAccordion();
  if (openIndex !== index) return null;

  return <div className="accordion-panel">{children}</div>;
};

// CONSUMER USAGE: Clean, declarative, and highly flexible JSX structure!
export function FAQPage() {
  return (
    <Accordion defaultOpenIndex={0}>
      <Accordion.Item index={0}>
        <Accordion.Header index={0}>What is your refund policy?</Accordion.Header>
        <Accordion.Panel index={0}>Full refunds within 30 days of purchase.</Accordion.Panel>
      </Accordion.Item>
      <Accordion.Item index={1}>
        <Accordion.Header index={1}>Do you support enterprise SSO?</Accordion.Header>
        <Accordion.Panel index={1}>Yes, SAML 2.0 and OIDC are fully supported.</Accordion.Panel>
      </Accordion.Item>
    </Accordion>
  );
}

2. Dynamic Code-Splitting: React.lazy and Suspense

By default, single-page applications bundle all JavaScript into a single massive bundle (e.g., bundle.js of 3MB). When a user visits the landing page, the browser is forced to download, parse, and compile code for admin dashboards, charting libraries, and settings pages they may never view.

Code-Splitting leverages native ES dynamic imports (import()) and Webpack/Vite chunking to split code into separate downloadable chunks that load on-demand.

Figure 18.1: Monolithic Bundle vs On-Demand Route Chunks
[ Monolithic Bundle: 2.8 MB Initial Download (Slow First Contentful Paint) ]
+-------------------------------------------------------------------------+
| Homepage (40KB) | Analytics Chart (850KB) | Admin Panel (1.2MB) | RichText (700KB) |
+-------------------------------------------------------------------------+

========================================================================

[ Code-Split Architecture: 95 KB Initial Download (Ultra-Fast FCP) ]
+------------------------+
| Main App Shell (95 KB) | ----> Initial Fast Load!
+------------------------+
            |
            | User clicks "/analytics" route
            v
+-------------------------------+
| analytics-chunk.js (850 KB)   | ----> Loaded on-demand via Suspense!
+-------------------------------+
javascript 
// src/App.jsx
import React, { Suspense, lazy } from "react";
import { BrowserRouter, Routes, Route, Link } from "react-router-dom";
import { LoadingSpinner } from "./components/LoadingSpinner";

// Dynamic lazy imports: Chunks are only requested when route is visited!
const Home = lazy(() => import("./pages/Home"));
const AnalyticsDashboard = lazy(() => import("./pages/AnalyticsDashboard"));
const AdminSettings = lazy(() => import("./pages/AdminSettings"));

export function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/analytics">Analytics</Link>
        <Link to="/admin">Admin</Link>
      </nav>

      {/* Suspense boundary displays fallback UI while network fetches chunk */}
      <Suspense fallback={<LoadingSpinner message="Loading view..." />}>
        <Routes>
          <Route path="/" element={<Home />} />
          <Route path="/analytics" element={<AnalyticsDashboard />} />
          <Route path="/admin" element={<AdminSettings />} />
        </Routes>
      </Suspense>
    </BrowserRouter>
  );
}

3. Memoization Economics: React.memo, useMemo, and useCallback

A common anti-pattern in React codebases is indiscriminate memoization: wrapping every single function in useCallback and every calculation in useMemo. This often degrades rather than improves performance.

Optimization Tool Underlying Cost (The "Overhead") Legitimate High-ROI Use Case Wasteful Anti-Pattern Use Case
React.memo(Component) Shallow comparison of every prop on every re-render; extra Fiber memory allocation. Heavy presentational components that re-render frequently with identical props due to unrelated parent state changes (e.g. data grids, chart SVGs). Wrapping tiny components (e.g. <Button>Click</Button>) or components whose props change on every render anyway.
useMemo(fn, deps) Dependency array allocation; shallow comparing every dependency on every render. Computations taking \(> 1\text{ms}\) (e.g. sorting or filtering 5,000 items), or stabilizing object references used in dependency arrays. Memoizing primitive transformations (e.g. useMemo(() => firstName + " " + lastName, [firstName, lastName])).
useCallback(fn, deps) Closure allocation and dependency array comparison. Passing callback functions down to React.memo child components or listing them in useEffect dependency arrays. Passing callbacks to raw HTML elements (e.g. <button onClick={useCallback(...)}>); native DOM elements do not benefit from reference stability!

4. List Virtualization: Rendering 100,000 Items at 60fps

When rendering large collections of items (e.g., search results, logs, chat feeds, tabular data), mounting 10,000 DOM nodes simultaneously causes severe browser jank. The DOM tree consumes hundreds of megabytes of RAM, and any subsequent reflow or style recalculation freezes the main thread.

Virtualization (Windowing) solves this by rendering only the items currently visible inside the viewport (plus a small overscan buffer above and below). As the user scrolls, DOM nodes outside the window are recycled or unmounted.

Figure 18.2: Virtual Scroll Windowing Calculation
[ Total Dataset: 50,000 Items | Total Virtual Height: 50,000 * 40px = 2,000,000px ]

+-------------------------------------------------------------+
| Virtual Spacer Top (Height = startIndex * itemHeight)       |
+-------------------------------------------------------------+  <-- ScrollTop: 12,000px
| Visible Item #300 (40px)                                    |
| Visible Item #301 (40px)                                    |
| Visible Item #302 (40px)    ===> VIEWPORT CONTAINER         |
| Visible Item #303 (40px)         (Height: 400px, 10 items)  |
| Visible Item #304 (40px)                                    |
| Visible Item #305 (40px)                                    |
+-------------------------------------------------------------+  <-- ScrollBottom: 12,400px
| Virtual Spacer Bottom (Height = (total - endIndex) * height)|
+-------------------------------------------------------------+
Total DOM nodes mounted: Exactly 15 nodes instead of 50,000 nodes!
javascript (Zero-Dependency Virtual List) 
import React, { useState, useRef } from "react";

export function VirtualizedList({ items, itemHeight = 40, containerHeight = 400 }) {
  const [scrollTop, setScrollTop] = useState(0);
  const containerRef = useRef(null);

  const totalItems = items.length;
  const totalHeight = totalItems * itemHeight;

  // Calculate visible index range based on current scroll position
  const startIndex = Math.max(0, Math.floor(scrollTop / itemHeight) - 2); // 2 overscan items
  const visibleCount = Math.ceil(containerHeight / itemHeight) + 4;       // Buffer
  const endIndex = Math.min(totalItems, startIndex + visibleCount);

  const visibleItems = items.slice(startIndex, endIndex);
  const offsetY = startIndex * itemHeight;

  const handleScroll = (e) => {
    setScrollTop(e.currentTarget.scrollTop);
  };

  return (
    <div
      ref={containerRef}
      onScroll={handleScroll}
      style={{
        height: containerHeight,
        overflowY: "auto",
        position: "relative",
        border: "1px solid #ccc"
      }}
    >
      {/* Phantom height div to force native browser scrollbar */}
      <div style={{ height: totalHeight, width: "100%", position: "relative" }}>
        {/* Absolute container shifted to viewport offset */}
        <div
          style={{
            transform: `translateY(${offsetY}px)`,
            position: "absolute",
            left: 0,
            right: 0,
            top: 0
          }}
        >
          {visibleItems.map((item, index) => (
            <div
              key={item.id}
              style={{
                height: itemHeight,
                boxSizing: "border-box",
                padding: "8px",
                borderBottom: "1px solid #eee"
              }}
            >
              <strong>#{startIndex + index + 1}</strong>: {item.label}
            </div>
          ))}
        </div>
      </div>
    </div>
  );
}

5. Resilient Error Boundaries & Production Crash Handling

In React, an unhandled JavaScript error thrown during rendering, lifecycle execution, or constructor calls will unmount the entire component tree, leaving the user with a blank white screen.

An Error Boundary is a React component that catches JavaScript errors anywhere in its child component tree, logs the error stack trace, and displays a fallback UI instead of crashing the application.

⚠️ What Error Boundaries Do NOT Catch

By design, Error Boundaries do not catch errors inside:

  • Event Handlers: (e.g. onClick). Use regular try / catch blocks inside event listeners.
  • Asynchronous Code: (e.g. setTimeout, requestAnimationFrame, unhandled Promise rejections).
  • Server-Side Rendering (SSR): During Node.js hydration passes.
  • Errors inside the Error Boundary itself: (rather than its children).
javascript 
// src/components/ErrorBoundary.jsx
import React from "react";

export class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false, error: null };
  }

  // 1. Static lifecycle: Update state so the next render shows fallback UI
  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  // 2. Lifecycle: Log error information to monitoring service (Sentry, Datadog)
  componentDidCatch(error, errorInfo) {
    console.error("[ErrorBoundary] Caught rendering failure:", error);
    console.error("[ErrorBoundary] Component Stack:", errorInfo.componentStack);

    if (this.props.onError) {
      this.props.onError(error, errorInfo);
    }
  }

  handleReset = () => {
    this.setState({ hasError: false, error: null });
  };

  render() {
    if (this.state.hasError) {
      if (this.props.fallback) {
        return this.props.fallback;
      }

      return (
        <div className="error-fallback-card" role="alert">
          <h3>Something went wrong in this module.</h3>
          <p>{this.state.error?.message || "An unexpected error occurred."}</p>
          <button type="button" onClick={this.handleReset}>
            Try Again
          </button>
        </div>
      );
    }

    return this.props.children;
  }
}

6. Profiling with React DevTools: Flamegraph & Commits

Diagnosing performance bottlenecks requires empirical measurement rather than guesswork. The React DevTools Profiler records rendering metrics during user interactions.

6.1 Interpreting the Flamegraph Chart

  • Bar Width: Represents how long the component took to render in milliseconds (render duration). Wide bars indicate heavy components.
  • Bar Color:
    • Grey: The component did not render during this commit (skipped due to React.memo or no prop/state change).
    • Blue / Green: Rendered quickly with low compute time.
    • Yellow / Red: High compute time during render phase; primary targets for optimization.
  • Commit History Bar: The timeline at top shows each React commit. Tall bars represent slow commits that may cause dropped frames (\(> 16.6\text{ms}\) budget for 60fps).

Exercise 18.1 Build a Modal with Focus Trapping and Portal Architecture

Problem: Create an accessible Modal component rendered via ReactDOM.createPortal into a dedicated #modal-root DOM container. Ensure the Escape key closes the modal, scrolling on document.body is locked while open, and cleanup restores background scrolling.

View Complete Solution
javascript 
import React, { useEffect } from "react";
import ReactDOM from "react-dom";

export function Modal({ isOpen, onClose, title, children }) {
  useEffect(() => {
    if (!isOpen) return;

    // 1. Prevent background page scroll while modal is active
    const originalStyle = window.getComputedStyle(document.body).overflow;
    document.body.style.overflow = "hidden";

    // 2. Keyboard accessibility: Close on Escape key press
    const handleKeyDown = (e) => {
      if (e.key === "Escape") {
        onClose();
      }
    };
    window.addEventListener("keydown", handleKeyDown);

    return () => {
      document.body.style.overflow = originalStyle;
      window.removeEventListener("keydown", handleKeyDown);
    };
  }, [isOpen, onClose]);

  if (!isOpen) return null;

  const modalRoot = document.getElementById("modal-root") || document.body;

  return ReactDOM.createPortal(
    <div className="modal-backdrop" onClick={onClose}>
      <div
        className="modal-content"
        role="dialog"
        aria-modal="true"
        aria-labelledby="modal-title"
        onClick={(e) => e.stopPropagation()} // Prevent closing when clicking content
      >
        <header className="modal-header">
          <h2 id="modal-title">{title}</h2>
          <button type="button" onClick={onClose} aria-label="Close modal">
            ×
          </button>
        </header>
        <div className="modal-body">{children}</div>
      </div>
    </div>,
    modalRoot
  );
}
