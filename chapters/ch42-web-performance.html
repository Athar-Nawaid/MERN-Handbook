1. The Core Web Vitals Mental Model: LCP, INP, and CLS

Historically, web performance was measured with technical network metrics like DOMContentLoaded and window.onload. While useful for measuring wire speed, these metrics failed to capture whether a user could actually see meaningful content or interact smoothly with the page.

Google standardized Core Web Vitals as a user-centric trinity evaluating loading speed, interactivity responsiveness, and visual stability:

Metric User Experience Dimension Good Threshold (75th Percentile) Needs Improvement Poor
LCP (Largest Contentful Paint) Loading Speed (Perceived Readability) ≤ 2.5 seconds 2.5s – 4.0s > 4.0s
INP (Interaction to Next Paint) Responsiveness (Smooth Interactivity) ≤ 200 ms 200ms – 500ms > 500ms
CLS (Cumulative Layout Shift) Visual Stability (No Content Jumps) ≤ 0.1 0.1 – 0.25 > 0.25

A. Largest Contentful Paint (LCP) Breakdown

LCP measures the time elapsed from the user initiating navigation until the largest visual element within the initial viewport completes rendering. The LCP candidate is typically:

  • An <img> element (hero banner or product image).
  • An image inside an <svg> or a CSS background-image: url(...).
  • A video poster frame or <video> preview element.
  • A block-level text container holding prominent headline typography.

LCP consists of four distinct sub-parts: LCP = TTFB (Time to First Byte) + Resource Load Delay + Resource Load Duration + Element Render Delay. To optimize LCP, you must identify which of the four stages represents the primary bottleneck.

B. Interaction to Next Paint (INP) vs. First Input Delay (FID)

In March 2024, Google officially replaced First Input Delay (FID) with Interaction to Next Paint (INP). FID was flawed because it only measured the input delay (the time waiting for the main thread to wake up) of the very first user interaction on the page. It ignored the JavaScript execution time and completely ignored subsequent clicks, tab switches, and interactions during the session.

INP measures the responsiveness of all qualifying interactions (clicks, taps, keyboard presses) throughout the full page lifecycle, reporting the worst interaction (excluding rare outliers, typically at the 98th or 75th percentile). An interaction's latency consists of three phases:

  1. Input Delay: Time spent waiting for background tasks or Long Tasks (>50ms) to clear the browser main thread event loop.
  2. Processing Time: Time taken executing JavaScript event handlers registered for that interaction.
  3. Presentation Delay: Time taken by the browser compositing engine to recalculate layout, style, paint, and display the next graphical frame.

C. Cumulative Layout Shift (CLS)

CLS quantifies the total score of all unexpected layout shifts occurring during the entire lifespan of a page. A layout shift occurs when any visible DOM element changes its start position between two frames. The score is calculated as:

Layout Shift Score = Impact Fraction × Distance Fraction

  • Impact Fraction: The percentage of the viewport area occupied by unstable elements before and after the shift.
  • Distance Fraction: The greatest distance unstable elements moved relative to the largest viewport dimension.

Common root causes of poor CLS include:

  • Images and iframes rendered without explicit width and height attributes or CSS aspect-ratio.
  • Dynamic client-side ads, banners, or newsletter signup bars injected into the DOM without reserved space placeholders.
  • Web fonts causing Flash of Invisible Text (FOIT) or Flash of Unstyled Text (FOUT) when the fallback font has different metrics than the web font.

2. Lab Data (Synthetic) vs. Field Data (Real User Monitoring)

One of the most frequent misconceptions in engineering teams is assuming that a 100/100 score in Google Lighthouse guarantees pristine real-world performance. In reality, performance metrics exist in two fundamentally different environments:

Dimension Lab Data (Synthetic / Lighthouse / CI) Field Data (Real User Monitoring / RUM / CrUX)
Environment Controlled, simulated environment with fixed CPU throttling, emulated mobile viewport, and predefined network speeds (e.g., Fast 3G). Real devices, real hardware variations (from \$100 Android phones to M3 MacBooks), and live cellular networks across the globe.
Interactivity Metric Total Blocking Time (TBT) as a synthetic proxy. INP cannot be measured in the lab without simulated user interaction scripts. Actual INP recorded across millions of live user interactions during checkout, search, and form inputs.
Reproducibility High reproducibility; ideal for automated pull request regression tests and local debugging in DevTools. Statistical distribution (75th percentile of all visits); fluctuates based on real-world traffic mix and geographies.
SEO & Ranking Impact Zero direct impact on Google Search rankings. Direct impact via the Chrome User Experience Report (CrUX) 28-day rolling window dataset.
JavaScript (Collecting Field Core Web Vitals) 
// Production field tracking using the official 'web-vitals' library
import { onLCP, onINP, onCLS } from 'web-vitals';

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name,        // 'LCP', 'INP', or 'CLS'
    value: metric.value,      // Numeric value in ms or unitless score
    rating: metric.rating,    // 'good', 'needs-improvement', or 'poor'
    delta: metric.delta,      // Change since last emission
    id: metric.id,            // Unique interaction or session ID
    navigationType: metric.navigationType // 'navigate', 'reload', 'back-forward'
  });

  // Use navigator.sendBeacon to ensure data is transmitted even if user closes the tab
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/telemetry/vitals', body);
  } else {
    fetch('/api/telemetry/vitals', {
      method: 'POST',
      body,
      headers: { 'Content-Type': 'application/json' },
      keepalive: true
    });
  }
}

// Subscribe to Core Web Vitals with reporting callbacks
onLCP(sendToAnalytics);
onINP(sendToAnalytics);
onCLS(sendToAnalytics);

3. Optimizing the Critical Rendering Path & Resource Hints

The Critical Rendering Path (CRP) is the sequence of steps the browser takes from receiving raw HTML bytes to painting pixels onto the screen:

HTML Bytes → Characters → Tokens → Nodes → DOM Tree
CSS Bytes → Characters → Tokens → Nodes → CSSOM Tree
DOM + CSSOM → Render Tree → Layout (Reflow) → Paint → Composite

By default, CSS is render-blocking: the browser halts rendering until all referenced stylesheets are downloaded and parsed into the CSSOM. Synchronous <script> tags are parser-blocking: the HTML parser freezes until the script is downloaded and executed.

A. Script Loading Attributes: Synchronous vs. defer vs. async

Loading Method Download Behavior Execution Timing Execution Order Preserved?
<script src="..."> Pauses HTML parsing immediately to download script. Executes immediately upon download; blocks HTML parser. Yes, in source document order.
<script async src="..."> Downloads asynchronously in parallel with HTML parsing. Executes the millisecond download finishes; pauses HTML parsing during execution. No; first script to finish downloads executes first (race condition).
<script defer src="..."> Downloads asynchronously in parallel with HTML parsing. Executes only after HTML document is fully parsed, right before DOMContentLoaded. Yes; strictly executes in source document order. Best for app bundles.

B. Modern Resource Hints

Resource hints inform the browser's speculative pre-parser about upcoming network dependencies before they are encountered in the document body:

HTML (Resource Hints) 
<head>
  <!-- 1. dns-prefetch: Resolves third-party DNS domain early (saves ~20-100ms) -->
  <link rel="dns-prefetch" href="https://api.stripe.com">

  <!-- 2. preconnect: Performs DNS lookup + TCP 3-way handshake + TLS negotiation in advance -->
  <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>

  <!-- 3. preload: High-priority download of critical resources needed in the current page -->
  <!-- Crucial for Hero Images (LCP element) and Critical Web Fonts -->
  <link rel="preload" href="/fonts/inter-bold.woff2" as="font" type="font/woff2" crossorigin>
  <link rel="preload" href="/images/hero-banner.webp" as="image" type="image/webp" fetchpriority="high">

  <!-- 4. prefetch: Low-priority background download for resources needed on the NEXT page -->
  <link rel="prefetch" href='https://example.com/js/checkout-modal.chunk.js' as="script">
</head>

4. Image, Media, and Font Optimization

Images and media typically account for over 60% to 75% of the total bytes transmitted over the wire for modern web applications. Unoptimized images are the single most common cause of failing LCP and CLS scores.

A. Next-Generation Formats: AVIF and WebP

Legacy formats like JPEG and PNG are vastly inefficient compared to modern video-derived codecs:

  • WebP: Supported by >97% of modern browsers; provides 25% to 35% smaller file sizes than JPEG at equivalent visual perceptual quality. Supports transparency (alpha channel) and animation.
  • AVIF (AV1 Image File Format): Derived from the open-source AV1 video codec. Slashes file sizes by 50% compared to JPEG and 20% compared to WebP, with superior color gradients and high-dynamic-range (HDR) preservation.
HTML (Responsive Art Direction with Picture Element) 
<!-- Use <picture> to serve AVIF with WebP and JPEG fallbacks, plus responsive srcset -->
<picture>
  <!-- AVIF for cutting-edge browsers -->
  <source 
    type="image/avif" 
    srcset="/images/hero-400.avif 400w, /images/hero-800.avif 800w, /images/hero-1600.avif 1600w"
    sizes="(max-width: 600px) 100vw, (max-width: 1200px) 50vw, 800px">
  
  <!-- WebP fallback -->
  <source 
    type="image/webp" 
    srcset="/images/hero-400.webp 400w, /images/hero-800.webp 800w, /images/hero-1600.webp 1600w"
    sizes="(max-width: 600px) 100vw, (max-width: 1200px) 50vw, 800px">

  <!-- Fallback IMG tag with explicit aspect ratio to prevent CLS -->
  <img 
    src="/images/hero-800.jpg" 
    alt="Developer workstation setup" 
    width="800" 
    height="450" 
    fetchpriority="high"
    decoding="async"
    style="aspect-ratio: 16 / 9; width: 100%; height: auto;">
</picture>
💡 Critical Rule for LCP Images vs. Below-the-Fold Images

Never lazy-load the LCP hero image! Adding loading="lazy" to an above-the-fold hero image forces the browser to wait until layout computation completes before starting the download, introducing an artificial 500ms–1500ms delay that destroys your LCP score.

Use fetchpriority="high" and <link rel="preload"> on the hero image. Use loading="lazy" and decoding="async" strictly for images located below the fold.

B. Web Font Optimization: Eliminating FOIT and FOUT

When browsers download custom web fonts, text can either disappear completely (Flash of Invisible Text — FOIT) or render momentarily in a system font before abruptly shifting in shape and size (Flash of Unstyled Text — FOUT), driving up CLS scores.

  • Use font-display: swap; in your @font-face declaration to ensure text is immediately visible with a fallback font, swapping in the custom font once downloaded.
  • Use modern WOFF2 format exclusively (which uses Brotli compression internally) and self-host font files to eliminate cross-origin connection handshakes.
  • Apply font subsetting to eliminate unused glyphs (e.g., stripping Asian or Cyrillic characters if serving an English-only portal).

5. JavaScript Bundle Optimization and Tree Shaking

JavaScript is the most expensive byte delivered over the wire. Unlike images, which are merely decoded and painted by the GPU, JavaScript must be downloaded, parsed, compiled (JIT), and executed by the V8 CPU engine on the main thread, directly contributing to severe INP bottlenecks.

A. Tree Shaking Requirements

Tree shaking relies strictly on the static structure of ECMAScript Modules (ESM):

  • import and export statements must appear at the top-level scope (static, cannot be placed inside an if block).
  • CommonJS (CJS) prevents tree shaking because const lib = require(condition ? './a' : './b') is dynamic and can only be evaluated at runtime. Bundlers are forced to include the entire CommonJS package.
  • Add "sideEffects": false in your package.json to declare that imported modules contain no global modifications (like modifying window or injecting CSS), allowing the bundler to safely drop unused files.

B. Code-Splitting and Dynamic Imports

Monolithic SPA bundles force users to download code for pages they may never visit (such as admin panels, heavy chart libraries, or billing forms). Code-splitting breaks the monolith into smaller on-demand chunks loaded via dynamic import():

JavaScript (Dynamic Import & React.lazy) 
import React, { Suspense, useState } from 'react';

// Route-based code splitting: The 450KB chart chunk is NOT in the main entry bundle
const HeavyAnalyticsDashboard = React.lazy(() => import('./components/HeavyAnalyticsDashboard'));

export function App() {
  const [showDashboard, setShowDashboard] = useState(false);

  return (
    <div>
      <h1>Customer Portal</h1>
      <button onClick={() => setShowDashboard(true)}>
        View Deep Analytics
      </button>

      {showDashboard && (
        <Suspense fallback={<div class="skeleton-loader">Loading analytics...</div>}>
          <HeavyAnalyticsDashboard />
        </Suspense>
      )}
    </div>
  );
}

6. HTTP Caching Headers and CDN Invalidation

The fastest network request is the request that never leaves the client's device. HTTP caching allows browsers and CDN edge caches to store copies of HTTP responses and serve them instantly without re-querying origin servers.

A. The Cache-Control Header Directives

Directive Meaning and Architecture Impact
public Response may be cached by intermediate proxies, CDNs, and browser caches.
private Response contains user-specific data (e.g. user profiles); only the client browser may cache it, never shared CDNs.
no-store Do not cache under any circumstances. Every request must hit the origin server (used for banking/auth endpoints).
no-cache Response may be cached locally, but the browser must validate with the origin (via ETag) before serving it.
max-age=N Specifies maximum freshness duration in seconds for browser caches.
s-maxage=N Overrides max-age specifically for shared public caches (CDNs/Cloudflare).
immutable Informs browser that the response body will never change during its lifetime. Prevents conditional validation checks on page refresh.
stale-while-revalidate=N Instructs the client to immediately return a cached stale response while asynchronously fetching fresh content in the background.

B. The Two Core Caching Architecture Strategies

Production web applications partition assets into two distinct caching categories:

HTTP Response Headers 
# STRATEGY 1: Static Hashed Assets (JS, CSS, Images with content hashes like app.a7b9c1.js)
# Safe to cache FOREVER because if code changes, the filename hash changes!
Cache-Control: public, max-age=31536000, immutable

# STRATEGY 2: Dynamic Entrypoint HTML (index.html, API endpoints)
# Must never be cached permanently; browser must re-check server on every navigation
Cache-Control: public, no-cache, must-revalidate
ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"

C. Conditional Validation with ETags (304 Not Modified)

When an asset with Cache-Control: no-cache or an expired max-age is requested, the client sends a conditional HTTP request with the If-None-Match header containing the cached ETag:

  1. Client sends: GET /index.html with If-None-Match: "33a64d..."
  2. Origin server checks its current content hash.
  3. If the hash matches, the server replies with HTTP/1.1 304 Not Modified with an empty response body (0 payload bytes transferred), saving bandwidth and completing in one fast network round-trip.
  4. If the hash differs, the server transmits HTTP/1.1 200 OK with the new body and new ETag.

A. Understanding Long Tasks and Main Thread Starvation

Any JavaScript execution task that occupies the browser main thread for more than 50 milliseconds is designated as a Long Task (flagged with a red triangle warning in DevTools).

When a Long Task runs, the browser event loop is completely paralyzed. User keystrokes, mouse clicks, scrolling gestures, and screen paints cannot be processed. If a user clicks during a 150ms Long Task, the click sits queued in the browser event queue, resulting in an unacceptably high INP score.

B. Breaking Up Long Tasks with scheduler.yield()

Heavy calculations should be broken into discrete chunks that yield control back to the browser event loop between iterations:

JavaScript (Yielding to Main Thread) 
// Modern task scheduling using scheduler.yield() with fallback to setTimeout
async function yieldToMain() {
  if ('scheduler' in window && 'yield' in window.scheduler) {
    return window.scheduler.yield();
  }
  // Fallback for older browsers: macro-task scheduled at end of current task
  return new Promise(resolve => setTimeout(resolve, 0));
}

// Processing a massive 50,000 item dataset without blocking INP
async function processLargeBatch(items) {
  let count = 0;
  for (const item of items) {
    heavyCalculation(item);
    count++;

    // Yield control back to browser every 50 items so paints and clicks can proceed
    if (count % 50 === 0) {
      await yieldToMain();
    }
  }
}

C. Avoiding Forced Synchronous Reflow (Layout Thrashing)

Layout (reflow) is normally batched lazily by the browser at the end of the frame. However, if your JavaScript writes to the DOM and then immediately reads geometric properties (such as offsetWidth, clientHeight, or getBoundingClientRect()), you trigger Forced Synchronous Reflow:

JavaScript (Layout Thrashing Anti-Pattern vs. Batched Fix) 
// ❌ ANTI-PATTERN: Layout Thrashing (Read/Write interleaved inside a loop)
// Causes N recalculate style & layout passes inside a single frame!
elements.forEach(el => {
  const currentHeight = el.offsetHeight; // READ (Forces immediate synchronous layout recalculation)
  el.style.height = `${currentHeight + 10}px`; // WRITE (Dirty invalidation)
});

// ✅ SOLUTION: Batch all Reads first, then batch all Writes
// Triggers exactly ONE layout pass!
const heights = elements.map(el => el.offsetHeight); // Batch READS
elements.forEach((el, index) => {
  el.style.height = `${heights[index] + 10}px`;       // Batch WRITES
});

Exercise 42.2

Building a Production HTTP Caching & Conditional ETag Engine in Express

Build an Express.js middleware configuration that establishes a bulletproof multi-tier caching strategy:

  • Static built assets located in /public/dist (generated with Vite content hashes) must be cached for 1 year with immutable.
  • Dynamic JSON API routes (e.g. /api/catalog) must support ETag generation and return 304 Not Modified with empty body when the client provides a matching If-None-Match header.
  • Sensitive user authentication endpoints (/api/user/profile) must strictly forbid all caching across both browsers and CDNs.
View Architectural Solution
JavaScript (Express Production Caching Architecture) 
import express from 'express';
import path from 'path';
import crypto from 'crypto';

const app = express();

// 1. TIER 1: Immutable Static Content (Vite Hashed Bundles)
// Express static handles maxAge and immutable natively
app.use('/static', express.static(path.join(__dirname, 'public/dist'), {
  maxAge: '1y',               // Cache-Control: max-age=31536000
  immutable: true,            // Cache-Control: ..., immutable
  etag: true,
  lastModified: true
}));

// 2. TIER 2: Sensitive Private Endpoints (Zero Caching)
app.use('/api/user', (req, res, next) => {
  res.setHeader('Cache-Control', 'no-store, no-cache, must-revalidate, private');
  res.setHeader('Pragma', 'no-cache');
  res.setHeader('Expires', '0');
  next();
});

// 3. TIER 3: Dynamic Data with Strong ETag & Conditional Revalidation
app.get('/api/catalog', async (req, res) => {
  const catalogData = await fetchProductCatalogFromDB();
  const serialized = JSON.stringify(catalogData);

  // Compute strong SHA-256 ETag hash
  const etag = `"${crypto.createHash('sha256').update(serialized).digest('hex')}"`;

  // Set revalidation cache-control
  res.setHeader('Cache-Control', 'public, no-cache, stale-while-revalidate=60');
  res.setHeader('ETag', etag);

  // Check conditional client header
  const clientEtag = req.headers['if-none-match'];
  if (clientEtag && clientEtag === etag) {
    // 304 Not Modified: zero body payload transferred over wire!
    return res.status(304).end();
  }

  res.setHeader('Content-Type', 'application/json');
  return res.status(200).send(serialized);
});

20 Comprehensive Web Performance Interview Questions & Answers

Q1 What are the three Core Web Vitals and what specific user experience dimensions do they measure? Beginner
Spoken Interview Answer

"The three Core Web Vitals are Largest Contentful Paint (LCP), Interaction to Next Paint (INP), and Cumulative Layout Shift (CLS). LCP measures perceived loading speed by recording when the largest visual viewport element renders—our target is under 2.5 seconds. INP measures interactivity responsiveness by tracking the latency of clicks, taps, and keypresses through to frame presentation—targeted under 200 milliseconds. CLS measures visual stability by calculating unexpected layout jumps—targeted under 0.1."

Q2 Why did Google replace First Input Delay (FID) with Interaction to Next Paint (INP) in 2024? Beginner
Spoken Interview Answer

"FID had a major blind spot: it only measured the input delay of the very first user interaction on the page, completely ignoring the JavaScript execution time and all subsequent user actions. In contrast, INP measures the complete end-to-end latency—input delay, event execution duration, and browser paint presentation—across all qualifying interactions throughout the entire session, reporting the worst-case interaction to reflect true user experience."

Q3 What is the difference between Lab Data and Field Data in web performance? Intermediate
Spoken Interview Answer

"Lab data is gathered in a synthetic, controlled environment like Lighthouse with fixed network and CPU throttling. It is reproducible and excellent for CI regression testing, but cannot measure real user interactions like INP. Field data, or Real User Monitoring (RUM), is captured from actual visitors across diverse real-world hardware, networks, and viewports. Google uses 28-day rolling field data from the CrUX dataset to determine search ranking factors."

Q4 How do you diagnose and optimize an underperforming Largest Contentful Paint (LCP)? Intermediate
Spoken Interview Answer

"I decompose LCP into its four sub-parts: Time to First Byte (TTFB), Resource Load Delay, Resource Load Duration, and Element Render Delay. If TTFB is slow, I optimize server response times and CDN edge caching. To fix Resource Load Delay, I remove `loading='lazy'` from the hero image and inject ``. To reduce Load Duration, I compress images into AVIF/WebP with responsive `srcset`. To eliminate Render Delay, I ensure the image isn't blocked by client-side hydration or heavy CSSOM cascades."

Q5 What causes Cumulative Layout Shift (CLS) and how do you prevent it? Intermediate
Spoken Interview Answer

"CLS is caused by visible elements shifting position between render frames. The most common causes are images or iframes lacking explicit width and height dimensions, dynamic ads or widgets injected into the DOM without reserved placeholder containers, and late-loading web fonts causing FOUT. I prevent CLS by defining `width`, `height`, or CSS `aspect-ratio` on all media, applying CSS `min-height` to dynamic containers, and using `font-display: swap` with size-adjusted fallback fonts."

Q6 Compare the script attributes: synchronous, async, and defer. Intermediate
Spoken Interview Answer

"A regular synchronous script halts HTML parsing while the script is downloaded and executed. An `async` script downloads in parallel with parsing and executes the moment download completes, interrupting HTML parsing and executing out-of-order. A `defer` script downloads in parallel but waits until HTML parsing is completely finished, executing strictly in document order right before `DOMContentLoaded`. `defer` is the standard for application scripts."

Q7 How does tree shaking work and why can't bundlers tree-shake CommonJS modules? Intermediate
Spoken Interview Answer

"Tree shaking uses static analysis on the ECMAScript Module AST to detect unused exports and eliminate them from the production bundle. It requires ESM's static `import` and `export` syntax at top-level scope. CommonJS uses `require()`, which is dynamic and can be called conditionally at runtime inside functions or `if` blocks. Because the bundler cannot prove what might be executed at runtime without running the code, it must safely include the entire CommonJS module."

Q8 What is a Long Task in browser runtime performance and how does it degrade INP? Advanced
Spoken Interview Answer

"A Long Task is any uninterrupted JavaScript execution occupying the browser main thread for longer than 50 milliseconds. Because JavaScript runs on a single-threaded event loop, a Long Task starves the main thread, preventing user input events (clicks, keypresses) from being processed. The user interaction sits queued until the Long Task completes, directly inflating the Input Delay phase and causing severe INP regressions."

Q9 How do you break up long-running JavaScript execution without starving the event loop? Advanced
Spoken Interview Answer

"I use task yielding. In modern browsers, `await scheduler.yield()` yields control back to the main thread while maintaining priority. In older browsers, scheduling a micro-chunk via `await new Promise(r => setTimeout(r, 0))` posts a macro-task to the event queue. This allows the browser to process queued user input clicks and perform display layout/paint updates between chunks. For CPU-bound operations like crypto or image parsing, I offload work entirely to Web Workers."

Q10 What is Forced Synchronous Reflow (Layout Thrashing) and how do you prevent it? Intermediate
Spoken Interview Answer

"Browsers normally batch DOM layout changes lazily. Forced Synchronous Reflow happens when JavaScript modifies the DOM (a write) and then immediately reads geometric properties like `offsetHeight` or `getBoundingClientRect()`. To return an accurate number, the browser is forced to flush pending styles and recalculate layout synchronously right in that microsecond. If done in a loop, it triggers layout thrashing. I fix this by batching all geometric reads first, then batching all style writes."

Q11 Explain the difference between Cache-Control: no-cache and Cache-Control: no-store. Intermediate
Spoken Interview Answer

"`no-store` instructs the browser and all intermediate caches to never store any version of the response under any circumstance—every request must re-fetch the complete body from origin. In contrast, `no-cache` allows the response to be stored in the cache, but mandates that the browser must validate freshness with the origin server (using ETags or Last-Modified) before serving it. If unchanged, the server returns a 304 with zero body transfer."

Q12 How does conditional HTTP validation work using ETags and If-None-Match? Intermediate
Spoken Interview Answer

"An ETag is an opaque content hash sent in the HTTP response header representing the entity state. On subsequent requests, the browser sends that hash back in the `If-None-Match` header. The server compares the client's hash against the current content hash. If they match, the server returns `304 Not Modified` with an empty body, saving network bandwidth and execution time. If different, it sends `200 OK` with the new body."

Q13 Why do production single-page applications use immutable caching for JS bundles but no-cache for index.html? Intermediate
Spoken Interview Answer

"Modern bundlers inject content hashes into asset filenames like `app.4f9a1c.js`. If the code never changes, the URL never changes, making it safe to cache for 1 year with `immutable`. However, `index.html` references those hashed script URLs. If `index.html` were cached aggressively, users would never receive updates when a new deployment occurs. Serving `index.html` with `no-cache` forces immediate validation on refresh to instantly serve updated script links."

Q14 What is the stale-while-revalidate HTTP directive and when is it preferred? Advanced
Spoken Interview Answer

"`stale-while-revalidate=N` instructs the client or CDN edge cache that if an asset is stale, it can immediately return the cached stale copy to the user with zero latency, while simultaneously triggering an asynchronous background revalidation request to the origin server. It provides instantaneous loading for users while ensuring the cache updates for the subsequent visit, making it ideal for catalog pages, search results, and avatar feeds."

Q15 What are the resource hints preconnect, dns-prefetch, preload, and prefetch? Beginner
Spoken Interview Answer

"`dns-prefetch` resolves third-party domain DNS early. `preconnect` goes further by performing DNS lookup, TCP handshake, and TLS negotiation in advance. `preload` forces high-priority download of a critical resource needed immediately on the current page (like hero images or critical fonts). `prefetch` downloads low-priority resources in background idle time that are expected to be needed on the next navigation."

Q18 What is Total Blocking Time (TBT) and how does it correlate with INP? Advanced
Spoken Interview Answer

"TBT is a synthetic lab metric measuring the total duration between FCP and Time to Interactive (TTI) where the main thread was blocked by tasks exceeding 50ms (summing the blocking portion of each task). While TBT is measured in the lab without user interaction, it strongly correlates with field INP because an application with high TBT has an overloaded main thread that will inevitably cause input delays when real users click."

Q19 How does fetchpriority="high" impact resource scheduling in Chromium engines? Advanced
Spoken Interview Answer

"By default, images have 'Low' network fetch priority in the browser resource scheduler until initial layout finishes. When you apply `fetchpriority='high'`, the browser elevates the image to 'High' priority alongside render-blocking CSS and early scripts. This allows the network stream to download the hero LCP image concurrently with early resources rather than waiting in the queue, shaving hundreds of milliseconds off LCP."

Q20 How do you track Core Web Vitals in production without impacting page performance? Advanced
Spoken Interview Answer

"I use the lightweight official `web-vitals` library (under 2KB) which hooks into browser `PerformanceObserver` APIs. To transmit metric telemetry to analytics without blocking user interaction or delaying page unloads, I send payloads via `navigator.sendBeacon()`, or `fetch()` with `keepalive: true`. This queues transmissions directly to the browser network stack asynchronously with zero main-thread overhead."
