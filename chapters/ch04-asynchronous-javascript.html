1. The Event Loop Architecture: Call Stack, Web APIs, and Queues

JavaScript is a single-threaded language: it has exactly one Call Stack and can execute only one instruction at any single instant in time. However, web browsers and Node.js are multithreaded host environments.

+---------------------+ +---------------------------------------+ | CALL STACK | | WEB APIS / LIBUV | | (Single-Threaded) | | (Multithreaded Background C++ Ops) | | | | | | [ functionC() ] | | - DOM Events (click, keydown) | | [ functionB() ] | | - Timers (setTimeout, setInterval) | | [ main() ] | | - Network requests (fetch, http) | +---------------------+ | - File System I/O (Node.js) | | +---------------------------------------+ | (Stack Empty) | v v +------------------------------------------------------------------------------------+ | EVENT LOOP | +------------------------------------------------------------------------------------+ ^ | | v +---------------------+ +---------------------------------------+ | MICROTASK QUEUE | | TASK (MACROTASK) QUEUE | | (High Priority) | | (Standard Priority) | | | | | | - Promise callbacks | | - setTimeout / setInterval | | - queueMicrotask() | | - setImmediate (Node.js) | | - process.nextTick | | - I/O events & Network callbacks | | (Node.js Top) | | - UI Rendering & PostMessage | +---------------------+ +---------------------------------------+
Figure 4.1: The Complete JavaScript Event Loop Runtime Architecture

The Golden Execution Loop Rule

The engine follows a strict, deterministic sequence on every cycle of the Event Loop:

  1. Execute Synchronous Code: Run the current script or function on the Call Stack until the stack is completely empty.
  2. Drain the ENTIRE Microtask Queue: If there are microtasks pending, dequeue and execute them one by one. If a microtask enqueues another microtask, that new microtask runs immediately in the same cycle! The engine will not touch macro tasks or paint pixels until the microtask queue is 100% drained.
  3. Render Viewport (Browser Only): If the browser window is scheduled for a screen refresh (usually every 16.6ms for 60Hz displays), run requestAnimationFrame callbacks and perform Style, Layout, and Paint.
  4. Execute Exactly ONE Macrotask: Dequeue and execute the oldest task from the Macrotask queue.
  5. Repeat: Return immediately to Step 2 to drain any new microtasks produced by that macrotask!
🚨 Microtask Starvation Warning

Because the microtask queue is drained completely before any macrotask or browser screen rendering can take place, infinitely chaining microtasks (e.g., function loop() { Promise.resolve().then(loop); }) will permanently starve the Event Loop, completely freezing the UI and locking up the thread!

2. Browser vs Node.js Event Loop Differences

While the browser follows the HTML5 event-loop specification, Node.js implements its event loop via the libuv C library. Libuv divides each event loop tick into 6 distinct phases:

Phase Queue Monitored Operations Executed
1. Timers Timer Heap Executes callbacks scheduled by expired setTimeout() and setInterval().
2. Pending Callbacks I/O Callback Queue Executes I/O callbacks deferred from previous loop iterations (e.g., system-level errors like TCP connection refused).
3. Idle, Prepare Internal Used internally by libuv for housekeeping.
4. Poll I/O Polling Retrieves new I/O events (incoming network connections, disk reads); blocks and waits for I/O if no timers are scheduled.
5. Check Check Queue Executes callbacks scheduled explicitly by setImmediate().
6. Close Callbacks Close Queue Executes close event handlers, e.g., socket.on('close', ...).

process.nextTick() vs setImmediate() in Node.js

  • process.nextTick(): Technically not part of the libuv event loop. It belongs to the Node.js internal microtask queue. It runs immediately after the current operation finishes, before the event loop advances to any next phase!
  • setImmediate(): Belongs to the Check phase of the libuv event loop. It is designed to run after I/O callbacks have completed in the Poll phase.
// Node.js Phase Comparison
setTimeout(() => console.log('1. setTimeout'), 0);
setImmediate(() => console.log('2. setImmediate'));
process.nextTick(() => console.log('3. process.nextTick'));
Promise.resolve().then(() => console.log('4. Promise.then'));

// Output in Node.js:
// 3. process.nextTick  (Highest priority microtask)
// 4. Promise.then      (Standard microtask)
// 1. setTimeout        (Timers phase)
// 2. setImmediate      (Check phase)

4. Promises and Promise Combinators

A Promise is an object representing the eventual completion (or failure) of an asynchronous operation. A promise exists in one of three mutually exclusive states:

  • Pending: Initial state, neither fulfilled nor rejected.
  • Fulfilled: Operation completed successfully (\(\to\) calls .then(onFulfilled)).
  • Rejected: Operation failed (\(\to\) calls .catch(onRejected)).

The 4 Promise Combinators Compared

When managing multiple concurrent asynchronous operations, modern JavaScript provides 4 static combinator methods on the Promise constructor:

Method Settlement Condition Short-Circuit Behavior Ideal Production Use Case
Promise.all() Waits for ALL promises to fulfill. Fails fast: Rejects immediately if any single promise rejects. Dependent parallel requests (e.g., fetch user profile, orders, and settings needed together for a dashboard).
Promise.allSettled() Waits for ALL promises to settle (fulfill or reject). Never rejects. Returns an array of objects: { status: 'fulfilled', value } or { status: 'rejected', reason }. Independent operations where partial success is acceptable (e.g., sending batch notification emails or uploading multi-file attachments).
Promise.race() Settles as soon as the FIRST promise settles (fulfills OR rejects). Resolves or rejects immediately with the outcome of the fastest promise. Implementing request timeouts (racing a network fetch against a timeout promise).
Promise.any() Resolves as soon as the FIRST promise fulfills. Ignores rejections unless every single promise rejects, in which case it rejects with an AggregateError. Querying redundant mirror servers, CDNs, or multiple cache replicas (fastest valid response wins). 
// Example: Implementing a Network Timeout with Promise.race
function fetchWithTimeout(url, timeoutMs = 5000) {
  const timeoutPromise = new Promise((_, reject) => {
    setTimeout(() => reject(new Error(`Request timed out after ${timeoutMs}ms`)), timeoutMs);
  });

  return Promise.race([fetch(url), timeoutPromise]);
}

5. Request Cancellation: Fetch and AbortController

Before the AbortController standard, once a network request or async operation was launched, there was no native way to cancel it at the socket level. AbortController provides a standardized signal mechanism to cancel operations. 

// Canceling a fetch request on user input change
let currentController = null;

async function handleSearch(query) {
  // Abort any pending previous in-flight search request!
  if (currentController) {
    currentController.abort("User typed a newer character");
  }

  currentController = new AbortController();
  const { signal } = currentController;

  try {
    const res = await fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal });
    const data = await res.json();
    renderSearchResults(data);
  } catch (err) {
    if (err.name === 'AbortError') {
      console.log('Previous search was aborted successfully:', err.message);
    } else {
      console.error('Real network failure:', err);
    }
  } finally {
    if (currentController.signal === signal) {
      currentController = null;
    }
  }
}

Modern Timeout Cancellation: AbortSignal.timeout()

In modern browsers and Node.js 18+, you no longer need manual setTimeout wrappers to implement request timeouts: 

// Built-in 3-second timeout signal
const response = await fetch("https://api.example.com/data", {
  signal: AbortSignal.timeout(3000)
});

6. Concurrency Limiting: The Async Pool Pattern

A common production disaster is firing Promise.all(urls.map(fetch)) across 1,000 URLs. This simultaneously opens 1,000 TCP sockets, exhausting file descriptors, triggering rate limits (429 Too Many Requests), or crashing the Node.js memory process.

We solve this by implementing a Concurrency Pool that limits simultaneous active tasks to a fixed maximum \(N\).

Interview Implementation: Build a Concurrency Pool (`p-limit`) Senior Architectural Pattern 
/**
 * Runs an array of task-generating functions with a concurrency limit.
 * @param {Array<() => Promise>} tasks
 * @param {number} limit
 * @returns {Promise>}
 */
async function asyncPool(tasks, limit = 3) {
  const results = [];
  const executing = new Set();

  for (let i = 0; i < tasks.length; i++) {
    const taskIndex = i;
    // Execute task and wrap it to capture its completion
    const promise = Promise.resolve().then(() => tasks[taskIndex]());
    
    // Store result at exact index
    const wrappedPromise = promise.then(result => {
      results[taskIndex] = result;
      executing.delete(wrappedPromise); // Free up worker slot
    });

    executing.add(wrappedPromise);

    // If active worker slots hit the limit, wait for the fastest to finish!
    if (executing.size >= limit) {
      await Promise.race(executing);
    }
  }

  // Wait for all remaining active tasks to drain
  await Promise.all(executing);
  return results;
}

// Verification:
const mockTask = (id, ms) => () => new Promise(res => {
  console.log(`[START] Task ${id}`);
  setTimeout(() => {
    console.log(`[DONE] Task ${id}`);
    res(`Result ${id}`);
  }, ms);
});

const taskList = [
  mockTask(1, 1000),
  mockTask(2, 500),
  mockTask(3, 300),
  mockTask(4, 800),
  mockTask(5, 200)
];

asyncPool(taskList, 2).then(results => {
  console.log("All tasks finished successfully:", results);
});

Interview Questions and Answers

20 high-yield interview questions testing your understanding of asynchronous execution, microtasks, Promise combinators, race conditions, and event loop internals.

Q1 What is the difference between synchronous and asynchronous code in JavaScript? Beginner
Spoken Interview Answer

"Synchronous code is blocking: each instruction executes sequentially, and subsequent lines must wait until the current operation finishes on the Call Stack. Asynchronous code is non-blocking: operations that take time (such as network requests, file reading, or timers) are delegated to the host environment (browser Web APIs or Node.js libuv), allowing the main JavaScript thread to continue executing remaining code immediately. When the async operation completes, its callback is scheduled onto a queue to be processed by the Event Loop."

Q2 What is the difference between a Task (Macrotask) and a Microtask? Name examples of each. Intermediate
Spoken Interview Answer

"The primary difference is priority and execution timing. When the Call Stack empties, the Event Loop will drain the ENTIRE Microtask queue before executing even a single Macrotask. Microtasks include Promise reactions (.then/.catch/.finally), queueMicrotask, MutationObserver, and process.nextTick in Node.js. Macrotasks include setTimeout, setInterval, setImmediate, I/O callbacks, and UI rendering."

Q3 Compare `Promise.all` and `Promise.allSettled`. When would you choose one over the other? Intermediate
Spoken Interview Answer

"`Promise.all` is fail-fast: if any promise in the array rejects, the returned promise immediately rejects with that error, discarding the results of the other promises. We choose it when operations are interdependent—such as loading the critical data needed to render a page. `Promise.allSettled` waits for all promises to finish regardless of success or failure, returning an array of settlement status objects. We choose it for independent batch operations where partial success is acceptable, such as sending bulk notification emails."

Q4 How does `async/await` work under the hood? What does an async function actually return? Advanced
Spoken Interview Answer

"`async/await` is syntactic sugar built on top of Generator functions and Promises. An `async` function always returns a Promise, wrapping non-promise return values via `Promise.resolve()`. When the engine encounters an `await` expression, it pauses execution of that specific async function, pushes the remainder of the function into the Microtask Queue as a promise `.then()` continuation, and frees up the Call Stack to continue executing external code."

Q5 What happens if you forget to `await` a Promise inside an async function or forget to catch a rejection? Intermediate
Spoken Interview Answer

"If you forget to `await`, the function continues executing synchronously, holding the raw pending Promise object instead of the resolved value. If a Promise rejects without a `.catch()` handler or `try/catch` block, an `UnhandledPromiseRejection` event is triggered. In modern Node.js versions, unhandled rejections terminate the Node process with a non-zero exit code, crashing your backend server!"

Q6 What is the difference between `process.nextTick()` and `setImmediate()` in Node.js? Advanced
Spoken Interview Answer

"`process.nextTick()` is a Node-specific microtask that executes immediately after the current operation finishes, before the event loop advances to ANY libuv phase. `setImmediate()` is a macrotask that executes specifically during the 'Check' phase of the libuv event loop, right after I/O polling completes. Despite its name, `process.nextTick()` fires earlier than `setImmediate()`."

Q7 What is the difference between `Promise.race()` and `Promise.any()`? Intermediate
Spoken Interview Answer

"`Promise.race()` resolves or rejects as soon as the FIRST promise settles, whether it succeeds or fails. `Promise.any()` resolves as soon as the FIRST promise FULFILLS; it completely ignores rejections until all input promises fail, in which case it rejects with an AggregateError containing all reasons. We use `Promise.race` for timeouts and `Promise.any` to fetch from redundant mirror endpoints."

Q8 Scenario: What does this code print? Explain why `setTimeout(..., 0)` does not execute immediately. Scenario 
console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");
Spoken Interview Answer

"Output is: A, C, B. `console.log('A')` runs synchronously. `setTimeout` delegates the timer to the host Web API, which immediately places callback B into the Macrotask Queue. Then `console.log('C')` runs synchronously. Even though the delay is 0ms, the callback cannot jump into the Call Stack until all synchronous code finishes and the Call Stack is completely clear."

Q9 What is the 4ms timer clamping rule in web browsers? Advanced
Spoken Interview Answer

"Under the HTML5 living standard, once a `setTimeout` nesting level reaches 5 or more (i.e. five recursive nested timeouts), the browser enforces a minimum clamping delay of 4 milliseconds, even if set to 0ms. Furthermore, modern browsers throttle timers down to 1000ms (1 second) or suspend them entirely when a tab is minimized or running in the background to preserve battery and CPU."

Q10 Scenario: You have a race condition where a slow user query finishes AFTER a faster newer query, overwriting the UI with stale data. How do you resolve this? Scenario
Spoken Interview Answer

"I solve this using an `AbortController`. When the user initiates a new query, I invoke `abort()` on the previous controller's signal, canceling the in-flight network request at the browser socket level so its response never reaches the application layer. Alternatively, I track a monotonically increasing request ID or timestamp, discarding any response whose ID is older than the latest dispatched request."

Q11 Why should you avoid `forEach` with async/await? What should you use instead? Intermediate
Spoken Interview Answer

"`Array.prototype.forEach` does not wait for promises returned by its callback. It fires all callbacks concurrently and returns immediately without awaiting them. If you want sequential execution, use a standard `for...of` loop with `await`. If you want parallel execution with awaiting, use `Promise.all(array.map(async fn))`." 

// BUG: Will NOT wait for items to process!
items.forEach(async item => {
  await saveToDb(item);
});
console.log('Done!'); // Logs BEFORE items are saved!

// FIX 1: Sequential Execution
for (const item of items) {
  await saveToDb(item);
}
console.log('All saved sequentially!');

// FIX 2: Parallel Execution
await Promise.all(items.map(item => saveToDb(item)));
console.log('All saved in parallel!');
Q12 How do you create an asynchronous sleep or delay utility in JavaScript? Advanced
Spoken Interview Answer

"By wrapping `setTimeout` inside a Promise: `const sleep = ms => new Promise(resolve => setTimeout(resolve, ms))`. In an async function, you can then pause execution non-blockingly via `await sleep(1000)`."

Q13 What is "Callback Hell" (Pyramid of Doom), and what two fundamental problems did Promises solve? Beginner
Spoken Interview Answer

"Callback Hell is deeply nested callback functions resulting from sequential async operations, causing illegible pyramid-shaped code and painful error handling. Promises solved two critical issues: 1. Inversion of Control (instead of passing control of your callback to a third-party library, the function returns a promise you control), and 2. Composable Error Propagation (errors bubble down the promise chain to a centralized `.catch()` block)."

Q14 What is the difference between `queueMicrotask(fn)` and `Promise.resolve().then(fn)`? Advanced
Spoken Interview Answer

"Both schedule a callback on the Microtask Queue. However, `queueMicrotask` is a dedicated, standardized API that does not allocate a Promise object in the heap, making it slightly more performant and cleaner when you don't need promise chaining or error capture. If an exception is thrown inside `queueMicrotask`, it is reported as an uncaught exception rather than an unhandled promise rejection."

Q15 Scenario: Your service needs to retry a failing external HTTP API call up to 3 times with exponential backoff and jitter. How do you implement this? Scenario
Spoken Interview Answer

"I implement an async retry loop. If the call fails, I calculate a delay using formula `baseDelay * (2 ** attempt) + randomJitter`. The jitter randomizes the delay to prevent a thundering herd where all retrying clients hit the recovering server at the exact same millisecond. I await a sleep promise for the delay and retry until attempts are exhausted." 

async function retryWithBackoff(fn, retries = 3, baseDelay = 500) {
  for (let attempt = 0; attempt <= retries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === retries) throw err;
      // Exponential backoff + full jitter
      const expDelay = baseDelay * (2 ** attempt);
      const jitter = Math.random() * expDelay;
      const totalDelay = expDelay + jitter;
      console.warn(`Attempt ${attempt + 1} failed. Retrying in ${Math.round(totalDelay)}ms...`);
      await new Promise(r => setTimeout(r, totalDelay));
    }
  }
}
Q16 Can a Promise change its state from fulfilled to rejected or vice versa? Intermediate
Spoken Interview Answer

"No. A Promise is an immutable state machine. Once it transitions from Pending to either Fulfilled or Rejected, it is permanently 'settled'. Any subsequent calls to `resolve()` or `reject()` within the executor are silently ignored."

Q17 What is Backpressure in Node.js streams and how does it prevent memory exhaustion? Advanced
Spoken Interview Answer

"Backpressure occurs when data is read from a source faster than the destination can write it (e.g., reading a 10GB file from disk and streaming it over a slow 3G network socket). If unchecked, unwritten chunks buffer in memory, crashing the Node process with Out-Of-Memory. When the destination buffer hits its `highWaterMark`, `writable.write()` returns false, signaling the readable stream to pause until the `drain` event fires."

Q18 What is the return value of a `.then()` callback if you don't return anything? Beginner
Spoken Interview Answer

"In JavaScript, functions without an explicit return statement return `undefined`. Therefore, if a `.then()` callback does not return a value, it resolves the next chained promise with `undefined`. If it returns a primitive or object, it wraps it in `Promise.resolve(val)`. If it returns a promise, the next `.then()` waits for that returned promise to settle."

Q19 Scenario: What is the output of this code snippet involving Promise chaining? Scenario 
Promise.resolve(1)
  .then(x => x + 1)
  .then(x => { throw new Error('Boom'); })
  .catch(err => 10)
  .then(x => x + 5)
  .then(console.log);
Spoken Interview Answer

"Output is: 15. The first then transforms 1 to 2. The second then throws an Error, skipping subsequent then handlers and jumping to the nearest `.catch()`. The `.catch()` catches the error and returns 10, effectively recovering the chain and returning a fulfilled promise with value 10. The next then receives 10, adds 5, and logs 15."

Q20 Explain the Node.js `EventEmitter` pattern. What happens if an 'error' event is emitted without a listener? Advanced
Spoken Interview Answer

"`EventEmitter` is an implementation of the Observer pattern in Node.js, providing `.on(event, listener)` to subscribe and `.emit(event, ...args)` to publish events synchronously to all registered callbacks. Uniquely, if an EventEmitter emits an 'error' event and NO listener has been attached to 'error', Node.js treats it as an uncaught exception, prints the stack trace, and immediately terminates the Node process!"
