1. REST Foundations & Architectural Constraints

Representational State Transfer (REST) is an architectural style formulated by Roy Fielding in his 2000 doctoral dissertation. Unlike SOAP or gRPC, REST is not a rigid protocol or standard; it is a set of design constraints intended to induce scalability, loose coupling, visibility, reliability, and simplicity across distributed hypermedia systems.

Constraint Architectural Mechanism Engineering Benefit
1. Client-Server Separation UI concerns are strictly separated from data storage and business logic across well-defined interfaces. Allows frontend clients (React SPA, mobile apps, CLI) to evolve independently of the backend database or OS.
2. Statelessness Every client request contains all context needed to process it. No session state is retained on the server across requests. Enables effortless horizontal scaling across cloud nodes without sticky sessions or centralized session synchronization.
3. Cacheability Responses must explicitly declare themselves cacheable or non-cacheable via HTTP headers (Cache-Control, ETag). Eliminates redundant network round-trips, reduces backend load, and decreases client-perceived latency.
4. Layered System A client cannot ordinarily determine whether it is connected directly to the origin server or to an intermediary proxy, CDN, or load balancer. Enables transparent addition of reverse proxies (Nginx), security firewalls (Cloudflare), and caching layers.
5. Uniform Interface Standardized interaction: identification of resources via URIs, manipulation of resources through representations, self-descriptive messages, and hypermedia (HATEOAS). Decouples the client from server implementation details; enables universal tooling (browsers, cURL, Postman).
6. Code on Demand (Optional) Servers can extend client functionality by transferring executable code (e.g., compiled WebAssembly or JavaScript applets). Reduces pre-installed client dependencies, though rarely utilized in pure backend REST APIs.
⚠️ The Industry Reality: Pragmatic REST vs Pure REST

In technical interviews, acknowledge that 99% of modern "REST APIs" (including GitHub, Stripe, and Twilio) are actually Pragmatic HTTP APIs (Richardson Level 2). They utilize JSON over HTTP, semantic verbs, and resource-oriented URIs, but intentionally omit HATEOAS hypermedia links because client-side state engines and mobile SDKs prefer static, typed contracts (like TypeScript types generated from OpenAPI) over dynamic link discovery.

2. The Richardson Maturity Model

Developed by Leonard Richardson and popularized by Martin Fowler, this model grades the degree to which an API embraces the core elements of the REST architectural style.

ASCII Diagram: Richardson Maturity Model Levels 
+-------------------------------------------------------------------------+
| Level 3: Hypermedia Controls (HATEOAS)                                 |
|          Responses include navigational links guiding client workflow   |
|          e.g., "_links": { "pay": { "href": "/orders/102/payments" } }  |
+-------------------------------------------------------------------------+
                                    ^
+-------------------------------------------------------------------------+
| Level 2: HTTP Verbs & Status Codes                                      |
|          Uses GET, POST, PUT, PATCH, DELETE + 200, 201, 204, 404, 409   |
|          Distinguishes safe vs idempotent actions accurately            |
+-------------------------------------------------------------------------+
                                    ^
+-------------------------------------------------------------------------+
| Level 1: Resources (Individual URIs)                                   |
|          Multiple endpoints: /users, /orders/42, /products              |
|          Still frequently uses POST for everything                      |
+-------------------------------------------------------------------------+
                                    ^
+-------------------------------------------------------------------------+
| Level 0: The Swamp of POX (Plain Old XML / RPC)                         |
|          Single endpoint (e.g., /api/service), POST-only,               |
|          Action & arguments hidden inside request payload body          |
+-------------------------------------------------------------------------+

Deconstructing the Levels

  • Level 0 (The Swamp of POX): Utilizes HTTP solely as a transport tunnel. All requests are routed to a single endpoint (e.g., POST /api/endpoint) with the action name specified in the payload (like XML-RPC, SOAP, or JSON-RPC). HTTP headers, methods, and status codes are ignored (always returning 200 OK with an internal error code).
  • Level 1 (Resources): Replaces the monolithic endpoint with discrete resource URIs (e.g., /api/orders, /api/orders/501). However, operations often still abuse POST (e.g., POST /api/orders/501/delete).
  • Level 2 (HTTP Verbs & Status Codes): Aligns HTTP methods strictly to actions (GET for retrieval, POST for creation, DELETE for removal) and maps execution outcomes to official HTTP status codes (201 Created, 404 Not Found, 409 Conflict). Most production cloud APIs reside here.
  • Level 3 (Hypermedia Controls / HATEOAS): Hypermedia As The Engine Of Application State. API responses include dynamic hypermedia links indicating permissible subsequent state transitions. The client requires zero hardcoded URL routes; it navigates the API purely by discovering links embedded in returned resources.

3. HTTP Methods: Safety, Idempotency & Status Code Taxonomy

Two foundational properties define HTTP method semantics in RFC 9110: Safety and Idempotency.

HTTP Verb Safe? Idempotent? Primary Use Case & Expected Response
GET ✅ Yes ✅ Yes Read-only resource retrieval. Must never alter server state. Returns 200 OK or 404 Not Found.
HEAD ✅ Yes ✅ Yes Identical to GET but returns headers only (no response body). Used to check file size (Content-Length) or freshness (Last-Modified).
OPTIONS ✅ Yes ✅ Yes Queries communication options and CORS preflight allowances (Allow: GET, POST, OPTIONS).
POST ❌ No ❌ No Creates a subordinate resource or triggers arbitrary server execution. Calling \(N\) times creates \(N\) resources. Returns 201 Created with Location header.
PUT ❌ No ✅ Yes Complete replacement of the target resource with the uploaded payload, or creation at a known URI. Calling \(N\) times results in identical state. Returns 200 OK or 204 No Content.
PATCH ❌ No ⚠️ Not necessarily Applies partial modifications to a resource (e.g., updating a user's phone number). Usually implemented as idempotent, but not guaranteed by RFC 5789 (e.g., JSON Patch operations like {"op": "increment", "value": 5}).
DELETE ❌ No ✅ Yes Removes the identified resource. Subsequent calls return 204 No Content or 404 Not Found, but final server state remains identical.
💡 The Core Difference Between Safe and Idempotent

An operation is Safe if it creates zero side effects on the server (it only reads data). An operation is Idempotent if executing it multiple identical times produces the exact same side-effect and end server state as executing it once. All safe methods are naturally idempotent, but not all idempotent methods are safe (e.g., DELETE mutates state, but deleting a user 5 times leaves the user deleted).

Critical Status Codes for Full-Stack Interviews

  • 200 OK: Standard success with response payload.
  • 201 Created: Resource created successfully. Must include a Location: /api/v1/orders/789 header pointing to the new resource.
  • 202 Accepted: Request accepted for asynchronous processing (e.g., video transcoding or batch queue), but processing is not yet complete.
  • 204 No Content: Action succeeded, but response intentionally has zero body bytes (standard for DELETE or PUT).
  • 301 Moved Permanently vs 302 Found: 301 is aggressively cached by browsers and search engines; 302 is temporary redirect without caching.
  • 304 Not Modified: Conditional GET cache validation (matching If-None-Match ETag). Payload body is omitted to save bandwidth.
  • 400 Bad Request: Malformed request syntax or unparseable JSON body.
  • 401 Unauthorized: Missing, invalid, or expired authentication credentials (literally means Unauthenticated).
  • 403 Forbidden: Authenticated identity lacks permission/privilege to access the target resource (Authorization failure).
  • 404 Not Found: Target URI does not exist (or concealed intentionally for security).
  • 409 Conflict: Business rule or database constraint violation (e.g., unique email collision, concurrent edit version clash).
  • 422 Unprocessable Content: Syntactically valid JSON body that fails semantic schema validation (e.g., negative price, invalid email format).
  • 429 Too Many Requests: Rate limit exceeded. Should return Retry-After: 60 header.
  • 500 Internal Server Error: Uncaught backend exception or fatal crash.
  • 502 Bad Gateway: Reverse proxy (Nginx) received an invalid or dropped response from upstream Node.js application.
  • 503 Service Unavailable: Backend server is temporarily overloaded or undergoing maintenance.
  • 504 Gateway Timeout: Reverse proxy timed out waiting for upstream application server to reply.

4. Standardized Error Contracts: RFC 7807 (Problem Details)

A common anti-pattern in amateur APIs is returning ad-hoc error structures (sometimes { "error": "msg" }, sometimes { "message": "msg" }, or worse, { "status": "fail", "data": null } with a 200 OK status code).

The Internet Engineering Task Force (IETF) standardized HTTP API error responses in RFC 7807 (Problem Details for HTTP APIs) using the media type application/problem+json.

JSON: RFC 7807 Standard Error Envelope 
{
  "type": "https://api.myapp.com/errors/validation-failed",
  "title": "Validation Failed",
  "status": 422,
  "detail": "Your request parameters failed semantic validation checks.",
  "instance": "/api/v1/orders/draft-884",
  "invalidParams": [
    {
      "name": "quantity",
      "reason": "Quantity must be a positive integer between 1 and 100."
    },
    {
      "name": "paymentMethodId",
      "reason": "Payment method 'pm_expired' has expired."
    }
  ]
}

Production Express RFC 7807 Error Handler

TypeScript: Express RFC 7807 Centralized Middleware 
import { Request, Response, NextFunction } from 'express';

export interface AppErrorOptions {
  type: string;
  title: string;
  status: number;
  detail: string;
  invalidParams?: Array<{ name: string; reason: string }>;
}

export class AppError extends Error {
  public readonly type: string;
  public readonly title: string;
  public readonly status: number;
  public readonly detail: string;
  public readonly invalidParams?: Array<{ name: string; reason: string }>;

  constructor(opts: AppErrorOptions) {
    super(opts.detail);
    this.type = opts.type;
    this.title = opts.title;
    this.status = opts.status;
    this.detail = opts.detail;
    this.invalidParams = opts.invalidParams;
    Object.setPrototypeOf(this, new.target.prototype);
  }
}

// Global Error Handler Middleware
export function rfc7807ErrorHandler(
  err: Error,
  req: Request,
  res: Response,
  next: NextFunction
): void {
  // Set RFC 7807 content type
  res.setHeader('Content-Type', 'application/problem+json');

  if (err instanceof AppError) {
    res.status(err.status).json({
      type: err.type,
      title: err.title,
      status: err.status,
      detail: err.detail,
      instance: req.originalUrl,
      ...(err.invalidParams ? { invalidParams: err.invalidParams } : {})
    });
    return;
  }

  // Handle unexpected internal server crashes
  const isDev = process.env.NODE_ENV !== 'production';
  res.status(500).json({
    type: 'https://api.myapp.com/errors/internal-server-error',
    title: 'Internal Server Error',
    status: 500,
    detail: isDev ? err.message : 'An unexpected internal fault occurred.',
    instance: req.originalUrl,
    ...(isDev ? { stack: err.stack } : {})
  });
}

5. Idempotency in Non-Idempotent Operations: The Idempotency-Key Pattern

In distributed networks, communication over HTTP is fundamentally unreliable. When a client sends a POST /api/v1/payments request to charge $100, the server might successfully charge the user's card in its database, but the network connection may drop before the 200 OK response reaches the client.

If the client blindly retries the POST request, the user gets double-charged. The industry standard solution pioneered by Stripe and standardized by the IETF is the Idempotency-Key header.

ASCII Diagram: Distributed Idempotency Key Workflow 
Client                         Express Backend                     Redis Cache
  |                                   |                                |
  |-- POST /charge (Key: "abc-123") ->|                                |
  |                                   |-- SET "idem:abc-123" "LOCKED" ->| (Lock acquired)
  |                                   |   NX EX 120                    |
  |                                   |<--------- OK ------------------|
  |                                   |                                |
  |                                   |-- Execute Payment in DB...     |
  |                                   |-- Cache Response in Redis ----->| Store status & body
  |                                   |   SET "idem:abc-123"           | TTL 24 hours
  |<-- 201 Created { id: "ch_99" } ---|                                |
  |                                   |                                |
  | (Network drops or Client retries) |                                |
  |-- POST /charge (Key: "abc-123") ->|                                |
  |                                   |-- GET "idem:abc-123" ---------->|
  |                                   |<-- Return Cached Response -----| (Cache Hit)
  |                                   |                                |
  |<-- 201 Created { id: "ch_99" } ---| (Exact cached response replayed! Zero DB duplicate charge)
  |                                   |                                |

Production Redis Idempotency Middleware

TypeScript: Production Idempotency Middleware 
import { Request, Response, NextFunction } from 'express';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL || 'redis://localhost:6379');

export function idempotencyMiddleware(ttlSeconds = 86400) {
  return async (req: Request, res: Response, next: NextFunction): Promise<void> => {
    // Idempotency keys only apply to state-mutating requests (POST, PATCH)
    if (req.method !== 'POST' && req.method !== 'PATCH') {
      return next();
    }

    const idempotencyKey = req.header('Idempotency-Key');
    if (!idempotencyKey) {
      return next(); // Or return 400 if strictly required
    }

    const redisKey = `idempotency:${idempotencyKey}`;

    try {
      // 1. Check if we already processed this exact key
      const cached = await redis.get(redisKey);
      if (cached) {
        if (cached === 'IN_PROGRESS') {
          res.status(409).json({
            type: 'https://api.myapp.com/errors/concurrent-request',
            title: 'Conflict',
            status: 409,
            detail: 'A request with this Idempotency-Key is currently being processed.'
          });
          return;
        }

        // Return exact saved response
        const { status, headers, body } = JSON.parse(cached);
        res.set(headers);
        res.setHeader('Idempotent-Replayed', 'true');
        res.status(status).send(body);
        return;
      }

      // 2. Acquire atomic distributed lock (expires in 2 minutes to prevent stuck locks)
      const acquired = await redis.set(redisKey, 'IN_PROGRESS', 'EX', 120, 'NX');
      if (!acquired) {
        res.status(409).json({
          title: 'Concurrent Request In-Flight',
          status: 409,
          detail: 'Simultaneous request detected with the same Idempotency-Key.'
        });
        return;
      }

      // 3. Intercept res.send to cache response upon completion
      const originalSend = res.send.bind(res);
      res.send = (body: any): Response => {
        // Cache only successful completions (2xx status codes)
        if (res.statusCode >= 200 && res.statusCode < 300) {
          const payload = {
            status: res.statusCode,
            headers: { 'content-type': res.get('content-type') },
            body: typeof body === 'string' ? body : JSON.stringify(body)
          };
          redis.set(redisKey, JSON.stringify(payload), 'EX', ttlSeconds).catch(console.error);
        } else {
          // If request failed, release lock so client can retry with same key
          redis.del(redisKey).catch(console.error);
        }
        return originalSend(body);
      };

      next();
    } catch (err) {
      next(err);
    }
  };
}

6. Pagination Strategies: Offset vs. Keyset Cursor

APIs must never return unbounded collections. There are two primary architectural patterns for paginating data:

Criterion Offset / Limit Pagination Keyset / Cursor Pagination
Query Mechanism SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000; SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;
Time Complexity \(\mathcal{O}(N)\): Database must read, parse, and discard all 100,000 skipped rows before returning 20. \(\mathcal{O}(\log N)\): Database performs a direct B-Tree index seek to id = 100000 and reads 20 rows.
Offset Drift Hazard High: If a record is inserted on page 1 while the user is reading page 2, all items shift down, causing duplicate rows or missing rows. Zero: Cursors anchor to a fixed immutable record identity. Concurrent writes do not shift the cursor pointer.
Jump to Arbitrary Page Easy (User can click "Go to Page 45"). Impossible (Client can only navigate forward or backward via opaque cursor tokens).
Best Fit Internal admin dashboards with tiny datasets (<10k rows) and random page hopping. High-volume public APIs, mobile infinite feeds, real-time event streams (Twitter, Slack, Stripe).

Cursor Pagination Contract & Implementation

In a production cursor API, the cursor should be an opaque, Base64-encoded string representing the composite sorting columns (e.g., created_at and id for tie-breaking).

TypeScript: Production Keyset Cursor Query & Envelope 
import { Request, Response } from 'express';
import { pool } from '../db';

interface CursorData {
  createdAt: string;
  id: string;
}

function encodeCursor(data: CursorData): string {
  return Buffer.from(JSON.stringify(data)).toString('base64url');
}

function decodeCursor(cursor: string): CursorData {
  const json = Buffer.from(cursor, 'base64url').toString('utf8');
  return JSON.parse(json);
}

export async function getOrders(req: Request, res: Response): Promise<void> {
  const limit = Math.min(Math.max(parseInt(req.query.limit as string) || 20, 1), 100);
  const cursorParam = req.query.cursor as string | undefined;

  let query: string;
  let params: any[];

  if (cursorParam) {
    const { createdAt, id } = decodeCursor(cursorParam);
    // Composite Keyset filtering with deterministic tie-breaking on id
    query = `
      SELECT id, user_id, amount, created_at
      FROM orders
      WHERE (created_at, id) < ($1, $2)
      ORDER BY created_at DESC, id DESC
      LIMIT $3;
    `;
    params = [createdAt, id, limit + 1]; // Request limit + 1 to detect hasMore
  } else {
    query = `
      SELECT id, user_id, amount, created_at
      FROM orders
      ORDER BY created_at DESC, id DESC
      LIMIT $1;
    `;
    params = [limit + 1];
  }

  const { rows } = await pool.query(query, params);
  const hasMore = rows.length > limit;
  const items = hasMore ? rows.slice(0, limit) : rows;

  const nextCursor = hasMore && items.length > 0
    ? encodeCursor({
        createdAt: items[items.length - 1].created_at.toISOString(),
        id: items[items.length - 1].id
      })
    : null;

  res.json({
    data: items,
    pagination: {
      limit,
      hasMore,
      nextCursor
    }
  });
}

7. API Versioning Strategies

APIs inevitably evolve. Breaking changes (removing a field, altering a data type, changing authentication requirements) must never break existing client applications in production.

Strategy Example Pattern Trade-Offs & Analysis
URI Path Versioning (Most Common) GET /api/v1/users
GET /api/v2/users		 Pros: Highly visible, easy to test in browser/cURL, zero proxy caching issues.
Cons: Violates pure REST principle that a URI identifies a resource, not its schema version. Code duplication across route trees.
Custom Header Versioning X-API-Version: 2026-10-01 Pros: Keeps URIs pristine and uniform across versions.
Cons: Requires custom client header configuration; CDNs and reverse proxies must include header in cache key (Vary: X-API-Version) or risk serving wrong version.
Accept Header Content Negotiation Accept: application/vnd.company.v2+json Pros: The strictest alignment with Fielding's REST constraints. Version is treated as media representation.
Cons: High client complexity. Awkward to test manually; CDN caching requires strict Vary: Accept headers.
Query Parameter Versioning GET /api/users?version=2 Pros: Easy to specify conditionally or default to v1.
Cons: Intermingles resource filtering/query params with architectural version routing; generally discouraged.

9. Webhook Architectures & Cryptographic Signatures

A Webhook is an inverted API pattern (often called a "Reverse API"): rather than a client polling an API server for updates, the server proactively issues an HTTP POST request to a client-configured destination URL upon domain event occurrences (e.g., invoice.paid, order.shipped).

TypeScript: Production Webhook Verification Handler 
import crypto from 'crypto';
import { Request, Response } from 'express';

export function verifyWebhookSignature(
  rawBody: Buffer,
  signatureHeader: string | undefined,
  secret: string,
  toleranceSeconds = 300
): boolean {
  if (!signatureHeader) return false;

  // Header format: t=1700000000,v1=abcdef123456...
  const parts = signatureHeader.split(',').reduce((acc, part) => {
    const [k, v] = part.split('=');
    acc[k.trim()] = v.trim();
    return acc;
  }, {} as Record<string, string>);

  const timestamp = parseInt(parts.t, 10);
  const signature = parts.v1;

  if (isNaN(timestamp) || !signature) return false;

  // Replay Attack Defense: Reject signatures older than tolerance window
  const now = Math.floor(Date.now() / 1000);
  if (Math.abs(now - timestamp) > toleranceSeconds) {
    return false;
  }

  // Reconstruct signed payload
  const signedPayload = `${timestamp}.${rawBody.toString('utf8')}`;
  const expectedSignature = crypto
    .createHmac('sha256', secret)
    .update(signedPayload)
    .digest('hex');

  // Timing-safe comparison to prevent side-channel timing attacks
  const sigBuffer = Buffer.from(signature, 'hex');
  const expectedBuffer = Buffer.from(expectedSignature, 'hex');

  if (sigBuffer.length !== expectedBuffer.length) return false;
  return crypto.timingSafeEqual(sigBuffer, expectedBuffer);
}

// Express Endpoint (Requires express.raw({ type: 'application/json' }))
export function handleWebhook(req: Request, res: Response): void {
  const secret = process.env.WEBHOOK_SECRET!;
  const sigHeader = req.headers['x-webhook-signature'] as string;

  const isValid = verifyWebhookSignature(req.body, sigHeader, secret);
  if (!isValid) {
    res.status(401).send('Invalid signature');
    return;
  }

  const event = JSON.parse(req.body.toString('utf8'));

TypeScript Solution 
import { z } from 'zod';

const CursorPayloadSchema = z.object({
  createdAt: z.string().datetime(),
  id: z.string().uuid()
});

export type ValidCursor = z.infer<typeof CursorPayloadSchema>;

export function safeDecodeCursor(cursor: string | undefined): ValidCursor | null {
  if (!cursor || typeof cursor !== 'string') return null;

  try {
    const rawJson = Buffer.from(cursor, 'base64url').toString('utf8');
    const parsed = JSON.parse(rawJson);
    const result = CursorPayloadSchema.safeParse(parsed);
    return result.success ? result.data : null;
  } catch {
    // Return null if malformed Base64 or non-JSON
    return null;
  }
}

Q01 What is the difference between a Safe and an Idempotent HTTP method? Beginner
Spoken Interview Answer

"A Safe HTTP method produces zero state mutations or side effects on the server; it only retrieves representations—like GET and HEAD. An Idempotent method can mutate server state, but executing it \(N\) identical times produces the exact same end state as executing it once. For example, DELETE is idempotent because removing resource #10 multiple times leaves it removed, but it is not safe because the first execution alters database state."

Q02 What is the difference between PUT and PATCH? Beginner
Spoken Interview Answer

"PUT is defined as a complete replacement of the target resource. If an entity has ten fields and the client submits a PUT payload containing only two fields, the remaining eight fields should be overwritten or reset to defaults. PATCH, defined in RFC 5789, applies partial modifications, altering only the attributes specified in the payload while preserving existing unmentioned fields."

Q03 When should an API return 401 Unauthorized vs 403 Forbidden? Beginner
Spoken Interview Answer

"401 Unauthorized represents an Authentication failure: the client has not provided valid identity credentials, or the token is expired. 403 Forbidden represents an Authorization failure: the server knows exactly who the client is, but that authenticated identity lacks sufficient permissions or role privileges to perform the requested operation on that resource."

Q04 What does the 204 No Content status code indicate? Beginner
Spoken Interview Answer

"204 No Content indicates that the server successfully fulfilled the request, but intentionally returns an empty response body. It is standard for DELETE operations or updates where the client already has full state and transmitting redundant JSON back across the wire would waste network bandwidth."

Q05 What is the purpose of the 201 Created status code and what header should accompany it? Beginner
Spoken Interview Answer

"201 Created signifies that a new resource was successfully instantiated as a result of the request. According to HTTP standards, it should be accompanied by a `Location` header containing the absolute or relative URI pointing directly to the newly created resource, such as `Location: /api/v1/users/892`."

Q06 What is the Richardson Maturity Model and what characterizes Level 2 vs Level 3? Intermediate
Spoken Interview Answer

"The Richardson Maturity Model grades API maturity across four tiers (0 through 3). Level 2 uses discrete resource URIs combined with standard HTTP verbs (GET, POST, PUT, DELETE) and semantic status codes; this is where most production APIs operate. Level 3 introduces HATEOAS, where responses contain hypermedia links instructing the client which actions and state transitions are valid next."

Q07 What is RFC 7807 (Problem Details for HTTP APIs) and why is it preferred over custom error formats? Intermediate
Spoken Interview Answer

"RFC 7807 defines a standardized JSON structure (`application/problem+json`) for HTTP error payloads with five standard attributes: `type`, `title`, `status`, `detail`, and `instance`. It eliminates proprietary, ad-hoc error formats across microservices, allowing client SDKs, API gateways, and monitoring tools to parse error metadata consistently."

Q08 Why does OFFSET pagination degrade in performance at scale, and what is the 'Offset Drift' problem? Intermediate
Spoken Interview Answer

"`OFFSET N` forces the database engine to perform an O(N) scan: to return 20 rows at `OFFSET 100000`, PostgreSQL must fetch and discard the preceding 100,000 index entries. Furthermore, Offset Drift occurs when new records are inserted while a user navigates between pages, causing existing items to shift forward and appear duplicated on subsequent pages."

Q09 How does Keyset (Cursor) Pagination work and what are its trade-offs? Intermediate
Spoken Interview Answer

"Keyset pagination anchors to the values of an indexed sort column from the last visible record, querying `WHERE (created_at, id) < (cursor_date, cursor_id) ORDER BY created_at DESC LIMIT 20`. This executes in O(log N) index seek time and completely eliminates page drift. The trade-off is that clients cannot jump to arbitrary page numbers; they can only traverse forward and backward."

Q10 How do you implement an Idempotency-Key pattern in a distributed Node.js/Express environment? Intermediate
Spoken Interview Answer

"The client passes a unique UUID in the `Idempotency-Key` header. The server attempts an atomic Redis lock (`SET key 'IN_PROGRESS' NX EX 120`). If the key already exists with status 'COMPLETED', the server immediately replays the cached status code, headers, and body without re-executing business logic. If lock acquisition fails because a request is in-flight, it returns 409 Conflict."

Q11 Compare URI Path versioning vs Custom Header versioning vs Accept Header content negotiation. Intermediate
Spoken Interview Answer

"URI Path versioning (`/v1/orders`) is the most practical and visible, caching cleanly across CDNs without header dependencies. Custom Headers (`X-API-Version: 2`) keep URIs clean but require downstream proxies to configure `Vary: X-API-Version`. Accept Header versioning (`Accept: application/vnd.company.v2+json`) aligns with pure REST principles, but increases client implementation complexity."

Q12 When is a 409 Conflict status code appropriate vs a 422 Unprocessable Content? Intermediate
Spoken Interview Answer

"Use 422 Unprocessable Content when the request JSON is syntactically valid but fails business field constraints (e.g., negative price, invalid postal code). Use 409 Conflict when the request violates the current state of server resources—such as an email already taken in the database or an optimistic concurrency lock version mismatch."

Q13 What is the purpose of the 202 Accepted status code and how should clients poll for completion? Intermediate
Spoken Interview Answer

"202 Accepted signifies that the request was valid and queued for asynchronous execution, but processing is not yet complete. The response should provide a `Location` header pointing to a status polling endpoint (e.g., `Location: /api/v1/jobs/456`), optionally returning a `Retry-After: 10` header indicating when the client should poll next."

Q14 What is Contract-First vs Code-First API development with OpenAPI? Intermediate
Spoken Interview Answer

"Contract-First writes the OpenAPI specification upfront before coding, enabling frontend and backend teams to mock endpoints and write tests in parallel. Code-First writes route handlers and derives OpenAPI specs via annotations or runtime schemas (like Zod). Contract-First prevents breaking API changes, while Code-First reduces spec maintenance friction."

Q15 How do you prevent Webhook Replay Attacks and verify authenticity using HMAC SHA-256? Advanced
Spoken Interview Answer

"The sender signs `timestamp + '.' + rawBody` using HMAC SHA-256 with a shared secret and transmits it in a header (`X-Signature: t=..., v1=...`). The receiver first checks if the timestamp is within a 5-minute tolerance window to prevent replay attacks, then recomputes the HMAC on the raw buffer and verifies using `crypto.timingSafeEqual` to avoid timing side-channel attacks."

Q16 Why must raw request body buffers be used when verifying webhook HMAC signatures in Express? Advanced
Spoken Interview Answer

"Because standard JSON parsers (`express.json()`) re-serialize objects, altering whitespace, key ordering, or Unicode characters. Any single byte discrepancy between the sender's original transmission and the re-serialized JSON alters the SHA-256 digest completely. Verification requires the exact unmodified raw byte buffer captured via `express.raw()`."

Q17 How should outbound webhook delivery systems handle rate limits, timeouts, and downstream failures? Advanced
Spoken Interview Answer

"Outbound webhooks must be dispatched through persistent background job queues (like BullMQ). Deliveries should enforce strict 3–5 second HTTP timeouts. Failed attempts must retry using truncated exponential backoff with full jitter (e.g., 5s, 1m, 15m, 1h). Exhausted deliveries move to a Dead-Letter Queue (DLQ) for alerting and manual inspection."

Q18 What is the difference between 301 Moved Permanently and 308 Permanent Redirect? Advanced
Spoken Interview Answer

"Historically, user agents often rewrote POST requests to GET when encountering a 301 Moved Permanently status code. RFC 7538 introduced 308 Permanent Redirect to guarantee that the HTTP method and request payload body remain strictly unchanged across the redirect (a POST request remains a POST request)."

Q19 How do you handle API rate limiting headers using IETF standards? Advanced
Spoken Interview Answer

"IETF standardizes three rate-limiting headers: `RateLimit-Limit` (total quota per window), `RateLimit-Remaining` (remaining requests), and `RateLimit-Reset` (seconds until window renewal). When the quota is exhausted, the server responds with status `429 Too Many Requests` accompanied by a `Retry-After: ` header."

Q20 How do you explain the trade-offs of HATEOAS to a technical lead who wants to adopt Level 3 REST? Intermediate
Spoken Interview Answer

"HATEOAS provides theoretical elegance by allowing backends to evolve workflows without breaking hardcoded client routes. However, modern single-page applications and mobile SDKs rely on static TypeScript types and compile-time code generation. The payload overhead of repeating link relations across millions of records and the lack of client-side tooling mean Level 2 with OpenAPI contracts provides far higher developer velocity and performance."
