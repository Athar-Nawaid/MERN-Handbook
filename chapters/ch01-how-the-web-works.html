1. Client-Server Architecture

At its foundational level, the internet is built on the Client-Server model. In this distributed computing paradigm, workloads are partitioned between resource and service providers (servers) and service requesters (clients).

+--------------------+ HTTP/HTTPS Request +--------------------+ | | -------------------------------------> | | | Client Browser | | Node.js / Express | | (React Frontend) | <------------------------------------- | App Server | | | HTTP/HTTPS Response | | +--------------------+ +--------------------+ | ^ Database Query | | Result Set (SQL / Mongoose)| | v | +--------------------+ | PostgreSQL / | | MongoDB Server | +--------------------+
Figure 1.1: The Three-Tier Full-Stack Web Request-Response Architecture

Why the Architecture Exists

Separating clients and servers provides essential system properties:

  • Centralized Data Integrity & Security: Business rules, authentication, credit card processing, and authoritative database records remain isolated in secure server environments, completely shielded from client manipulation.
  • Independent Scalability: Frontends can be statically deployed and cached across worldwide Content Delivery Networks (CDNs), while backend Node.js services scale horizontally behind load balancers based on CPU/memory pressure.
  • Heterogeneous Clients: A single Express REST or GraphQL API can simultaneously serve desktop web browsers, iOS apps, Android clients, and automated third-party webhooks.
Real-World Analogy: The Restaurant Model

Think of the client as a customer sitting at a dining table holding a menu. The customer cannot walk directly into the pantry to cook food or check cash register balances (security violation). Instead, they give an order to the waiter (the HTTP Request). The waiter delivers the order to the kitchen (the Express backend server). The chef gathers raw ingredients from the walk-in refrigerator (the PostgreSQL/MongoDB database), prepares the meal, and the waiter delivers the finished dish back to the customer's table (the HTTP Response).

2. Browsers, Servers, DNS, IP Addresses, and Ports

To deliver any packet across the globe, the internet relies on the Internet Protocol (IP). Every physical or virtual host on a network is assigned an IP Address.

IPv4 vs IPv6

  • IPv4 (Internet Protocol version 4): 32-bit numerical address expressed as four 8-bit octets separated by dots (e.g., 192.168.1.1 or 142.250.190.46). IPv4 yields \(2^{32} \approx 4.29 \text{ billion}\) addresses, which has been exhausted globally.
  • IPv6 (Internet Protocol version 6): 128-bit hexadecimal address separated by colons (e.g., 2001:0db8:85a3:0000:0000:8a2e:0370:7334). IPv6 yields \(2^{128} \approx 3.4 \times 10^{38}\) unique addresses, effectively infinite for human networking needs.

The Domain Name System (DNS)

Humans remember domain names like api.github.com or mycompany.com, but routers and network switches only route IP packets. DNS is the global, distributed, hierarchical database that translates human-friendly domain names into machine-routable IP addresses.

3. Transport Protocols: TCP versus UDP

At the Transport Layer (Layer 4 of the OSI model), all web communication relies on either TCP (Transmission Control Protocol) or UDP (User Datagram Protocol).

Feature TCP (Transmission Control Protocol) UDP (User Datagram Protocol)
Connection State Connection-oriented (Requires 3-way handshake before data transfer) Connectionless (Fire-and-forget datagrams, no handshake)
Delivery Guarantee Guaranteed. Lost packets are automatically retransmitted. No guarantee. Lost packets are discarded silently.
Packet Ordering Strictly ordered via Sequence Numbers (\(SEQ\)) and Acknowledgment Numbers (\(ACK\)). Packets may arrive out of order or not at all.
Flow & Congestion Control Built-in sliding window flow control and congestion avoidance algorithms (Cubic, BBR). None. Transmits at whatever speed the host supplies.
Header Overhead 20 to 60 bytes. Fixed 8 bytes.
Primary Use Cases Web browsing (HTTP/1.1, HTTP/2), REST APIs, file downloads, SSH, database connections. DNS lookups, live video streaming, multiplayer gaming, WebRTC audio/video, HTTP/3 (QUIC).

The TCP Three-Way Handshake

Before any HTTP request can be sent over TCP, the client and server must agree on initial sequence numbers to track data bytes accurately:

  1. SYN (Synchronize): The client picks a random Initial Sequence Number \(ISN_C\) (e.g., 1000) and sends a TCP packet with the SYN flag set to the server.
  2. SYN-ACK (Synchronize-Acknowledge): The server receives the SYN, records \(ISN_C\), picks its own random Initial Sequence Number \(ISN_S\) (e.g., 5000), and sends back a packet with both SYN and ACK flags set. The acknowledgment number is \(ACK = ISN_C + 1 = 1001\).
  3. ACK (Acknowledge): The client receives the SYN-ACK and responds with an ACK packet containing \(ACK = ISN_S + 1 = 5001\). At this point, the TCP socket is in the ESTABLISHED state, and data payload transmission begins.
💡 Latency Impact (Round Trip Time)

The TCP handshake requires 1 full Round Trip Time (1 RTT) before a single byte of HTTP application data can travel across the wire. If your client is in London and your server is in California with a ping latency of 150ms, the TCP handshake alone consumes 150ms of dead waiting time!

4. TLS / HTTPS and Cryptographic Handshakes

Standard HTTP transmits data in cleartext. Anyone eavesdropping on the physical wire, Wi-Fi router, or ISP transit backbone can read passwords, session cookies, and private user data. HTTPS (Hypertext Transfer Protocol Secure) runs HTTP on top of a TLS (Transport Layer Security) encrypted tunnel.

Core Objectives of TLS

  • Confidentiality (Encryption): Only the client and server can read the transmitted message payload.
  • Integrity: Messages cannot be altered, dropped, or tampered with in transit without detection (via Message Authentication Codes).
  • Authentication: Proves that the server actually owns the domain name using cryptographically signed digital certificates from trusted Certificate Authorities (CAs).

TLS 1.2 vs TLS 1.3: The Latency Revolution

In TLS 1.2, negotiating cipher suites and exchanging asymmetric public keys required 2 RTTs (added to the 1 RTT for TCP, totaling 3 RTTs before HTTP data could flow).

In modern TLS 1.3, the handshake was streamlined down to 1 RTT using Diffie-Hellman key exchange. Furthermore, with 0-RTT Session Resumption, returning visitors can begin sending encrypted application data on the very first round trip!

HTTP Methods and Idempotency

An operation is Idempotent if making the exact same request \(N\) times produces the exact same server state as making it once (\(f(f(x)) = f(x)\)).

HTTP Method Standard Semantic Purpose Safe? Idempotent?
GET Retrieve a resource without modifying server state. Yes Yes
POST Create a new subordinate resource or trigger an arbitrary action. No No (Sending 5 POSTs creates 5 separate database records).
PUT Completely replace an existing resource with the provided payload. No Yes (Replacing a record with identical values 5 times yields the same final state).
PATCH Apply partial modifications to an existing resource. No Generally No (though carefully designed patches can be made idempotent).
DELETE Remove the specified resource. No Yes (Deleting ID 42 once deletes it; deleting it again leaves it deleted).
HEAD Same as GET, but returns only response headers without the message body. Yes Yes
OPTIONS Used by browsers in CORS preflight requests to query supported methods/headers. Yes Yes

HTTP Status Code Classifications

  • 1xx (Informational): Request received, continuing process (e.g., 101 Switching Protocols for WebSockets).
  • 2xx (Success): Action successfully received and accepted:
    • 200 OK: Standard successful GET, PUT, or PATCH.
    • 201 Created: Successfully created a new resource (standard for POST).
    • 204 No Content: Action succeeded, but response intentionally has no body (often for DELETE).
  • 3xx (Redirection): Further action needed to complete request:
    • 301 Moved Permanently: Resource permanently at new URI (browsers cache this aggressively).
    • 302 Found / 307 Temporary Redirect: Temporary redirect.
    • 304 Not Modified: Client cached copy is still fresh (conditional request via If-None-Match or ETag).
  • 4xx (Client Error): Client issued an invalid or unauthorized request:
    • 400 Bad Request: Malformed syntax, failed schema validation.
    • 401 Unauthorized: Missing or invalid authentication token/credentials.
    • 403 Forbidden: Authenticated, but user lacks permission to access resource (RBAC).
    • 404 Not Found: Resource does not exist at requested URL.
    • 409 Conflict: State conflict (e.g., unique email already registered).
    • 429 Too Many Requests: Rate limit exceeded.
  • 5xx (Server Error): Server encountered an unhandled exception:
    • 500 Internal Server Error: Uncaught exception in backend code.
    • 502 Bad Gateway: Reverse proxy (Nginx) received an invalid response from upstream (Express crashed).
    • 503 Service Unavailable: Server is overloaded or undergoing scheduled maintenance.
    • 504 Gateway Timeout: Upstream server failed to respond within reverse proxy timeout limit.

6. Browser Rendering Internals: The Critical Rendering Path

Once the browser receives the raw HTML byte stream over HTTP, how does it turn those characters into interactive pixels on the screen? This multi-stage pipeline is known as the Critical Rendering Path (CRP).

HTML Bytes ---> Characters ---> Tokens ---> Nodes ---> DOM Tree | +---> Render Tree ---> Layout ---> Paint ---> Composite | (Visual nodes) (Geometry) (Pixels) (GPU Layers) CSS Bytes ---> Characters ---> Tokens ---> Nodes ---> CSSOM Tree
Figure 1.4: The Browser Critical Rendering Path Pipeline

The 5 Steps of Browser Rendering

  1. 1. DOM (Document Object Model) Construction: The browser decodes HTML raw bytes into characters, parses them into tokens (e.g., <html>, <body>, <p>), turns tokens into node objects with properties, and links them into a hierarchical tree data structure called the DOM Tree.
  2. 2. CSSOM (CSS Object Model) Construction: As the parser encounters <link rel="stylesheet"> or <style>, it processes CSS rules into another tree where every node contains cascading computed styles. CSS is render-blocking: the browser will not paint anything until the CSSOM is completely constructed to avoid the Flash of Unstyled Content (FOUC).
  3. 3. Render Tree Creation: The browser combines the DOM and CSSOM to build the Render Tree. Only elements that are visually displayed are included. Elements styled with display: none and non-visual tags like <head> and <script> are excluded. (Note: elements with visibility: hidden are included because they still occupy physical geometry).
  4. 4. Layout (Reflow): The browser calculates the exact geometric coordinates, width, and height of every node on the viewport (e.g., node \(X\) is 300px wide, 120px tall, positioned at coordinates \((45, 120)\)).
  5. 5. Paint & Compositing: The engine rasterizes the nodes into actual screen pixels (colors, text, shadows, borders) into separate memory bitmap layers. Finally, the GPU composites these layers together onto the physical screen buffer.
⚠️ Performance Bottleneck: Reflow vs Repaint

Modifying geometric CSS properties (e.g., width, height, top, margin) forces the browser to recalculate the Layout for the entire page (a heavy Reflow). Modifying color or visibility (e.g., color, background-color) skips Layout and triggers only a Repaint. For butter-smooth 60fps animations, always animate transform and opacity, which skip both Layout and Paint, running directly on the GPU via Compositing!

8. Practical Exercises & Code Walkthrough

Exercise 1.1: Building a Minimal HTTP/1.1 Server in Vanilla Node.js Hands-on

To understand HTTP without Express abstractions, write a native Node.js script using the built-in http module that inspects headers, parses query parameters, handles methods, and returns a formatted JSON payload with appropriate status codes and custom headers. 

// server.js - Native Node.js HTTP Server
const http = require('http');
const url = require('url');

const server = http.createServer((req, res) => {
  // 1. Parse URL and query strings
  const parsedUrl = url.parse(req.url, true);
  const path = parsedUrl.pathname;
  const method = req.method.toUpperCase();

  console.log(`[${new Date().toISOString()}] ${method} request to ${path}`);

  // 2. Set default security & content headers
  res.setHeader('Content-Type', 'application/json');
  res.setHeader('X-Powered-By', 'NodeJS-Native-Engine');

  // 3. Simple Router
  if (path === '/api/health' && method === 'GET') {
    res.writeHead(200);
    return res.end(JSON.stringify({ status: 'ok', uptime: process.uptime() }));
  }

  if (path === '/api/tasks' && method === 'POST') {
    let rawBody = '';

    // Collect data stream chunks (Non-blocking I/O)
    req.on('data', chunk => {
      rawBody += chunk.toString();
    });

    req.on('end', () => {
      try {
        const payload = JSON.parse(rawBody);

        if (!payload.title) {
          res.writeHead(400);
          return res.end(JSON.stringify({ error: 'Field "title" is required.' }));
        }

        const newTask = {
          id: Math.floor(Math.random() * 10000),
          title: payload.title,
          createdAt: new Date().toISOString()
        };

        res.writeHead(201);
        return res.end(JSON.stringify(newTask));
      } catch (err) {
        res.writeHead(400);
        return res.end(JSON.stringify({ error: 'Malformed JSON payload.' }));
      }
    });
    return;
  }

  // 4. Default 404 handler
  res.writeHead(404);
  res.end(JSON.stringify({ error: 'Endpoint not found.' }));
});

const PORT = 3000;
server.listen(PORT, () => {
  console.log(`Server actively listening on http://localhost:${PORT}`);
});

Interview Questions and Answers

Below are 16 essential technical interview questions designed to test your knowledge of networking, HTTP mechanics, TLS, and browser rendering.

Q1 What is the difference between TCP and UDP, and when would you choose one over the other? Beginner
Spoken Interview Answer

"TCP is a connection-oriented, reliable protocol that guarantees in-order packet delivery through sequence numbers and retransmissions. UDP is a connectionless, lightweight protocol that transmits packets with no delivery or ordering guarantees. We use TCP whenever data accuracy is non-negotiable—such as web browsing (HTTP), REST APIs, and database transactions. We choose UDP where low latency is prioritized over individual dropped packets—such as real-time gaming, live video streaming, DNS lookups, and the modern HTTP/3 protocol via QUIC."

Technical Deep Dive: TCP guarantees reliability through its sliding window mechanism, checksums, and acknowledgments. If a packet is dropped, TCP halts delivery of subsequent packets until the missing packet is retransmitted (known as Head-of-Line Blocking). UDP avoids this by having zero retransmissions and an 8-byte minimal header (compared to TCP's 20-60 byte header).

Common Trap: Stating that "UDP is always faster." UDP has lower protocol overhead, but if your application layer tries to rebuild reliability over UDP poorly, it will be slower and buggier than well-tuned kernel TCP.

Interviewer Follow-up:

"If TCP has head-of-line blocking, how does HTTP/3 solve this while remaining fast?"

Answer: HTTP/3 runs on top of QUIC, which implements its own multiplexed streams over UDP. If one stream loses a packet, only that specific stream pauses; all other parallel streams continue without head-of-line blocking.

Q2 What is the difference between HTTP/1.1, HTTP/2, and HTTP/3? Intermediate
Spoken Interview Answer

"HTTP/1.1 is text-based and processes requests sequentially per TCP connection, leading to head-of-line blocking unless browsers open multiple parallel sockets (typically up to 6 per domain). HTTP/2 introduced binary framing, multiplexing multiple concurrent streams over a single TCP connection, header compression via HPACK, and Server Push. HTTP/3 replaces TCP with QUIC over UDP, eliminating TCP-level head-of-line blocking and providing faster 0-RTT handshakes."

Comparison Table:

  • HTTP/1.1: Text-formatted headers, persistent connections (Keep-Alive), pipelining (rarely supported), 6 socket limit per origin.
  • HTTP/2: Binary protocol, multiplexed streams over 1 TCP connection, HPACK header compression, eliminates application-level HOL blocking.
  • HTTP/3: Built on QUIC (UDP), connection migration across Wi-Fi/cellular IP changes, independent stream retransmissions.
Q3 Explain the difference between idempotent and non-idempotent HTTP methods. Why is POST not idempotent? Intermediate
Spoken Interview Answer

"An HTTP method is idempotent if executing the identical request multiple times produces the exact same server state as executing it once. GET, PUT, and DELETE are idempotent. POST is not idempotent because repeating the request creates multiple independent resources—such as creating duplicate orders or charging a credit card multiple times."

Why PUT is idempotent while POST is not:

# PUT /api/users/42 -> sets user 42 name to "Alice"
# Doing this 10 times leaves user 42 name as "Alice". (Idempotent)

# POST /api/orders -> creates an order
# Doing this 10 times creates 10 separate order rows with 10 IDs. (Non-idempotent)
Interviewer Follow-up:

"How do production payment gateways like Stripe make POST requests safe from duplicate charges if a network timeout occurs?"

Answer: They use an Idempotency Key (a unique UUID sent in a custom header like Idempotency-Key: e82b-...). The server records the key in Redis/database; if a duplicate request arrives with the same key, it returns the cached response instead of charging again.

Q4 What is the difference between a 401 Unauthorized and a 403 Forbidden HTTP status code? Beginner
Spoken Interview Answer

"401 Unauthorized means the user has not provided valid authentication credentials—the server does not know who they are. 403 Forbidden means the server successfully authenticated who the user is, but the user lacks the necessary authorization or role permissions to access the requested resource."

Analogy: 401 is trying to board an airplane without an ID. 403 is showing a valid ID, but holding an Economy ticket while trying to sit in the First Class cabin.

Q5 What is the difference between Reflow (Layout) and Repaint in browser rendering? How do you prevent layout thrashing? Advanced
Spoken Interview Answer

"Reflow is the computation of the physical geometry, position, and dimensions of elements on the page. Repaint is drawing pixels (colors, borders, shadows) onto memory buffers after the layout is finalized. Reflow always triggers Repaint, making it much more computationally expensive. Layout thrashing happens when JavaScript repeatedly reads layout properties (like offsetHeight) immediately after writing style changes inside a loop, forcing synchronous layout recalculations. We prevent it by batching DOM reads and writes or utilizing requestAnimationFrame."

Vulnerable Code (Layout Thrashing):

// BAD: Forces browser to recalculate layout on every iteration!
for (let i = 0; i < elements.length; i++) {
  const width = elements[i].offsetWidth; // READ (Forces Reflow)
  elements[i].style.width = width + 10 + 'px'; // WRITE (Invalidates Layout)
}

// GOOD: Batch reads first, then batch writes
const widths = elements.map(el => el.offsetWidth); // Batch READ
elements.forEach((el, i) => {
  el.style.width = widths[i] + 10 + 'px'; // Batch WRITE
});
Q6 How does DNS resolution work step-by-step when resolving a domain name? Intermediate
Spoken Interview Answer

"The browser first checks its internal DNS cache, then the OS DNS cache, and the local hosts file. If not found, it queries the recursive resolver (such as your ISP or 8.8.8.8). If the resolver doesn't have it cached, it performs an iterative lookup: querying the Root Nameserver to locate the Top-Level Domain server (.com), querying the TLD server to locate the Authoritative Nameserver for the domain, and finally querying the Authoritative server to obtain the final A or AAAA record with an IP address."

Q7 What are the key security attributes on HTTP Cookies: HttpOnly, Secure, and SameSite? Intermediate
Spoken Interview Answer

"HttpOnly blocks JavaScript from accessing document.cookie, completely protecting the session token from XSS script theft. Secure ensures the cookie is only transmitted over encrypted HTTPS connections, preventing plaintext sniffing. SameSite governs cross-site request behavior to prevent CSRF attacks: Strict never sends the cookie on third-party links, Lax sends it only on top-level GET navigations, and None permits cross-site sharing (only allowed when Secure is also set)."

Q8 What happens during a TLS 1.3 handshake, and how does it achieve 1-RTT and 0-RTT latency? Advanced
Spoken Interview Answer

"In TLS 1.3, the client sends its supported cipher suites and its ephemeral Diffie-Hellman public key shares directly inside the very first ClientHello packet. The server responds with ServerHello, selecting the cipher and providing its key share and digital certificate. Both parties immediately derive the shared symmetric encryption key in just 1 round trip. In 0-RTT resumption, returning clients use a pre-shared session ticket from a previous session to send encrypted application data in the initial packet."

Q9 Scenario: Your frontend API call returns a 502 Bad Gateway. Where in the architecture is the failure occurring, and how do you debug it? Scenario
Spoken Interview Answer

"A 502 Bad Gateway indicates that an edge reverse proxy (such as Nginx, Cloudflare, or an AWS ALB) attempted to forward the request to an upstream application server (like Node.js Express), but the upstream server either crashed, refused the connection, closed the socket unexpectedly, or was completely unreachable. To debug, I first verify if the Node.js process is running via PM2 or systemctl, inspect the Nginx error logs (error.log), and check Node application logs for unhandled exceptions or Out-Of-Memory (OOM) crashes."

Step-by-step diagnostic checklist:

  1. Check reverse proxy error logs: tail -f /var/log/nginx/error.log (look for connect() failed (111: Connection refused) while connecting to upstream).
  2. Check Node.js status: pm2 status or docker ps.
  3. Verify local port binding: netstat -tlpn | grep 3000 or curl -I http://localhost:3000/api/health directly on the server host.
  4. Check memory pressure: dmesg -T | grep -i oom to check if the Linux kernel OOM-killer killed the Node process.
Q10 Scenario: A user clicks "Pay Now" on an e-commerce checkout page, but their mobile connection drops before the server response returns. How do you design the system so they aren't charged twice upon retrying? Scenario
Spoken Interview Answer

"I implement an Idempotency Layer. When the checkout modal renders, the client generates a unique UUID (Idempotency Key). When submitting the POST /checkout request, this key is included in the headers. On the backend, before processing payment, we check Redis using an atomic SETNX key with a lock. If the key already exists and has completed, we return the cached successful receipt. If it's currently processing, subsequent clicks are told to wait. If it failed, it safely permits a retry."

Q11 What is the difference between a 301 and a 302/307 redirect? What are the SEO and caching implications? Beginner
Spoken Interview Answer

"301 Moved Permanently tells browsers and search engine crawlers that the resource has permanently relocated to the new URL; search engines transfer link equity (SEO rank), and browsers cache the redirect aggressively. 302 Found or 307 Temporary Redirect indicates that the relocation is temporary; search engines keep indexing the original URL, and browsers do not cache the redirection permanently."

Q12 Why is CSS render-blocking while JavaScript is parser-blocking by default? How do `async` and `defer` change this? Intermediate
Spoken Interview Answer

"CSS is render-blocking because the browser cannot calculate layout or paint pixels without the CSSOM; painting HTML before CSS finishes parsing causes a jarring Flash of Unstyled Content. JavaScript is parser-blocking because scripts can execute document.write() or manipulate the DOM tree synchronously, forcing the HTML tokenizer to pause. With defer, the script downloads in parallel in the background and executes in document order only after HTML parsing completes. With async, the script downloads in parallel and executes immediately whenever it finishes downloading, pausing the parser at that instant."

Q13 What is TCP Head-of-Line (HOL) blocking versus HTTP Head-of-Line blocking? Advanced
Spoken Interview Answer

"HTTP Head-of-Line blocking in HTTP/1.1 occurs when a client must wait for a previous slow request (like a large file download) to finish over the connection before the next request can be served. HTTP/2 solved this at the application layer with multiplexed streams. However, TCP Head-of-Line blocking occurs at the transport layer: because TCP guarantees strictly ordered byte streams, if a single packet is lost on the network, all other multiplexed streams inside that TCP connection are stalled at the OS kernel buffer until the lost packet is retransmitted. HTTP/3 solves this by migrating to QUIC over UDP."

Q14 What is the difference between URI, URL, and URN? Beginner
Spoken Interview Answer

"A URI (Uniform Resource Identifier) is the overarching umbrella identifier for any resource. A URL (Uniform Resource Locator) is a URI that specifies both the resource's identity and how to access it (the protocol and location, like https://example.com/index.html). A URN (Uniform Resource Name) identifies a resource by name in a particular namespace without specifying where to find it (like urn:isbn:0451450523)."

Q15 What is an ETag and how does conditional HTTP caching work with 304 Not Modified? Intermediate
Spoken Interview Answer

"An ETag (Entity Tag) is an HTTP response header containing an opaque hash or version identifier representing the state of a resource. When the browser requests the resource again, it sends the stored hash in the If-None-Match header. If the resource hasn't changed, the server responds with a 304 Not Modified with no response body, saving bandwidth and network latency."

Q16 Scenario: Your website has high initial page load latency for users in Australia, while your servers are located in North America. What architectural changes would you propose to reduce latency? Scenario

"The root cause is physical speed-of-light latency across 12,000 km, where each round trip adds 150–200ms. I would implement three solutions: 1. Deploy a Global CDN (such as Cloudflare or AWS CloudFront) to cache static assets (HTML, CSS, JS, images) and terminate TLS at an Australian Edge Point-of-Presence, reducing the TCP/TLS handshake latency from 300ms to under 15ms. 2. For dynamic API calls, utilize edge caching or deploy read-replica databases with region-specific serverless/container endpoints."
