1. useState: Snapshots, Functional Updates, and Lazy Initialization

State in React behaves like a snapshot of a single render. When you call setCount(count + 1), you are not mutating a variable in place; you are scheduling a new render with a new state snapshot.

1.1 Direct Value vs Functional Updater Form

Because state is a snapshot, calling a setter multiple times in the same tick using the direct value reads the same snapshot value:

javascript 
function CounterBug() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    // In this render snapshot, count is 0
    setCount(count + 1); // setCount(0 + 1)
    setCount(count + 1); // setCount(0 + 1)
    setCount(count + 1); // setCount(0 + 1)
    // Result after render: count is 1, NOT 3!
  };

  return <button onClick={handleClick}>Count: {count}</button>;
}

function CounterFixed() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    // Functional updater receives the pending state from the queue:
    setCount((prev) => prev + 1); // 0 + 1 = 1
    setCount((prev) => prev + 1); // 1 + 1 = 2
    setCount((prev) => prev + 1); // 2 + 1 = 3
    // Result after render: count is 3!
  };

  return <button onClick={handleClick}>Count: {count}</button>;
}

1.2 Lazy State Initialization

If your initial state requires an expensive computation (e.g. reading from localStorage or parsing a large JSON string), passing the expression directly executes that computation on every single render, even though React only uses it during the initial mount!

javascript 
// SLOW: JSON.parse runs on EVERY re-render, wasting CPU cycles
const [user, setUser] = useState(JSON.parse(localStorage.getItem("user_profile")));

// FAST: Lazy Initializer function runs ONCE on initial mount only
const [user, setUser] = useState(() => {
  const saved = localStorage.getItem("user_profile");
  return saved ? JSON.parse(saved) : { name: "Guest", role: "viewer" };
});

2. Automatic Batching (React 18 vs React 17)

Batching is React's mechanism of grouping multiple state updates into a single re-render to avoid unnecessary repaints.

Execution Context React 17 Batching Behavior React 18+ Automatic Batching
React Event Handlers (e.g. onClick) Batched into 1 render. Batched into 1 render.
Asynchronous Promises (e.g. fetch().then()) Unbatched! Each state update triggered a separate immediate re-render! Automatically Batched! Multiple updates produce 1 render.
Native Timers (e.g. setTimeout) Unbatched! Triggered multiple renders. Automatically Batched! Produces 1 single render.
Bypassing Batching Not applicable (already unbatched). Use flushSync(() => { setState(...) }) if synchronous DOM read is required.

3. useEffect: Synchronization, Cleanups, and StrictMode

In class components, developers thought in terms of lifecycles: "When the component mounts, do X; when it unmounts, do Y."

In functional React with Hooks, the mental model is Synchronization: "Synchronize the component with an external system (DOM, network, WebSockets, timers) based on state and props."

Figure 16.1: The useEffect Lifecycle & Cleanup Timing
[ Initial Mount: Render 1 ]
   1. Component renders UI
   2. DOM painted on screen
   3. useEffect setup function runs (Subscribes to Chat Room A)

========================================================================

[ Props Change: roomId changes from 'Room A' to 'Room B' -> Render 2 ]
   1. Component re-renders with roomId = 'Room B'
   2. DOM updated and painted
   3. PREVIOUS Cleanup runs! (Unsubscribes from Chat Room A)
   4. NEW setup function runs! (Subscribes to Chat Room B)

========================================================================

[ Component Unmounts ]
   1. Final Cleanup function runs! (Unsubscribes from Chat Room B)
javascript 
import { useState, useEffect } from "react";

export function ChatConnection({ roomId }) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    let isCancelled = false; // Prevents race condition if roomId changes fast

    console.log(`[Effect] Connecting to room ${roomId}...`);
    const socket = new WebSocket(`wss://chat.example.com/rooms/${roomId}`);

    socket.onmessage = (event) => {
      if (!isCancelled) {
        const newMsg = JSON.parse(event.data);
        setMessages((prev) => [...prev, newMsg]);
      }
    };

    // CLEANUP FUNCTION: Runs before the effect re-executes AND on unmount
    return () => {
      console.log(`[Cleanup] Disconnecting from room ${roomId}...`);
      isCancelled = true;
      socket.close();
    };
  }, [roomId]); // Dependency array: only re-run when roomId changes

  return <div>Connected to Room {roomId}. Messages: {messages.length}</div>;
}
⚠️ Why does useEffect run twice on mount in React 18?

In React 18 development mode with <React.StrictMode>, React intentionally mounts the component, unmounts it immediately (running your cleanup function), and mounts it again:

Mount \(\to\) Cleanup \(\to\) Mount

This intentional double-mount stresses your effects to ensure you implemented a proper cleanup function. If your effect leaks event listeners, leaves open socket connections, or fails to cancel fetch requests, the double-mount immediately exposes the bug during local development. In production builds, effects run only once on mount.

4. useRef: Persistent References without Re-renders

useRef(initialValue) returns a plain JavaScript object with a mutable .current property: { current: initialValue }.

Use Case Why State Fails Why useRef Succeeds
Direct DOM Access (focus, scroll position, measurement) State has no reference to actual browser DOM nodes. Attaching ref={myRef} to JSX sets myRef.current directly to the underlying DOM node upon mounting.
Storing Timer IDs (e.g. setInterval) Calling setTimerId(...) triggers a re-render every time a timer is set. Mutating timerRef.current = id updates the reference without triggering any re-render.
Tracking Previous Props / State State triggers an infinite loop if updated inside render. Can store the previous value in ref.current inside an effect after render completes.
javascript 
import { useState, useRef, useEffect } from "react";

// Pattern: Custom hook to track previous value across renders
export function usePrevious(value) {
  const ref = useRef();
  
  useEffect(() => {
    ref.current = value; // Updates AFTER render phase completes
  }, [value]);

  return ref.current; // Returns previous value during render
}

export function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  const timerRef = useRef(null); // Holds timer ID without re-rendering

  const start = () => {
    if (timerRef.current !== null) return;
    timerRef.current = setInterval(() => {
      setSeconds((s) => s + 1);
    }, 1000);
  };

  const stop = () => {
    clearInterval(timerRef.current);
    timerRef.current = null;
  };

  // Clean up interval on unmount
  useEffect(() => {
    return () => clearInterval(timerRef.current);
  }, []);

  return (
    <div>
      <h2>Elapsed: {seconds}s</h2>
      <button onClick={start}>Start</button>
      <button onClick={stop}>Stop</button>
    </div>
  );
}

5. useMemo and useCallback: Referential Identity and Performance

On every re-render of a component, all functions declared inside the component body are re-instantiated with new memory addresses:

\[ \text{fn}_{\text{render1}} \neq \text{fn}_{\text{render2}} \]

Similarly, complex derived calculations (filtering, sorting 10,000 array items) run from scratch on every re-render, even when the underlying data did not change.

Hook What It Returns Primary Use Case
useMemo(fn, deps) The memoized result value of executing fn(). Caching expensive synchronous computations (sorting, math) or stabilizing object references passed to child components.
useCallback(fn, deps) The memoized function reference itself. Stabilizing callback function identities passed down to memoized child components (React.memo) to prevent re-renders.
javascript 
import React, { useState, useMemo, useCallback } from "react";

// Memoized child component: only re-renders if props change by shallow equality
const ExpensiveChart = React.memo(function ExpensiveChart({ onSelectPoint, data }) {
  console.log("[Child] Rendering ExpensiveChart...");
  return (
    <div className="chart">
      <button onClick={() => onSelectPoint(data[0])}>Select First Point</button>
    </div>
  );
});

export function Dashboard({ rawMetrics }) {
  const [theme, setTheme] = useState("dark");

  // 1. useMemo: Avoid recalculating expensive statistical aggregation on theme changes
  const computedStats = useMemo(() => {
    console.log("[Computation] Recalculating heavy metrics...");
    return rawMetrics.map((m) => m * 1.5).sort((a, b) => b - a);
  }, [rawMetrics]); // Only re-computes when rawMetrics changes

  // 2. useCallback: Stabilize function reference across re-renders
  const handleSelectPoint = useCallback((point) => {
    console.log("Selected point:", point);
  }, []); // Empty deps: function identity never changes!

  return (
    <div className={theme}>
      <button onClick={() => setTheme(theme === "dark" ? "light" : "dark")}>
        Toggle Theme
      </button>
      {/* ExpensiveChart will NOT re-render when theme toggles! */}
      <ExpensiveChart data={computedStats} onSelectPoint={handleSelectPoint} />
    </div>
  );
}
⚠️ The Cost of Premature Optimization with useMemo / useCallback

Do not wrap every function and calculation in useCallback and useMemo by default! Each hook call incurs overhead:

  1. Memory allocation for the dependency array.
  2. Iterating over previous dependencies and shallow comparing every element.
  3. Extra closure allocations in JavaScript V8 memory.

Rule of Thumb: Only use useCallback when the function is passed to a React.memo-wrapped child or listed in a useEffect dependency array. Only use useMemo for truly heavy calculations (> 1ms execution time or > 1,000 items) or to preserve referential equality for dependency arrays.

6. Stale Closures in Hooks: Diagnosis & Solution

A Stale Closure occurs when a callback or effect captures a snapshot of state from an earlier render and continues referencing that old snapshot even after state has changed.

javascript 
// BUGGY: Classic Stale Closure in setInterval
function StaleCounter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(() => {
      // In this closure, `count` was captured as `0` at mount time!
      // On every tick, it calls setCount(0 + 1) = 1!
      console.log("Tick with count:", count); // Always 0!
      setCount(count + 1);
    }, 1000);

    return () => clearInterval(timer);
  }, []); // Missing count in dependency array!

  return <h1>Count: {count}</h1>; // Stays at 1 forever!
}

// FIX 1: Functional updater (Eliminates the dependency entirely)
function FixedCounterUpdater() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const timer = setInterval(() => {
      setCount((prev) => prev + 1); // Reads fresh pending state
    }, 1000);

    return () => clearInterval(timer);
  }, []); // Safe! No dependency needed!

  return <h1>Count: {count}</h1>;
}

// FIX 2: useRef pattern when you need to read fresh state inside a callback
function FixedCounterRef() {
  const [count, setCount] = useState(0);
  const countRef = useRef(count);

  // Keep ref synchronized with latest state
  useEffect(() => {
    countRef.current = count;
  }, [count]);

  useEffect(() => {
    const timer = setInterval(() => {
      console.log("Fresh count:", countRef.current);
    }, 1000);

    return () => clearInterval(timer);
  }, []);

  return <button onClick={() => setCount(count + 1)}>Count: {count}</button>;
}

7. useContext and Mitigating Re-render Storms

useContext solves Prop Drilling (passing props through 10 intermediate components that don't need them). However, React Context comes with a severe architectural caveat:

Whenever the Context value changes, EVERY component that calls useContext(MyContext) will re-render, even if it only consumes a property that didn't change, and even if wrapped in React.memo!

7.1 The Solution: Context Splitting (State vs Dispatch)

By splitting state and dispatch into two separate Contexts, components that only trigger actions (like buttons) never re-render when state changes!

javascript 
import { createContext, useContext, useReducer } from "react";

// 1. Separate State Context and Dispatch Context
const CartStateContext = createContext(null);
const CartDispatchContext = createContext(null);

function cartReducer(state, action) {
  switch (action.type) {
    case "ADD_ITEM":
      return { ...state, items: [...state.items, action.payload] };
    case "CLEAR":
      return { ...state, items: [] };
    default:
      return state;
  }
}

export function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });

  return (
    <CartStateContext.Provider value={state}>
      {/* Dispatch reference NEVER changes, so this context never triggers re-renders! */}
      <CartDispatchContext.Provider value={dispatch}>
        {children}
      </CartDispatchContext.Provider>
    </CartStateContext.Provider>
  );
}

// Custom consumption hooks with guard clauses
export function useCartState() {
  const context = useContext(CartStateContext);
  if (!context) throw new Error("useCartState must be used within CartProvider");
  return context;
}

export function useCartDispatch() {
  const context = useContext(CartDispatchContext);
  if (!context) throw new Error("useCartDispatch must be used within CartProvider");
  return context;
}

8. useReducer: Finite State Machines in React

When component state has multiple sub-values, complex transitions, or the next state depends on multiple previous values, useState leads to fragmented, error-prone logic.

useReducer centralizes state transitions in a pure reducer function:

\[ (state, action) \implies newState \]

javascript 
import { useReducer, useEffect } from "react";

// State Machine definition: IDLE -> LOADING -> SUCCESS / ERROR
const initialState = {
  status: "idle", // 'idle' | 'loading' | 'success' | 'error'
  data: null,
  error: null
};

function fetchReducer(state, action) {
  switch (action.type) {
    case "FETCH_START":
      return { status: "loading", data: null, error: null };
    case "FETCH_SUCCESS":
      return { status: "success", data: action.payload, error: null };
    case "FETCH_ERROR":
      return { status: "error", data: null, error: action.payload };
    default:
      return state;
  }
}

export function useFetch(url) {
  const [state, dispatch] = useReducer(fetchReducer, initialState);

  useEffect(() => {
    let isMounted = true;
    const controller = new AbortController();

    async function fetchData() {
      dispatch({ type: "FETCH_START" });
      try {
        const res = await fetch(url, { signal: controller.signal });
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = await res.json();
        if (isMounted) dispatch({ type: "FETCH_SUCCESS", payload: data });
      } catch (err) {
        if (err.name !== "AbortError" && isMounted) {
          dispatch({ type: "FETCH_ERROR", payload: err.message });
        }
      }
    }

    fetchData();

    return () => {
      isMounted = false;
      controller.abort(); // Cancel in-flight network request on unmount/re-run!
    };
  }, [url]);

  return state;
}

9. Practical Exercises & Code Walkthrough

Exercise 16.1 Build a Production useDebounce Custom Hook

Problem: Create a reusable custom hook useDebounce(value, delayMs) that delays updating its returned value until the specified delay has elapsed without new changes. Ensure timers are cleanly reset on rapid changes and cancelled on unmount.

View Complete Solution
javascript 
import { useState, useEffect } from "react";

export function useDebounce(value, delay = 500) {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    // Schedule update after delay
    const handler = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);

    // Cancel timer if value changes (user is still typing) or component unmounts
    return () => {
      clearTimeout(handler);
    };
  }, [value, delay]);

  return debouncedValue;
}

// Usage in live search:
export function SearchInput({ onSearch }) {
  const [text, setText] = useState("");
  const debouncedSearch = useDebounce(text, 300);

  useEffect(() => {
    if (debouncedSearch) {
      onSearch(debouncedSearch);
    }
  }, [debouncedSearch, onSearch]);

  return (
    <input
      type="text"
      placeholder="Type to search..."
      value={text}
      onChange={(e) => setText(e.target.value)}
    />
  );
}

10. Chapter-Specific Interview Questions and Answers

Master these 20 high-frequency interview questions covering React Hooks, memory lifecycles, and performance optimization.

Q01 Why does calling setCount(count + 1) three times in a single event handler only increment the counter by 1? Beginner
Spoken Interview Answer

"Because state in React behaves like a snapshot of the current render. If `count` is 0 at the time the click handler executes, all three `setCount(count + 1)` calls resolve to `setCount(0 + 1)`. React batches these updates and applies the final scheduled value, which is 1. To queue multiple sequential increments, you must pass a functional updater: `setCount(prev => prev + 1)`. The functional updater receives the pending state from React's internal queue rather than the stale snapshot."

Q02 What is Automatic Batching in React 18, and how does it differ from React 17? Intermediate
Spoken Interview Answer

"In React 17, state updates were only batched when triggered directly inside React synthetic event handlers. Updates occurring inside native promises (`fetch.then()`), `setTimeout`, or native DOM event listeners were executed immediately and unbatched, causing multiple re-renders and paints. React 18 introduced Automatic Batching: all state updates, regardless of whether they originate inside React handlers, asynchronous promises, or timers, are automatically batched into a single render pass."

Q03 What is a Stale Closure in React, and how can it be diagnosed and resolved? Advanced
Spoken Interview Answer

"A stale closure occurs when a callback, timer, or effect captures a snapshot of a variable from an earlier render and holds on to that reference even after state has updated. For example, a `setInterval` created inside a `useEffect` with an empty dependency array will only ever see the initial render's state. To fix it, you can: 1. Use functional state updaters (`setState(prev => ...)`), which do not depend on closure variables, or 2. Synchronize the state into a `useRef`, which preserves referential identity and allows reading `ref.current` to always get the latest value."

Q04 What is the exact execution timing of the useEffect cleanup function? Intermediate
Spoken Interview Answer

"The cleanup function runs in two scenarios: First, when the component unmounts from the DOM. Second, and crucially, before the effect re-executes on a subsequent render due to a dependency change. When dependencies change, React first runs the cleanup function from the PREVIOUS render to tear down old subscriptions or timers, and only then executes the new effect setup function with the new values."

Q05 What is Lazy State Initialization in useState, and when should you use it? Beginner
Spoken Interview Answer

"Lazy initialization is when you pass a function to `useState(() => expensiveInitialValue())` instead of the value directly. If you pass an expression like `useState(JSON.parse(localStorage.getItem('key')))` directly, JavaScript executes `localStorage.getItem` and `JSON.parse` on every single render, even though React discards the result after the initial mount. Passing a function ensures the expensive logic runs only once during initial mounting."

Q06 What is the difference between useMemo and useCallback? Intermediate
Spoken Interview Answer

"`useMemo` memoizes the RESULT of calling a calculation function: `useMemo(() => computeValue(a, b), [a, b])`. It returns a cached value. `useCallback` memoizes the FUNCTION REFERENCE itself: `useCallback((e) => handleEvent(e), [dep])`. In fact, `useCallback(fn, deps)` is syntactically equivalent to `useMemo(() => fn, deps)`. `useCallback` is primarily used to pass stable callback references to memoized child components (`React.memo`)."

Q07 Why does wrapping everything in useMemo and useCallback lead to worse performance? Advanced
Spoken Interview Answer

"Memoization is not free. Every call to `useMemo` or `useCallback` incurs computational and memory overhead: allocating memory for the hook closure, allocating the dependency array, and performing shallow comparison checks on every single dependency on every render. If the computation being memoized is cheap (like basic math or small array filtering), the overhead of dependency comparison exceeds the computation cost itself. Only use memoization when profiling proves a performance bottleneck or when preserving referential equality for child `React.memo` components."

Q08 What is the difference between useRef and useState? When does mutating useRef NOT trigger a re-render? Intermediate
Spoken Interview Answer

"`useState` stores data that affects the visual UI output; updating state notifies React and triggers a component re-render. `useRef` returns a plain mutable JavaScript container `{ current: initialValue }` that persists across renders. Mutating `ref.current` is a direct object property mutation; React does not track object mutations and NEVER triggers a re-render. Use `useRef` when storing data that does not impact JSX rendering, such as DOM elements, timer IDs, or previous values."

Q09 What is the Re-render Cascade problem with useContext, and how do you prevent it? Advanced
Spoken Interview Answer

"Whenever the `value` of a Context Provider changes, every component calling `useContext(MyContext)` is forced to re-render, even if wrapped in `React.memo`, and even if it only cares about an untouched property in the context object. To mitigate this: 1. Split contexts into smaller, granular contexts—most commonly separating State from Dispatch (`CartStateContext` and `CartDispatchContext`). Because `dispatch` identity never changes, components consuming dispatch never re-render. 2. Colocate state as close to its consumers as possible."

Q10 When should you prefer useReducer over useState? Intermediate
Spoken Interview Answer

"You should prefer `useReducer` when: 1. You have complex state logic involving multiple sub-values (e.g. status, data, error, pagination) that update together. 2. The next state depends on multiple previous states. 3. State transitions represent a Finite State Machine (e.g. idle -> loading -> success). 4. You want to pass a stable `dispatch` function down deep component trees via context rather than passing multiple callback props."

Q11 What is the difference between useEffect and useLayoutEffect? When MUST you use useLayoutEffect? Advanced
Spoken Interview Answer

"`useEffect` runs asynchronously and passively AFTER the browser has painted pixels to the screen, ensuring effects do not block user visuals. `useLayoutEffect` runs synchronously immediately after React commits DOM mutations, but BEFORE the browser paints. You MUST use `useLayoutEffect` when reading DOM layout measurements (e.g. `getBoundingClientRect()`, scroll height) and synchronously adjusting styles before the user sees the screen. Using `useEffect` for DOM measurements can cause visual screen flickering."

Q12 Why does React StrictMode invoke effects and render functions twice in development mode? Beginner
Spoken Interview Answer

"In React 18 development mode, StrictMode intentionally double-invokes component functions and effect lifecycles (`mount -> cleanup -> mount`). This is designed to uncover bugs caused by impure render functions and missing effect cleanups (such as uncancelled network requests, forgotten event listeners, or timer leaks). It prepares codebases for future Concurrent React features like Offscreen caching. This behavior only occurs in development; production executes once."

Q13 Scenario: A user rapidly types 'React' then 'Node' into a search box. The 'React' network request takes 2 seconds, but 'Node' takes 200ms. The UI shows 'React' results instead of 'Node'. How do you fix this race condition? Scenario
Spoken Interview Answer

"This is an asynchronous race condition where an older, slower request completes after a newer request. There are two solutions: 1. `AbortController`: In the `useEffect`, instantiate an `AbortController` and pass `signal` to `fetch()`. In the effect cleanup function, call `controller.abort()`. When the search term updates, React cancels the previous pending fetch request immediately. 2. A boolean `isCancelled` flag inside the effect that is set to `true` in cleanup, ignoring responses from superseded renders."

Q14 What are the rules for writing a Custom Hook? Do custom hooks share state between component instances? Intermediate
Spoken Interview Answer

"A custom hook is a JavaScript function whose name starts with 'use' (e.g. `useFetch`, `useAuth`) and that may call other React hooks. Crucially, custom hooks share stateful LOGIC, NOT state itself! Each component that invokes a custom hook receives an entirely independent, isolated instance of state and effects, exactly as if those hooks were called directly inside the component body."

Q15 What is flushSync in React 18, and what is its legitimate use case? Advanced
Spoken Interview Answer

"`flushSync` is a utility from `react-dom` that forces React to exit automatic batching and flush any pending state updates to the real DOM immediately and synchronously. Its primary use case is when an action requires immediate DOM layout calculation—for instance, adding a new message to a chat list and immediately scrolling the container to the very bottom: `flushSync(() => setMessages(...)); chatBoxRef.current.scrollTop = chatBoxRef.current.scrollHeight;`."

Q16 Why must functions or objects defined inside a component body be wrapped in useCallback/useMemo if placed in a useEffect dependency array? Intermediate
Spoken Interview Answer

"In JavaScript, objects and functions are compared by reference equality (`===`). Every time a component renders, functions and objects declared inside its body are recreated at brand-new memory addresses. If listed in a `useEffect` dependency array, the effect compares the new reference with the old reference, sees they are unequal, and triggers the effect again. This causes an infinite loop: render -> new reference -> effect runs -> state updates -> render."

Q17 What is the useId hook introduced in React 18, and what problem does it solve in full-stack SSR apps? Advanced
Spoken Interview Answer

"`useId` generates unique, stable ID strings that are guaranteed to match across both server-side rendering (SSR) and client-side hydration. In SSR applications, using random numbers (`Math.random()`) or sequential counters causes hydration mismatch errors because the ID generated on the Node.js server differs from the ID generated during client hydration. `useId` derives IDs deterministically from the component's position in the Fiber tree, ensuring perfect hydration match."

Q18 What happens if you omit the dependency array in useEffect entirely: useEffect(fn)? Beginner
Spoken Interview Answer

"If you pass no dependency array at all (`useEffect(fn)`), the effect function executes after EVERY single render of the component (both mount and every re-render). If that effect updates state (`setState`), it triggers another re-render, creating an immediate infinite loop that freezes the browser. An empty array `[]` means run only on mount; passing dependencies `[a, b]` means run on mount and when `a` or `b` changes."

Q19 Scenario: You have a modal that should close when the user clicks outside it. How do you implement a useOnClickOutside custom hook safely? Scenario
Spoken Interview Answer

"I would create a custom hook that accepts a `ref` pointing to the modal container and a `handler` callback. Inside a `useEffect`, attach a `mousedown` or `touchstart` event listener to `document`. When a click occurs, check `ref.current && !ref.current.contains(event.target)`. If the target is not contained within the modal ref, call `handler(event)`. In the effect cleanup function, remove the listener from `document` to prevent memory leaks."

Q20 What is the useTransition hook in React 18, and how does it improve perceived performance? Advanced
Spoken Interview Answer

"`useTransition` allows developers to differentiate between urgent updates and non-urgent transitions. Urgent updates (like typing in a text field) must update the DOM immediately to keep the UI responsive. Non-urgent transitions (like filtering a heavy list of 5,000 items) are wrapped in `startTransition(() => setFilter(value))`. React marks transition updates with a lower priority Lane, keeping the typing input responsive at 60fps while rendering the filtered list in the background, exposing an `isPending` boolean for loading spinners."
