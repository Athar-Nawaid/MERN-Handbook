1. TypeScript Fundamentals: The Compiler & Type Erasure

TypeScript is a statically typed superset of JavaScript that compiles to plain JavaScript. The fundamental truth of TypeScript is:

⚠️ The Law of Type Erasure

TypeScript types exist ONLY at compile time. During the compilation build step (via tsc, esbuild, or SWC), all interfaces, type aliases, generic signatures, and type annotations are completely stripped away from the generated JavaScript code!

Why TypeScript Exists

In large teams, dynamic JavaScript suffers from three critical failure modes:

  1. Silent Runtime Crashes: TypeError: Cannot read properties of undefined accounts for the vast majority of frontend bugs.
  2. Fear of Refactoring: Renaming a database column or API field in backend code leaves you guessing which frontend components will silently break.
  3. Lack of Self-Documenting Contracts: Without types, developers must constantly inspect network JSON logs to understand API payloads.

2. Interfaces versus Type Aliases

One of the most frequent junior-to-mid interview questions is: "What is the difference between an interface and a type alias?"

Feature interface type Alias
Definition Target Can only define Object shapes and function call signatures. Can define objects, primitives, unions (A | B), tuples, functions, and intersections.
Declaration Merging Supported. Declaring the same interface name twice merges their fields automatically (essential for library typing). Forbidden. Declaring the same type alias twice throws a duplicate identifier error.
Extending Inherits via interface B extends A { ... } Combines via intersection: type B = A & { ... }
Computed Properties Limited (cannot create mapped types directly). Fully supported with mapped types (e.g. [K in Keys]: string).
Performance in TSC Slightly faster type-checking because interfaces are cached by name. Can be slower on deeply nested recursive type intersections. 
// Declaration Merging Example (Widely used to extend Express.Request with authenticated user)
declare global {
  namespace Express {
    interface Request {
      user?: {
        id: string;
        role: "admin" | "user";
      };
    }
  }
}

// Now `req.user` is recognized by TypeScript across your entire Express project!

3. Type Narrowing and Type Guards

TypeScript analyzes your control flow to narrow broad union types down to specific concrete types.

The 4 Primary Type Guard Patterns

  1. typeof Guard: Used for JavaScript primitives (string, number, boolean, symbol).
  2. instanceof Guard: Used for classes and constructor instances (Error, Date, RegExp).
  3. in Operator Guard: Checks for the existence of a specific property on an object union.
  4. User-Defined Type Predicate (arg is Type): A custom function whose boolean return value informs the compiler of the argument's type.
// User-Defined Type Guard with `is` predicate
interface AdminUser {
  id: string;
  role: "admin";
  permissions: string[];
}

interface CustomerUser {
  id: string;
  role: "customer";
  loyaltyPoints: number;
}

type AppUser = AdminUser | CustomerUser;

// Custom Type Predicate
function isAdmin(user: AppUser): user is AdminUser {
  return user.role === "admin" && Array.isArray((user as AdminUser).permissions);
}

function processUser(user: AppUser) {
  if (isAdmin(user)) {
    // TypeScript automatically narrows 'user' to AdminUser here!
    console.log("Admin permissions:", user.permissions.join(", "));
  } else {
    // TypeScript narrows 'user' to CustomerUser here!
    console.log("Customer points:", user.loyaltyPoints);
  }
}

4. Discriminated Unions: Eliminating Impossible States

A Discriminated Union (or Tagged Union) is a pattern where every object type in a union shares a common literal property (the discriminant, e.g. status or type).

+---------------------------------------+ | AsyncState | +---------------------------------------+ | +--------------------------------+--------------------------------+ | | | v v v +--------------------+ +--------------------+ +--------------------+ | LoadingState | | SuccessState | | ErrorState | | status: 'loading' | | status: 'success' | | status: 'error' | | (data: null) | | data: Task[] | | error: string | +--------------------+ +--------------------+ +--------------------+
Figure 5.1: Discriminated Union Modeling State Machine Without Invalid States
// ANTI-PATTERN: The "Bag of Optionals" (Allows impossible states like loading=true AND data=[...])
interface BadState {
  isLoading: boolean;
  data?: Task[];
  error?: string;
}

// PRODUCTION PATTERN: Discriminated Union
type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: string };

function renderUI(state: RequestState) {
  switch (state.status) {
    case "idle":
      return "Ready to search.";
    case "loading":
      return "Loading spinner...";
    case "success":
      // TypeScript guarantees state.data exists here!
      return `Loaded ${state.data.length} items.`;
    case "error":
      // TypeScript guarantees state.error exists here!
      return `Failed: ${state.error}`;
    default:
      // Exhaustiveness checking with 'never'
      const _exhaustiveCheck: never = state;
      return _exhaustiveCheck;
  }
}

5. Generics and Utility Types

Generics allow you to write reusable, type-safe functions, classes, and interfaces that work over a variety of types rather than a single one, while preserving exact type information. 

// Generic API Response wrapper with default type
interface ApiResponse {
  status: "success" | "fail";
  statusCode: number;
  data: TData;
  timestamp: string;
}

// Generic function with constraints (T must have an 'id' property)
function findById(items: T[], id: string | number): T | undefined {
  return items.find(item => item.id === id);
}

Core Utility Types Every Full-Stack Engineer Must Know

  • Partial<T>: Makes all properties in T optional (used for PATCH payloads).
  • Required<T>: Makes all properties in T required.
  • Readonly<T>: Marks all properties as read-only.
  • Record<K, T>: Constructs an object type whose property keys are K and property values are T.
  • Pick<T, K>: Constructs a type by picking the set of properties K from T.
  • Omit<T, K>: Constructs a type by picking all properties from T and then removing K.
  • ReturnType<T>: Extracts the return type of a function type.
  • Awaited<T>: Recursively unwraps Promise types (e.g., Awaited<Promise<string>> becomes string).

7. Runtime Validation with Zod vs Compile-Time Types

Because TypeScript types are completely erased at runtime, TypeScript cannot protect your backend against malicious HTTP requests or corrupted database payloads!

Modern full-stack engineering pairs compile-time typing with Zod: a schema declaration library that parses runtime JSON and automatically infers compile-time TypeScript types. 

import { z } from "zod";

// 1. Define the Runtime Schema
export const UserRegistrationSchema = z.object({
  email: z.string().email("Invalid email format"),
  password: z.string().min(8, "Password must be at least 8 characters"),
  age: z.number().int().min(18, "Must be at least 18 years old").optional()
});

// 2. Automatically infer the compile-time TypeScript type!
export type UserRegistrationDTO = z.infer;
// Equivalent to:
// type UserRegistrationDTO = {
//   email: string;
//   password: string;
//   age?: number | undefined;
// }

// 3. Express Validation Middleware
export function validateBody(schema: z.ZodSchema) {
  return (req: any, res: any, next: any) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      return res.status(400).json({
        error: "Validation Failed",
        details: result.error.flatten().fieldErrors
      });
    }
    req.body = result.data; // Safely sanitized & typed!
    next();
  };
}

Interview Questions and Answers

20 technical interview questions covering TypeScript compiler mechanics, type narrowing, generics, React/Express typing, and runtime validation.

Q1 What is the difference between `any` and `unknown` in TypeScript? Beginner
Spoken Interview Answer

"`any` completely turns off TypeScript's type checker, allowing you to access any property or call any method without safety checks, which can lead to runtime crashes. `unknown` is the type-safe counterpart of any: it accepts any value, but TypeScript forbids you from performing any operations on it until you explicitly narrow its type using a type guard or assertion. In production, we always prefer `unknown` over `any` when dealing with uncertain inputs like API responses."

Q2 Explain the difference between `interface` and `type` alias. When should you use which? Intermediate
Spoken Interview Answer

"`interface` is specifically for defining object shapes and supports declaration merging—meaning defining the same interface twice combines their properties, which is essential when augmenting third-party library types like Express. `type` is more flexible and can define union types, primitives, tuples, and mapped types. The industry standard is to use `interface` for public APIs and object models, and `type` for unions, intersections, and complex utility transformations."

Q3 What is a Discriminated Union and why is it superior to using optional properties for state? Intermediate
Spoken Interview Answer

"A Discriminated Union is a pattern where a union of object types shares a common literal string property (the discriminant, such as status: 'loading' | 'success'). It is superior to optional properties because it makes impossible states unrepresentable in the type system. For example, it prevents a state object from having both isLoading=true and data=[...], forcing your code to handle each state cleanly in a switch statement."

Q4 What is a Type Predicate (`arg is Type`), and when is it necessary? Advanced
Spoken Interview Answer

"A type predicate is a custom type guard function with a return signature formatted as `value is SpecificType`. Normal functions return a boolean, but TypeScript cannot deduce that a `true` return means the input is a specific type. A type predicate informs the TypeScript compiler that if the function returns true, the checked variable is guaranteed to be that specific type within that branch." 

function isError(err: unknown): err is Error {
  return err instanceof Error;
}
Q5 What does the `as const` assertion do in TypeScript? Give a practical example. Intermediate
Spoken Interview Answer

"`as const` instructs TypeScript to infer the narrowest literal type possible for expressions instead of widening them to general primitives (like string or number), and marks all nested properties as `readonly`. For example, `const routes = ['home', 'about'] as const` creates a readonly tuple with literal types `'home' | 'about'`, rather than a mutable `string[]`."

Q6 What is the difference between `never` and `void` in TypeScript? Beginner
Spoken Interview Answer

"`void` indicates that a function returns normally, but returns no value (its runtime return value is `undefined`). `never` indicates a function that NEVER returns at all—such as a function that always throws an exception or enters an infinite loop. `never` is also used for exhaustiveness checking in switch statements."

Q7 Explain the `Pick` and `Omit` utility types. What are their internal definitions? Intermediate
Spoken Interview Answer

"`Pick` creates a new type by choosing only the specified subset of keys from an existing type. `Omit` creates a new type by removing the specified keys from an existing type. Under the hood, `Pick` uses mapped types `[P in K]: T[P]`, and `Omit` is implemented as `Pick>`."

Q8 How do you implement Exhaustiveness Checking with `never`? Why is it crucial during refactoring? Advanced
Spoken Interview Answer

"In the `default` branch of a switch statement handling a discriminated union, you assign the state to a variable typed as `never`: `const _exhaustive: never = state`. Because every valid case was handled above, the default case should be unreachable. If someone adds a new member to the union (like status: 'paused') and forgets to update the switch statement, TypeScript will throw a compile error at the `never` assignment, catching unhandled cases instantly during refactoring."

Q9 Scenario: You have a backend Express route receiving user input. Why is relying solely on TypeScript interfaces a security risk? How do you fix it? Scenario
Spoken Interview Answer

"TypeScript types are completely erased during compilation and do not exist at runtime in the Node.js process. An attacker can send any malformed JSON payload (or inject extra fields like `role: 'admin'`), and TypeScript cannot validate it over the wire. To fix this, we use runtime schema validation libraries like Zod or Joi to inspect and sanitize incoming HTTP payloads, and infer compile-time TypeScript types from the runtime schemas via `z.infer`."

Q10 What are Generic Constraints (`T extends ...`), and why are they needed? Advanced
Spoken Interview Answer

"By default, a generic parameter `T` can be any type, which prevents you from accessing specific properties inside the generic function. A generic constraint uses `extends` (e.g. `T extends { length: number }`) to restrict `T` to types that satisfy that contract. This allows you to safely access `.length` inside the function while still preserving the exact returned type."

Q11 What is the difference between Type Assertions (`as SomeType`) and Type Annotations (`: SomeType`)? Intermediate
Spoken Interview Answer

"A type annotation (`const x: User = ...`) instructs TypeScript to verify that the value matches the `User` contract during assignment. If a required field is missing, it fails at compile time. A type assertion (`const x = val as User`) tells the compiler to override its own inference and trust the developer that `val` is a `User`, completely suppressing missing property errors. Overusing `as` assertions introduces runtime bugs by lying to the compiler."

Q12 What does the non-null assertion operator (`!`) do? When should you avoid it? Beginner
Spoken Interview Answer

"The non-null assertion operator `!` tells the compiler to assume an expression is not null or undefined, stripping those types from unions. It should generally be avoided because it bypasses safety checks; if the value actually is null at runtime, accessing properties on it will cause an unhandled `TypeError` crash. Instead, prefer optional chaining (`?.`) or explicit null checks."

Q13 What is the `Awaited` utility type, and when is it useful? Intermediate
Spoken Interview Answer

"`Awaited` recursively unwraps Promises, extracting the resolved inner type. It models the behavior of `await` in async functions or the `.then()` method on Promises. It is especially useful when extracting the return type of async functions: `type User = Awaited>`."

Q14 What are Mapped Types in TypeScript? Show how to make all properties optional. Advanced
Spoken Interview Answer

"Mapped types allow you to create new types by iterating over the keys of an existing type using the `[P in keyof T]` syntax, similar to array mapping. For example, TypeScript's built-in `Partial` is defined as `type MyPartial = { [P in keyof T]?: T[P] }`, which iterates over every key in T and adds the optional `?` modifier."

Q15 Scenario: How do you share DTOs and API contracts between a React frontend and Node.js backend in a monorepo? Scenario
Spoken Interview Answer

"In a monorepo (using Turborepo, Nx, or npm workspaces), I create a dedicated shared package (e.g. `@app/shared-types`). In this package, I export Zod schemas and infer TypeScript types from them. Both the Express backend and React frontend import from `@app/shared-types`. When a backend developer alters an API contract, TypeScript immediately highlights compiler errors in frontend components during the build pipeline."

Q16 How do you type `useRef` in React for DOM elements versus mutable instance variables? Intermediate
Spoken Interview Answer

"For DOM elements, pass the element type with an initial value of null: `const inputRef = useRef(null)`. This produces a `RefObject` with a read-only `.current` property managed by React. For mutable instance variables (like a timer ID), pass the type without null or with an initial value: `const timerRef = useRef(null)`. This produces a `MutableRefObject` whose `.current` property can be modified directly."

Q17 What is Declaration Merging and how is it used in Express apps? Beginner
Spoken Interview Answer

"Declaration merging is a TypeScript feature where multiple interface declarations with the identical name in the same namespace are merged into a single interface definition. In Express applications, it is commonly used to extend the `Express.Request` interface with an authenticated `user` property (`req.user`) in custom middleware, avoiding type errors when accessing `req.user` in controllers."

Q18 What is the difference between `Exclude` and `Omit`? Advanced
Spoken Interview Answer

"`Exclude` operates on UNION types, excluding members of U from T (e.g., `Exclude<'a' | 'b' | 'c', 'a'>` yields `'b' | 'c'`). `Omit` operates on OBJECT types, removing properties whose keys match K from object T."

Q19 Scenario: You have a legacy JavaScript codebase and need to migrate it to TypeScript without stopping feature work. What is your incremental migration strategy? Scenario
Spoken Interview Answer

"I adopt a phased strategy: 1. Add `tsconfig.json` with `allowJs: true` and `checkJs: false` so existing .js files compile without errors. 2. Enable strict linting and establish a rule that all NEW files must be written in TypeScript (.ts/.tsx). 3. Migrate shared models, DTOs, and utility functions to TypeScript first. 4. Gradually rename legacy .js files to .ts file-by-file during feature updates, enabling `strict: true` once the core codebase is migrated."

Q20 What are Conditional Types in TypeScript? Explain the `infer` keyword. Advanced
Spoken Interview Answer

"Conditional types select one of two possible types based on a condition: `T extends U ? X : Y`. The `infer` keyword is used within the condition to introduce a type variable to be deduced from the type being checked. For example, `type ReturnType = T extends (...args: any[]) => infer R ? R : any` uses `infer R` to extract the return type R directly from the function signature."
