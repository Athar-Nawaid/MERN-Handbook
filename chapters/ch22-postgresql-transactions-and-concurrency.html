1. ACID Guarantees in PostgreSQL

In relational databases, a Transaction is a single logical unit of work consisting of one or more SQL operations. To ensure data integrity in the face of network partitions, crashes, and concurrent clients, PostgreSQL guarantees ACID properties:

Property Definition PostgreSQL Internal Mechanism
Atomicity "All or Nothing." If any statement in a transaction fails or crashes, all previous modifications are rolled back completely. Tracked via transaction status in the Commit Log (pg_xact). Uncommitted tuples remain invisible to other transactions.
Consistency A transaction transforms the database from one valid state to another, strictly satisfying all declared constraints (Foreign Keys, CHECK, UNIQUE, NOT NULL). Engine-enforced constraint validation during execution and deferred constraint verification at COMMIT.
Isolation Concurrent transactions execute without stepping on each other's intermediate state, appearing as if they executed sequentially. Multi-Version Concurrency Control (MVCC) snapshots and table/row-level locks.
Durability Once a transaction commits, its changes survive permanently, even in the event of an immediate operating system crash or power outage. Write-Ahead Logging (WAL): Changes are flushed sequentially to append-only disk logs before the client receives the commit confirmation.

1.1 How Write-Ahead Logging (WAL) Works

Modifying database data files on disk directly on every commit is too slow because it requires random I/O writes across scattered disk pages.

Instead, PostgreSQL writes changes sequentially to an append-only log called the Write-Ahead Log (WAL):

  1. Data changes are made to in-memory pages in the Shared Buffers pool (creating "dirty pages").
  2. A WAL record describing the mutation is appended and flushed to disk using fsync().
  3. Once the WAL record is safely persisted to disk, the transaction is marked as committed and success is returned to the client.
  4. Periodically, a background process called the Checkpointer flushes the accumulated dirty in-memory pages from Shared Buffers to the actual table data files on disk. If the server loses power, PostgreSQL replays the WAL log from the last checkpoint upon restart (Crash Recovery).

2. Transaction Isolation Levels & Read Phenomena

The SQL standard defines four transaction isolation levels to balance consistency against concurrency. Lower isolation levels increase transaction throughput but allow subtle concurrency anomalies:

Isolation Level Dirty Read Non-Repeatable Read Phantom Read Serialization Anomaly
Read Uncommitted Allowed by SQL standard (PostgreSQL treats as Read Committed!) Possible Possible Possible
Read Committed (PostgreSQL Default) Prevented Possible Possible Possible
Repeatable Read Prevented Prevented Prevented in PostgreSQL! Possible (e.g. Write Skew)
Serializable Prevented Prevented Prevented Prevented (Full strict serializability)

2.1 Deconstructing the Concurrency Phenomena

  • Dirty Read: Transaction A reads uncommitted data written by Transaction B. If Transaction B rolls back, Transaction A acted on data that never officially existed. (PostgreSQL never allows dirty reads under any isolation level!)
  • Non-Repeatable Read (Fuzzy Read): Transaction A reads a row. Transaction B updates or deletes that row and commits. Transaction A re-reads the same row and sees modified or missing values.
  • Phantom Read: Transaction A executes a range query (e.g. WHERE age > 30). Transaction B inserts a new row matching that predicate and commits. Transaction A re-runs the range query and sees new "phantom" rows.
  • Serialization Anomaly (Write Skew): Two concurrent transactions read overlapping state, make independent decisions based on that state, and write changes that violate a global business invariant when combined (e.g., two on-call doctors simultaneously request leave because each sees the other doctor still active).
📌 Statement Snapshot vs Transaction Snapshot

In PostgreSQL's default Read Committed level, a brand-new snapshot is created at the beginning of each individual SQL statement. If another transaction commits between Query 1 and Query 2 in the same transaction, Query 2 sees the new data.

In Repeatable Read, a single snapshot is created at the beginning of the first non-transaction-control statement in the transaction. All subsequent queries throughout the transaction see that exact frozen point-in-time snapshot, regardless of external commits!

3. PostgreSQL MVCC Internals: xmin, xmax, and Bloat

In traditional databases, readers block writers and writers block readers. In PostgreSQL, readers never block writers, and writers never block readers. This is made possible by Multi-Version Concurrency Control (MVCC).

3.1 The Hidden System Columns: xmin and xmax

Every physical row (called a tuple) stored in a PostgreSQL table header contains hidden metadata fields:

  • xmin: The Transaction ID (XID) of the transaction that inserted this tuple.
  • xmax: The Transaction ID of the transaction that deleted or updated this tuple (set to 0 if active).
Figure 22.1: PostgreSQL MVCC Row Updating & Versioning
[ Step 1: Initial Insert by Transaction 100 ]
+-----------------------------------------------------------+
| xmin: 100 | xmax: 0   | id: 1 | balance: $500             | (Active)
+-----------------------------------------------------------+

[ Step 2: Transaction 105 executes UPDATE balance = $600 ]
PostgreSQL DOES NOT overwrite the row! It writes a brand-new row version:
+-----------------------------------------------------------+
| xmin: 100 | xmax: 105 | id: 1 | balance: $500             | (Old Version: "Dead Tuple")
+-----------------------------------------------------------+
| xmin: 105 | xmax: 0   | id: 1 | balance: $600             | (New Version: Active)
+-----------------------------------------------------------+

- Any transaction that started BEFORE Tx 105 committed still reads the $500 version!
- Any transaction that started AFTER Tx 105 committed reads the $600 version!

3.2 Table Bloat and the Autovacuum Daemon

Because updates and deletes create dead tuples rather than overwriting space, PostgreSQL tables accumulate dead tuples over time. This phenomenon is known as table bloat.

The VACUUM process scans tables, reclaims space occupied by dead tuples, and marks those storage slots as reusable for future inserts:

  • Autovacuum Daemon: Runs continuously in the background, automatically vacuuming tables whose dead tuple count exceeds configured thresholds (e.g. autovacuum_vacuum_scale_factor = 0.2).
  • VACUUM FULL: Completely rewrites the entire table on disk to compact space back to the operating system. Warning: Acquires an ACCESS EXCLUSIVE lock that completely halts application reads and writes! Avoid in production.

4. Row-Level Locking: FOR UPDATE, FOR SHARE, and SKIP LOCKED

When multiple application threads attempt to update the same record concurrently, application-level race conditions occur (e.g. reserving the last concert ticket or deducting from an account balance).

Lock Mode SQL Syntax What It Locks Conflicts With
FOR UPDATE SELECT ... FOR UPDATE Exclusive row lock. Prevents other transactions from updating, deleting, or locking the row. All other row locks (FOR UPDATE, FOR NO KEY UPDATE, FOR SHARE).
FOR NO KEY UPDATE SELECT ... FOR NO KEY UPDATE Weaker lock. Allows concurrent FOR SHARE locks if foreign key columns are not modified. FOR UPDATE and other FOR NO KEY UPDATE locks.
FOR SHARE SELECT ... FOR SHARE Shared lock. Allows other transactions to read or acquire FOR SHARE, but blocks updates/deletes. FOR UPDATE and FOR NO KEY UPDATE.
SKIP LOCKED SELECT ... FOR UPDATE SKIP LOCKED Skips any rows already locked by other transactions instead of waiting! The cornerstone of high-performance task queues in PostgreSQL.
sql (High-Throughput Job Queue with SKIP LOCKED) 
-- Worker query: Atomically fetch and lock the next available pending job
-- Without SKIP LOCKED, 10 workers would contend and wait on the exact same row!
-- With SKIP LOCKED, each worker instantly grabs the next unlocked job with 0 contention!
BEGIN;

WITH next_job AS (
  SELECT id
  FROM background_jobs
  WHERE status = 'PENDING'
  ORDER BY priority DESC, created_at ASC
  LIMIT 1
  FOR UPDATE SKIP LOCKED -- Skips rows locked by other concurrent workers!
)
UPDATE background_jobs
SET 
  status = 'PROCESSING',
  locked_by = 'worker-node-04',
  updated_at = NOW()
FROM next_job
WHERE background_jobs.id = next_job.id
RETURNING background_jobs.*;

COMMIT;

5. Optimistic vs Pessimistic Concurrency Control

Strategy Core Concept When to Use Trade-Offs
Pessimistic Concurrency Assume conflict is frequent. Acquire an explicit database lock (SELECT ... FOR UPDATE) before reading and hold it until the transaction commits. High-contention financial transactions, inventory decrementing, flight seat reservations. High lock contention; slow transactions can hold locks, causing cascading timeouts or deadlocks.
Optimistic Concurrency (OCC) Assume conflict is rare. Read data without any locks, along with a version INT or updated_at column. When writing, verify the version hasn't changed. Low-contention web applications, document editors, user profile updates. Zero database lock overhead. If conflict occurs, the write is rejected and the application must catch and retry.
javascript (Optimistic Concurrency Control in Node.js) 
// Optimistic Concurrency Control (OCC) pattern: Compare-and-Swap
export async function updateArticleContent(articleId, newContent, clientProvidedVersion) {
  // Execute atomic update only if version matches what client read
  const result = await db.query(
    `UPDATE articles 
     SET content = $1, version = version + 1, updated_at = NOW() 
     WHERE id = $2 AND version = $3 
     RETURNING *`,
    [newContent, articleId, clientProvidedVersion]
  );

  // If rowCount is 0, someone else updated the article in the meantime!
  if (result.rowCount === 0) {
    const error = new Error("Conflict: This article was modified by another user. Please reload.");
    error.statusCode = 409; // HTTP 409 Conflict
    throw error;
  }

  return result.rows[0];
}

6. Deadlocks: Causes, Detection, and Prevention

A Deadlock occurs when two or more transactions hold locks that the other transactions need to proceed, creating a circular dependency where neither transaction can finish:

Figure 22.2: Circular Deadlock Dependency
[ Transaction 1 ]                              [ Transaction 2 ]
Holds Lock on Account A                        Holds Lock on Account B
Wants Lock on Account B (Waits...)             Wants Lock on Account A (Waits...)
          \                                          /
           \-------------> [ DEADLOCK! ] <----------/

6.1 Deadlock Detection in PostgreSQL

PostgreSQL does not check for deadlocks on every lock request because building dependency wait-for graphs is computationally expensive.

Instead, PostgreSQL waits for the duration specified by deadlock_timeout (default: 1 second). If a transaction has been waiting for a lock for longer than 1 second, the engine initiates a deadlock check. If a cycle is detected, PostgreSQL automatically terminates one of the offending transactions with error code 40P01 (deadlock detected), allowing the other transaction to complete!

6.2 Prevention Rule: Deterministic Lock Acquisition Order

The most robust defense against deadlocks is application discipline: always acquire locks in a globally consistent, deterministic order (e.g. sorted by primary key ID).

sql (Deadlock-Free Fund Transfer Pattern) 
-- DEADLOCK-PRONE:
-- Tx 1 transfers from Account 1 to Account 2 (locks 1 then 2)
-- Tx 2 transfers from Account 2 to Account 1 (locks 2 then 1) --> DEADLOCK!

-- DEADLOCK-FREE PATTERN: Always lock lower ID first!
CREATE OR REPLACE FUNCTION transfer_funds(
  from_account INT, 
  to_account INT, 
  amount NUMERIC
) RETURNS VOID AS $$
DECLARE
  first_lock INT;
  second_lock INT;
BEGIN
  -- Determine strictly sorted order regardless of transfer direction!
  IF from_account < to_account THEN
    first_lock := from_account;
    second_lock := to_account;
  ELSE
    first_lock := to_account;
    second_lock := from_account;
  END IF;

  -- Lock both rows in guaranteed ascending order
  PERFORM * FROM accounts WHERE id = first_lock FOR UPDATE;
  PERFORM * FROM accounts WHERE id = second_lock FOR UPDATE;

  -- Execute transfers safely
  UPDATE accounts SET balance = balance - amount WHERE id = from_account;
  UPDATE accounts SET balance = balance + amount WHERE id = to_account;
END;
$$ LANGUAGE plpgsql;

Exercise 22.1 Build a Concurrency-Safe Inventory Reservation System

Problem: An e-commerce flash sale has 10 units of an item. 1,000 users attempt to checkout simultaneously. Implement a PostgreSQL PL/pgSQL function or transaction that decrements inventory safely without overselling, guarantees no deadlocks, and returns immediately if stock is depleted.

View Complete Solution
sql 
-- Atomic Single-Statement Reservation Pattern (Zero lock wait overhead!)
-- A single UPDATE statement is inherently atomic in PostgreSQL and operates under implicit row locking.
CREATE OR REPLACE FUNCTION reserve_inventory(
  p_product_id UUID, 
  p_quantity INT
) RETURNS BOOLEAN AS $$
DECLARE
  rows_updated INT;
BEGIN
  UPDATE products
  SET 
    stock_quantity = stock_quantity - p_quantity,
    updated_at = NOW()
  WHERE id = p_product_id AND stock_quantity >= p_quantity;

  GET DIAGNOSTICS rows_updated = ROW_COUNT;

  -- Returns TRUE if reserved, FALSE if stock was insufficient!
  RETURN (rows_updated > 0);
END;
$$ LANGUAGE plpgsql;

8. Chapter-Specific Interview Questions and Answers

Master these 20 high-frequency interview questions covering transactions, MVCC, isolation levels, row locks, and concurrency anomalies.

Q01 What are the ACID properties in database systems? Beginner
Spoken Interview Answer

"ACID stands for: Atomicity (all operations within a transaction succeed or all are rolled back), Consistency (data always satisfies all schema constraints and foreign keys), Isolation (concurrent transactions execute independently without observing intermediate uncommitted states), and Durability (committed changes survive permanently via Write-Ahead Logging even across system crashes)."

Q02 How does Write-Ahead Logging (WAL) guarantee durability while maintaining high write performance? Intermediate
Spoken Interview Answer

"Directly modifying table data pages on disk on every commit is slow because it requires random I/O writes. With WAL, PostgreSQL writes data modifications to in-memory Shared Buffers, but synchronously appends a sequential log record to the WAL file on disk before confirming the commit. Sequential disk writes are orders of magnitude faster than random writes. In the event of a power failure, PostgreSQL replays the WAL from the last checkpoint upon reboot to restore full state."

Q03 How does PostgreSQL's MVCC work under the hood using xmin and xmax? Intermediate
Spoken Interview Answer

"PostgreSQL does not overwrite rows in place. Every tuple has header fields: `xmin` (the transaction ID that inserted it) and `xmax` (the transaction ID that deleted or updated it). When an UPDATE occurs, PostgreSQL sets `xmax` on the old tuple and inserts a brand-new tuple with a new `xmin`. Each transaction has an active snapshot defining which transaction IDs are visible. A transaction only reads tuples whose `xmin` has committed and whose `xmax` is either uncommitted or greater than the snapshot point."

Q04 What is Table Bloat in PostgreSQL, and how does the autovacuum process address it? Advanced
Spoken Interview Answer

"Table bloat occurs because updates and deletes leave old dead tuples on disk. Over time, tables and B-Tree indexes consume unnecessary disk space and require extra page I/O reads. The `autovacuum` background daemon periodically scans tables, finds dead tuples that are no longer visible to any active transaction snapshot, and marks their space in the Free Space Map (FSM) so future inserts can reuse those physical disk slots without expanding the table file."

Q05 What is the difference between Read Committed and Repeatable Read isolation levels in PostgreSQL? Intermediate
Spoken Interview Answer

"In the default Read Committed level, a new snapshot is generated at the start of each individual SQL statement within the transaction. If another transaction commits changes between two SELECT statements, the second SELECT will see those changes. In Repeatable Read, a single snapshot is captured at the start of the first statement and held for the entire transaction; all subsequent queries see that identical frozen point in time, preventing non-repeatable reads and phantom reads."

Q06 Can Dirty Reads occur in PostgreSQL? Beginner
Spoken Interview Answer

"No. Even if you explicitly configure `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED`, PostgreSQL internally treats it as Read Committed. Due to its MVCC architecture, uncommitted tuples lack committed `xmin` stamps and are physically invisible to other transactions, making dirty reads impossible in PostgreSQL."

Q07 What is the Serialization Anomaly (Write Skew), and how does the Serializable isolation level prevent it? Advanced
Spoken Interview Answer

"Write Skew occurs when two concurrent transactions read overlapping datasets, make decisions based on that state, and write changes that break a global business invariant when executed concurrently (e.g. two doctors taking leave simultaneously). Serializable Snapshot Isolation (SSI) tracks read-write dependency locks (SIREAD locks) in memory. If a dangerous cycle of dependencies is detected, PostgreSQL aborts one transaction with error 40001 (serialization_failure), allowing the application to retry."

Q08 What is the difference between SELECT ... FOR UPDATE and SELECT ... FOR SHARE? Intermediate
Spoken Interview Answer

"`FOR UPDATE` acquires an exclusive row lock, preventing any other transaction from locking, modifying, or deleting the selected rows until the transaction ends. `FOR SHARE` acquires a shared read lock: multiple transactions can hold `FOR SHARE` locks on the same row concurrently, but any transaction attempting to update or delete those rows will be blocked until all shared locks release."

Q09 Why is SELECT ... FOR UPDATE SKIP LOCKED essential for building task queues in PostgreSQL? Advanced
Spoken Interview Answer

"Without `SKIP LOCKED`, if 10 concurrent worker processes query `SELECT ... FROM jobs WHERE status = 'PENDING' LIMIT 1 FOR UPDATE`, all workers target the same first job row. One worker locks it, while the other 9 workers block and wait. With `SKIP LOCKED`, workers automatically skip any rows currently locked by peers and immediately lock the next available unlocked job, enabling lock-free concurrent job distribution with zero wait time."

Q10 What is a Deadlock, and how does PostgreSQL detect and resolve it? Intermediate
Spoken Interview Answer

"A deadlock occurs when two transactions have circular lock dependencies: Tx 1 holds Lock A and waits for Lock B, while Tx 2 holds Lock B and waits for Lock A. PostgreSQL has a `deadlock_timeout` timer (default 1s). When a transaction waits for a lock longer than 1 second, PostgreSQL runs a cycle-detection algorithm on the wait-for graph. If a cycle exists, PostgreSQL terminates one transaction with error 40P01, allowing the other to proceed."

Q11 How do you prevent deadlocks in financial fund transfers between two accounts? Intermediate
Spoken Interview Answer

"Deadlocks during transfers happen when Tx 1 transfers from A to B (locking A then B), and Tx 2 transfers from B to A (locking B then A). The golden rule is Deterministic Lock Ordering: always acquire locks in sorted order of primary key ID (`min(A, B)` first, then `max(A, B)`), regardless of who is sending or receiving money. Since both transactions acquire locks in identical numerical order, circular lock cycles are mathematically impossible."

Q12 What is Optimistic Concurrency Control (OCC), and how is it implemented in SQL? Intermediate
Spoken Interview Answer

"OCC assumes conflicts are rare and avoids holding database locks. A `version INT` column is added to the table. When updating, the query executes a Compare-and-Swap: `UPDATE items SET val = $1, version = version + 1 WHERE id = $2 AND version = $3`. If another user updated the item in the meantime, the version no longer matches, the update affects 0 rows, and the application detects the conflict and informs the user to refresh."

Q13 What are PostgreSQL Advisory Locks, and when should you use them? Advanced
Spoken Interview Answer

"Advisory locks are application-defined distributed mutexes managed by PostgreSQL (`pg_advisory_lock(int)` or `pg_try_advisory_lock(int)`). They do not lock physical tables or rows; instead, they lock an arbitrary 64-bit integer key. They are ideal for synchronizing application-level operations—such as ensuring only one instance of a nightly cron job runs across a cluster of 20 microservices—without needing a separate Redis instance."

Q14 What is a Checkpoint in PostgreSQL, and why does it occur? Beginner
Spoken Interview Answer

"A checkpoint is a periodic point in the WAL transaction log where PostgreSQL flushes all modified dirty data pages from in-memory Shared Buffers to physical disk files. Once completed, a checkpoint record is written to the WAL. Checkpoints bound crash recovery time: if the database crashes, it only needs to replay WAL logs recorded since the latest checkpoint."

Q15 What is the Heap-Only Tuples (HOT) optimization in PostgreSQL? Advanced
Spoken Interview Answer

"HOT allows PostgreSQL to update a row without adding new index entries if: 1. No indexed columns were modified, and 2. The new tuple version fits inside the same data page as the old tuple. The old tuple points directly to the new tuple via an intra-page pointer chain. This drastically reduces index bloat and disk write I/O during frequent column updates."

Q16 Scenario: A flash sale has 1 product remaining. Two users click 'Buy' at the exact same millisecond. How do you prevent overselling using a single SQL query? Scenario
Spoken Interview Answer

"Execute an atomic conditional update: `UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1 RETURNING *`. Because an individual UPDATE statement executes under an implicit row lock in PostgreSQL, the engine serializes the two queries. The first query succeeds and decrements stock to 0. The second query tests `stock >= 1`, finds 0, updates nothing, and returns 0 rows, signaling out-of-stock without needing complex transaction blocks."

Q17 What is the difference between VACUUM and VACUUM FULL? Intermediate
Spoken Interview Answer

"Standard `VACUUM` runs concurrently with active queries without locking; it frees dead tuple space within data pages for future inserts, but does NOT return empty disk space to the OS. `VACUUM FULL` physically rewrites the entire table into a new disk file to compact all space back to the OS. However, `VACUUM FULL` requires an `ACCESS EXCLUSIVE` lock, completely blocking all reads and writes until it finishes."

Q18 What is Transaction ID (XID) Wraparound, and how does PostgreSQL prevent catastrophic data loss? Advanced
Spoken Interview Answer

"PostgreSQL uses 32-bit transaction IDs, which wrap around after ~4 billion transactions. Without protection, a wrapped-around transaction would treat old historical transactions as occurring in the future, rendering past data invisible. Autovacuum prevents this by running 'aggressive freezing': it replaces old `xmin` values with a special frozen transaction ID `FrozenTransactionId` (2), guaranteeing older data remains permanently visible."

Q19 What is the difference between a table-level ACCESS SHARE lock and an ACCESS EXCLUSIVE lock? Intermediate
Spoken Interview Answer

"`ACCESS SHARE` is acquired automatically by read queries (`SELECT`); it only conflicts with `ACCESS EXCLUSIVE`. `ACCESS EXCLUSIVE` is the heaviest lock in PostgreSQL, acquired by commands like `ALTER TABLE`, `DROP TABLE`, and `VACUUM FULL`. It conflicts with ALL other lock modes, completely blocking all concurrent reads, inserts, and updates."

Q20 Why should you avoid long-running transactions in PostgreSQL? Advanced
Spoken Interview Answer

"A long-running transaction holds its snapshot open. Autovacuum CANNOT clean up any dead tuples created after that snapshot's `xmin`! This causes massive table and index bloat across the entire database. Additionally, long transactions hold row or table locks, blocking DDL migrations and accumulating queue locks, and prevent WAL log truncation, risking disk space exhaustion."
