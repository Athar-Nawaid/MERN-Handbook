1. The Git Object Model & Content-Addressable Storage

Underneath its command-line interface, Git is not a file delta tracker (like SVN or CVS); it is a Content-Addressable Key-Value Store built on a Directed Acyclic Graph (DAG).

Every piece of data stored in Git lives inside the .git/objects/ directory. Its key is a 40-character SHA-1 (or SHA-256) cryptographic hash derived from the object's payload size and content:

ASCII Diagram: Git Object Types and Relationships 
  Commit Object (hash: a1b2c3d)
  +-------------------------------------------------------------+
  | tree: 98f4e2 (Root Tree)                                    |
  | parent: e5f6a7 (Parent Commit)                              |
  | author: Alex <alex@dev.com> 1700000000 +0000               |
  | committer: Alex <alex@dev.com> 1700000000 +0000            |
  |                                                             |
  | feat(auth): add JWT login endpoint                         |
  +-------------------------------------------------------------+
               |
               v
  Tree Object (hash: 98f4e2) [Root directory: "/"]
  +-------------------------------------------------------------+
  | 100644 blob 3e8a10  package.json                           |
  | 040000 tree 7c5d91  src/                                   |
  +-------------------------------------------------------------+
                           |
                           v
              Subtree Object (hash: 7c5d91) [directory: "src/"]
              +-------------------------------------------------+
              | 100644 blob 4f2b90  server.ts                   |
              | 100644 blob e8a3d1  auth.ts                     |
              +-------------------------------------------------+
                                       |
                                       v
                          Blob Object (hash: e8a3d1)
                          +-----------------------------+
                          | export function login() {   |
                          |   // raw file bytes...      |
                          | }                           |
                          +-----------------------------+

The 4 Core Git Objects

Object Type Header & Contents Role in Git DAG
Blob (Binary Large Object) blob <content_size>\0<file_contents> Stores the raw byte content of a file. Blobs contain no filenames, directory paths, or timestamps—only the pure file bytes. If two identical files exist in different folders, Git stores only one single blob!
Tree tree <size>\0[mode type hash filename]... Represents a directory. Maps human-readable filenames and file permissions (e.g., 100644 for normal files, 100755 for executables) to their underlying Blob or Subtree hashes.
Commit commit <size>\0tree <hash>\nparent <hash>... A permanent snapshot of the project state. Points to a root Tree object, zero or more parent commit hashes, author info, committer info, and the commit message.
Annotated Tag tag <size>\0object <hash>\ntype commit\n... An explicit, immutable pointer to a commit. Includes tagger name, timestamp, message, and optional GPG cryptographic signature (unlike lightweight tags, which are simple pointer files in .git/refs/tags/).

2. The Three Trees Architecture

Understanding Git requires visualizing its three operational areas (often referred to as the "Three Trees"):

ASCII Diagram: The Three Trees Pipeline 
Working Directory               Staging Index (Cache)              HEAD (Repository)
 [Files on disk]                 [.git/index binary]             [Committed Snapshots]
        |                                 |                                 |
        |--- 1. Edit code ----------------|                                 |
        |                                 |                                 |
        |--- 2. git add <file> ----------->|                                 |
        |    (Creates Blobs in objects/)  |                                 |
        |                                 |--- 3. git commit --------------->|
        |                                 |    (Creates Tree & Commit)       |
        |                                 |                                 |
        |<-- 4. git restore <file> -------| (Discards uncommitted edits)   |
        |                                 |                                 |
        |<------------------ 5. git reset --hard HEAD ----------------------|
        |                    (Overwrites working dir & index with commit)   |
  • 1. Working Directory: The local sandbox on your physical filesystem where you create, modify, and delete code. Files here can be untracked, modified, or clean.
  • 2. Staging Index (The Index): A binary file located at .git/index. It acts as the staging area where you assemble the exact contents of your next prospective commit snapshot via git add.
  • 3. HEAD (Repository): A pointer (stored in .git/HEAD) that references your currently checked-out commit or branch tip. When you execute git commit, Git takes the snapshot recorded in the Staging Index, writes a root Tree object, and creates a new Commit object pointing to HEAD as its parent.

3. Merge vs. Rebase: Mechanics and Economics

When integrating changes from a feature branch (feat/auth) into main, Git provides two fundamentally distinct strategies: Merge and Rebase.

ASCII Diagram: Merge vs Rebase Visual Comparison 
Initial State:
         C --- D (feat)
        /
  A --- B (main)

Option 1: git merge feat (into main)
  Creates a non-destructive 3-way Merge Commit (M) with two parents:
         C --- D
        /       \
  A --- B ------- M (main)

Option 2: git rebase main (on feat branch)
  Rewrites commits C and D into C' and D' atop B:
  A --- B (main)
         \
          C' --- D' (feat) [Linear history! Zero merge commit needed!]
Dimension Git Merge Git Rebase
History Integrity Chronologically truthful: Preserves exact timestamps, commit hashes, and the parallel nature of branch development. Rewrites history: Creates brand-new commit objects with new SHA hashes and timestamps; makes history appear completely linear.
Commit Count Introduces an extra "Merge commit" (e.g., Merge branch 'feat' into main), unless a Fast-Forward is possible. Zero extraneous merge commits. Every commit represents a clean, self-contained unit of work.
Debugging (git bisect) Can be confusing during bisecting because commits on the feature branch may interleave chronologically with commits on main. Ideal for git bisect; every commit builds sequentially on top of the latest trunk state.
Safety & Team Impact Safe: purely additive, never changes existing commit SHAs. Dangerous if misused on shared public branches: force pushing (git push --force) destroys other developers' work.
⚠️ The Golden Rule of Rebasing

Never rebase commits that exist outside your local repository and have been pushed to a shared public branch (like main, staging, or a collaborative team branch). Rebasing rewrites commit SHA hashes; other teammates will have history that has diverged, causing chaotic merge conflicts and duplicate commits.

4. Interactive Rebase: Polishing Local History

Before opening a Pull Request, senior developers use Interactive Rebase (git rebase -i HEAD~N) to clean up messy local commits (e.g., "wip", "fixed typo", "trying again").

Bash: The Interactive Rebase Menu 
# Interactively rebase the last 4 commits on current branch
git rebase -i HEAD~4

# Git opens your default text editor with this plan:
pick a1b2c3d feat(auth): add login route
squash e5f6a7b fix typo in auth middleware
squash 9c8d7e6 fix failing test
reword 3b4a5c6 feat(auth): add refresh token endpoint

# Commands:
# p, pick <commit> = use commit
# r, reword <commit> = use commit, but edit the commit message
# e, edit <commit> = use commit, but stop for amending
# s, squash <commit> = meld into previous commit (combines messages)
# f, fixup <commit> = like "squash", but discard this commit's log message
# d, drop <commit> = remove commit completely

5. Undoing Changes: Reset vs. Revert vs. Restore

Knowing how to safely undo changes without losing work is a core qualification for professional engineers:

Command Working Directory Staging Area (Index) Commit History (HEAD) Safe for Shared Branches?
git reset --soft HEAD~1 Unchanged (keeps edits) Unchanged (keeps staged) Rewinds HEAD back 1 commit ❌ Local branches only (Rewrites history)
git reset --mixed HEAD~1 (default) Unchanged (keeps edits) Un-stages changes to match new HEAD Rewinds HEAD back 1 commit ❌ Local branches only (Rewrites history)
git reset --hard HEAD~1 Destroys all uncommitted edits! Overwrites with previous commit Rewinds HEAD back 1 commit ❌ High Risk: Uncommitted working edits are lost!
git revert <commit-hash> Updated to reflect inverse diff Updated and staged Creates a NEW forward commit with opposite diff ✅ 100% Safe: The standard way to undo commits on main
git restore <file> Discards local working edits to match staging Unchanged Unchanged ✅ Safe local file discard (Modern alternative to git checkout -- file)
git restore --staged <file> Unchanged Un-stages file back to working tree Unchanged ✅ Safe un-staging (Modern replacement for git reset HEAD file)

6. Disaster Recovery: The Power of git reflog

In Git, almost nothing is truly lost. Even if you accidentally run git reset --hard or delete a local branch, the commit objects remain in .git/objects/ until garbage collected (which takes 30 to 90 days by default).

The Reference Log (git reflog) records every single time the HEAD pointer moved in your local repository:

Bash: Recovering Lost Commits with Reflog 
# View recent movements of HEAD
git reflog

# Output:
# 3b4a5c6 (HEAD -> main) HEAD@{0}: reset: moving to HEAD~2  <-- You ran reset --hard by mistake!
# e8a3d12 HEAD@{1}: commit: feat(billing): add Stripe webhooks  <-- Lost commit!
# 7c5d914 HEAD@{2}: commit: feat(billing): add checkout session

# To recover the accidentally deleted commit e8a3d12:
# Method A: Point a new branch directly to the lost commit:
git branch recovery-branch e8a3d12

# Method B: Reset HEAD back to the state before the mistake:
git reset --hard HEAD@{1}

7. Team Branching Strategies: Trunk-Based vs. GitFlow

Branching Model Core Workflow & Mechanics Pros & Modern Applicability
Trunk-Based Development (Modern Standard) Developers merge short-lived feature branches (<1–2 days old) directly into main (the "trunk"). Incomplete features are hidden behind runtime Feature Flags (toggles). Pros: Eliminates "Merge Hell", enables Continuous Deployment (multiple deploys per day), fosters smaller PRs, and accelerates team velocity.
Best for: SaaS, web startups, microservices, and high-frequency deployment teams.
GitFlow (Legacy Model) Heavy branching structure with long-lived branches: master, develop, feature/*, release/*, and hotfix/*. Feature branches merge into develop; releases branch from develop and merge to both master and develop. Pros: Provides rigid, formal milestone gates for release management.
Cons: High merge conflict overhead; slow release cycles; antithetical to modern CI/CD automation.

# In the editor, configure:
# pick 1111111 added button
# fixup 2222222 fixed css
# fixup 3333333 oops fixed typo

9. Chapter-Specific Interview Questions & Answers

20 high-frequency interview questions covering Git DAG internals, merge vs rebase, reflog recovery, Three Trees mechanics, and team branching models.

Q01 What are the three main areas (trees) in Git? Beginner
Spoken Interview Answer

"Git operates across Three Trees: the Working Directory (your physical files on disk), the Staging Area or Index (a binary staging cache where you assemble snapshot contents using `git add`), and HEAD (the repository snapshot representing the currently checked-out commit)."

Q02 What is the difference between git merge and git rebase? Beginner
Spoken Interview Answer

"`git merge` combines two branch tips by creating a non-destructive three-way merge commit with two parent references, preserving exact chronological history. `git rebase` rewrites history by replaying your branch's commits one by one on top of the target branch tip, producing a clean, linear commit history without extraneous merge commits."

Q03 What is a Fast-Forward merge? Beginner
Spoken Interview Answer

"A Fast-Forward merge occurs when the target branch has received zero new commits since the feature branch diverged. Because there are no divergent changes to reconcile, Git simply moves the target branch pointer forward to point to the latest commit on the feature branch without creating a merge commit."

Q04 What does git cherry-pick do? Beginner
Spoken Interview Answer

"`git cherry-pick ` takes the exact change introduced by a specific commit from another branch and applies it as a brand-new commit on your currently checked-out branch. It is commonly used to backport critical bug fixes from `main` into a release maintenance branch without merging unreleased features."

Q05 What is the difference between git fetch and git pull? Beginner
Spoken Interview Answer

"`git fetch` downloads commits, files, and refs from the remote repository into your local repository without modifying your working files or current branch. `git pull` performs a `git fetch` followed immediately by a `git merge` (or `git rebase` if configured) to integrate those changes into your currently active working branch."

Q06 What are the four core internal object types in Git? Intermediate
Spoken Interview Answer

"The four core objects in `.git/objects/` are: 1) Blobs, which store raw uncompressed file contents without filenames; 2) Trees, which represent directories mapping filenames and permissions to Blob or Subtree hashes; 3) Commits, which link to a root Tree, parent commit hashes, author metadata, and a log message; and 4) Annotated Tags, which point to a commit with a message and optional GPG signature."

Q07 What is the difference between git reset --soft, --mixed, and --hard? Intermediate
Spoken Interview Answer

"`--soft` moves the HEAD pointer back to a specified commit while leaving your Staging Index and Working Directory untouched; your changes remain staged. `--mixed` (the default) moves HEAD and un-stages the changes, leaving modified files in your working directory. `--hard` moves HEAD, wipes the Staging Index, and overwrites your Working Directory to match the target commit, permanently discarding uncommitted changes."

Q08 What is the difference between git reset and git revert? Intermediate
Spoken Interview Answer

"`git reset` rewinds history by moving the branch pointer backward, effectively erasing commits from the current branch history. `git revert` is purely forward-moving: it generates a brand-new commit that applies the exact inverse diff of the target commit. Because it doesn't rewrite existing commit history, `git revert` is the safe, required approach for undoing changes on shared branches like `main`."

Q09 What is git reflog and how do you use it to recover an accidentally deleted branch? Intermediate
Spoken Interview Answer

"`git reflog` (reference log) records every movement of local branch tips and HEAD, even when commits are orphaned or branches deleted. Running `git reflog` displays recent commit hashes. Once you identify the hash corresponding to the tip of your deleted branch, you can instantly resurrect it by running `git branch `."

Q10 What is the Golden Rule of Rebasing and why does it exist? Intermediate
Spoken Interview Answer

"The Golden Rule of Rebasing states: Never rebase commits that have been pushed to a shared public branch. Rebasing creates brand-new commit hashes for replayed commits. If teammates have already based work on the old commits, force-pushing rewritten commits creates divergent histories, leading to corrupted branches and painful merge conflict resolution."

Q11 What is the difference between git restore and git checkout? Intermediate
Spoken Interview Answer

"Historically, `git checkout` was overloaded: it was used to switch branches, create branches, and discard file modifications. Git 2.23 introduced `git restore` dedicated specifically to restoring files (e.g., `git restore file.js` to discard working changes or `git restore --staged file.js` to un-stage), while `git switch` is used exclusively for switching branches."

Q12 What is the difference between squash and fixup in an interactive rebase? Intermediate
Spoken Interview Answer

"Both commands meld the selected commit into the commit immediately preceding it in the rebase plan. However, `squash` opens an editor prompt concatenating both commit messages so you can combine them into a unified log. `fixup` discards the selected commit's message entirely, retaining only the parent commit's message."

Q13 Compare Trunk-Based Development with GitFlow. Intermediate
Spoken Interview Answer

"Trunk-Based Development emphasizes merging short-lived feature branches into `main` frequently (multiple times per day), relying on automated CI test suites and Feature Flags for unfinished code. GitFlow relies on long-lived branches (`develop`, `release`, `hotfix`, `master`). Trunk-Based is favored in modern continuous delivery because it eliminates merge conflicts and accelerates shipping."

Q14 What are Conventional Commits and why are they valuable in CI/CD? Intermediate
Spoken Interview Answer

"Conventional Commits enforce a structured message format: `type(scope): description` (e.g., `feat(auth):`, `fix(db):`, `BREAKING CHANGE:`). In automated CI/CD pipelines, tools like `semantic-release` parse these prefixes to automatically calculate Semantic Version bumps (patch for fixes, minor for feats, major for breaking changes) and generate release changelogs."

Q15 How does Git store identical files located in different folders internally? Advanced
Spoken Interview Answer

"Because Git is a content-addressable storage system, the key for a Blob object is determined strictly by the SHA hash of its content. If you have 50 identical files across different folders, Git creates exactly ONE Blob object in `.git/objects/`. The distinct directory locations and filenames are stored inside Tree objects, each pointing to the same underlying Blob SHA."

Q16 What is a detached HEAD state in Git and how do you resolve it? Advanced
Spoken Interview Answer

"Normally, HEAD points to a named branch reference (e.g., `ref: refs/heads/main`). A detached HEAD occurs when you check out a specific commit hash or tag directly (`git checkout a1b2c3d`). Any commits made in this state belong to no branch and will become orphaned when you switch branches. To save your work, create a new branch immediately: `git switch -c new-feature-branch`."

Q17 What is git bisect and how does it locate regressions automatically? Advanced
Spoken Interview Answer

"`git bisect` performs a binary search through commit history to identify the exact commit that introduced a bug. You specify a known good commit (`git bisect good`) and a bad commit (`git bisect bad`). Git checks out the midpoint commit for testing. With an automated test script (`git bisect run npm test`), Git can isolate a regression across 1,000 commits in just 10 test iterations (O(log N))."

Q18 Why should you use git push --force-with-lease instead of git push --force? Advanced
Spoken Interview Answer

"`git push --force` blindly overwrites the remote branch ref with your local ref, annihilating any commits pushed by teammates in the meantime. `--force-with-lease` is a protective check: it only forces the push if your local remote tracking ref (`origin/branch`) matches the actual state on the remote server, failing gracefully if a teammate pushed new work."

Q19 What happens under the hood during git stash? Advanced
Spoken Interview Answer

"`git stash` creates two or three commit objects behind the scenes: one commit stores the changes in your Staging Index, another commit stores your modified working directory changes (with the first commit as its parent), and an optional third commit stores untracked files. A special ref `refs/stash` is updated to point to the working tree stash commit."

Q20 How do you explain the value of linear commit history to an engineering team? Intermediate
Spoken Interview Answer

"A linear commit history created through rebasing and squashing provides an immaculate, readable narrative of what changed and why. It makes code reviews straightforward, simplifies rollback procedures because features can be reverted with a single `git revert` commit, and allows `git bisect` to locate production regressions with 100% precision."
