1. Event Loop Lag: The Critical Metric

In Node.js web servers, the most dangerous performance degradation is not high CPU or memory usage; it is Event Loop Delay (Lag).

Event loop lag measures how long an asynchronous task is forced to wait in the queue before the Call Stack is free to process it. If a synchronous task takes 200ms, event loop lag jumps to 200ms, causing every single concurrent client request to suffer an extra 200ms of latency! 

// Monitoring Event Loop Lag in Production
const { monitorEventLoopDelay } = require('perf_hooks');

// Track histogram of event loop delays with 10ms sampling resolution
const histogram = monitorEventLoopDelay({ resolution: 10 });
histogram.enable();

setInterval(() => {
  const p50 = (histogram.percentile(50) / 1e6).toFixed(2); // Convert nanoseconds to ms
  const p99 = (histogram.percentile(99) / 1e6).toFixed(2);
  const max = (histogram.max / 1e6).toFixed(2);

  console.log(`[EventLoop Health] P50: ${p50}ms | P99: ${p99}ms | Max: ${max}ms`);

  // Alert if P99 lag exceeds 50ms (critical threshold for HTTP services!)
  if (histogram.percentile(99) / 1e6 > 50) {
    console.warn("⚠️ CRITICAL: Event loop lag exceeding 50ms threshold!");
  }

  histogram.reset();
}, 5000);

2. Redis Caching & Cache Stampede Defense

The Cache-Aside (Lazy Loading) pattern is the standard for web applications:

  1. Application receives read request for key user:123.
  2. Check Redis: if Cache Hit, return cached JSON immediately (1–2ms).
  3. If Cache Miss, query the PostgreSQL database (50–100ms).
  4. Store the result in Redis with a Time-To-Live (TTL) and return to client.
10,000 Concurrent Requests arrive at 12:00:00 (Cache expires at 12:00:00!) | v +----------------------------+ | REDIS CACHE MISS! | (Key 'popular-news' has expired) +----------------------------+ | +-------------------------------------------------------+ | ALL 10,000 REQUESTS SIMULTANEOUSLY QUERY DATABASE! | v v +---------------------------------------------------------------------+ | POSTGRESQL DATABASE SERVER OVERLOAD! | | (Connection Pool Exhaustion -> 100% CPU -> System Crash) | +---------------------------------------------------------------------+
Figure 12.1: The Thundering Herd / Cache Stampede Disaster

Defending Against Cache Stampedes: The Distributed Mutex

When a cache miss occurs under high concurrency, only ONE worker should query the database while all other concurrent requests wait for that worker to populate the cache: 

// Cache-Aside with Mutex Lock to prevent Cache Stampede
async function getCachedData(key, fetchFromDbFn, ttlSeconds = 300) {
  // 1. Check Redis
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  // 2. Cache Miss: Acquire atomic distributed lock (SETNX with 5s expiry)
  const lockKey = `lock:${key}`;
  const acquiredLock = await redis.set(lockKey, "locked", "NX", "EX", 5);

  if (acquiredLock) {
    try {
      // WINNER: Only this request queries the database!
      const data = await fetchFromDbFn();
      await redis.set(key, JSON.stringify(data), "EX", ttlSeconds);
      return data;
    } finally {
      await redis.del(lockKey); // Release lock
    }
  } else {
    // LOSER: Another request is fetching data; sleep 50ms and retry reading cache!
    await new Promise(r => setTimeout(r, 50));
    return getCachedData(key, fetchFromDbFn, ttlSeconds);
  }
}

3. Distributed Locking & Redlock Algorithm

In a distributed microservice cluster with 10 instances of an Express backend, an in-memory lock (like a JavaScript variable or Mutex) cannot synchronize processes. We need a Distributed Lock backed by Redis.

The Anatomy of a Safe Distributed Lock

A correct single-instance Redis lock requires an atomic command: 

SET resource_name my_random_value NX PX 30000
  • NX: Only set the key if it does NOT already exist (atomic check-and-set).
  • PX 30000: Expire the key automatically after 30 seconds (prevents deadlocks if the server crashes before unlocking).
  • my_random_value: A unique UUID per caller, preventing a slow process from accidentally releasing another process's lock!

Safe Release with Lua Script

-- Lua script executed atomically on Redis:
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end

4. Asynchronous Queue Architecture: BullMQ with Redis

Operations like processing video uploads, generating invoices, sending transactional emails, or compiling reports must never be executed inside the HTTP request-response cycle.

Client: POST /api/v1/invoices/generate | v Express Controller -> Pushes Job { orderId: 987 } to BullMQ Redis Queue | Responds immediately: 202 Accepted { jobId: 'job_456' } (5ms) v Client receives fast response! ... [Background Worker Process (BullMQ)] | +---> Dequeues job from Redis +---> Compiles PDF, uploads to S3, updates DB status to 'ready' +---> Emits WebSocket event to client: "Invoice Ready"
Figure 12.2: Decoupling Heavy Tasks via Asynchronous Message Queues
// Producer (Express Route):
const { Queue } = require('bullmq');
const emailQueue = new Queue('email-queue', { connection: redisConfig });

app.post('/api/welcome', async (req, res) => {
  // Enqueue job with automatic retry policy!
  await emailQueue.add('sendWelcomeEmail', { email: req.body.email }, {
    attempts: 3,
    backoff: { type: 'exponential', delay: 1000 }
  });

  res.status(202).json({ message: "Welcome email scheduled." });
});

// Consumer (Worker Process):
const { Worker } = require('bullmq');

const worker = new Worker('email-queue', async (job) => {
  console.log(`Processing email job ${job.id} for ${job.data.email}`);
  await sendEmail(job.data.email);
}, { connection: redisConfig });

5. The Circuit Breaker Pattern

When an external downstream service (e.g. Stripe, SendGrid, or an inventory microservice) goes down, continuing to send thousands of requests results in socket timeouts, thread contention, and cascading failure of your entire backend.

A Circuit Breaker wraps external calls and manages three states:

[CLOSED] (Normal Operation: Requests flow to downstream service) | | (Failure rate exceeds threshold, e.g. 50% errors) v [OPEN] (Tripped: Requests FAIL FAST immediately without calling service!) | | (Sleep window expires, e.g. 10 seconds) v [HALF-OPEN] (Trial: Sends a small canary test request) / \ (Canary Succeeds) (Canary Fails) v v [CLOSED] [OPEN]

Interview Questions and Answers

20 senior-level interview questions testing event loop monitoring, Redis caching architectures, distributed locking, background worker queues, and performance benchmarking.

Q1 What is Event Loop Delay (Lag), and why is it more critical to monitor than CPU usage in Node.js? Beginner
Spoken Interview Answer

"Event Loop Lag measures the time between when an asynchronous callback is scheduled and when the Call Stack actually executes it. Because Node.js is single-threaded, a high event loop lag means synchronous JavaScript is monopolizing the processor, causing all incoming network connections, database queries, and timers to wait. A server can show only 30% CPU usage while having severe 500ms event loop lag, resulting in catastrophic response latency for all concurrent users."

Q2 What is a Cache Stampede (Thundering Herd Problem)? How do you prevent it? Intermediate
Spoken Interview Answer

"A Cache Stampede occurs when a high-traffic cached key expires, and thousands of concurrent HTTP requests experience a cache miss simultaneously. All requests hit the database at the exact same instant to recalculate the data, causing database CPU spikes, connection pool exhaustion, and server crashes. We prevent it using: 1. A distributed mutex lock so only one request queries the database while others wait, or 2. Probabilistic Early Expiration (XFetch algorithm), where a background worker refreshes the cache before it actually expires."

Q3 How does Redis SET with `NX` and `PX` create a safe distributed lock? Why is a random value required? Advanced
Spoken Interview Answer

"`SET resource_id random_val NX PX 30000` is atomic: `NX` ensures the lock is only acquired if no other process holds it, and `PX 30000` sets an automatic 30-second TTL to prevent deadlocks if the holder crashes. The random value is critical to avoid accidentally releasing another process's lock: if Client A takes longer than 30s, its lock expires, and Client B acquires it. When Client A finally finishes, checking that `val === random_val` via a Lua script ensures Client A does not delete Client B's active lock!"

Q4 What is the difference between Cache-Aside, Read-Through, and Write-Through caching? Intermediate
Spoken Interview Answer

"In Cache-Aside, the application code coordinates caching directly: it queries the cache first, and on a miss, queries the database and populates the cache. In Read-Through, the application treats the cache as the main data store; the cache library automatically fetches from the database on a miss. In Write-Through, the application writes data to the cache first, and the cache synchronously writes to the database before returning, ensuring cache and database are always in lockstep."

Q5 What is the Circuit Breaker pattern, and what three states does it manage? Advanced
Spoken Interview Answer

"A Circuit Breaker prevents cascading failures when downstream dependencies (third-party APIs or microservices) fail. It manages three states: 1. CLOSED: Normal state; requests pass through. 2. OPEN: Tripped when error rates exceed a threshold (e.g. 50%); requests fail fast immediately without making network calls, protecting resources. 3. HALF-OPEN: After a timeout, sends a small percentage of canary requests to test if the service has recovered, transitioning back to Closed on success or Open on failure."

Q6 What is the difference between Latency and Throughput? Beginner
Spoken Interview Answer

"Latency is the time it takes for a single request to travel from client to server and return a response (measured in milliseconds). Throughput is the volume of work or number of requests the server can successfully process within a given timeframe (measured in Requests Per Second, RPS)."

Q7 Explain latency percentiles: P50, P95, and P99. Why is average latency misleading? Intermediate
Spoken Interview Answer

"Average latency masks severe outliers: 99 requests taking 10ms and 1 request taking 10,000ms yields an average of ~110ms, hiding the fact that 1% of users had an unacceptable 10-second experience. P50 (median) means 50% of requests are faster than that value. P99 means 99% of requests are faster, isolating the worst 1% tail latency experienced by power users under heavy load."

Q8 How do you take and analyze a V8 Heap Snapshot in Node.js to find memory leaks? Advanced
Spoken Interview Answer

"Start Node with `--inspect` and connect Chrome DevTools (`chrome://inspect`). In the Memory tab, take Snapshot 1 under idle conditions. Trigger simulated traffic with a load-testing tool (Autocannon). Take Snapshot 2. Use the 'Comparison' view in DevTools to sort by 'Alloc. Size' and '# Delta'. Inspect the 'Retaining Tree' of accumulating objects to identify the root reference (e.g. an uncleaned event listener, a global Map, or an unclosed stream) preventing garbage collection."

Q9 Scenario: You need to generate 10,000 PDF invoices nightly without crashing your web server or blocking user logins. How do you architect this? Scenario
Spoken Interview Answer

"I decouple PDF generation entirely from the web server using BullMQ backed by Redis. The web API enqueues invoice job IDs into the queue in milliseconds. An independent background Worker process (running on a separate container or machine) pulls jobs from the queue with a concurrency limit of 5. It uses a Worker Thread pool to compile PDFs, uploads them to AWS S3, and writes completion status to the database, ensuring zero CPU contention on user-facing web servers."

Q10 What is a CPU Flamegraph, and how do you generate one for a Node.js application? Intermediate
Spoken Interview Answer

"A Flamegraph is a visual representation of profiled software execution over time: the X-axis represents the percentage of CPU time spent in each function, and the Y-axis represents the Call Stack depth. Wider blocks indicate functions consuming more CPU cycles. In Node.js, we generate flamegraphs using the `0x` CLI tool (`npx 0x app.js`) while running a load test, immediately pinpointing which specific line of code or algorithm is bottlenecking the CPU."

Q11 What is the "Fencing Token" pattern, and why is it needed with distributed locks? Advanced
Spoken Interview Answer

"If a process acquires a distributed lock but experiences a long Garbage Collection pause or network hiccup, its lock may expire in Redis while it is paused. A second process acquires the lock. When the first process wakes up, both processes believe they own the lock! A Fencing Token is a monotonically increasing counter issued by the lock service: the shared resource (database) rejects any write attempt bearing a fencing token lower than the highest token it has already processed."

Q12 What is Autocannon, and how do you use it for load testing? Beginner
Spoken Interview Answer

"Autocannon is a fast, Node.js-based HTTP/1.1 benchmarking and load-testing tool. We execute it via terminal: `npx autocannon -c 100 -d 10 http://localhost:3000/api/tasks`, which simulates 100 concurrent connections over a 10-second duration. It reports requests per second, throughput, error counts, and exact latency percentiles (P50, P90, P99)."

Q13 How does Jitter improve Exponential Backoff during retry storms? Intermediate
Spoken Interview Answer

"Exponential backoff doubles delay on each retry (`1s, 2s, 4s, 8s`). However, if 1,000 clients fail simultaneously due to a network blip, all 1,000 clients will retry at the exact same second, hammering the recovering database with synchronized waves of traffic (Thundering Herd). Jitter introduces random variance (e.g. `delay * random(0.5, 1.5)`), smoothing out the retries over a continuous time spectrum and allowing the server to recover."

Q14 What is the Redlock algorithm, and what controversy surrounds its safety in distributed systems? Advanced
Spoken Interview Answer

"Redlock is an algorithm proposed by Salvatore Sanfilippo (Redis creator) for multi-node Redis clusters: a client acquires locks across \(N\) independent Redis masters (e.g. 5 nodes) and considers the lock held if acquired on a majority (\(\ge 3\)) within a short timeout. The controversy (analyzed by Martin Kleppmann) centers on the fact that asynchronous networks with uncoordinated system clock drift and non-deterministic GC pauses cannot guarantee strict mutual exclusion without fencing tokens."

Q15 Scenario: An Express endpoint queries three independent microservices (UserProfile, Orders, Recommendations). How do you execute this with minimum latency and handle timeouts? Scenario
Spoken Interview Answer

"I execute them in parallel using `Promise.allSettled`, wrapping each fetch with `AbortSignal.timeout(2000)` to enforce a 2-second hard deadline. If UserProfile fails, the request fails. If Recommendations times out, the endpoint gracefully degrades by omitting recommendations rather than failing the entire page. Because they run concurrently, total response time equals the single slowest request rather than their sum."

Q16 What is Cache Invalidation, and why is it considered one of the two hard things in Computer Science? Intermediate
Spoken Interview Answer

"Cache Invalidation is the process of declaring cached data stale when the underlying authoritative database record changes. It is challenging because data is often duplicated across multiple cache keys, queries with different filters/sorts, and CDN edges. Failing to invalidate produces stale, inconsistent reads for users; over-invalidating destroys cache hit ratios and overloads databases."

Q17 How does Database Connection Pool sizing affect throughput? What happens if `max` is set too high? Advanced
Spoken Interview Answer

"Setting `max` too high is counter-productive: if a database host has 8 CPU cores and 100 concurrent queries execute simultaneously, the database OS spends more CPU time on context switching between threads than doing actual query work, degrading overall throughput. A properly sized smaller pool (e.g. 15–25 connections per Node instance) maximizes CPU cache efficiency and provides higher sustained throughput."

Q18 What is the difference between In-Memory Caching (Node memory) and Distributed Caching (Redis)? Beginner
Spoken Interview Answer

"In-Memory Caching stores data inside the Node.js process heap (via a Map or LRU cache); it has near-zero latency but does not scale horizontally (each container has separate isolated cache state) and consumes server RAM. Distributed Caching uses a shared external cluster (like Redis); all container instances share a single authoritative cache, data survives application restarts, and cache invalidation is synchronized."

Q19 Scenario: A BullMQ background worker crashes while processing a job. How does BullMQ ensure the job is not permanently lost? Scenario
Spoken Interview Answer

"BullMQ uses Redis streams and hashes to track job lifecycle states (`waiting`, `active`, `completed`, `failed`). When a worker picks up a job, it moves to `active` and the worker maintains a recurring heartbeat lock. If the worker crashes, the lock expires; BullMQ's stalled job checker detects the abandoned job, moves it back to `waiting`, and delegates it to another active worker based on the configured retry policy."

Q20 What is the Probabilistic Early Expiration (XFetch) algorithm for cache management? Advanced
Spoken Interview Answer

"XFetch is a mathematical algorithm that dynamically refreshes a cache entry before it expires. Rather than waiting for TTL to hit zero, whenever a client reads the cache, it evaluates a probabilistic formula: `currentTime - (computationTime * beta * ln(random())) > expiry`. As the expiration approaches and traffic increases, the probability of triggering an asynchronous background refresh approaches 1. Exactly one worker refreshes the cache before expiration, completely eliminating cache misses and stampedes."
