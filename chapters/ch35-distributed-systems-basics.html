1. Monoliths vs. Microservices & The 8 Fallacies

Moving from a monolithic codebase to distributed microservices is not an automatic upgrade; it is a fundamental architectural trade-off swapping code complexity for operational, network, and data consistency complexity.

Architectural Dimension Modular Monolith Microservice Architecture
Deployment Unit Single executable or container artifact running all domain modules. Dozens of independently deployable containerized services.
Communication In-memory method/function invocations (\(\sim 10\text{ ns}\) overhead). Network RPC / HTTP / gRPC calls (\(\sim 5\text{--}50\text{ ms}\) overhead).
Data Management Single shared relational database; immediate ACID transactions via SQL. Database-per-Service pattern; eventual consistency and distributed sagas.
Team Scaling (Conway’s Law) Can experience git merge bottlenecks when scaling past 50+ engineers. Small autonomous two-pizza teams owning independent deployment lifecycles.
Operational Overhead Low: single CI/CD pipeline, centralized logging, simple local debugging. High: requires service mesh, distributed tracing (OpenTelemetry), and complex orchestration.

The 8 Fallacies of Distributed Computing

Formulated by L. Peter Deutsch and James Gosling at Sun Microsystems, these eight false assumptions lead to catastrophic distributed failures when taken for granted:

  1. The network is reliable: Switches fail, optical cables get cut, and packets drop. Systems must handle network timeouts gracefully.
  2. Latency is zero: In-memory calls take nanoseconds; cross-datacenter calls take tens to hundreds of milliseconds.
  3. Bandwidth is infinite: Serializing massive payloads across services saturates network interfaces and introduces serialization CPU drag.
  4. The network is secure: Internal networks are not trusted environments. Microservices must use mTLS (mutual TLS) and identity tokens.
  5. Topology doesn't change: Cloud instances autoscale, restart, and change IP addresses constantly. Dynamic service discovery is mandatory.
  6. There is one administrator: Independent teams manage different services with distinct deployment schedules and configurations.
  7. Transport cost is zero: Network serialization, JSON parsing, and TLS handshake negotiation consume tangible CPU cycles.
  8. The network is homogeneous: Services are written in polyglot languages (Node.js, Go, Python) communicating across diverse network protocols.

2. The CAP Theorem & PACELC Theorem

Formulated by Eric Brewer in 2000 and mathematically proven by Gilbert and Lynch in 2002, the CAP Theorem establishes fundamental limits on distributed data stores:

ASCII Diagram: The CAP Theorem Trilemma 
                     Consistency (C)
                     [Every read receives most recent write]
                           /         \
                          /           \
                         /   Network   \
                        /   Partition   \
                       /   is Mandatory  \
                      /      in Cloud     \
                     /                     \
       Availability (A) ----------------- Partition Tolerance (P)
 [Every non-failing node             [System operates despite
  returns non-error response]         dropped network messages]

CRITICAL REALITY: Network partitions (P) are physical certainties.
Therefore, distributed architectures can ONLY choose between CP or AP!

Deconstructing CAP

  • Consistency (Linearizability): Every read request receives the most up-to-date committed write or an error.
  • Availability: Every non-failing node must return a successful non-error response for any received request (though it may not be the newest write).
  • Partition Tolerance: The system continues to operate despite an arbitrary number of dropped or delayed messages between network nodes.
⚠️ The CAP False Dichotomy: You Cannot "Choose CA"

In distributed systems across networks, network partitions are physical realities (switches disconnect, cables fail, cloud availability zones experience packet loss). You cannot reject Partition Tolerance. When a network partition inevitably occurs, you must choose between:

  • CP (Consistency over Availability): Reject or block writes to nodes that cannot reach a quorum (e.g., MongoDB primary step-down, ZooKeeper, CockroachDB). Better to return an error than stale/corrupted data.
  • AP (Availability over Consistency): Allow isolated nodes to accept reads and writes, achieving high availability while accepting that nodes will be inconsistent until the partition heals (e.g., Cassandra, DynamoDB, CouchDB).

The PACELC Theorem

Formulated by Daniel Abadi in 2012, PACELC extends CAP by explaining what happens when the network is running normally:

If there is a Partition (P), how does the system trade off Availability (A) vs Consistency (C)?
Else (E) (normal operation), how does the system trade off Latency (L) vs Consistency (C)?
Classification Database Examples Behavior Profile
PC / EC PostgreSQL (synchronous replication), CockroachDB, Spanner During partitions, prioritizes Consistency. In normal state, accepts higher Latency to guarantee synchronous consistency.
PA / EL Apache Cassandra, Amazon DynamoDB (eventual) During partitions, prioritizes Availability. In normal state, sacrifices immediate consistency to achieve ultra-low Latency.
PC / EL MongoDB (default primary read/write) During partitions, halts writes if no majority primary exists (CP). In normal state, uses asynchronous replication to keep Latency low.

3. Message Queues & Streaming: Kafka vs. RabbitMQ

Asynchronous messaging decouples service execution, smooths traffic spikes (load leveling), and enables reliable event-driven systems.

Architectural Dimension RabbitMQ (AMQP Message Broker) Apache Kafka (Distributed Commit Log)
Core Architecture Smart Broker, Dumb Consumer: Broker tracks message delivery state, acknowledgments, consumer availability, and routing topologies (Exchanges to Queues). Dumb Broker, Smart Consumer: Broker is an immutable distributed append-only log on disk. Consumers track their own reading position via Offsets.
Message Retention Messages are deleted upon consumer acknowledgment. Not designed for historical storage. Messages are persisted durably based on time (e.g., 7 days) or size, independent of consumer consumption.
Replayability ❌ Impossible: once acknowledged and removed from the queue, a message cannot be re-read. ✅ Effortless: consumers can rewind their offset to timestamp 0 and re-process months of events.
Throughput High (\(\sim 50{,}000\) msg/sec), constrained by complex routing tables and per-message tracking. Extreme (\(\sim 1{,}000{,}000+\) msg/sec per cluster) via sequential disk I/O, OS page cache, and zero-copy network sends.
Best Fit Complex routing, task workers, transactional workflows, immediate priority queues. High-throughput event streaming, analytics pipelines, audit trails, Change Data Capture (CDC).

4. Delivery Semantics & The Idempotent Consumer

In distributed networks, communication guarantees fall into three categories:

  1. At-Most-Once: Messages are dispatched without retries. If the network drops or the worker crashes mid-execution, the message is permanently lost. Zero duplicates, but data loss is possible.
  2. At-Least-Once (Industry Standard): The producer retries until an acknowledgment is received. If an ACK drops on the network, the message is re-delivered. Duplicates will occur.
  3. Exactly-Once: The theoretical ideal where every message is processed once and only once. In practice, true exactly-once across heterogeneous distributed systems is physically impossible; it is emulated using At-Least-Once Delivery + Idempotent Processing.
TypeScript: Production Idempotent Message Consumer 
import { Pool } from 'pg';

export interface DomainEvent {
  id: string; // Unique UUID generated by producer
  type: string;
  payload: any;
}

export async function processPaymentEvent(event: DomainEvent, pool: Pool): Promise<void> {
  const client = await pool.connect();

  try {
    await client.query('BEGIN');

    // 1. Idempotency Check: Attempt to insert message ID into processed_events table
    // If the ID already exists, ON CONFLICT DO NOTHING returns zero rows
    const insertSql = `
      INSERT INTO processed_events (event_id, event_type, processed_at)
      VALUES ($1, $2, NOW())
      ON CONFLICT (event_id) DO NOTHING
      RETURNING event_id;
    `;
    const res = await client.query(insertSql, [event.id, event.type]);

    if (res.rows.length === 0) {
      // Duplicate message detected! Skip business execution safely
      await client.query('ROLLBACK');
      console.log(`[Idempotent Skip] Event ${event.id} already processed.`);
      return;
    }

    // 2. Execute actual domain business logic inside same transaction
    await client.query(
      'UPDATE accounts SET balance = balance + $1 WHERE id = $2',
      [event.payload.amount, event.payload.accountId]
    );

    // 3. Commit both business mutation AND idempotency record atomically
    await client.query('COMMIT');
  } catch (err) {
    await client.query('ROLLBACK');
    throw err; // Re-throw to trigger message broker retry
  } finally {
    client.release();
  }
}

5. Distributed Transactions: The Saga Pattern

In a microservice architecture where each service owns its private database, traditional ACID transactions across services are impossible. Historically, systems attempted Two-Phase Commit (2PC), but 2PC suffers from coordinator single points of failure, blocking database row locks across high-latency networks, and extreme scalability collapse.

The modern distributed standard is the Saga Pattern: a sequence of local transactions where each service updates its own database. If a step fails, the saga executes a series of Compensating Transactions to undo previous changes:

ASCII Diagram: E-Commerce Checkout Saga with Compensation 
Step 1: Order Service        Step 2: Payment Service         Step 3: Inventory Service
     [Create Order]               [Charge Card]                   [Reserve Stock]
           |                            |                               |
           v (Success)                  v (Success)                     v (FAILS: Out of Stock!)
     +------------+               +------------+                  +------------+
     | Order: PEND|               | Charge: OK |                  | Stock: ERR |
     +------------+               +------------+                  +------------+
           |                            |                               |
           |                            |<-- Trigger Compensation -------|
           |                            |    Refund Customer Card       |
           |<-- Trigger Compensation ---|                               |
           |    Cancel Order (FAILED)   |                               |
           v                            v                               v
     [Final State: Consistency Restored! No orphaned charge; order marked CANCELLED]

Orchestration vs. Choreography

Saga Style Workflow Mechanics Trade-Off Analysis
Choreography (Event-Driven) Services listen to domain events and independently publish subsequent events. (e.g., OrderCreated \(\rightarrow\) Payment listens and emits PaymentProcessed \(\rightarrow\) Inventory listens). Pros: Decentralized, no single orchestrator bottleneck.
Cons: Hard to visualize end-to-end workflow state; high risk of cyclic event loops. Best for simple 2–3 step workflows.
Orchestration (Command-Driven) A centralized Orchestrator service tells participants what local transactions to execute via explicit commands and records global saga state. Pros: Centralized state visibility; easy to audit, test, and handle complex compensation logic.
Cons: Central orchestrator can become a hub of business logic if not designed carefully. Best for complex enterprise flows.

6. Eliminating Dual Writes: The Transactional Outbox Pattern

A pervasive anti-pattern in distributed engineering is the Dual Write Problem: updating a database and publishing an event to a message broker in the same application function.

TypeScript: The Fatal Dual-Write Anti-Pattern 
// ❌ FATAL ANTI-PATTERN: Dual Write
async function createOrder(orderData: OrderData): Promise<void> {
  // 1. Write to database
  await db.orders.insert(orderData);

  // 💣 WHAT IF: The Node.js process crashes here?
  // 💣 WHAT IF: Kafka is down or network disconnects here?
  // Database has the order, but Kafka NEVER received the event!
  // Downstream payment, inventory, and email services are never notified! System corrupted!

  // 2. Publish to message broker
  await kafkaProducer.send({ topic: 'order-created', messages: [orderData] });
}

The Architectural Solution: Transactional Outbox

To achieve 100% atomicity without distributed transactions, we write the business entity AND an outbox message to the same database in a single local ACID transaction:

ASCII Diagram: Transactional Outbox with CDC 
Application Server                  PostgreSQL Database
        |                                   |
        |--- 1. BEGIN --------------------->|
        |--- 2. INSERT INTO orders -------->| (Write business data)
        |--- 3. INSERT INTO outbox_table -->| (Write event payload)
        |--- 4. COMMIT -------------------->| (Atomic local transaction!)
                                            |
                                            |
        +-----------------------------------+
        | (Transaction Log / WAL)
        v
  Debezium CDC (Change Data Capture) or Dedicated Message Relay Worker
        |
        |--- 5. Reads outbox table / WAL stream
        v
  Apache Kafka / RabbitMQ
        |
        v
  Downstream Consumer Microservices

Exercise 2: Simulating Saga Compensation in TypeScript

Scenario: Write a lightweight Saga coordinator function that executes step 1 (Book Flight) and step 2 (Book Hotel). If step 2 throws an error, it invokes the compensating action for step 1 (Cancel Flight) and re-throws.

View Complete Solution
TypeScript Solution 
interface SagaStep {
  name: string;
  execute: () => Promise<any>;
  compensate: () => Promise<void>;
}

export async function runSaga(steps: SagaStep[]): Promise<void> {
  const executedSteps: SagaStep[] = [];

  for (const step of steps) {
    try {
      console.log(`Executing step: ${step.name}`);
      await step.execute();
      executedSteps.push(step);
    } catch (err) {
      console.error(`Step ${step.name} failed! Starting compensations...`, err);

      // Execute compensations in reverse order
      for (const executed of executedSteps.reverse()) {
        try {
          console.log(`Compensating: ${executed.name}`);
          await executed.compensate();
        } catch (compErr) {
          console.error(`CRITICAL: Compensation failed for ${executed.name}! Requires manual intervention.`, compErr);
        }
      }
      throw new Error(`Saga aborted due to failure in step ${step.name}`);
    }
  }
}

8. Chapter-Specific Interview Questions & Answers

20 high-frequency interview questions covering distributed computing fallacies, CAP/PACELC theorems, Kafka vs RabbitMQ, delivery guarantees, Sagas, and Outbox patterns.

Q01 What is the core premise of the CAP Theorem? Beginner
Spoken Interview Answer

"The CAP theorem proves that in an asynchronous network where partitions (P) are physically inevitable, a distributed system can guarantee at most two of three properties: Consistency, Availability, and Partition Tolerance. In real-world cloud architectures, you must choose between CP (Consistency over Availability, rejecting writes when partitions occur) or AP (Availability over Consistency, accepting writes that will synchronize eventually)."

Q02 Why can't a distributed system choose 'CA' (Consistency and Availability)? Beginner
Spoken Interview Answer

"Because network partitions—caused by hardware router failures, GC pauses, or cable disconnects—are an unavoidable physical certainty in distributed systems. Choosing 'CA' would mean assuming network partitions are impossible, which is only true for a single-node system. As soon as you have two or more nodes across a network, you must support Partition Tolerance."

Q03 What is the difference between At-Least-Once and At-Most-Once delivery? Beginner
Spoken Interview Answer

"At-Most-Once sends messages without confirmation or retries; messages may be lost during network drops, but will never be duplicated. At-Least-Once retries delivery until an acknowledgment is received; messages are guaranteed never to be lost, but duplicate deliveries can occur if network ACKs drop. Production systems pair At-Least-Once delivery with Idempotent consumers to achieve effective exactly-once semantics."

Q04 What is an Idempotent Consumer and why is it essential? Beginner
Spoken Interview Answer

"An Idempotent Consumer safely handles duplicate message deliveries by verifying whether the message ID was already processed. If a duplicate arrives, it acknowledges the message and exits without re-executing business operations (like charging a credit card twice). It is essential because distributed message brokers rely on At-Least-Once delivery."

Q05 What is Conway's Law and how does it relate to Microservices? Beginner
Spoken Interview Answer

"Conway's Law states that organizations design systems that mirror their internal communication structures. In large companies with multiple independent engineering teams, monolithic codebases create deployment bottlenecks. Microservices align service boundaries directly to team boundaries, allowing teams to develop, test, and deploy independently without cross-team coordination."

Q06 What is the PACELC Theorem and what gap in the CAP theorem does it address? Intermediate
Spoken Interview Answer

"The CAP theorem only describes system behavior during rare network partitions. PACELC explains the trade-off during normal operations: If Partition (P), trade off Availability (A) vs Consistency (C); Else (E) in normal state, trade off Latency (L) vs Consistency (C). For example, DynamoDB is PA/EL (prioritizing availability during partitions and low latency normally), whereas CockroachDB is PC/EC."

Q07 Compare Apache Kafka and RabbitMQ architectural models. Intermediate
Spoken Interview Answer

"RabbitMQ is a traditional message broker using a 'smart broker, dumb consumer' model: it routes messages to queues and deletes them upon acknowledgment, excelling at complex routing and task queues. Kafka is an immutable distributed commit log using a 'dumb broker, smart consumer' model: messages persist on disk, consumers maintain their own offsets, and messages can be replayed, enabling millions of events per second."

Q08 What is the Dual Writes problem and why does it cause data corruption? Intermediate
Spoken Interview Answer

"Dual Writes happen when an application updates a database and publishes to a message broker in the same function. Because there is no distributed transaction spanning both systems, if the server crashes or the network drops after writing to the database but before publishing to the broker, downstream services never receive the event, permanently corrupting system state."

Q09 How does the Transactional Outbox Pattern solve the Dual Writes problem? Intermediate
Spoken Interview Answer

"The application writes both the business entity (e.g., `orders`) and an event record into an `outbox` table within the same local ACID database transaction. A separate background relay worker or Change Data Capture (CDC) tool like Debezium tails the database transaction log (WAL) and publishes events to Kafka with guaranteed At-Least-Once delivery, eliminating dual-write inconsistencies."

Q10 What is the Saga Pattern and how does it replace Two-Phase Commit (2PC)? Intermediate
Spoken Interview Answer

"Two-Phase Commit holds distributed locks across services, creating severe latency and single points of failure. The Saga pattern breaks a distributed transaction into a sequence of local database transactions. If any intermediate step fails, the saga triggers compensating transactions in reverse order to undo previously committed changes, achieving eventual consistency without global locking."

Q11 Compare Saga Orchestration vs Saga Choreography. Intermediate
Spoken Interview Answer

"In Choreography, services react to domain events published by peers without central coordination; it is simple for small workflows but difficult to debug and trace at scale. In Orchestration, a dedicated orchestrator service manages the state machine, dispatching commands to participant services and coordinating compensation logic. Orchestration is preferred for complex multi-step enterprise workflows."

Q12 What is Change Data Capture (CDC) and how does Debezium work? Intermediate
Spoken Interview Answer

"Change Data Capture is a software pattern that monitors and captures row-level inserts, updates, and deletes committed to a database. Tools like Debezium read directly from the database's Write-Ahead Log (WAL in PostgreSQL or oplog in MongoDB) and stream those mutations as events into Apache Kafka in near real-time with zero polling overhead on application tables."

Q13 What is a Dead-Letter Queue (DLQ) and what is its role in event-driven systems? Intermediate
Spoken Interview Answer

"A Dead-Letter Queue is a designated secondary queue where messages that repeatedly fail processing (poison pills) are routed after exceeding maximum retry attempts. This prevents unprocessable messages from blocking the main queue, allows the system to continue processing healthy events, and isolates erroneous payloads for engineering inspection and replay."

Q14 What is the difference between Synchronous and Asynchronous microservice communication? Intermediate
Spoken Interview Answer

"Synchronous communication (REST, gRPC) requires the client to wait for the receiver to process the request, creating temporal coupling where downstream latency or downtime directly cascades upstream. Asynchronous communication (Kafka, RabbitMQ) decouples caller from callee via message queues, allowing producers to fire-and-forget while consumers process at their own pace."

Q15 What is the Fallacy of Zero Latency and how does it manifest in naive microservices? Advanced
Spoken Interview Answer

"Developers migrating from monoliths often assume function calls can be replaced with HTTP/RPC calls with negligible cost. In reality, network round-trips take 5–50ms. If an aggregation service makes 20 sequential RPC calls to render a single user dashboard, latency explodes to 1,000ms. Overcoming this requires batching, parallelizing calls with `Promise.all`, or adopting event-driven data co-location."

Q16 How does Apache Kafka achieve message ordering guarantees? Advanced
Spoken Interview Answer

"Kafka guarantees message ordering strictly within a single Partition, not across the entire Topic. When producers publish events, messages sharing the same Partition Key (e.g., `user_id`) are routed to the exact same partition via hashing. A single consumer within a Consumer Group exclusively reads from that partition, guaranteeing strictly sequential processing for that entity."

Q17 Why can Compensating Transactions in a Saga fail, and how do you handle partial compensation? Advanced
Spoken Interview Answer

"Unlike a database `ROLLBACK` which cleanly reverts to uncommitted state, a compensating transaction is a brand-new forward transaction that can itself encounter network timeouts or constraint errors. Sagas must design compensating actions to be 100% idempotent and retry them indefinitely until success, logging exhausted failures to alert on-call engineers for manual remediation."

Q18 What is the Backpressure problem in event streams and how do consumer groups mitigate it? Advanced
Spoken Interview Answer

"Backpressure happens when producers publish data faster than consumers can process it. In push-based brokers, unconstrained queues can exhaust consumer memory. Kafka uses a pull-based model where consumers actively pull messages at their own sustainable processing rate. Scaling consumers horizontally across partitions in a Consumer Group parallelizes processing to absorb surges."

Q19 What is the difference between Linearizable Consistency and Eventual Consistency? Advanced
Spoken Interview Answer

"Linearizability (Strong Consistency) guarantees that as soon as a write completes, all subsequent reads across all nodes immediately return that new value, behaving like a single atomic register. Eventual Consistency guarantees that if no new updates are made, all replicas will eventually converge to the same value, but reads may return stale data in the interim."

Q20 How do you advise a team on when to break up a monolith into microservices? Intermediate
Spoken Interview Answer

"I advise starting with a well-structured Modular Monolith. Break out a service only when: 1) Independent scaling is mandatory (e.g., video transcoding requiring 100x CPU); 2) Distinct team ownership demands independent deployment cadence; or 3) Strict compliance or security boundaries require isolation. Never split into microservices just to achieve clean architecture."
